Практика 12. Docker: образы, реестр и агенты в контейнерах.

Файлы к практике: files/docker/ (образ сайта, образ агента, файл реестра,
настройка демона и пояснения к ней) и files/pipelines/Jenkinsfile.docker.
Опирается на практику 6 (репозиторий и credentials) и практику 11 (выкат).

Машины: admin 10.0.2.5 — контроллер, Gitea, реестр образов; node2 10.0.2.14
— агент с метками web, node2, docker и Docker на нём; node1 10.0.2.13 —
агент с метками web и node1, Docker ему не нужен. Порты: 8080 — портал,
3000 — Gitea, 5000 — реестр, 8081 — сайт в контейнере на node2, 80 — сайт
под nginx. ВАЖНО: образы, кэш сборки и журналы контейнеров лежат
в /var/lib/docker — на диске 20 ГБ место заканчивается первым (раздел 12).


=========================================================================
ЗАЧЕМ DOCKER В КОНВЕЙЕРЕ
=========================================================================

Docker решает четыре задачи, и все они про воспроизводимость.

  * ОДИНАКОВЫЕ ИНСТРУМЕНТЫ. «На node1 сборка проходит, а на node2 падает»
    обычно означает, что на node1 другая версия rsync. Docker переносит
    инструменты в образ: версия становится свойством образа, не машины.
  * ИЗОЛЯЦИЯ СБОРОК: контейнер даёт каждой сборке своё окружение.
  * ОДИНАКОВОЕ ОКРУЖЕНИЕ НА ВСЕХ АГЕНТАХ: новый агент — это Docker
    и образ, а не список пакетов, который когда-то ставили руками.
  * АРТЕФАКТ, КОТОРЫЙ ЗАПУСКАЕТСЯ ВЕЗДЕ ОДИНАКОВО: образ — результат
    сборки вместе с окружением.

КОГДА DOCKER НЕ НУЖЕН. Наш сайт — страница и файл со сведениями о сборке;
выкат практики 11 копирует их rsync, и это проще. Docker добавляет здесь
сборочный шаг, реестр и обновление образа при каждой правке. Практика
нужна затем, что Docker обязателен там, где есть зависимости: компилятор
нужной версии, сервис в нескольких экземплярах, пакеты, которые
не ставятся одной командой apt.

=========================================================================
1. УСТАНОВКА DOCKER НА ADMIN И NODE2
=========================================================================

Ставим из официального репозитория Docker, а не из пакета docker.io
Ubuntu: там версия отстаёт, а плагины идут отдельными пакетами. Команды
раздела выполняются и на admin, и на node2.

1.1. Ключ репозитория:

sudo apt update
sudo apt install -y ca-certificates curl gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg

1.2. Подключение репозитория:

echo "deb [arch=$(dpkg --print-architecture)" \
     "signed-by=/etc/apt/keyrings/docker.gpg]" \
     "https://download.docker.com/linux/ubuntu" \
     "$(. /etc/os-release && echo "${VERSION_CODENAME}") stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

Выпуск берётся из /etc/os-release, архитектура из dpkg: вписанный руками
выпуск при опечатке даст «пакет не найден».

1.3. Установка и запуск:

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io \
    docker-buildx-plugin docker-compose-plugin

sudo systemctl enable --now docker
sudo docker version

Пакеты: docker-ce — демон, docker-ce-cli — клиент, containerd.io — среда
запуска контейнеров, docker-buildx-plugin — docker buildx,
docker-compose-plugin — docker compose, ею поднимем реестр.

ПОЧЕМУ НА ОБЕИХ МАШИНАХ: на admin контейнером работает реестр и оттуда
идёт сборка; на node2 конвейер запускает контейнер сайта — там метка
docker.


=========================================================================
2. ГРУППА DOCKER И ЕЁ ОПАСНОСТЬ
=========================================================================

Агент Jenkins работает не от root, и sudo ему не выдан, поэтому доступ
к демону дают через группу. Группа нужна каждому, кто запускает команды
docker: и вам, и пользователю агента jenkins. На обеих машинах:

sudo usermod -aG docker engineer
sudo usermod -aG docker jenkins

ВАЖНО: группу надо выдать именно пользователю jenkins, а не только своему
engineer. Конвейер идёт на node2 под jenkins, и с одной лишь группой
у engineer первая же команда docker в сборке упадёт с «permission denied
while trying to connect to the Docker daemon socket».

ВАЖНО: ключ -a обязателен. Команда без него (usermod -G docker engineer)
ЗАМЕНЯЕТ список дополнительных групп, и пользователь теряет sudo.

Группа применяется только в НОВОЙ сессии: список групп процесса
фиксируется при её создании, и открытый терминал ничего не заметит.

id -nG
newgrp docker

У пользователя jenkins новый вход организовать нельзя, поэтому выдачу
группы агент подхватит только после перезапуска: работающий процесс Java
сохраняет старый список групп. Проверяем оба случая:

docker ps
sudo -u jenkins docker ps

ОБРАТИТЕ ВНИМАНИЕ: членство в группе docker равносильно правам root
на машине. Демон работает от root, и через сокет ему можно поручить
почти всё:

docker run -it --rm -v /:/host alpine chroot /host sh

Это корневая оболочка на хосте; так же читается файл с хешами паролей.
Поэтому в рабочей среде группа docker считается административной,
а на серверах сборки предпочитают rootless-режим. Подробнее в разделе 10.


=========================================================================
3. СВОЙ РЕЕСТР ОБРАЗОВ
=========================================================================

Собранный образ надо где-то хранить, чтобы его забрал агент на node2;
хранилище образов называется реестром.

ЗАЧЕМ СВОЙ, А НЕ DOCKER HUB: Hub требует учётной записи, образы уезжали
бы наружу, а без интернета конвейер встал бы. Свой реестр работает
внутри подсети; следить за местом и обновлением придётся самому.

3.1. Разбираем files/docker/registry-compose.yml:

  * image: registry:2.8 — версия зафиксирована, а не latest: поведение
    не меняется без наших правок;
  * container_name: lab-registry, restart: unless-stopped — по имени
    смотрим состояние, после перезагрузки машины реестр поднимается сам;
  * ports: "0.0.0.0:5000:5000" — слушаем все интерфейсы, а не только
    127.0.0.1: иначе push с других машин не пройдёт;
  * REGISTRY_STORAGE_DELETE_ENABLED: "true" — разрешает удалять образы
    через API реестра; без этого освободить место будет нечем;
  * REGISTRY_AUTH и два ключа со словом HTPASSWD — проверка логина
    и пароля по файлу htpasswd, смонтированному внутрь только для чтения;
  * volumes: registry-data:/var/lib/registry — именованный том: образы
    переживут пересоздание контейнера;
  * volumes: ./htpasswd:/auth/htpasswd:ro — файл паролей; относительный
    путь считается от каталога compose-файла, поэтому файл лежит рядом
    с registry-compose.yml.

ПОЧЕМУ ПАРОЛЬ В ОТДЕЛЬНОМ ФАЙЛЕ: compose-файл лежит в репозитории и виден
в истории, а пароль — не конфигурация, его меняют, не трогая сервис.
В Jenkins тот же принцип: пароль живёт в credentials, а не в Jenkinsfile.

3.2. Файл паролей на admin:

sudo apt install -y apache2-utils
cd ~/site/files/docker
htpasswd -Bbn labuser Console47 > htpasswd
cat htpasswd

Строка получится вида labuser:$2y$05$... ; ключи: -B — хеш bcrypt,
-b — пароль из аргумента, -n — вывод на экран. Файл с паролем
в репозиторий не заливаем:

echo 'htpasswd' >> .gitignore
chmod 600 htpasswd

УТОЧНЕНО: ключ -b удобен в лаборатории, но пароль из него попадает
в историю команд; там, где это важно, htpasswd вызывают без -b.

3.3. Запуск и проверка из корня рабочей копии репозитория:

cd ~/site
docker compose -f files/docker/registry-compose.yml up -d

Без пароля должно быть отказано:

curl -i http://10.0.2.5:5000/v2/_catalog
# HTTP/1.1 401 Unauthorized

Отказ — хороший результат: проверка пароля работает. Теперь с паролем:

curl -u labuser:Console47 http://10.0.2.5:5000/v2/_catalog
# {"repositories":[]}

Пустой список означает, что реестр работает, пароль принят, образов нет.
ОБРАТИТЕ ВНИМАНИЕ: адрес реестра пишется с портом — 10.0.2.5:5000.


=========================================================================
4. НАСТРОЙКА ДЕМОНА: INSECURE-REGISTRIES И ЖУРНАЛЫ
=========================================================================

Без следующего шага ничего не заработает. Проверим:

sudo docker login 10.0.2.5:5000 -u labuser
# Error response from daemon: Get "https://10.0.2.5:5000/v2/":
# http: server gave HTTP response to HTTPS client

ПОЧЕМУ ТАК: Docker по умолчанию требует HTTPS с настоящим сертификатом,
а наш реестр работает по http — белого IP и сертификата у стенда нет,
и это осознанное решение лаборатории. Такой реестр надо разрешить явно.

4.1. Разбираем files/docker/daemon.json — настройку ДЕМОНА Docker:

  * insecure-registries — реестры, к которым разрешено обращаться по http.
    В рабочей среде этого ключа быть не должно: там реестр ставят
    за HTTPS с сертификатом внутреннего центра сертификации;
  * log-driver и log-opts — ограничение журналов контейнеров: 10 МБ
    на файл и три файла. Без ограничения журнал растёт бесконечно
    и однажды занимает весь диск; снаружи это выглядит как «Jenkins
    перестал работать» без причины, а на деле кончилось место;
  * live-restore — контейнеры работают, пока служба Docker перезапускается.

ВАЖНО: JSON не поддерживает комментарии, а демон разбирает файл строго:
неизвестное поле — и служба не стартует. Поэтому пояснения вынесены
в files/docker/README.txt, а в файле только рабочие ключи.

4.2. Ставим файл и перезапускаем службу — на ОБЕИХ машинах:

sudo install -m 0644 files/docker/daemon.json /etc/docker/daemon.json
sudo systemctl restart docker

Проверка:

docker info | grep -A2 'Insecure Registries'
# Insecure Registries:
#   10.0.2.5:5000

Теперь вход проходит: docker login 10.0.2.5:5000 -u labuser

ПОЧЕМУ НА КАЖДОЙ МАШИНЕ: настройка действует на уровне демона, а демонов
у нас два — на admin и на node2. Забыть про вторую машину легко: сборка
и push с admin пройдут, а запуск контейнера на node2 упадёт с той же
ошибкой про HTTPS. Так же и docker login действует только там, где он
выполнен.


=========================================================================
5. ОБРАЗ САЙТА: РАЗБИРАЕМ DOCKERFILE.SITE
=========================================================================

Открываем files/docker/Dockerfile.site и разбираем инструкции.

  FROM nginx:1.27-alpine

Версия зафиксирована, а не взята как latest. Тег latest означает «то, что
сейчас в реестре»: сегодня одна версия, завтра другая, а Dockerfile тот
же, — и сборка «вчера работала, сегодня нет» без правок обычно ровно
про это. Обновляться нужно осознанно: поменять строку FROM и посмотреть,
что изменилось. Alpine выбран ради размера: около 50 МБ вместо 190 МБ.

  LABEL org.opencontainers.image.*

Подписи образа: название, описание, автор; видны в docker inspect.

  COPY index.html      /usr/share/nginx/html/index.html
  COPY build-info.txt  /usr/share/nginx/html/build-info.txt

Копируются только нужные файлы. Каталог целиком копировать нельзя: лишние
файлы уедут в образ и останутся в истории слоёв, даже если удалить их
следующей командой — удаление в следующем слое образ не уменьшает.
/usr/share/nginx/html — каталог, откуда официальный nginx отдаёт статику.

  EXPOSE 80

Это документирование порта, а не публикация: наружу порт выводит ключ -p
при запуске (-p 8081:80). На node2 порт 80 занят nginx из практики 11,
поэтому контейнер получает 8081.

  HEALTHCHECK --interval=30s --timeout=3s --start-period=5s \
      --retries=3 CMD wget -q -O /dev/null http://127.0.0.1/ || exit 1

Docker раз в 30 секунд запускает wget внутри контейнера и ставит статус
healthy или unhealthy; взят wget, потому что он есть в alpine из коробки.
Так ловится частая авария: «контейнер запущен, а страницу не отдаёт».

УТОЧНЕНО: статус unhealthy сам контейнер не перезапускает — перезапуск
делает ключ --restart, и только когда процесс завершился. Проверка нужна,
чтобы состояние было видно снаружи.

Запуск от непривилегированного пользователя: в образе nginx мастер-процесс
стартует от root, чтобы занять порт 80, а рабочие процессы идут
от пользователя nginx. Строки USER в нашем Dockerfile поэтому нет.


=========================================================================
6. СБОРКА, ТЕГИ И ПУБЛИКАЦИЯ
=========================================================================

Соберём образ вручную, чтобы увидеть механику до того, как её спрячет
конвейер. Контекст сборки — каталог, содержимое которого видит Dockerfile.

cd ~/site
rm -rf build/docker-context
mkdir -p build/docker-context

cp files/www/index.html build/docker-context/index.html
sed -i 's/__BUILD_NUMBER__/1/g' build/docker-context/index.html
sed -i 's/__GIT_COMMIT__/manual/g' build/docker-context/index.html
printf 'build_number=1\njob=manual\nagent=admin\n' \
  > build/docker-context/build-info.txt

ЗАЧЕМ ПОДСТАНОВКА: в странице (files/www/index.html) есть маркеры
__BUILD_NUMBER__ и __GIT_COMMIT__, и конвейер заменяет их номером сборки
и ревизией. Оставшийся маркер означает, что подстановка не сработала.

6.1. Сборка и проверка до публикации:

docker build --file files/docker/Dockerfile.site \
    --tag 10.0.2.5:5000/lab-site:1 build/docker-context

docker rm -f lab-site-test 2>/dev/null || true
docker run -d --name lab-site-test -p 8082:80 \
    10.0.2.5:5000/lab-site:1
curl -s http://10.0.2.5:8082/ | grep -i 'Hello from DevOps Engineer'
docker rm -f lab-site-test

ЗАЧЕМ ЗДЕСЬ 8082, А НЕ 8081. Порт 8081 занят контейнером, который
выкатил предыдущий запуск конвейера: он работает постоянно и нужен,
чтобы сайт был доступен. Если запустить проверочный контейнер на том же
порту, Docker ответит «port is already allocated» — проверка образа
не должна зависеть от того, что сейчас работает на хосте.

В имени образа три части: 10.0.2.5:5000 — адрес реестра, lab-site — имя
репозитория, 1 — тег; разбор имени и есть указание, куда образ поедет
при push. Ключ --file обязателен, когда Dockerfile не рядом с контекстом.
ВАЖНО: образ собран — это ещё не значит, что он рабочий.

6.2. Публикация:

docker login 10.0.2.5:5000 -u labuser
docker tag 10.0.2.5:5000/lab-site:1 10.0.2.5:5000/lab-site:latest
docker push 10.0.2.5:5000/lab-site:1
docker push 10.0.2.5:5000/lab-site:latest

curl -u labuser:Console47 http://10.0.2.5:5000/v2/lab-site/tags/list
# {"name":"lab-site","tags":["1","latest"]}

docker logout 10.0.2.5:5000

ДИСЦИПЛИНА ТЕГОВ. Неизменяемый тег (номер сборки) — то, по чему
выкатывают: он указывает на конкретный образ и не меняется. latest —
подвижный тег «дай последний образ». «Выкатывать latest» означает
не знать, что работает: у вас и в реестре может оказаться разное.

КЛАССИЧЕСКАЯ ОШИБКА: образ собран, но не запушен. На admin всё хорошо,
на node2 образа нет, и конвейер падает на запуске контейнера. Ещё одна
ошибка — имя без адреса реестра: lab-site:1 Docker ищет в Docker Hub
и отвечает «pull access denied for lab-site».


=========================================================================
7. КОНВЕЙЕР FILES/PIPELINES/JENKINSFILE.DOCKER
=========================================================================

Задание: New Item -> Pipeline -> Pipeline script from SCM, Git,
Repository URL ssh://git@10.0.2.5:2222/engineer/site.git, Credentials —
gitea-reader, Branch Specifier — */main, Script Path —
files/pipelines/Jenkinsfile.docker.

Credentials для реестра: Manage Jenkins -> Credentials -> System ->
Global credentials -> Add Credentials, Kind «Username with password»,
ID docker-registry, Username labuser, Password Console47. Идентификатор
важен: конвейер ищет секрет именно по этой строке.

7.1. Стадии.

  1. Забрать код: deleteDir() и checkout scm. В options конвейера задан
     skipDefaultCheckout(true), поэтому автоматическое скачивание кода
     отключено и checkout в этой стадии делается явно.
  2. Подготовить контекст: создаётся build/docker-context, туда копируется
     страница с подставленными номером сборки и ревизией, рядом пишется
     build-info.txt.
  3. Собрать образ: docker build с двумя тегами — ${BUILD_NUMBER} и latest.
  4. Проверить образ: контейнер lab-site-demo-test поднимается на
     ОТДЕЛЬНОМ порту — переменная TEST_PORT (8082), а не на том же 8081,
     где работает выкат. Страница и build-info.txt проверяются curl-ом
     по этому порту, затем контейнер удаляется. Порт проверки обязан
     отличаться от порта выката: 8081 занят контейнером предыдущего
     выката (снимает его стадия 6, а она идёт позже), и вторая сборка
     подряд упала бы на этой стадии с «port is already allocated».
     Проверяется не «что-то ответило», а что ответила именно эта сборка.
  5. Опубликовать в реестр: логин и push внутри withCredentials.
  6. Перезапустить контейнер: старый удаляется через docker rm -f, новый
     поднимается с тем же именем и ключом --restart unless-stopped.
  7. Проверить снаружи: files/scripts/smoke_test.sh проверяет код ответа,
     текст на странице и номер сборки — то же, что увидит человек.

ПРО ДВА ПОРТА В ЭТОМ КОНВЕЙЕРЕ. В блоке environment их два, и путать
их не нужно:

  HOST_PORT = '8081'   порт, на котором сайт в контейнере доступен людям
                       (стадии 6 и 7): на node2 порт 80 занят nginx
                       из практики 11, поэтому контейнер получает 8081;
  TEST_PORT = '8082'   порт, на котором контейнер живёт ТОЛЬКО во время
                       проверки образа в стадии 4 и который освобождается
                       сразу после неё.

Разделять их обязательно: если проверка займёт порт выката, конвейер
будет проходить только один раз.

ПРОВЕРЬТЕ СРАЗУ ВТОРЫМ ЗАПУСКОМ. Нажмите Build Now ещё раз и убедитесь,
что конвейер прошёл целиком. Это не формальность: конвейер должен быть
ПОВТОРЯЕМЫМ. Худший вид поломки — тот, при котором первая сборка после
настройки проходит, а вторая падает: значит, от первой осталось
состояние (контейнер, занятый порт, файл, том), и с ним нужно
что-то делать. Классический пример — порт проверки, совпавший с портом
выката (разбор — в разделе 12).

7.2. Три места, которые сделаны осознанно.

ПОЧЕМУ ПАРОЛЬ ПЕРЕДАЁТСЯ ЧЕРЕЗ STDIN:

echo "${REG_PASS}" | docker login "${REGISTRY}" \
    --username "${REG_USER}" --password-stdin

Аргументы командной строки видны в списке процессов и попадают в историю
команд: любой, кто заглянет в ps на агенте, увидит пароль к реестру.
Jenkins маскирует значения из credentials в журнале, но маскирование —
последняя линия обороны, а не разрешение печатать пароли.

ПОЧЕМУ В POST ЕСТЬ DOCKER LOGOUT: после docker login учётные данные
остаются в файле ~/.docker/config.json пользователя jenkins на node2,
и его читает любой процесс того же пользователя. Выход в конце сборки
убирает такую возможность.

ПОЧЕМУ В FAILURE ПЕЧАТАЕТСЯ DOCKER LOGS: контейнер, который сразу упал,
в docker ps не виден, и без журнала причина остаётся неизвестной — шаг
просто «завершился с кодом 1».

7.3. ИСПРАВЛЕНО.

ИСПРАВЛЕНО: сборка выполнялась в образе python:3.7 — он снят
с поддержки и удалён из Docker Hub, поэтому сборка падала уже
на скачивании базового образа. Python в конвейере не нужен вовсе.

ИСПРАВЛЕНО: в прежней версии не было ни проверки образа после сборки,
ни публикации в реестр, ни уборки за собой. Теперь цикл замкнут:
собрали, проверили, опубликовали, выкатили, проверили снаружи.

уйдёт туда; потеряете метку — сборка повиснет в очереди.

=========================================================================
9. АГЕНТЫ В КОНТЕЙНЕРАХ
=========================================================================

Главная выгода Docker не в упакованном сайте, а в том, что инструменты
сборки перестают быть свойством сервера. Разберём два способа.

СПОСОБ 1: КОНТЕЙНЕР НА ВРЕМЯ СТАДИИ. Директива agent { docker { ... } }
поднимает контейнер на агенте, выполняет в нём стадии и убирает его;
отвечает за это плагин docker-workflow.

    stage('Проверка Java') {
        agent { docker { image 'eclipse-temurin:21-jdk' } }
        steps { sh 'java -version' }
    }

Внешний agent { label 'docker' } выбирает машину с Docker — node2, у node1
метки docker нет. Внутренний agent { docker { ... } } означает, что стадии
этой ступени идут в контейнере из указанного образа: eclipse-temurin:21-jdk
— официальная сборка OpenJDK 21, и java внутри есть, что бы ни стояло
на самой машине. Рабочая копия агента монтируется внутрь контейнера.

Требования: на агенте есть Docker и у пользователя jenkins есть доступ
к сокету (sudo -u jenkins docker ps); образ доступен из кэша или
скачиванием — закрытый реестр отдаст его только после docker login;
в образе есть инструменты, нужные стадии. В eclipse-temurin нет ни rsync,
ни git: если стадии нужен rsync, берите образ агента из
files/docker/Dockerfile.agent. Родственный вариант — agent { dockerfile
true }: образ собирается из Dockerfile в корне репозитория.

СПОСОБ 2: ОБЛАКО DOCKER (плагин docker-plugin): описывают не среду
стадии, а парк агентов, и Jenkins сам поднимает эфемерные или постоянные
контейнеры по мере появления заданий. Manage Jenkins -> Clouds ->
New cloud -> тип Docker; основные поля — адрес демона
(unix:///var/run/docker.sock), метки шаблона (docker-agent), образ
(10.0.2.5:5000/jenkins-agent:1), рабочий каталог (/home/jenkins/agent),
способ подключения (Attach Docker container) и пользователь (jenkins).

ВАЖНО ПРО АДРЕС ДЕМОНА: облако указывает на демон Docker, а не на машину
агента. Docker на стенде стоит на admin, поэтому облако настраивается
на контроллере, а адрес демона — локальный сокет. Подключить облако
к демону на node2 можно только по сети, открыв порт 2375, — а это раздача
root любому в сети (раздел 10).

9.1. Разбираем files/docker/Dockerfile.agent.

  FROM jenkins/inbound-agent:jdk21

Основа — официальный образ агента Jenkins: в нём уже есть Java, сам агент
и правильный пользователь. Собирать это с нуля — повторять чужую работу
и наступать на свои грабли: не тот уровень прав, не тот рабочий каталог,
не тот способ подключения. Тег jdk21 фиксирует версию Java.

  USER root

  RUN apt-get update \
   && apt-get install -y --no-install-recommends \
          rsync curl ca-certificates openssh-client git jq \
   && rm -rf /var/lib/apt/lists/*

Пакеты ставятся от root, потому что apt иначе не работает. Зачем эти:
rsync — выкат файлов, как в практике 11; curl — проверки; ca-certificates
— доверие к сертификатам; openssh-client — git по ssh; git и jq — то,
чего в сборках всегда не хватает. --no-install-recommends не тянет лишние
пакеты, а удаление списков apt в том же слое не оставляет мусора.

  USER jenkins
  WORKDIR /home/jenkins/agent

Обратно на пользователя jenkins: процесс агента не должен выполняться
от root. Рабочий каталог совпадает с remoteFS при создании агента; если
значения не совпадут, сборки пойдут в каталог по умолчанию.

Собираем и публикуем образ агента (контекст — корень репозитория,
инструкций COPY в файле нет):

docker build -f files/docker/Dockerfile.agent \
    -t 10.0.2.5:5000/jenkins-agent:1 .
docker push 10.0.2.5:5000/jenkins-agent:1

9.2. ЭФЕМЕРНЫЙ АГЕНТ: ЧЕМ ЛУЧШЕ И ЧЕМ ХУЖЕ.

Лучше: среда одинаковая у всех сборок, потому что описана образом; мусор
исчезает вместе с контейнером; нет «снежинки» — машины, которую нельзя
пересоздать, потому что на ней «что-то настроено»; видно, с каким набором
инструментов собиралась версия полгода назад.

Хуже: каждая сборка платит за подъём контейнера; кэши инструментов между
сборками не сохраняются без отдельного тома; секреты приходится передавать
внутрь контейнера; доступ к Docker идёт через сокет, и это опасно.


=========================================================================
10. БЕЗОПАСНОСТЬ DOCKER В JENKINS
=========================================================================

Самый распространённый совет в интернете: «смонтируйте в контейнер агента
сокет Docker, чтобы внутри можно было собирать образы». Совет рабочий
и почти всегда опрометчивый.

ПОЧЕМУ МОНТИРОВАНИЕ СОКЕТА — ЭТО ВЫДАЧА ROOT НА ХОСТ.
/var/run/docker.sock — точка входа в демон, а демон работает от root.
Тот, кто может отдать демону команду, может попросить у него почти всё:

docker run -it --rm -v /:/host alpine chroot /host sh

Это корневая оболочка на хосте со всеми файлами и ключами. Уязвимости
в Docker не нужны: вы воспользовались выданным доступом. В мире CI это
означает, что любой, кто может изменить Jenkinsfile, получает root.

Что делать вместо этого:

  1. НЕ МОНТИРОВАТЬ СОКЕТ. Наш случай: Docker стоит на node2, конвейер
     идёт на node2 и обращается к демону как обычный клиент.
  2. ЗАПУСКАТЬ DOCKER НА САМОМ АГЕНТЕ, А НЕ В КОНТЕЙНЕРЕ. Агент — процесс
     на машине с Docker, контейнеры — его дочерние процессы; права
     на сокет ограничены пользователем jenkins, как у нас и сделано.
  3. ОГРАНИЧЕННЫЕ ОБЁРТКИ ВМЕСТО ДЕМОНА: Kaniko собирает образ внутри
     контейнера без сокета, BuildKit умеет rootless-режим. Углубляться
     не будем, но направление стоит знать.
  4. ROOTLESS-РЕЖИМ DOCKER: демон и контейнеры работают от обычного
     пользователя, и побег из контейнера не даёт root на хосте.

Вывод для стенда: сборка идёт на node2, сокет в контейнеры не монтируется,
реестр на admin — отдельный демон. Сборки на контроллере не запускаем —
правило из практики 2.


=========================================================================
11. ГИГИЕНА ОБРАЗОВ
=========================================================================

11.1. ПОРЯДОК ИНСТРУКЦИЙ И КЭШ СЛОЁВ. Каждая инструкция Dockerfile
создаёт слой, и слои кэшируются: если слой не изменился, он берётся
из кэша, а кэш сбрасывается на первом изменившемся слое и на всех
последующих. Отсюда правило: то, что меняется чаще, — ниже. В Dockerfile
сайта так и сделано.

Обратный пример: поставьте COPY index.html в начало, а после него долгий
apt-get install — и каждая правка страницы будет заново ставить пакеты.
Ещё приём, знакомый по образу агента: связанные команды собирают в одну
инструкцию RUN через &&, а временные файлы удаляют в том же слое.

11.2. МНОГОЭТАПНАЯ СБОРКА (MULTI-STAGE): один Dockerfile, несколько
этапов. На первом тяжёлый образ с компилятором, на нём проект собирается;
на втором маленький образ, куда копируется только результат.

  FROM golang:1.23 AS build
  RUN go build -o /out/app ./cmd/app

  FROM alpine:3.20
  COPY --from=build /out/app /usr/local/bin/app
  ENTRYPOINT ["app"]

ЗАЧЕМ ЭТО НУЖНО: в финальный образ не попадают ни компилятор, ни
исходники, ни кэш зависимостей. Образ становится в разы меньше, а вместе
с размером уходит значительная часть уязвимостей. У НАС многоэтапная
сборка не нужна: сайт статический, собирать нечего.

11.3. ПРОВЕРКА ОБРАЗА СКАНЕРОМ. Образ — чужой код вместе с библиотеками,
а часть библиотек со временем получает известные уязвимости. Самый
распространённый сканер — trivy (проект aquasecurity); ставится отдельно,
пакетом проекта или бинарником, в репозитории Ubuntu его нет:

trivy image --severity HIGH,CRITICAL 10.0.2.5:5000/lab-site:1

Сканер печатает пакет, версию, уязвимость и версию с исправлением. Если
ставить его не хочется, полезен и минимум: docker history показывает, что
лежит в слоях. ВАЖНО: «образ с прошлого года без обновлений» — это риск,
а не экономия, поэтому базовый образ полезно заново скачивать при сборке
(docker build --pull).

11.4. ОГРАНИЧЕНИЕ РЕСУРСОВ КОНТЕЙНЕРА. По умолчанию контейнер может
занять всю память и все ядра машины, а один такой контейнер способен
положить агента: система убьёт процессы сборки, и в журнале появится
«Killed» с кодом 137 из практики 3.

docker run -d --name lab-site-demo \
    --memory 256m --cpus 1 \
    --restart unless-stopped -p 8081:80 \
    10.0.2.5:5000/lab-site:latest

--memory 256m — предел памяти, --cpus 1 — примерно одно ядро; для сборок
предел подбирают по факту, с запасом в полтора раза. Ограничение
превращает «аварию на всём узле» в «одна сборка упала».


=========================================================================
12. УБОРКА ДИСКА
=========================================================================

Docker умеет тихо съесть диск целиком: кэш сборки, остановленные
контейнеры, старые образы и журналы лежат в /var/lib/docker и сами
не удаляются.

12.1. Смотрим, что занимает место:

docker system df
docker system df -v

Первая команда показывает четыре категории: образы, контейнеры, тома
и кэш сборки; вторая — подробности по каждому объекту.

12.2. Точечная уборка:

docker container prune -f     # удалить остановленные контейнеры
docker image prune -f         # удалить «висячие» образы (dangling)
docker builder prune -f       # очистить кэш сборки

Висячий образ — слои без тега, оставшиеся после пересборки, когда тег
переехал на новый образ; именно они незаметно занимают гигабайты.

ДОБАВЛЕНО: у этих команд есть ключ --filter, и по возрасту он полезнее
ручной уборки: docker image prune -af --filter "until=168h" удалит то,
что не использовалось неделю, и оставит нужное.

12.3. ЧЕГО НЕ ДЕЛАТЬ.

docker system prune -a

На машине сборки это плохая идея. Ключ -a означает «удалить все образы,
не используемые запущенными контейнерами». Под это попадают базовые
образы (например, nginx:1.27-alpine) и образы, которые нужны следующим
сборкам: сейчас они не используются, но понадобятся через минуту. Сборка
качает сотни мегабайт заново, а без интернета просто падает. Правило:
точечные prune с фильтром по возрасту — можно, system prune -a — нет.

12.4. РЕГУЛЯРНАЯ УБОРКА. Разовая уборка проблему не решает: диск
заполнится снова. Настраивают её либо в cron:

sudo crontab -e
# раз в неделю, по воскресеньям в 5 утра
0 5 * * 0 /usr/bin/docker image prune -af --filter until=336h \
  >> /var/log/docker-prune.log 2>&1

либо заданием в самом Jenkins — для курса это логичнее: уборка видна
в истории сборок и выполняется на нужном агенте (Pipeline с Build
periodically, например H 5 * * 0, и шаги sh с теми же командами prune).
Проверяем результат:

df -h /var/lib/docker
docker system df


=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: «permission denied while trying to connect to the Docker daemon»

Пользователь не входит в группу docker либо сессия старая:

id -nG
ls -l /var/run/docker.sock

Если группы нет — sudo usermod -aG docker engineer и новая сессия.
Если docker есть, а ошибка осталась, сессия создана до изменения группы:
список групп процесса фиксируется при входе. Лечится newgrp docker или
повторным входом, а для агента Jenkins — перезапуском агента.

ОБРАТИТЕ ВНИМАНИЕ: для сборок выдача группы пользователю engineer
не помогает. В конвейере команды docker выполняет пользователь jenkins
на node2, поэтому группу нужно выдать ему (sudo usermod -aG docker
jenkins) и перезапустить агента — иначе ошибка останется прежней, хотя
в своём терминале docker у вас работает.

ПРОБЛЕМА: «Cannot connect to the Docker daemon ... Is the daemon running?»

Демон не запущен:

sudo systemctl status docker --no-pager
sudo journalctl -u docker -n 30
sudo systemctl start docker

Если служба падает сразу после старта, чаще всего виноват синтаксис
/etc/docker/daemon.json — лишняя запятая или строка с решёткой:

python3 -m json.tool /etc/docker/daemon.json

ПРОБЛЕМА: «http: server gave HTTP response to HTTPS client»

Docker обратился к реестру по HTTPS, а реестр отвечает по http: адрес
не прописан в insecure-registries либо демон не перезапущен после правки.

docker info | grep -A2 'Insecure Registries'

Если адреса 10.0.2.5:5000 нет, проверьте, что файл files/docker/daemon.json
скопирован в /etc/docker/daemon.json ИМЕННО на этой машине: на admin
настройка есть, а на node2 её забыли — самая частая причина. После
копирования: sudo systemctl restart docker

ПРОБЛЕМА: «unauthorized: authentication required»

Не выполнен вход в реестр либо не подходит пароль:

docker login 10.0.2.5:5000 -u labuser
curl -u labuser:Console47 http://10.0.2.5:5000/v2/_catalog

Если curl отвечает 401, дело не в Jenkins: не совпадает пара логин-пароль
в файле htpasswd (посмотреть пользователей: cut -d: -f1 htpasswd
в каталоге compose-файла). Пароль хеширован, восстановить его нельзя;
при сомнениях файл пересоздают и перезапускают реестр:

docker compose -f files/docker/registry-compose.yml restart

И помните: вход выполняется на той машине, где идёт push.

ПРОБЛЕМА: «no space left on device»

Место кончилось:

df -h
docker system df
docker builder prune -f
docker image prune -af --filter "until=168h"

Если мало, ищем крупные объекты: docker system df -v показывает размер
по каждому образу и контейнеру, а удаление образа освобождает место
не сразу, а после удаления зависящих от него контейнеров.

ПРОБЛЕМА: «container name already in use» и «port is already allocated»

Старый контейнер держит имя либо порт:

docker ps -a --filter name=lab-site-demo
docker rm -f lab-site-demo

Порт 8081 занят — на нём кто-то сидит: старый контейнер, контейнер
от предыдущей попытки или перенастроенный nginx из практики 11:

sudo ss -ltnp | grep 8081

Конвейер защищён от первой половины проблемы: в стадии 6 он сначала
делает docker rm -f для того же имени.

ОТДЕЛЬНО ПРО ПОВТОРНЫЙ ЗАПУСК. Если конвейер падает на стадии 4
с «port is already allocated» именно на второй сборке, дело не в
контейнере lab-site-demo (его снимает стадия 6, она идёт позже) и не
в вашей ошибке: стадия проверки образа просто заняла порт, на котором
работает выкат. Порт проверки должен отличаться от порта выката —
в конвейере за это отвечают две переменные в environment: HOST_PORT
(8081, порт выката) и TEST_PORT (8082, порт проверки). Если такой
конвейер вы писали сами и взяли один порт на оба дела, добавьте
TEST_PORT и подставьте его в стадию проверки образа.

ПРОБЛЕМА: контейнер запускается и сразу останавливается

Главный инструмент — журнал контейнера:

docker ps -a --filter name=lab-site-demo
docker logs --tail 50 lab-site-demo

Типичные причины по журналу: «no such file or directory» — в образе нет
файла по ожидаемому пути (забыт COPY); «bind: address already in use» —
порт занят; «exec format error» — образ собран для другой архитектуры;
пустой журнал и код возврата 0 — процесс просто завершился, потому что
это не служба, а разовая команда. Что реально лежит в образе, видно так:

docker run --rm -it --entrypoint sh 10.0.2.5:5000/lab-site:1

ПРОБЛЕМА: образ не найден на агенте

Сообщение «Unable to find image ... locally» и следом отказ. Проверяем:
образ запушен в реестр (curl к 10.0.2.5:5000/v2/lab-site/tags/list с
логином labuser); на агенте выполнен docker login; на агенте разрешён
http-реестр (docker info | grep -A2 Insecure); имя образа включает адрес
реестра — 10.0.2.5:5000/lab-site:1, а не lab-site:1, потому что без
адреса Docker ищет образ в Docker Hub.

ПРОБЛЕМА: сборка образа «висит» на шаге apt-get

Скорее всего на машине нет доступа в интернет или он идёт через прокси:

curl -sI https://download.docker.com | head -n 1
ping -c2 8.8.8.8

Прокси указывают для демона Docker, а не для оболочки: в файл
/etc/systemd/system/docker.service.d/http-proxy.conf добавляют переменные
HTTP_PROXY и HTTPS_PROXY, после чего выполняют daemon-reload и restart.
Другая причина — скачивание большого образа по медленному каналу: это
видно в выводе docker build по строкам про загрузку слоёв. И третья:
обращение к внешнему реестру вместо своего, если имя образа записано
без адреса 10.0.2.5:5000.


=========================================================================
УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

1. Демонстрационный контейнер на node2:

docker ps -a --filter name=lab-site-demo
docker rm -f lab-site-demo

Если он запускался вручную под именем lab-site-test, удаляем и его.

2. Тестовые образы на admin:

docker rmi 10.0.2.5:5000/lab-site:latest
docker rmi 10.0.2.5:5000/lab-site:1

ОБРАТИТЕ ВНИМАНИЕ: удаление локальной копии не удаляет образ
из реестра — это отдельное хранилище в томе registry-data. Радикальная
чистка реестра:

docker compose -f files/docker/registry-compose.yml down -v

Ключ -v удаляет том с данными реестра, то есть все образы.

3. Накопившееся:

docker container prune -f
docker image prune -f
docker system df

4. Что оставить. Реестр можно оставить работающим: он занимает немного
места и ничему не мешает. Можно и остановить: для практики 13 Docker
не нужен вовсе, там речь о библиотеке шагов в самом Jenkins.

docker compose -f files/docker/registry-compose.yml stop

Обратно поднимается командой start с тем же файлом.

УТОЧНЕНО: если реестр остановлен, а конвейер сборки образа запустить
снова, он упадёт на стадии публикации — не потому, что что-то сломалось,
а потому, что реестр не работает.

5. Проверяем:

docker ps -a
docker system df
systemctl is-active docker

Служба Docker на admin и node2 остаётся включённой: в практике 14 мы
поднимаем Jenkins заново на новой машине и проверяем восстановление
из копии.


=========================================================================
ЧТО ДАЛЬШЕ
=========================================================================

Мы прошли путь от установки Docker до конвейера, который собирает образ,
проверяет его, публикует в свой реестр и выкатывает контейнером. Попутно
разобрали то, что отличает учебный пример от эксплуатации: опасность
группы docker и сокета, дисциплину тегов, гигиену образов, уборку диска.

Дальше в курсе:

  * практика 13 — общие библиотеки (Shared Libraries): повторяющиеся
    стадии, проверки и шаги выката выносят из Jenkinsfile в библиотеку,
    версионируют и подключают. Docker для этой практики не нужен;

  * практика 14 — конфигурация как код и восстановление: резервные копии
    JENKINS_HOME, JCasC — описание конфигурации Jenkins файлом вместо
    ручных настроек в портале, и проверка того, что Jenkins поднимается
    с нуля по этим файлам. Docker для этой практики не требуется:
    восстановление проверяется на новой машине с пакетным Jenkins.

Полезно вернуться к этой практике и позже: когда появится настоящий
проект с компиляцией, многоэтапная сборка из раздела 11 и агент
в контейнере из раздела 9 применятся почти без изменений.
