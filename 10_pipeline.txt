Практика 10. Конвейеры: Jenkinsfile вместо набора галочек.

Конвейер — это описание сборки, записанное текстом. Обычное задание
(Freestyle project) состоит из галочек и полей в портале: репозиторий,
триггеры, шаги сборки. Конвейер делает то же самое, но его описание —
файл, который выполняется как программа: у него есть стадии, переменные,
условия и действия после завершения.

ЧТО ЭТО ДАЁТ

  * описание сборки можно положить рядом с кодом и обсуждать как код:
    правка проходит ревью, откатывается вместе с коммитом;
  * журнал сборки превращается в последовательность стадий, и сразу видно,
    на какой именно стадии всё остановилось;
  * конфигурация воспроизводима: чтобы поднять такую же сборку на другом
    Jenkins, достаточно скопировать репозиторий и завести задание;
  * сложные сценарии — параллельный выкат на два сервера, подтверждение
    перед выкатом, автоматический откат — описываются обычным кодом.

ПЛАТА ЗА ЭТО тоже есть, и о ней честно: нужно немного знать Groovy
(кавычки, подстановка значений), ошибка компиляции сообщает номер строки
в описании конвейера, а не в вашем скрипте, и первый конвейер почти всегда
не запускается с первого раза.

ЧТО МЫ СДЕЛАЕМ. Соберём конвейер прямо в портале, в задании
Pipeline_job_1, за шесть шагов: от «Hello, World» до полного конвейера
с тремя стадиями, ограничениями и блоком post. Каждый шаг — полный текст
конвейера целиком: вставляем в портал, запускаем, читаем журнал. Затем
перенесём готовый конвейер в репозиторий как Jenkinsfile и создадим
задание site_pipeline. В части 2 добавим параллельные стадии, условия
и ручное подтверждение.

ИСПРАВЛЕНО: в прежней версии курса примеры не запускались. Ошибки,
которые там были, — по одной строке на каждую:

  * «agent nay» вместо agent any — такого значения не существует;
  * потеряны закрывающие скобки, и из-за этого стадии оказались вложены
    друг в друга;
  * не совпадали кавычки: фрагмент echo 'Building...." Groovy считает
    незакрытой строкой;
  * два задания с именем Pipeline_job_2 — непонятно, какое запускается;
  * образ «python:3.7» устарел: берите актуальную версию образа.
Ещё одна ошибка, которая встречается постоянно: файл, оборванный
без закрывающей скобки блока pipeline.

ЧАСТЬ 1. БАЗОВАЯ ПРАКТИКА

=========================================================================
1. ПЕРВЫЙ КОНВЕЙЕР: МИНИМУМ
=========================================================================

Создаём задание: New Item → имя Pipeline_job_1 → Pipeline → OK.
В разделе Pipeline оставляем Definition: Pipeline script — текст конвейера
живёт прямо в задании, и так удобно пробовать синтаксис. Вставляем:

pipeline {
    agent any

    stages {
        stage('Привет') {
            steps {
                echo 'Hello, World'
            }
        }
    }
}

Save → Build Now. Открываем сборку и читаем журнал:

Started by user engineer
Running on node1 in /home/jenkins/agent/workspace/Pipeline_job_1
[Pipeline] { (Привет)
Hello, World
Finished: SUCCESS

ОБРАТИТЕ ВНИМАНИЕ: портал — http://10.0.2.5:8080, а сборка идёт не
на контроллере. agent any выбрал узел node1: /home/jenkins/agent — это
рабочий каталог агента, а на стенде агентов два (node1 и node2, практика 4).

РАЗБОР ПО СТРОКАМ

pipeline { } — внешний блок, обязателен. Всё описание конвейера лежит
внутри него, и такой блок в файле один. После закрывающей скобки pipeline
не должно быть ничего, кроме комментариев и объявлений функций.

agent any — где выполнять. Обязателен. any означает «любой доступный
агент»; в настоящих конвейерах здесь стоит метка, например
agent { label 'web' }.

stages { } — контейнер стадий, обязателен. Стадии внутри идут по порядку,
одна за другой.

stage('Привет') { } — стадия, единица отчётности. Её имя видно в портале
в полосе стадий (Stage View), поэтому имя пишут так, чтобы по нему было
понятно, что происходит.

steps { } — обязателен внутри стадии, в которой есть работа. Здесь вызовы
шагов: echo (напечатать строку), sh (выполнить команду оболочки) и другие.

echo 'Hello, World' — шаг печати: ничего не делает, кроме строки в журнале.

ОБЯЗАТЕЛЬНЫ ТРИ БЛОКА: pipeline, agent и stages. Без agent Jenkins
не знает, где выполнять сборку, без stages — что выполнять.

ЧТО ДОБАВИЛОСЬ В ЭТОЙ ВЕРСИИ: каркас — pipeline, agent any, одна стадия
с шагом echo. Это минимальный конвейер, который вообще запускается.

=========================================================================
2. ШАГ SH: КОМАНДЫ В КОНВЕЙЕРЕ
=========================================================================

Дописываем в stages вторую стадию, которая делает настоящую работу.
Полный текст версии 2:

pipeline {
    agent any

    stages {
        stage('Привет') {
            steps {
                echo 'Hello, World'
            }
        }

        stage('Команды') {
            steps {
                sh 'hostname; whoami; pwd'
                sh '''
                    set -eu
                    mkdir -p build
                    date > build/build-stamp.txt
                    cat build/build-stamp.txt
                '''
            }
        }
    }
}

ПОЧЕМУ НЕЛЬЗЯ НАПИСАТЬ КОМАНДУ ПРОСТО ТАК. Внутри steps { } Jenkins
читает Groovy, а не shell. Строка ls -la была бы понята как вызов метода
ls с аргументом -la, и сборка упала бы с сообщением «No such DSL method
'ls' found among steps». Команды оболочки всегда оборачиваются в sh.

КАКИЕ КАВЫЧКИ ВЫБРАТЬ

  * одинарные — обычная строка, Groovy её не трогает:
    sh 'hostname; whoami; pwd';
  * двойные — Groovy подставляет свои значения перед выполнением:
    sh "echo \"Проект: ${env.PROJECT_NAME}\"".

ОСТОРОЖНО: внутри одинарных кавычек ${...} доходит до shell как есть,
и раскрывает его сам shell; внутри двойных первым подставляет Groovy.

МНОГОСТРОЧНЫЙ СКРИПТ пишут в тройных кавычках — как в обычном шаге
Execute shell. Тройные одинарные (''') означают, что Groovy не трогает
содержимое: это удобно, когда в скрипте есть свои переменные shell.

ЗАЧЕМ set -eu в начале скрипта: e — остановиться на первой ошибке,
u — считать ошибкой обращение к необъявленной переменной. Без этого
скрипт продолжит работу после неудачной команды и «успешно» завершится.

ЕСЛИ КОМАНДА ПАДАЕТ, А ЭТО НОРМАЛЬНО. Иногда нужен не провал сборки,
а код возврата или вывод команды:

def code = sh(script: 'test -f build/build-stamp.txt',
              returnStatus: true)
echo "проверка вернула код ${code}"
def stamp = sh(script: 'cat build/build-stamp.txt',
               returnStdout: true).trim()
echo "содержимое метки: ${stamp}"

Обе опции отменяют автоматическое падение сборки: решение принимает
конвейер, поэтому результат нужно проверять самому. trim() убирает
завершающий перевод строки — без него значение займёт две строки.

ЧТО ДОБАВИЛОСЬ В ЭТОЙ ВЕРСИИ: стадия «Команды» с шагом sh, многострочный
скрипт и правило про кавычки.

=========================================================================
3. ПЕРЕМЕННЫЕ: ENVIRONMENT И ВСТРОЕННЫЕ ЗНАЧЕНИЯ
=========================================================================

Добавляем блок environment и стадию, которая печатает переменные.
Полный текст версии 3:

pipeline {
    agent any

    environment {
        PROJECT_NAME = 'site'
        SITE_DIR     = 'build/www'
    }

    stages {
        stage('Привет') {
            steps {
                echo "Проект: ${env.PROJECT_NAME}"
            }
        }

        stage('Команды') {
            steps {
                sh '''
                    set -eu
                    mkdir -p build
                    date > build/build-stamp.txt
                '''
            }
        }

        stage('Переменные') {
            steps {
                echo "Сборка номер: ${env.BUILD_NUMBER}"
                echo "Проект: ${env.PROJECT_NAME}, каталог: ${SITE_DIR}"
                echo "Агент: ${env.NODE_NAME}"
                echo "Рабочий каталог: ${env.WORKSPACE}"
                sh 'echo "Внутри shell видно то же: ${BUILD_NUMBER}"'
            }
        }
    }
}

environment { } — переменные, доступные всем стадиям: объявляются один раз.
В Groovy к ним обращаются как env.ИМЯ, в скриптах shell они видны как
обычные переменные окружения — последняя стадия это показывает.

ВСТРОЕННЫЕ ПЕРЕМЕННЫЕ выставляет сам Jenkins, объявлять их не нужно:

  BUILD_NUMBER — номер сборки;
  BUILD_URL — адрес страницы сборки в портале;
  JOB_NAME — имя задания, включая каталоги, если они есть;
  WORKSPACE — путь рабочего каталога сборки на агенте;
  NODE_NAME — имя агента, на котором выполняется сборка;
  GIT_COMMIT — хеш коммита: заполняется, когда репозиторий забирает
    плагин Git (в конвейере из репозитория это настоящая ревизия).

ПОЧЕМУ В ENVIRONMENT НЕ МЕСТО СЕКРЕТАМ: значения из этого блока Jenkins
печатает в журнал сборки в открытом виде. Пароли и ключи подключают через
credentials — это практика 11, а не environment.

УТОЧНЕНО про GIT_COMMIT: если репозиториев несколько, в переменной
окажется последний полученный; если код забирается командой git clone
внутри sh, она будет пустой. Надёжнее брать ревизию у самой рабочей копии:
git rev-parse --short HEAD — так в файл сборки попадает то, что реально
лежит в рабочем каталоге.

ОБРАТИТЕ ВНИМАНИЕ на путь к рабочему каталогу: имя его последней части
совпадает с именем задания, только пока имя простое. На другом агенте
меняется вся первая часть пути, поэтому в скриптах используют
относительные пути и ${WORKSPACE}.

ЧТО ДОБАВИЛОСЬ В ЭТОЙ ВЕРСИИ: блок environment с PROJECT_NAME и SITE_DIR,
стадия «Переменные» и встроенные переменные Jenkins.

=========================================================================
4. СТАДИИ BUILD → TEST → DEPLOY
=========================================================================

Делаем конвейер рабочим: три стадии — сборка, проверка результата, выкат.
Полный текст версии 4:

pipeline {
    agent any

    environment {
        PROJECT_NAME  = 'site'
        SITE_DIR      = 'build/www'
        DEPLOY_DIR    = 'deploy'
        EXPECTED_TEXT = 'Hello from DevOps Engineer'
    }

    stages {
        stage('1. Сборка') {
            steps {
                sh '''
                    set -eu
                    rm -rf "${SITE_DIR}"
                    mkdir -p "${SITE_DIR}"
                    echo "<h1>${EXPECTED_TEXT}</h1>" >"${SITE_DIR}/index.html"
                    echo "<p>${BUILD_NUMBER}</p>" >>"${SITE_DIR}/index.html"
                '''
            }
        }

        stage('2. Проверка') {
            steps {
                sh '''
                    set -eu
                    page="${SITE_DIR}/index.html"
                    test -f "${page}"
                    grep -q "${EXPECTED_TEXT}" "${page}"
                    if grep -q '__BUILD_NUMBER__' "${page}"; then
                        echo "ошибка: в странице остался маркер подстановки"
                        exit 1
                    fi
                    echo "проверка страницы пройдена"
                '''
            }
        }

        stage('3. Выкат') {
            steps {
                sh '''
                    set -eu
                    rm -rf "${DEPLOY_DIR}"
                    cp -a "${SITE_DIR}" "${DEPLOY_DIR}"
                    find "${DEPLOY_DIR}" -type f
                '''
            }
        }
    }
}

ЗАЧЕМ КАЖДАЯ КОМАНДА. Стадия «Сборка» создаёт каталог build/www
и страницу index.html с ожидаемым текстом и номером сборки. Стадия
«Проверка» отвечает на три вопроса: файл существует (test -f); текст
в файле есть (grep -q); маркер подстановки __BUILD_NUMBER__ не остался —
если остался, значит, подстановка не сработала, и на сайт уехала бы
готовая ошибка. Стадия «Выкат» копирует собранное в каталог deploy.

ЗАЧЕМ ПРОВЕРЯТЬ ДО ВЫКАТА: проверка занимает секунды, а откат — время
и нервы. Дешёвая проверка всегда стоит перед дорогим действием: то, что
можно выяснить на агенте, не надо выяснять на серверах.

ЗАЧЕМ ОТДЕЛЬНЫЕ СТАДИИ: упавшая стадия видна в журнале по имени, а в
портале полоса стадий показывает, где остановилось. Откройте задание
Pipeline_job_1 и посмотрите таблицу под списком сборок: по горизонтали
сборки, по вертикали стадии. Зелёная клетка — стадия прошла, красная —
упала, серая — не выполнялась, клетка с полоской внутри — выполняется
сейчас. Одна стадия «собрать и выкатить» такой картины не даёт.

УТОЧНЕНО: выкат в этой версии учебный — копирование в каталог deploy
внутри рабочего каталога агента. Настоящий выкат на node1 и node2 через
nginx разбирается в практике 11: в базовой части — простой, без релизов
и симлинка, а релизы, симлинк и откат — в приложении к ней. Наши стадии —
заготовка той же формы.

ЧТО ДОБАВИЛОСЬ В ЭТОЙ ВЕРСИИ: три стадии, проверка результата
и каталог выката.

=========================================================================
5. OPTIONS: ТАЙМАУТ, ИСТОРИЯ, ЗАПРЕТ ПАРАЛЛЕЛЬНЫХ СБОРОК
=========================================================================

Добавляем блок options сразу после agent. Полный текст версии 5:

pipeline {
    agent any

    options {
        timestamps()
        timeout(time: 15, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '10'))
        disableConcurrentBuilds()
    }

    environment {
        PROJECT_NAME  = 'site'
        SITE_DIR      = 'build/www'
        DEPLOY_DIR    = 'deploy'
        EXPECTED_TEXT = 'Hello from DevOps Engineer'
    }

    stages {
        stage('1. Сборка') {
            steps {
                sh '''
                    set -eu
                    rm -rf "${SITE_DIR}"
                    mkdir -p "${SITE_DIR}"
                    echo "<h1>${EXPECTED_TEXT}</h1>" >"${SITE_DIR}/index.html"
                    echo "<p>${BUILD_NUMBER}</p>" >>"${SITE_DIR}/index.html"
                '''
            }
        }

        stage('2. Проверка') {
            steps {
                sh '''
                    set -eu
                    page="${SITE_DIR}/index.html"
                    test -f "${page}"
                    grep -q "${EXPECTED_TEXT}" "${page}"
                    if grep -q '__BUILD_NUMBER__' "${page}"; then
                        echo "ошибка: в странице остался маркер подстановки"
                        exit 1
                    fi
                    echo "проверка страницы пройдена"
                '''
            }
        }

        stage('3. Выкат') {
            steps {
                sh '''
                    set -eu
                    rm -rf "${DEPLOY_DIR}"
                    cp -a "${SITE_DIR}" "${DEPLOY_DIR}"
                '''
            }
        }
    }
}

ЧТО ДЕЛАЕТ КАЖДАЯ СТРОКА

  timestamps() — печатать время у каждой строки журнала: по журналу сразу
  видно, сколько шла каждая стадия (плагин timestamper);
  timeout(time: 15, unit: 'MINUTES') — если конвейер зависнет, он будет
  остановлен через пятнадцать минут. Единицы: SECONDS, MINUTES, HOURS;
  buildDiscarder(logRotator(numToKeepStr: '10')) — хранить историю десяти
  последних сборок: без этого каталог сборок на контроллере растёт
  бесконечно, и однажды на нём кончается место;
  disableConcurrentBuilds() — запретить две сборки одного задания
  одновременно. Это защита не от жадности: две сборки работают в одном
  рабочем каталоге и пишут в одни файлы.

ЧТО ДОБАВИЛОСЬ В ЭТОЙ ВЕРСИИ: блок options с таймаутом, ограничением
истории и запретом параллельных сборок.

=========================================================================
6. POST: ЧТО ДЕЛАТЬ ПОСЛЕ СБОРКИ
=========================================================================

Последний штрих — блок post: он выполняется после завершения конвейера.
Полный текст версии 6, итоговый конвейер практики:

pipeline {
    agent any

    options {
        timestamps()
        timeout(time: 15, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '10'))
        disableConcurrentBuilds()
    }

    environment {
        PROJECT_NAME  = 'site'
        SITE_DIR      = 'build/www'
        DEPLOY_DIR    = 'deploy'
        EXPECTED_TEXT = 'Hello from DevOps Engineer'
    }

    stages {
        stage('1. Сборка') {
            steps {
                sh '''
                    set -eu
                    rm -rf "${SITE_DIR}"
                    mkdir -p "${SITE_DIR}"
                    echo "<h1>${EXPECTED_TEXT}</h1>" >"${SITE_DIR}/index.html"
                    echo "<p>${BUILD_NUMBER}</p>" >>"${SITE_DIR}/index.html"
                    cp "${SITE_DIR}/index.html" build-info.html
                '''
            }
        }

        stage('2. Проверка') {
            steps {
                sh '''
                    set -eu
                    page="${SITE_DIR}/index.html"
                    test -f "${page}"
                    grep -q "${EXPECTED_TEXT}" "${page}"
                    if grep -q '__BUILD_NUMBER__' "${page}"; then
                        echo "ошибка: в странице остался маркер подстановки"
                        exit 1
                    fi
                    echo "проверка страницы пройдена"
                '''
            }
        }

        stage('3. Выкат') {
            steps {
                sh '''
                    set -eu
                    rm -rf "${DEPLOY_DIR}"
                    cp -a "${SITE_DIR}" "${DEPLOY_DIR}"
                '''
            }
        }
    }

    post {
        success {
            echo "Сборка ${env.BUILD_NUMBER} завершилась успешно"
        }
        unstable {
            echo "Сборка ${env.BUILD_NUMBER} нестабильна"
        }
        failure {
            echo "Сборка ${env.BUILD_NUMBER} провалилась, смотрите лог выше"
        }
        cleanup {
            sh 'rm -rf build-info.html'
        }
        always {
            archiveArtifacts artifacts: 'build/**', allowEmptyArchive: true
        }
    }
}

УСЛОВИЯ БЛОКА POST

  success    сборка завершилась успешно;
  unstable   сборка завершилась, но результат помечен нестабильным
             (чаще всего — упавшие тесты);
  failure    сборка провалилась: стадия вернула ненулевой код, упало
             исключение, провалилась проверка;
  cleanup    выполняется самым последним — здесь место уборке;
  always     выполняется всегда, чем бы сборка ни закончилась.

Есть и другие условия: changed (результат отличается от предыдущей
сборки), fixed (прошлая упала, эта успешна), regression, aborted.

ВАЖНО И НЕОЧЕВИДНО: ЭТО НЕ ВЕТКИ IF/ELSE, А НЕЗАВИСИМЫЕ ДЕЙСТВИЯ,
И ВЫПОЛНЯЮТСЯ ОНИ В ФИКСИРОВАННОМ ПОРЯДКЕ:

always → changed → fixed → regression → aborted → failure →
success → unstable → cleanup

ОБРАТИТЕ ВНИМАНИЕ: always идёт РАНЬШЕ failure, а cleanup — последним.
Из этого следует практическое правило, которое ломает первый конвейер
с откатом: если уборку — удаление временных файлов, закрытие соединений —
повесить на always, она выполнится ДО failure, и к моменту, когда
конвейер попробует откатить выкат, нужного каталога уже не будет.
Для уборки есть cleanup: он выполняется после всех остальных условий.

archiveArtifacts в always публикует файлы сборки в портал, поэтому
собранное видно и после того, как рабочий каталог перезапишет следующая
сборка. allowEmptyArchive: true означает, что отсутствие файлов
не превратит успешную сборку в проваленную.

ЧТО ДОБАВИЛОСЬ В ЭТОЙ ВЕРСИИ: блок post с условиями, уборкой через
cleanup и публикацией артефактов. Это итоговый конвейер практики.

7. ТО ЖЕ САМОЕ В РЕПОЗИТОРИИ: JENKINSFILE
=========================================================================

Конвейер, который лежит в настройках задания, невозможно отревьюить
и унести вместе с кодом. Переносим его в репозиторий: сохраняем текст
версии 6 в файл Jenkinsfile в корне репозитория и отправляем в main.

cd ~/site
vim Jenkinsfile
git add Jenkinsfile
git commit -m "Конвейер вместо набора шагов"
git push origin main

Создаём второе задание: New Item → имя site_pipeline → Pipeline → OK,
и в разделе Pipeline заполняем поля:

  Definition:        Pipeline script from SCM
  SCM:               Git
  Repository URL:    ssh://git@10.0.2.5:2222/engineer/site.git
  Credentials:       gitea-reader
  Branches to build: */main
  Script Path:       Jenkinsfile

Save → Build Now. Задание больше не содержит текста конвейера: оно лишь
указывает, где этот текст взять.

ЧЕТЫРЕ ПОЛЯ, КОТОРЫЕ ЗДЕСЬ ВАЖНЫ: Repository URL — адрес по ssh, а не
по http: ключом из credentials gitea-reader Jenkins подключается к Gitea
без пароля (порт 2222 — это ssh-порт Gitea); Branches to build — шаблон
*/main, то есть ветка main; Script Path — Jenkinsfile, и именно это поле
решает, какой файл считается описанием сборки (файл ci/Jenkinsfile
указывался бы здесь целиком).

ЗАЧЕМ ТАК ЛУЧШЕ: описание сборки становится частью кода. Его видно
в репозитории, его правка проходит ревью, его можно откатить вместе
с коммитом, и при переезде Jenkins на другую машину настройки задания
восстанавливать не нужно.

Первая сборка задания site_pipeline: в журнале будет строка вида
Obtained Jenkinsfile from git ssh://git@10.0.2.5:2222/engineer/site.git —
это ответ на вопрос, какой файл и какая ревизия выполняются. Ещё полезен
Replay на странице сборки: там виден текст конвейера целиком.

УТОЧНЕНО: в задании типа Pipeline script переменная scm не определена —
поэтому checkout scm работает только в задании, которое собирается
из репозитория. Та же структура конвейера, что мы собрали, лежит готовым
файлом: files/pipelines/Jenkinsfile.simple — можно сверить свой текст
с ним, если что-то не запускается.

=========================================================================
8. ПАРАЛЛЕЛЬНЫЕ СТАДИИ И АГЕНТЫ
=========================================================================

До сих пор конвейер выполнялся на любом агенте. В настоящей работе место
выполнения важно: сборка сайта идёт на серверах с меткой web (это node1
с метками web node1 и node2 с метками web node2 docker — практика 4).

АГЕНТ ДЛЯ ВСЕГО КОНВЕЙЕРА — заменяем первую строку:

agent { label 'web' }

МЕТКА У ОТДЕЛЬНОЙ СТАДИИ — когда стадии нужны разные машины:

stage('3. Выкат') {
    agent { label 'web' }
    steps {
        sh 'echo "выполняется на ${NODE_NAME}"'
    }
}

ВАЖНО: если агент указан и у конвейера, и у стадии, стадия получит своего
агента, а её рабочий каталог — свой. Файлы, собранные раньше, на новом
агенте не видны, и это главная ловушка смены агента. Есть и цена:
каждая смена агента — ожидание свободного исполнителя в очереди.

ПАРАЛЛЕЛЬНЫЕ СТАДИИ. Две независимые работы можно выполнять одновременно.
Фрагмент вместо стадии «3. Выкат»:

stage('3. Выкат') {
    parallel {
        stage('node1') {
            steps { sh 'echo "выкат на node1"' }
        }
        stage('node2') {
            steps { sh 'echo "выкат на node2"' }
        }
    }
}

Обе вложенные стадии стартуют сразу и видны в полосе как две колонки
внутри родительской стадии. ОБРАТИТЕ ВНИМАНИЕ: если одна ветка упала,
сборка считается проваленной, а остальные ветки прерываются — Jenkins
не продолжает работу, которая уже никому не нужна.

ДОБАВЛЕНО: остановку веток можно сделать немедленной — записью
failFast true внутри стадии с parallel или parallelsAlwaysFailFast()
в блоке options всего конвейера.

ПЕРЕНОС ФАЙЛОВ НА ДРУГОЙ АГЕНТ. Если стадия выполняется на другом
агенте, наработанное нужно передать. Для этого есть stash и unstash:

stage('1. Сборка') {
    steps {
        sh 'mkdir -p build && echo "содержимое" > build/artifact.txt'
        stash name: 'artifact', includes: 'build/**'
    }
}

stage('2. Проверка') {
    agent { label 'node2' }
    steps {
        unstash 'artifact'
        sh 'cat build/artifact.txt'
    }
}

stash упаковывает файлы и отправляет их на контроллер Jenkins, а unstash
распаковывает в рабочем каталоге текущей стадии. Работает это только
внутри одной сборки, права на файлы после распаковки могут отличаться
от исходных, а большие каталоги (кэши, .git, node_modules) в stash
не кладут: они идут через контроллер и занимают его диск.

=========================================================================
9. WHEN И INPUT: УСЛОВИЯ И РУЧНОЕ ПОДТВЕРЖДЕНИЕ
=========================================================================

WHEN пропускает стадию, если условие не выполнено. Пропущенная стадия
видна в полосе серой клеткой, и это нормальный результат, а не ошибка.

Условие по ветке — выкатывать только из main:

stage('3. Выкат') {
    when { branch 'main' }
    steps {
        sh 'echo "выкат"'
    }
}

Условие по параметру сборки (параметры разбирались в практике 8):

parameters {
    booleanParam(name: 'DEPLOY', defaultValue: false,
                 description: 'Выкатывать сайт')
}

stage('3. Выкат') {
    when {
        expression { return params.DEPLOY }
    }
    steps {
        sh 'echo "выкат выполняется: DEPLOY = ${DEPLOY}"'
    }
}

Есть и другие условия: not { branch 'main' } — отрицание, внутрь можно
положить любое другое условие; environment name: 'STAGE', value: 'prod';
changeset 'files/www/**' — изменились указанные файлы.

Ручное подтверждение перед опасным действием — директива input:

stage('3. Выкат') {
    options {
        timeout(time: 30, unit: 'MINUTES')
    }
    input {
        message 'Выкатывать сайт?'
        ok 'Выкатываем'
        submitter 'engineer'
    }
    steps {
        sh 'echo "подтверждение получено, выкатываем"'
    }
}

Сборка останавливается и ждёт, пока человек нажмёт кнопку на странице
сборки. ВАЖНО: БЕЗ TIMEOUT РЯДОМ С INPUT СБОРКА ЖДЁТ ЧЕЛОВЕКА БЕСКОНЕЧНО
и занимает исполнитель — поэтому блок options { timeout(...) } стоит прямо
в этой же стадии. Это самая частая причина «конвейер висит уже сутки»:
выкат запустили вечером, а подтвердить забыли. Прервать такую сборку можно
кнопкой Abort на её странице.

КТО МОЖЕТ ПОДТВЕРДИТЬ: строка submitter 'engineer' перечисляет
пользователей или группы через запятую. Полагаться на неё как на защиту
нельзя: в некоторых способах запуска (например, через CLI) она не
проверяется — тогда подтвердить сможет любой, у кого есть право запускать
задание. Настоящая защита — права Jenkins, об этом практика 2.

ЧТО ДОБАВИЛОСЬ В ЭТОЙ ВЕРСИИ: условия when для стадии выката и ручное
подтверждение input с обязательным таймаутом.

=========================================================================
11. ОТЛАДКА И ХОРОШИЕ ПРИВЫЧКИ
=========================================================================

КАК ЧИТАТЬ ЖУРНАЛ. Ищите в нём три вещи: строки [Pipeline] stage и имя
стадии — где конвейер находился; вывод шагов (в sh он начинается
со строки вида + команда, это работа флага x); сообщение об ошибке
с номером строки Jenkinsfile. На странице сборки слева есть Pipeline Steps:
пошаговый разбор с временем каждого шага — когда непонятно, что вообще
делал конвейер, читать нужно его.

REPLAY: ПРАВКА БЕЗ КОММИТА. Ссылка Replay на странице сборки открывает
текст конвейера, который выполнялся, и позволяет поправить его и запустить
сборку заново. Это удобно для отладки, но ПОМНИТЕ: правка в Replay
не попадает в репозиторий. Следующая сборка запустится снова с версией
из репозитория, и ваша правка исчезнет. Право на Replay — отдельное право
Jenkins (практика 2).

DECLARATIVE DIRECTIVE GENERATOR. В разделе Pipeline Syntax задания (ссылка
рядом с полем Pipeline script) есть генератор директив: выбираете
директиву и параметры, он показывает правильный текст. Там же Snippet
Generator — он строит вызовы шагов с аргументами. ЗАЧЕМ: не помнить
наизусть имена параметров; ошибка в имени стоит целой сборки.

ГДЕ ИСКАТЬ ПРИЧИНУ В ТЕКСТЕ. Jenkins сообщает номер строки
(«WorkflowScript: 42: ...») по тому файлу, который разбирался, считая
комментарии и пустые строки. ОБРАТИТЕ ВНИМАНИЕ: при незакрытой скобке
или кавычке настоящая причина обычно на строку-две ВЫШЕ указанной.
Ошибку в блоке sh проверяйте отдельно: скопируйте скрипт в файл
и выполните bash -n.

ХОРОШИЕ ПРИВЫЧКИ, которые видно на нашем конвейере:

  * маленькие стадии с понятными именами: по полосе стадий должно быть
    ясно, что произошло, без чтения журнала;
  * проверка — перед выкатом: дешёвая проверка раньше дорогого действия;
  * явный timeout и запрет параллельных сборок;
  * уборка в cleanup, а не в always (раздел 6);
  * артефакты публикуются, а не остаются в рабочем каталоге;
  * никаких секретов в описании конвейера;
  * длинные shell-скрипты живут отдельными файлами в репозитории,
    а не внутри Jenkinsfile: их можно проверить командой bash -n
    и отревьюить как код. В практике 11 конвейер вызывает скрипты выката
    и проверки из репозитория именно поэтому.

=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: «unexpected token» ИЛИ «Expecting '}' but found ...»

Ошибка разбора Groovy: не закрыта или лишняя скобка либо не совпали
кавычки. Обычно причина на строку-две ВЫШЕ указанной. Посчитайте фигурные
скобки — в правильном файле их количество совпадает.

ПРОБЛЕМА: «No such DSL method 'sh' found among steps»

Команда вызвана там, где шагов быть не может: в блоке environment, прямо
в post без условия или между стадиями. Команды выполняются только внутри
steps; свой Groovy-код вызывается из блока script { }.

ПРОБЛЕМА: ЧАСТЬ ОШИБОК ПОЯВЛЯЕТСЯ ИЗ-ЗА КАВЫЧЕК

Фрагмент echo 'Building...." — открыта одинарная кавычка, закрыта
двойная: Groovy считает строку незакрытой и сообщает об ошибке в конце
файла, а не в этой строке. Проверяйте именно ту строку, где кавычки
открылись.

ПРОБЛЕМА: checkout ВЕРНУЛ ПУСТОЙ РАБОЧИЙ КАТАЛОГ

Неверная ветка в Branches to build (записи */main и main — разные шаблоны,
а в старых репозиториях главная ветка называется master); не те
credentials — ключ без доступа к репозиторию; агент не может дойти
до Gitea: проверьте на агенте ssh -p 2222 git@10.0.2.5.

ПРОБЛЕМА: «credentials not found»

Идентификатор указан с опечаткой: gitea-reader — не gitea_reader и не
Gitea-Reader, Jenkins сравнивает строку целиком. Вторая причина — секрет
создан в другом месте (в папке, а не глобально) или имеет неподходящий
тип.

ПРОБЛЕМА: СБОРКА ВИСИТ И НИЧЕГО НЕ ДЕЛАЕТ

Стадия input ждёт подтверждения, а timeout рядом не поставлен. Прервите
сборку кнопкой Abort и добавьте в стадию блок options с timeout.

ПРОБЛЕМА: «Waiting for next available executor» ИЛИ «no node with label»

Первое: все исполнители агента заняты — сборок больше, чем исполнителей.
Посмотрите Manage Jenkins → Nodes и очередь сборок. Второе: метка
не совпадает ни с одним агентом — сверьте метки по практике 4, включая
регистр. Отдельный случай — агент offline: причина в соединении.

ПРОБЛЕМА: СБОРКА «УСПЕШНА», ХОТЯ СТАДИЯ БЫЛА КРАСНОЙ

Так бывает в двух случаях: стадия пропущена по условию when (серая
клетка — это не ошибка), либо проверка выполнялась с returnStatus: true
или returnStdout: true, и код возврата никто не проверил. Второе лечится
явной проверкой: if (code != 0) { error 'проверка не пройдена' }.
