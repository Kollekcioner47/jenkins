Практика 11. Секреты и выкат сайта на node1 и node2.

ВЫКАТ — это доставка результата сборки туда, где его видят пользователи.
До сих пор всё оставалось внутри Jenkins: сборки печатали текст,
складывали артефакты, запускались по триггеру. Здесь конвейер впервые
меняет состояние чужих машин: копирует страницу на node1 и node2, и она
появляется в браузере по адресам http://10.0.2.13/ и http://10.0.2.14/.

ПОЧЕМУ НЕЛЬЗЯ ПРОСТО СКОПИРОВАТЬ РУКАМИ. Через неделю никто не вспомнит,
из какого коммита собрана страница на сервере, а «я поправил прямо
на сервере» — самая частая причина, по которой следующий выкат затирает
чужую правку.

ПЛАН ПРАКТИКИ. Часть 1 — минимальный рабочий выкат: собираем страницу,
копируем её по ssh через rsync на оба сервера, проверяем ответ curl-ом
и открываем сайт в браузере. Часть 2 — приложение: релизы и симлинк,
откат, проверка скриптом, параллельный и канареечный выкат, полный
конвейер. Приложение не обязательное: к нему возвращаются позже.

Файлы курса, которые понадобятся:

  files/scripts/prepare_node.sh   подготовка node1 и node2 (часть 1)
  files/www/index.html            страница с маркерами подстановки
  files/scripts/deploy_site.sh    релизы и откат (приложение, Б)
  files/scripts/smoke_test.sh     сквозная проверка (приложение, Г)
  files/pipelines/Jenkinsfile.build-test-deploy   полный конвейер (Д)

=========================================================================
1. ЧТО НУЖНО ДЛЯ ВЫКАТА
=========================================================================

Для выката нужны три вещи, и все они у нас уже есть.

КЛЮЧ, КОТОРЫМ JENKINS ВОЙДЁТ НА СЕРВЕР. Пользователь jenkins создан
на node1 и node2, публичная часть ключа лежит в его authorized_keys —
это мы сделали в практике 4, когда подключали агентов. В самом Jenkins
ключ хранится как credentials с идентификатором node-ssh.

КАТАЛОГ НА СЕРВЕРЕ, КОТОРЫЙ ОТДАЁТ NGINX. Сайт живёт в /var/www/site:
каталог принадлежит пользователю jenkins, а nginx настроен отдавать
/var/www/site/current. Значит, выкат — это копирование файлов туда,
куда указывает current.

КОНВЕЙЕР. Он собирает страницу из репозитория, подставляет номер сборки,
копирует результат на серверы и проверяет ответ по HTTP. Всё это описано
кодом, поэтому выкат повторяем: одни и те же действия на обеих машинах,
а что произошло — видно в журнале сборки.

=========================================================================
2. ГОТОВИМ СЕРВЕРЫ
=========================================================================

Серверы выката — node1 (10.0.2.13) и node2 (10.0.2.14). На обоих нужны
nginx, каталог для сайта и пользователь, под которым идёт выкат. Всё это
делает скрипт files/scripts/prepare_node.sh: копируем его на каждую
машину и запускаем от пользователя engineer. Аргумент (node1 или node2)
скрипт подставляет в имя сервера и в ответ служебной страницы.

    scp files/scripts/prepare_node.sh engineer@10.0.2.13:/tmp/
    ssh engineer@10.0.2.13 'sudo bash /tmp/prepare_node.sh node1'

    scp files/scripts/prepare_node.sh engineer@10.0.2.14:/tmp/
    ssh engineer@10.0.2.14 'sudo bash /tmp/prepare_node.sh node2'

ЧТО ДЕЛАЕТ СКРИПТ:

  * ставит пакеты: nginx, rsync, curl, git и Java (машина — агент);
  * создаёт пользователя jenkins без пароля и каталог /var/www/site
    с подкаталогами releases и shared — всё принадлежит jenkins;
  * настраивает nginx (server на порту 80, root /var/www/site/current,
    страница /health) и разрешает jenkins без пароля ровно одну команду —
    systemctl reload nginx.

ПРО RELEASES И CURRENT В ЧАСТИ 1 ДУМАТЬ НЕ НУЖНО: это заготовка
для приложения (раздел Б), а сейчас мы просто пишем файлы туда, куда
указывает current, — на релиз-заглушку, созданный скриптом.

ПРОВЕРЯЕМ на каждом сервере:

    curl http://localhost/health

Ожидаем «node1 ok» на node1 и «node2 ok» на node2. ВАЖНО: проверяем ответ
сервера, а не файлы на диске — файл может лежать, а nginx отдавать другой
каталог или отвечать 403.

=========================================================================
3. СЕКРЕТЫ: CREDENTIALS И SSHAGENT
=========================================================================

Чтобы скопировать файлы на сервер, Jenkins должен войти туда по ssh.
Значит, ему нужен приватный ключ — а это секрет.

ПОЧЕМУ ПЛОХО НАПИСАТЬ КЛЮЧ ПРЯМО В ШАГЕ СБОРКИ. Значение увидят все,
у кого есть доступ к заданию; оно останется в журналах старых сборок;
оно уедет вместе с выгрузкой конфигурации; отозвать его можно только
правкой задания.

ЧТО ДЕЛАЮТ CREDENTIALS. Секрет хранится в Jenkins, а задание ссылается
на него по идентификатору — имени, которое видно в списке. Значение
в интерфейсе не показывается никогда: только тип, идентификатор
и описание. Наш ключ лежит под идентификатором node-ssh. Проверить,
что он на месте: Manage Jenkins → Credentials → System → Global
credentials (unrestricted); в списке должна быть запись node-ssh
(SSH Username with private key, пользователь jenkins).

ЧТО ТАКОЕ SSHAGENT. Шаг sshagent подставляет ключ в ssh-агент на время
своего блока:

    sshagent(credentials: ['node-ssh']) {
        sh 'ssh jenkins@10.0.2.13 hostname'
    }

ЗАЧЕМ ИМЕННО АГЕНТ, А НЕ ПЕРЕМЕННАЯ С КЛЮЧОМ: текст ключа не попадает
ни в переменные окружения, ни в файл, ни в журнал — конвейер его вообще
не знает. Ключ доступен только процессам внутри блока.

ЧТО СТОИТ ЗНАТЬ ПРО ЖУРНАЛ. Значения credentials в журнале заменяются
на ****, но маскируется ТОЧНОЕ значение: напечатанный по частям,
преобразованный (например, в base64) или записанный в файл ключ
маскирование не спасёт. Отсюда правило: секрет не печатать, не писать
в файл и не передавать параметром сборки.

=========================================================================
4. КОНВЕЙЕР ВЫКАТА
=========================================================================

СОЗДАЁМ ЗАДАНИЕ:

    New Item → имя SiteDeploySimple → Pipeline → OK
    Pipeline → Definition: Pipeline script

Текст конвейера вставляем прямо в задание, в поле Script: отдельных
файлов в репозитории не заводим — все конвейеры курса лежат
в files/pipelines и разбираются в приложении.

Вот весь конвейер:

pipeline {
    agent { label 'web' }

    options {
        timestamps()
        timeout(time: 15, unit: 'MINUTES')
        buildDiscarder(logRotator(numToKeepStr: '10'))
    }

    parameters {
        string(name: 'WEB_NODES', defaultValue: '10.0.2.13 10.0.2.14',
               description: 'Серверы, куда выкатывать сайт')
    }

    stages {
        stage('Забрать код') {
            steps {
                git url: 'ssh://git@10.0.2.5:2222/engineer/site.git',
                    credentialsId: 'gitea-reader',
                    branch: 'main'
            }
        }

        stage('Собрать страницу') {
            steps {
                sh '''
                    set -eu
                    rm -rf build/site
                    mkdir -p build/site
                    cp files/www/index.html build/site/index.html
                    cd build/site
                    commit=$(git rev-parse --short HEAD)
                    sed -i "s/__BUILD_NUMBER__/$BUILD_NUMBER/g" index.html
                    sed -i "s/__GIT_COMMIT__/$commit/g" index.html
                    head -n 20 index.html
                '''
            }
        }

        stage('Выкатить на серверы') {
            steps {
                sshagent(credentials: ['node-ssh']) {
                    sh '''
                        set -eu
                        dest=/var/www/site/current/
                        for host in ${WEB_NODES}; do
                            rsync -a --delete \
                                -e "ssh -o StrictHostKeyChecking=accept-new" \
                                build/site/ jenkins@${host}:${dest}
                            echo "${host}: файлы скопированы"
                        done
                    '''
                }
            }
        }

        stage('Проверить') {
            steps {
                sh '''
                    set -eu
                    for host in ${WEB_NODES}; do
                        curl -fsS "http://${host}/" \
                            | grep -q "Hello from DevOps Engineer"
                        curl -fsS "http://${host}/" \
                            | grep -q ">${BUILD_NUMBER}<"
                        echo "${host}: сайт отвечает, сборка на месте"
                    done
                '''
            }
        }
    }
}

РАЗБИРАЕМ ПО СТАДИЯМ.

agent { label 'web' } — сборка идёт на агенте с меткой web, то есть
на node1 или node2: на этих машинах есть git и rsync, их поставил
prepare_node.sh. Где именно шла сборка, для результата безразлично: файлы
копируются по ssh на оба сервера. options — привычный набор из практики
10: отметки времени, ограничение на 15 минут, хранение десяти последних
сборок. parameters — один параметр со списком серверов: можно выкатывать
на один сервер, поменяв значение, и не править конвейер.

СТАДИЯ «Забрать код» обновляет рабочую копию из репозитория: шаг git
получает адрес, credentials gitea-reader и ветку main. Без него в рабочем
каталоге агента не было бы каталога files, откуда берётся страница.

СТАДИЯ «Собрать страницу». Каталог build/site создаётся заново (rm -rf
и mkdir), чтобы в него не попали файлы от прошлой сборки. Затем страница
копируется из репозитория, и в ней заменяются маркеры: __BUILD_NUMBER__
— номером сборки, __GIT_COMMIT__ — короткой ревизией. Эти маркеры стоят
в файле files/www/index.html вместо значений; без подстановки по адресу
сайта невозможно понять, какая сборка там лежит. Последняя строка печатает
начало страницы в журнал: видно, что подстановка сработала, ещё до выката.

СТАДИЯ «Выкатить на серверы». Весь блок идёт внутри sshagent, поэтому
rsync и ssh внутри цикла пользуются подставленным ключом.

ПОЧЕМУ RSYNC, А НЕ SCP: rsync копирует только изменившееся, сохраняет
права и умеет --delete — удалять на сервере то, чего нет в источнике.
Копируем в /var/www/site/current/, потому что nginx отдаёт этот каталог
(в приложении, раздел Б, так делать нельзя: там файлы кладут в отдельный
каталог релиза, а симлинк переключают).

ЗАЧЕМ -o StrictHostKeyChecking=accept-new. У jenkins нет записи об этих
серверах в known_hosts, и без такой опции ssh отказался бы соединяться
(«Host key verification failed»). accept-new означает: отпечаток
неизвестного сервера добавить, а изменившийся ключ известного
не принимать. ЭТО КОМПРОМИСС ЛАБОРАТОРИИ: в рабочей среде known_hosts
заполняют заранее, иначе подменённый сервер будет принят за свой.

СТАДИЯ «Проверить» проверяет то, что отдаёт веб-сервер, а не файлы
на диске: страница отвечает и содержит ожидаемый текст, и на ней есть
номер именно этой сборки в виде «>N<». Ключ -f у curl считает ошибкой
коды 4xx и 5xx, поэтому 403 или 404 не пройдут незамеченными.

ЧЕГО В ЭТОЙ ВЕРСИИ НЕТ И ПОЧЕМУ. Нет релизов, симлинков, отката
и отдельных скриптов выката: для сайта из одной страницы это лишнее,
а вернуться к прежней версии можно, запустив конвейер на старом коммите.

=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: «Permission denied (publickey)» в блоке sshagent

Ключ не подошёл. Проверяем: тот ли credentials (нужен node-ssh, а не
gitea-reader), тот ли пользователь (jenkins@) и лежит ли публичная часть
ключа в /home/jenkins/.ssh/authorized_keys на целевой машине.

    sudo journalctl -u ssh -n 50

ПРОБЛЕМА: «Host key verification failed»

У пользователя jenkins нет записи об этом сервере в known_hosts. Лечится
опцией StrictHostKeyChecking=accept-new, которую мы передаём rsync через
-e: проверьте, что опция стоит в тех же кавычках, что и сама команда ssh.

ПРОБЛЕМА: «rsync: command not found»

На сервере не установлен rsync — сообщение приходит с удалённой машины,
хотя выглядит как локальная ошибка. Ставит его prepare_node.sh, а вручную:

    ssh engineer@10.0.2.13 'sudo apt install -y rsync'

ПРОБЛЕМА: «sudo: a password is required»

В части 1 ни одна команда не требует sudo: выкат копирует файлы
в каталог, который принадлежит jenkins, а перезапускать nginx не нужно.
Если ошибка появилась, значит, в конвейер попала команда с sudo —
уберите её.

ПРОБЛЕМА: сайт отдаёт старую страницу

Кэш браузера — откройте в приватном окне или добавьте к адресу параметр
http://10.0.2.13/?n=2. Не тот сервер — сравните номер на обоих адресах
с номером последней сборки. Наконец, nginx отдаёт другой каталог:
проверьте readlink -f /var/www/site/current и строку root (sudo nginx -T).

ПРОБЛЕМА: сайт отвечает 403 или 404

403 — nginx не может прочитать файл: каталог или файл не принадлежит
jenkins либо у них слишком узкие права. nginx работает под www-data
и должен иметь право читать файлы (0644) и проходить по каталогам (0755):

    ls -ld /var/www/site /var/www/site/current
    ls -l /var/www/site/current/

404 — файла нет там, где его ищет nginx: rsync скопировал файлы не туда
или в каталоге нет index.html.

ПРОБЛЕМА: на странице видно __BUILD_NUMBER__

Не сработала подстановка в первой стадии. Если в напечатанном начале
страницы маркер на месте, значит sed не выполнился или не нашёл файл:
проверьте, что страница сначала копируется в каталог сборки.

ПРОБЛЕМА: Jenkins не может склонировать репозиторий

Проверяем адрес репозитория (ssh://git@10.0.2.5:2222, порт 2222
обязателен), идентификатор credentials (gitea-reader), ветку (main)
и права пользователя git на репозиторий в Gitea. Точная причина
написана в журнале: «Permission denied», «repository not found»,
«couldn't find remote ref main» — три разные поломки.

Это не обязательная часть практики: здесь разобрано то, чем выкат

=========================================================================
А. ЧЕМ ПЛОХ ПРОСТОЙ ВЫКАТ
=========================================================================

Три недостатка части 1 — и каждому дальше соответствует свой приём.

САЙТ ОТДАЁТСЯ НЕ ЦЕЛИКОМ В МОМЕНТ КОПИРОВАНИЯ. rsync с --delete убирает
лишние файлы по ходу копирования: пока файлы переносятся, index.html
может быть уже новым, а стили ещё старыми. На одной странице это доли
секунды, на сайте из сотни файлов — заметная смесь версий. РЕШЕНИЕ:
собирать новую версию в отдельном каталоге и переключать одной операцией.

ОТКАТЫВАТЬСЯ НЕКУДА: предыдущая версия затёрта новыми файлами. Чтобы
вернуться, нужно найти старый коммит, дождаться сборки и выкатить заново.
РЕШЕНИЕ: хранить несколько релизов и переключаться между ними (раздел В).

НЕТ ИСТОРИИ ВЕРСИЙ НА СЕРВЕРЕ: в каталоге сайта всегда только текущее
состояние. РЕШЕНИЕ: та же схема релизов плюс файл с описанием сборки.
ОБЩАЯ ИДЕЯ: не менять работающий сайт, а готовить новую версию рядом.

=========================================================================
Б. РЕЛИЗЫ И СИМЛИНК: DEPLOY_SITE.SH
=========================================================================

Скрипт files/scripts/deploy_site.sh принимает каталог с готовыми файлами
сайта и делает его текущей версией — аккуратно и с возможностью
вернуться. Запускается он НА СЕРВЕРЕ: конвейер копирует его туда вместе
с сайтом и вызывает. Так на сервере не нужны ни Jenkins, ни Java.

РАСКЛАДКА RELEASES + CURRENT

    /var/www/site/releases/20250413-101500-1234/   релиз (сборка 12)
    /var/www/site/releases/20250413-104210-1250/   релиз (сборка 13)
    /var/www/site/current -> releases/20250413-104210-1250

Каждый выкат кладёт файлы в свой каталог: имя — метка времени и номер
процесса. Симлинк current указывает на релиз, который отдаётся сейчас,
а nginx по-прежнему отдаёт /var/www/site/current: конфигурацию менять
не нужно. Схема не наша выдумка: так же устроены Capistrano и Deployer,
потому что она решает сразу и атомарность, и откат, и историю версий.

РЕЖИМЫ РАБОТЫ

    deploy <каталог>   выкатить новый релиз
    rollback           вернуться к предыдущему релизу
    list               список релизов, от свежих к старым
    current            какой релиз отдаётся сейчас
    rotate             удалить старые релизы

ЧТО ДЕЛАЕТ РЕЖИМ deploy, ПО ШАГАМ: проверяет, что каталог существует
и что в нём есть index.html; проверяет, что в странице не осталось
маркера __BUILD_NUMBER__ (если остался, скрипт отказывается работать);
создаёт каталог релиза; копирует туда файлы целиком, вместе с правами;
переключает симлинк — и только теперь новая версия видна посетителям;
удаляет лишние релизы.

ПОЧЕМУ ПЕРЕКЛЮЧЕНИЕ АТОМАРНО. Симлинк создаётся не на месте, а рядом,
под временным именем, и лишь потом переименовывается:

    ln -sfn "${release}" "${CURRENT_LINK}.new"
    mv -Tf "${CURRENT_LINK}.new" "${CURRENT_LINK}"

Переименование в пределах одной файловой системы атомарно: состояния,
когда current не существует, не бывает. Если бы мы удаляли ссылку
и создавали заново, между командами была бы доля секунды, когда сайта
нет вообще.

РОТАЦИЯ. По умолчанию скрипт хранит пять последних релизов
(KEEP_RELEASES=5), остальные удаляет. ЗАЧЕМ ОГРАНИЧИВАТЬ: диск кончается
молча — ошибки не будет, просто однажды выкат упадёт на середине.

ПРОБУЕМ РУКАМИ. Копируем на node1 скрипт и страницу и запускаем выкат
от имени jenkins — так же, как это будет делать конвейер:

    h=10.0.2.13
    dep=/tmp/deploy_site.sh
    scp files/scripts/deploy_site.sh engineer@$h:$dep
    ssh engineer@$h 'mkdir -p /tmp/www'
    scp files/www/index.html engineer@$h:/tmp/www/
    ssh engineer@$h "sed -i s/__BUILD_NUMBER__/999/g /tmp/www/index.html"
    ssh engineer@$h "sudo -u jenkins bash $dep deploy /tmp/www"
    ssh engineer@$h "sudo -u jenkins bash $dep list"
    ssh engineer@$h "sudo -u jenkins bash $dep current"

ПОДСТАНОВКА МАРКЕРА ЗДЕСЬ РУЧНАЯ: в конвейере её делает стадия сборки,
а мы повторяем руками, чтобы увидеть, как скрипт ведёт себя без неё.
Уберите sed из этих команд — и deploy_site.sh откажется работать
с сообщением «в index.html остался маркер __BUILD_NUMBER__».

=========================================================================
В. ОТКАТ И АВТОМАТИЧЕСКИЙ ОТКАТ
=========================================================================

ОТКАТ ВРУЧНУЮ — одна команда на сервере:

    ssh engineer@10.0.2.13 \
        "sudo -u jenkins bash /tmp/deploy_site.sh rollback"

Скрипт берёт второй по свежести релиз и переключает симлинк на него:

    previous="$(ls -1dt "${RELEASES_DIR}"/*/ 2>/dev/null | sed -n 2p)"

ПОЧЕМУ ЭТО МГНОВЕННЫЙ ОТКАТ: ничего не пересобирается и не копируется.
Предыдущая версия всё это время лежала на диске целиком — просто на неё
никто не смотрел. Именно за это схема релизов платит дисковым местом:
место в обмен на откат за доли секунды. Проверить, что получилось:

    sudo -u jenkins bash /tmp/deploy_site.sh current
    curl -s http://localhost/ | grep -i сборка

АВТОМАТИЧЕСКИЙ ОТКАТ В КОНВЕЙЕРЕ. Ручной откат хорош, когда рядом есть
человек, но если выкат провалился в три часа ночи, ждать человека некому.
Поэтому в полном конвейере откат делается в блоке post:

    post {
        failure {
            sshagent(credentials: ['node-ssh']) {
                sh '''
                    set -u
                    for host in ${WEB_NODES}; do
                        t=/tmp/site-deploy-${BUILD_NUMBER}
                        ssh -o StrictHostKeyChecking=accept-new \
                            jenkins@${host} \
                            "bash ${t}/deploy_site.sh rollback" \
                            || echo "${host}: откат не выполнен"
                    done
                '''
            }
        }
    }

Читается так: если любая стадия упала, Jenkins выполняет блок failure,
заходит на каждый сервер и откатывает его к предыдущему релизу. Если
откат где-то не удался, команда печатает сообщение и продолжает: лучше
откатить то, что получается, и сказать об остальном прямо.

ПОЧЕМУ КОМАНДА ОТКАТА БЕРЁТСЯ ИЗ /tmp. Скрипт выката живёт на сервере
только на время работы конвейера: его туда скопировал тот же конвейер.
Поэтому каталог /tmp/site-deploy-<номер> нельзя удалять раньше, чем
отработает откат.

НАПОМИНАНИЕ ПРО ПОРЯДОК УСЛОВИЙ post. В декларативном конвейере условия
блока post выполняются не в том порядке, в каком написаны, а всегда
в фиксированном: сначала always, только потом failure, а самым последним
— cleanup (подробнее в практике 10). Значит, уборку, например удаление
/tmp/site-deploy-<номер>, нельзя помещать в always: она снесёт каталог
со скриптом раньше, чем failure успеет откатиться.

ЗАМЕЧАНИЕ К СХЕМЕ: rollback переключает симлинк на второй по свежести
релиз, не проверяя, что первый — тот, который выкатила эта сборка.

=========================================================================
Г. СКВОЗНАЯ ПРОВЕРКА СКРИПТОМ: SMOKE_TEST.SH
=========================================================================

В части 1 проверка была прямо в конвейере — несколько строк с curl
и grep. Скрипт files/scripts/smoke_test.sh делает то же самое, но
подробнее и с внятными сообщениями, поэтому им пользуются и конвейер,
и человек:

    smoke_test.sh <url> [ожидаемый-текст] [ожидаемый-номер-сборки]

ЧЕТЫРЕ ПРОВЕРКИ, по очереди: страница отвечает кодом 200 (curl
с --max-time, чтобы не висеть вечно, если сервер не отвечает); в ответе
есть ожидаемый текст (по умолчанию «Hello from DevOps Engineer»); в ответе
нет маркера __BUILD_NUMBER__ — он означает, что подстановка
не выполнялась; в ответе есть «>Номер<» — то есть на сайте именно та
сборка, которую мы выкатили, а не та, что была раньше.

ПОЧЕМУ ПРОВЕРЯЮТ ОТВЕТ СЕРВЕРА, А НЕ ФАЙЛЫ НА ДИСКЕ: файлы могут лежать
на месте, а отдаваться другая версия. Симлинк не переключился, nginx
смотрит в другой каталог, права не дают прочитать файл (тогда 403), кэш
отдаёт старое, наконец вы проверяете не ту машину. Всё это видно только
в ответе по HTTP.

ПОЧЕМУ КОД ВОЗВРАТА ВАЖНЕЕ ТЕКСТА. При успехе скрипт возвращает 0,
при провале — 1. Именно по коду возврата конвейер решает, продолжать
или откатываться. Проверка, которая печатает «плохо», но завершается
с кодом 0, бесполезна — Jenkins сочтёт её пройденной.

ПРОВЕРЯЕМ САМИ. Номер сборки берут из журнала сборки в портале; 999 —
номер, который мы подставили руками в разделе Б:

    bash files/scripts/smoke_test.sh http://10.0.2.13/ \
        'Hello from DevOps Engineer' 999

=========================================================================
Д. ПОЛНЫЙ КОНВЕЙЕР: JENKINSFILE.BUILD-TEST-DEPLOY
=========================================================================

Полный конвейер лежит в репозитории как
files/pipelines/Jenkinsfile.build-test-deploy. Он делает то же, что наш
простой конвейер, плюс релизы, проверку на сервере, параллельный выкат
и автоматический откат.

СОЗДАЁМ ЗАДАНИЕ:

    New Item → имя SiteDeploy → Pipeline → OK
    Pipeline → Definition: Pipeline script from SCM
    SCM: Git
      Repository URL: ssh://git@10.0.2.5:2222/engineer/site.git
      Credentials:    gitea-reader
      Branch:         main
    Script Path: files/pipelines/Jenkinsfile.build-test-deploy

Здесь конвейер берётся из репозитория, а не вставляется в задание.
Параметров у задания два: SITE_VERSION (v1 или v2) и WEB_NODES.

СХЕМА РАБОТЫ, КОТОРУЮ ВАЖНО ПОНЯТЬ: сборка идёт на агенте с меткой web;
выкат выполняется ОТТУДА ЖЕ, по ssh, на оба сервера; на них копируется
один каталог — скрипты выката и файлы сайта; переключение релиза делает
deploy_site.sh из раздела Б. Агент здесь не «машина, на которой лежит
сайт», а рабочая станция сборки.

СТАДИЯ «1. Забрать код»: deleteDir() и checkout scm. Рабочий каталог
чистится перед обновлением из репозитория — иначе в сборку попадут файлы
от прошлого запуска.

СТАДИЯ «2. Собрать каталог выката» — каталог build/deploy, который целиком
поедет на серверы. Версия страницы выбирается параметром (index.html или
index-v2.html), затем подставляются номер сборки и ревизия коммита.
Ревизия берётся из самого репозитория, а не из переменной сборки: так
на странице видно настоящий коммит. Кроме страницы в каталог кладутся
deploy_site.sh, smoke_test.sh и файл build-info.txt с номером сборки,
заданием, ревизией, версией и агентом. ВАЖНО: скрипты едут на сервер
вместе с сайтом — версия скрипта так же важна, как версия страницы.

СТАДИЯ «3. Проверить до выката»: файлы на месте, маркера __BUILD_NUMBER__
нет, ожидаемый текст есть. ЗАЧЕМ ПРОВЕРЯТЬ ДО ВЫКАТА: заведомо испорченную
сборку лучше не выкатывать вовсе — ошибка на этой стадии не трогает
серверы и не требует отката. Каталог к тому же архивируется: в сборке
остаётся ровно то, что уехало на серверы.

СТАДИЯ «4. Выкатить сайт» — параллельный блок из двух стадий, «node1
(10.0.2.13)» и «node2 (10.0.2.14)». Обе вызывают функцию deployToHost(host)
с одним и тем же телом: именно эта копипаста и уйдёт в практике 13, когда
её заменит вызов из общей библиотеки. Функция описана в конце файла,
после блока pipeline. Внутри sshagent она делает четыре шага:

    ssh ... "rm -rf /tmp/site-deploy-N && mkdir -p /tmp/site-deploy-N"
    rsync -a --delete -e "ssh ..." build/deploy/ jenkins@host:/tmp/.../
    ssh ... "cd /tmp/site-deploy-N && bash deploy_site.sh deploy www"
    ssh ... "bash /tmp/site-deploy-N/smoke_test.sh http://127.0.0.1/ ..."

Каталог на сервере создаётся заново (rm -rf и mkdir), чтобы в него
не попал мусор от прежних сборок. rsync с -a и --delete переносит каталог
выката: -a сохраняет права, время и символические ссылки, --delete
удаляет в приёмнике то, чего нет в источнике. Затем на сервере запускается
deploy_site.sh — переключение симлинка, которое меняет то, что видят
посетители. И сразу после него проверка smoke_test.sh по адресу
http://127.0.0.1/ на самом сервере: она отвечает на вопрос «отдаёт ли
nginx новую версию», не дожидаясь сетевых чудес.

СТАДИЯ «5. Проверить снаружи» прогоняет smoke_test.sh по обоим адресам
из списка WEB_NODES. ЗАЧЕМ ПРОВЕРЯТЬ ДВАЖДЫ: локальная проверка ловит
ошибки самого выката, внешняя — то, что видит пользователь: адрес, порт,
доступность из сети и ответ именно того сервера, который мы просили.

POST: при провале любой стадии выполняется откат на обоих серверах —
тот самый блок failure из раздела В; при успехе печатается, какие серверы
получили сборку. ЗА ЧТО МЫ ПЛАТИМ СЛОЖНОСТЬЮ, если сравнить с простым
конвейером из части 1: стадий пять вместо четырёх, два выката делаются
одним и тем же телом функции, зато испорченная сборка не доезжает
до серверов, а неудачный выкат откатывается сам.

=========================================================================
Е. КАНАРЕЕЧНЫЙ ВЫКАТ
=========================================================================

В полном конвейере выкат параллельный: обе машины получают новую версию
одновременно. Это быстро, но при плохой версии ломаются сразу оба
сервера. Канареечный выкат устроен иначе: сначала новая версия идёт
на одну машину, проверяется, и только потом — на остальные.

Переделывается это удалением блока parallel:

    stage('4. Выкатить сайт') {
        steps {
            deployToHost('10.0.2.13')
            deployToHost('10.0.2.14')
        }
    }

Теперь вызовы идут последовательно: выкат на node1, проверка там же,
и лишь затем node2.

ПЛЮСЫ: сломанная версия задевает половину площадки, а не всю; между
выкатами есть время посмотреть на результат живьём. МИНУСЫ: выкат вдвое
дольше; площадка во время раскатки неоднородна, и посетители видят
то одну версию, то другую.

ОГОВОРКА ПРО НАШУ ЛАБОРАТОРИЮ: два сервера за одним адресом нам
недоступны — балансировщика в стенде нет, поэтому долю трафика
на «канарейку» направить нечем. Канареечность здесь разбирается как
приём и проверяется вручную: по адресам http://10.0.2.13/ и
http://10.0.2.14/ видно, что на одной машине новая версия, а на другой
прежняя.

=========================================================================
Ж. ВЫКАТ БЕЗ ПРОСТОЯ
=========================================================================

Для статического сайта схема релизов уже даёт отсутствие простоя: файлы
готовятся в новом каталоге, пока старый продолжает отдаваться,
а переключение — одно атомарное переименование симлинка. Момента, когда
сайта нет, не существует. Перезапуск nginx при этом не нужен: он читает
файлы с диска по каждому запросу, а конфигурация не менялась.

ДЛЯ ПРИЛОЖЕНИЙ ЭТОГО НЕ ХВАТАЕТ. Там мешают: соединения к базе данных;
миграции схемы, которые делают отдельным шагом так, чтобы обе версии
работали одновременно; кэш, который после переключения приходится
прогревать заново; состояние в памяти — сессии, счётчики, очереди.

ПРОГРЕВ — предварительная нагрузка на новую версию перед тем, как
пустить на неё пользователей: приложение открывает соединения, наполняет
кэш, отвечает на несколько запросов. У нас роль прогрева играет проверка
smoke_test.sh на самом сервере.

ВАЖНО РАЗЛИЧАТЬ ДВЕ ОПЕРАЦИИ: «перезапустить сервис» и «переключить
версию». Перезапуск — событие с простоем: процесс останавливается
и поднимается заново. Переключение версии — смена симлинка, то есть
операция над файловой системой, процессов не касающаяся. Поэтому правило
«после выката перезапустить сервис» здесь не применяется: перезапускать
нечего — именно поэтому jenkins и разрешена одна команда sudo.

=========================================================================
З. ГИГИЕНА СЕКРЕТОВ: ЧЕК-ЛИСТ
=========================================================================

  * У КАЖДОГО ОКРУЖЕНИЯ СВОИ CREDENTIALS. Ключ, которым выкатывают
    на учебный стенд, не должен открывать продуктив: тогда ошибка
    в конвейере на тесте не приводит к выкату «не туда».
  * ПРАВА НА ИСПОЛЬЗОВАНИЕ СЕКРЕТА ВЫДАЮТ ОСОЗНАННО. Право видеть
    credentials в списке не означает «видит значение» — значения
    не показывает никто. Но оно означает «может использовать в своём
    задании»: кто может править конвейер, тот может и вывести секрет
    в журнал. Это и есть реальная граница доступа.
  * КЛЮЧИ ДЛЯ ВЫКАТА И ДЛЯ ЧТЕНИЯ ИСХОДНИКОВ НЕ ДОЛЖНЫ СОВПАДАТЬ.
    В лаборатории у нас один ключ node-ssh, и это учебное упрощение: он
    подходит и для подключения агентов, и для выката, и для чтения
    репозитория. В рабочей среде так нельзя — утечка одного ключа даёт
    доступ и к коду, и к серверам. Разводят так: отдельный ключ на чтение
    репозитория (на стороне Git-сервера его ограничивают командой
    git-upload-pack), отдельный — на выкат.
  * РОТАЦИЯ. Ключи и токены заменяют по расписанию и при уходе человека,
    у которого был доступ. Замена — это не «создать новый рядом»,
    а «создать новый, перевести на него задания и отозвать старый».
  * КТО И КОГДА ПОЛЬЗОВАЛСЯ СЕКРЕТОМ: по заданиям, которые ссылаются
    на идентификатор (он виден в настройках и в Jenkinsfile), и по
    журналам — обращения к серверам остаются в /var/log/auth.log
    и в журнале sudo на целевых машинах.
  * ЧТО ДЕЛАТЬ ПРИ УТЕЧКЕ, по шагам: отозвать (удалить ключ
    из authorized_keys, токен — в Gitea, пароль — сменить); заменить
    (создать новый секрет и перевести на него задания); проверить
    задания, где встречался старый идентификатор; посмотреть журналы
    обращений за время, пока ключ был доступен; сообщить тем, кого это
    касается.

=========================================================================
И. РАЗБОР ПОЛОМОК ПРОДВИНУТОГО УРОВНЯ
=========================================================================

ПРОБЛЕМА: sshagent не отдаёт ключ во время выката

Симптом: команды внутри блока sshagent не находят ключ. Проверяем:
sshagent вызывается в том же шаге sh, где идёт ssh (переменные окружения
не переживают выход из блока), и указан существующий идентификатор
credentials.

ПРОБЛЕМА: откат не сработал, потому что на сервере нет каталога выката

Блок failure вызывает deploy_site.sh из /tmp/site-deploy-<номер>,
а этого каталога нет: значит, выкат на этот сервер не дошёл — rsync упал
раньше. Это не поломка: сервер остался на прежней версии. Проверяем:

    readlink -f /var/www/site/current

ПРОБЛЕМА: симлинк не переключился

Скрипт печатает «выкат выполнен», но симлинк указывает на прежний релиз.
Смотрим владельца и права: переключить симлинк может только тот, у кого
есть право писать в /var/www/site, то есть jenkins:

    ls -ld /var/www/site /var/www/site/releases

ПРОБЛЕМА: после успешного выката сайт отдаёт старую версию

Сравниваем три вещи: куда указывает симлинк (readlink -f), что написано
в файле сборки (cat /var/www/site/current/build-info.txt) и что реально
отдаётся в ответе (curl -s http://localhost/). Если расходятся первое
и третье — nginx смотрит не на current, проверьте root (sudo nginx -T).
Если первое и второе — на сервер приехал не тот каталог выката.

ПРОБЛЕМА: nginx не читает каталог релиза (403)

nginx работает под www-data, а файлы релиза принадлежат jenkins: нужны
права 0755 на каталоги и 0644 на файлы. Классический случай — файл,
скопированный из чужого домашнего каталога с правами 0600:

    ls -ld /var/www/site/current/
    ls -l /var/www/site/current/

ПРОБЛЕМА: релизы занимают диск

Каждый выкат оставляет каталог с полной копией сайта, поэтому место
кончается предсказуемо. Чистим штатным режимом, он оставляет пять
последних релизов:

    sudo -u jenkins bash /tmp/deploy_site.sh rotate
