1. ОБХОД ПОРТАЛА: ЧТО ГДЕ ЛЕЖИТ
=========================================================================

Почти вся административная работа начинается с одного места — меню
Manage Jenkins. Откройте его и пройдитесь по разделам. Ниже — то, что
действительно используется, и то, что мы будем настраивать в курсе.

  System            — общие настройки: адрес портала, число исполнителей,
                      письмо администратора, переменные окружения,
                      интервал тишины. Пункт, в который заходят чаще всего.
  Tools             — Global Tool Configuration: где взять git, какими
                      версиями пользоваться.
  Plugins           — установка, обновление и удаление плагинов.
  Nodes             — агенты сборки (практика 4).
  Credentials       — ключи, пароли и токены (практика 11).
  Users             — учётные записи портала (эта практика).
  Security          — настройки входа, прав, защиты от подделки запросов.
  System Log        — журнал Jenkins, включая сообщения плагинов.
  System Information — состояние Java: память, потоки, свойства системы.
  Script Console    — выполнение Groovy-кода с правами администратора
                      (практика 9). Самый опасный пункт меню.
  Configuration as Code — просмотр и применение конфигурации из файла
                      (практика 14).
  Reload Configuration from Disk — перечитать файлы конфигурации
                      на диске, не перезапуская службу.

ОБРАТИТЕ ВНИМАНИЕ: разделы Manage Jenkins и Manage Plugins — это одно
и то же место, просто исторически к нему ведут два адреса. Если вы
встретите инструкцию с «Manage Plugins» — ищите Plugin Manager внутри
Manage Jenkins.

ДОБАВЛЕНО: в прежней версии курса эти названия писались с опечатками
(«Menage Jenkins», «Jankins»). На занятиях это превращалось в поиск
пункта, которого нет. Названия меню стоит запоминать точно: по ним
ищут документацию.

2. ПОЛЬЗОВАТЕЛИ: СВОЯ УЧЁТНАЯ ЗАПИСЬ ДЛЯ КАЖДОГО
=========================================================================

Первое, что делают с новым Jenkins, — перестают работать под одной
учётной записью.

2.1. Смотрим, кто уже есть:

Manage Jenkins → Users

Здесь должны быть две записи: engineer (её мы создали при установке)
и, возможно, автоматически созданный system. Учётная запись system
служебная: часть плагинов ходит в API под ней, трогать её не нужно.

2.2. Создаём служебного пользователя для автоматизации:

Manage Jenkins → Users → Create User

  Username: serviceuser
  Password: Console47
  Confirm password: Console47
  Full name: Служебный пользователь
  E-mail: service@lab.local

ЗАЧЕМ ОТДЕЛЬНЫЙ ПОЛЬЗОВАТЕЛЬ. У автоматизации (скриптов, внешних систем,
CLI — практика 5) должна быть своя учётная запись, а не ваша. Причины
две: по журналам видно, что именно сделал человек, а что — автомат;
и если токен автоматизации утечёт, его отзывают, не меняя ваш пароль.

ПРАВИЛО, КОТОРОЕ СТОИТ ЗАПОМНИТЬ: один человек — одна учётная запись,
одна автоматизация — одна учётная запись. Общие логины («admin»,
«jenkins», «ci») лишают вас и аудита, и возможности отозвать доступ
у одного, не тронув остальных.

2.3. Свой пароль и почта:

имя пользователя → Configure (или Manage Jenkins → Users → engineer →
Configure). Здесь же меняется описание, почта и — это нам понадобится
в практике 5 — создаются API-токены.

3. АУТЕНТИФИКАЦИЯ И АВТОРИЗАЦИЯ: ДВЕ РАЗНЫЕ ВЕЩИ
=========================================================================

Это различие стоит усвоить сразу, потому что вокруг него построена
вся безопасность Jenkins.

  АУТЕНТИФИКАЦИЯ отвечает на вопрос «кто ты». Настраивается в разделе
  Manage Jenkins → Security → Security Realm.

  АВТОРИЗАЦИЯ отвечает на вопрос «что тебе можно». Настраивается там же,
  в разделе Authorization.

Их легко перепутать, и это приводит к вопросам вида «я выдал права,
а он не может войти»: значит, не опознан (аутентификация), а не «прав
не хватило» (авторизация). Ошибки в интерфейсе Jenkins выглядят по-разному:

  401 Unauthorized — «не опознан»: пароль, токен, учётная запись;
  403 Forbidden — «опознан, но нельзя»: права.

3.1. Security Realm. Варианты:

  Jenkins' own user database — свои пользователи, пароли хранятся
    в Jenkins. То, что мы используем в курсе;
  LDAP / Active Directory — вход по корпоративной учётной записи;
  OIDC / SAML (плагины) — вход через внешний провайдер.

Наш выбор — своя база: на стенде нет домена, а принципы работы от этого
не меняются.

ВАЖНО ПРО ГАЛОЧКУ «Allow users to sign up». С ней любой, кто дотянулся
до портала, может создать себе учётную запись. Убедитесь, что она снята:

Manage Jenkins → Security → Security Realm:

  [ ] Allow users to sign up

3.2. Авторизация: стратегии. Их пять, и первые три опасны.

  Anyone can do anything — без входа можно всё. Никогда.
  Legacy mode — «как было раньше»: вошедший пользователь получает
    полные права. Так делали, когда пользователей было двое.
  Logged-in users can do anything — любой вошедший полный админ.
    Формально защищено паролем, фактически — нет: один сотрудник
    с обычной учётной записью может удалить все задания.
  Matrix-based security — таблица «пользователь × разрешение».
    То, что нужно.
  Project-based Matrix Authorization Strategy — то же плюс права
    на отдельные задания и папки. Нужен, когда проектов много
    и надо разделить доступ между командами.

3.3. Настраиваем Matrix-based security. Открываем:

Manage Jenkins → Security → Authorization → Matrix-based security

В таблице строки — пользователи, столбцы — разрешения. Основные группы
разрешений и что они означают:

  Overall: Read      — видеть портал; без этого пользователь не увидит
                       вообще ничего;
  Overall: Administer — полный администратор. Выдавать только тем,
                       кто действительно администрирует Jenkins;
  Agent: Build       — запускать сборки на агентах;
  Agent: Configure   — создавать и менять агентов;
  Job: Read / Build / Configure / Delete — видеть задание, запускать,
                       настраивать, удалять;
  Run: Replay        — перезапустить сборку с изменённым кодом конвейера.
                       Это скрытый, но важный доступ: возможность
                       изменить код сборки;
  View: Read / Configure — видеть и настраивать представления;
  Credentials: View / Create / Update / Delete — видеть существующие
                       секреты (не значения!), создавать свои, менять
                       чужие, удалять. Значение секрета не показывается
                       никому — но право «использовать» секрет означает
                       возможность его украсть через сборку;
  Manage: Configure / Scripts — настройки системы и Script Console.
                       Это уровень администратора.

Наша настройка для стенда:

  engineer    — Overall: Administer (то есть всё);
  authenticated — Overall: Read;
  serviceuser — Overall: Read, Job: Read, Job: Build, Job: Workspace,
                View: Read, Credentials: View.

ПОЧЕМУ СЛУЖЕБНОМУ ПОЛЬЗОВАТЕЛЮ НЕ ДАЁМ Job: CONFIGURE: пользователь
автоматизации не должен уметь править задание, которое выполняет.
Иначе утечка одного токена означает, что злоумышленник сначала меняет
задание, а потом выполняет свой код на всех агентах.

ПОЧЕМУ НЕ ДАЁМ Credentials: UPDATE: он может пользоваться секретом,
но не может подменить его на свой. Подмена секрета — способ увести
выкат в сторону, при этом все журналы выглядят нормально.

3.4. Сохраняем. С этого момента политика применяется сразу, поэтому
проверьте в другом окне браузера, что доступ работает так, как задумано.
Проверка прав у конкретного пользователя описана в пункте 13.

ВАЖНАЯ ОСТОРОЖНОСТЬ: если вы уберёте себе Overall: Administer и нажмёте
Save, доступ к управлению Jenkins вы потеряете сразу. Выбирайте сначала
себе полный доступ, проверяйте, потом ограничивайте остальных.

4. ЗАЩИТА ОТ ПОДДЕЛКИ ЗАПРОСОВ И ПРОЧИЕ НАСТРОЙКИ БЕЗОПАСНОСТИ
=========================================================================

В том же разделе Security есть настройки, которые не выглядят важными,
но именно они закрывают типовые дыры.

4.1. CSRF Protection (Prevent Cross Site Request Forgery exploits).
Должно быть включено. Смысл: без этой защиты любой сайт, открытый
в браузере администратора, может отправить запрос в Jenkins от его имени
(браузер приложит cookie сессии), и задание запустится. Jenkins защищается
тем, что требует дополнительный заголовок (crumb) в каждом изменяющем
запросе.

Следствие, с которым вы столкнётесь в практике 5 и 7: скрипты и curl
должны либо аутентифицироваться токеном, либо получать crumb заранее.
«Почему триггер не срабатывает из curl» почти всегда именно про это.

4.2. Agent → TCP port for inbound agents. Если входящие агенты (JNLP,
практика 4) не используются, порт лучше закрыть:

  Agent → TCP port for inbound agents: Disable

Дополнительный открытый порт — дополнительная поверхность атаки, и держать
его «на всякий случай» незачем.

4.3. Markup Formatter. Вариант Safe HTML означает, что в описаниях
заданий можно использовать часть HTML-тегов. Если Jenkins читают много
людей с разными правами, безопаснее Plain text: подстановка HTML
в описания — известный способ выманить у администратора действие
(описание задания выглядит как форма для ввода пароля).

Для стенда оставьте по умолчанию, но помните, почему этот пункт вообще
существует.

4.4. CLI. Если Jenkins CLI (практика 5) не нужен по сети, оставьте
значение по умолчанию — «Only authenticated users can access the CLI».
Вариант «Anyone can access» нам не нужен никогда.

4.5. Скрипты. В разделе Manage Jenkins → Security → Script Approval
(появляется после установки соответствующих прав и работы конвейеров)
видно, какие Groovy-вызовы из конвейеров Jenkins отказался выполнять.
Обещание не выдавать разрешения «не глядя» — тема практики 9.

5. ПЛАГИНЫ: САМАЯ ХРУПКАЯ ЧАСТЬ JENKINS
=========================================================================

Установка плагинов: Manage Jenkins → Plugins.

  Updates  — что можно обновить;
  Available — что можно поставить (список скачивается из центра обновлений);
  Installed — что установлено, с версиями и признаком загрузки;
  Advanced settings — установка плагина из файла .hpi и настройка
    источников обновлений (например, внутреннего зеркала).

5.1. Что поставить сразу. Если на этапе установки вы выбрали
«Install suggested plugins», большая часть уже есть. Проверьте, что
в списке Installed есть:

  workflow-aggregator     — система конвейеров;
  git, git-client         — работа с репозиториями;
  credentials,
  credentials-binding,
  plain-credentials       — секреты;
  ssh-agent               — ключ на время сборки;
  ssh-slaves              — агенты по SSH;
  matrix-auth             — матрица прав;
  timestamper             — время в журнале;
  ws-cleanup              — уборка рабочего каталога;
  build-timeout           — таймаут сборки;
  configuration-as-code   — конфигурация как код;
  gitea                   — интеграция с нашим Git-сервером (практика 6);
  docker-workflow,
  docker-plugin           — Docker (практика 12);
  job-dsl                 — создание заданий кодом (пригодится позже);
  pipeline-stage-view,
  pipeline-utility-steps,
  ansicolor.

Полный список, пригодный для автоматической установки, лежит в файле
files/jcasc/plugins.txt. Как его применять — практика 14.

5.2. Правила обращения с плагинами, которые экономят дни работы.

  ПРАВИЛО ПЕРВОЕ: плагин — это чужой код с правами Jenkins. Плагин
  работает внутри сервера, видит ваши credentials и может всё, что
  может Jenkins. Поэтому «поставить плагинчик, чтобы было красиво» —
  так себе идея.

  ПРАВИЛО ВТОРОЕ: не обновляйте всё сразу. Обновляйте по три-пять
  плагинов и после каждого обновления запускайте одну-две сборки.

  ПРАВИЛО ТРЕТЬЕ: перед обновлением важных плагинов делайте копию
  JENKINS_HOME. Перед установкой плагин сохраняет предыдущую версию
  файла рядом с расширением .bak — откатиться можно, но только если
  знать, какие файлы менялись.

  ПРАВИЛО ЧЕТВЁРТОЕ: смотрите на пометки. Если плагин помечен как
  deprecated (устаревший) или в описании сказано «не поддерживается
  с такого-то года» — планируйте замену. Именно так случилось
  с Publish over SSH, о котором речь в практике 11.

  ПРАВИЛО ПЯТОЕ: свежее — не значит лучше. Новая версия плагина может
  требовать более новое ядро Jenkins. Перед обновлением смотрите, какую
  версию Jenkins требует плагин.

5.3. Плагин не загрузился. Симптом: в списке Installed он есть, но рядом
предупреждение, а в портале не хватает целой страницы настроек. Причина
почти всегда одна: плагину нужна более новая версия Jenkins или
не хватает другого плагина.

Где смотреть причину:

Manage Jenkins → System Log → All Jenkins Logs

Ищите строки с именем плагина и словом ERROR или SEVERE. Если плагин
мешает запуску, его можно отключить в разделе Plugins → Installed,
сняв галочку. Скрипт инвентаризации из практики 9 показывает список
плагинов, ожидающих обновления, и отключённые плагины.

6. ОБЩИЕ НАСТРОЙКИ: SYSTEM И TOOLS
=========================================================================

6.1. Manage Jenkins → System. Что здесь стоит проверить сразу.

  Jenkins Location:
      System Admin e-mail address — адрес, от которого приходят письма;
      Jenkins URL — http://10.0.2.5:8080/. Это тот самый адрес, который
      попадает в ссылки в письмах и вебхуках. Значение localhost здесь —
      источник половины загадочных «ссылка не открывается»;
  # of executors — сколько сборок контроллер выполняет сам. В рабочей
      среде здесь ставят 0: контроллер не собирает. Мы разберём это
      в практике 4;
  Quiet period — сколько секунд Jenkins ждёт перед запуском сборки
      после события. Пять секунд на стенде — разумное значение;
  Environment variables — переменные, видимые всем сборкам. Удобно для
      некритичных значений (например, адрес внутреннего реестра).
      СЕКРЕТЫ ЗДЕСЬ НЕ ХРАНЯТ — переменные видны в журнале сборки;
  Shell — путь к оболочке для шагов сборки (/bin/bash по умолчанию);
  SCM — настройки Git: путь к исполняемому файлу, поведение при
      ошибках сети.

6.2. Manage Jenkins → Tools (Global Tool Configuration). Здесь Jenkins
хранит сведения об инструментах: где взять git, какую версию JDK
использовать для сборок.

Для нашего курса достаточно убедиться, что в разделе Git есть
автоматическая установка или корректный путь к git:

  Git → Add Git → Path to Git executable: /usr/bin/git

ЗАЧЕМ ЭТО ЗДЕСЬ: если git не найден, задание упадёт с сообщением
«Unable to find git» или «git not found», причём не в начале сборки,
а в момент checkout — то есть после того, как вы уже начали разбираться
не с тем.

6.3. Почта. Раздел E-mail Notification настраивается, если нужны письма.
В лаборатории почтового сервера нет, и мы этого не делаем: уведомления
смотрим в портале. В рабочей среде здесь указывают SMTP-сервер и адрес
отправителя, а сами письма чаще отправляют через плагины уведомлений
для конкретной команды.

7. ЖУРНАЛЫ: ГДЕ ИСКАТЬ ПРИЧИНУ
=========================================================================

У Jenkins несколько уровней журналирования, и понимание разницы между
ними сильно ускоряет разбор.

7.1. Журнал сборки (Console Output). Это вывод ваших команд. Относится
к конкретной сборке и не содержит внутренних сообщений Jenkins.

7.2. Системный журнал Jenkins:

Manage Jenkins → System Log → All Jenkins Logs

Здесь видно: запуск плагинов, ошибки конфигурации, попытки входа,
обработку вебхуков, сообщения агентов.

7.3. Файл журнала на диске:

sudo tail -f /var/log/jenkins/jenkins.log

Тот же журнал, но доступный без портала — а портал, напомню, иногда
именно то, что не работает. Первое место, куда смотрят при «Jenkins
не запускается».

7.4. Уровни журналирования. В разделе System Log можно добавить
источник (Add new log recorder) для конкретного класса. Практический
смысл: по умолчанию часть сообщений скрыта как слишком подробная,
а при разборе вебхуков или прав доступа именно они и нужны. Например,
для отладки прав удобно поднять уровень для класса
org.springframework.security: тогда в журнале видно, почему запрос
получил 403.

7.5. Ротация журналов. /var/log/jenkins/jenkins.log растёт, и без ротации
однажды займёт весь диск. Настройте logrotate для этого файла (правило
для стенда: 100 МБ и пять файлов) или хотя бы поставьте напоминание
проверять df -h.

ЖУРНАЛ СБОРОК И ЖУРНАЛ СЕРВЕРА — РАЗНЫЕ ВЕЩИ. Первый пишет ваша сборка,
второй — сам Jenkins. Если «сборка не запустилась», смотреть надо второй:
в журнале сборки ничего не будет, её же не было.

8. ОБСЛУЖИВАНИЕ: ПЕРЕЗАПУСК, КОНФИГУРАЦИЯ, СОСТОЯНИЕ
=========================================================================

8.1. Safe Restart. Пункт Manage Jenkins → Safe Restart (он же доступен
по адресу /safeRestart). Jenkins останавливается не сразу, а дождавшись
окончания выполняющихся сборок, и затем поднимается.

ПОЧЕМУ ЭТО ВАЖНО ПОНИМАТЬ: обычный restart убивает сборки на середине.
Прерванная на середине сборка выката — это, в лучшем случае, выкат
на половину серверов. В курсе мы делаем так, чтобы прерывание было
безопасным (практика 11), но безопаснее просто не прерывать.

Если ждать нельзя, есть Prepare for Shutdown: Jenkins перестаёт принимать
новые сборки, но даёт закончить текущие.

8.2. Reload Configuration from Disk. Перечитывает файлы конфигурации
с диска без перезапуска службы. Полезно, когда конфигурацию положили
извне — например, файл JCasC или задание из репозитория (практики 5 и 14).

ВАЖНО: изменения, сделанные в портале, при этом не теряются — Jenkins
перед перечитыванием сохраняет своё состояние. Но если файл на диске
и значение в памяти противоречат друг другу, победит файл.

8.3. System Information. Что здесь полезно смотреть:

  память Java (куча занята/выделена) — признак утечки памяти в плагине;
  количество потоков и загруженных классов;
  список системных свойств, включая версию Java и пути;
  переменные окружения процесса Jenkins — проверка, что нужные
        переменные действительно дошли до службы.

8.4. Ограничение числа одновременных сборок контроллера. Мы уже видели
этот параметр в разделе System. Запомните простое правило: контроллер —
не рабочая лошадка. Один исполнитель на контроллере на учебном стенде —
компромисс; в рабочей среде — ноль.

8.5. Скрипт-консоль. Manage Jenkins → Script Console. Мощнейший
инструмент и самая опасная кнопка в Jenkins. Ей целиком посвящена
практика 9, поэтому здесь только правило: доступ к ней — это доступ
ко всему, поэтому он есть только у администраторов.


#########################################################################
ЧАСТЬ 2. ПРОДОЛЖЕНИЕ: ПОРЯДОК И БЕЗОПАСНОСТЬ НА ПРАКТИКЕ
#########################################################################


=========================================================================
9. ЧТО МЫ ЗАЩИЩАЕМ: МОДЕЛЬ УГРОЗ В ДВУХ АБЗАЦАХ
=========================================================================

Jenkins — не просто сайт с кнопкой «собрать». Это система, которая:

  * хранит ключи и пароли (credentials);
  * может выполнять произвольные команды на всех подключённых машинах;
  * имеет доступ к исходному коду компании;
  * может выкатывать код в продакшен.

Отсюда главный вывод: ПРАВА В JENKINS — ЭТО ПРАВА НА ИНФРАСТРУКТУРУ.
Пользователь, который может запустить сборку задания с параметром или
настроить задание, в конечном счёте может выполнить свой код от имени
пользователя сборки.

От кого защищаемся:

  * от внешнего наблюдателя в сети — шифрованием (у нас его нет,
    стенд изолирован) и закрытым анонимным доступом;
  * от рядового сотрудника — минимумом прав по умолчанию: он должен
    уметь запускать сборки, а не менять их;
  * от вредоносного кода из репозитория — разделением прав между
    сборкой и выкатом (в практике 11 это видно на примере того,
    кто и какие credentials получает);
  * от вредоносного плагина — аккуратностью с источниками плагинов
    и обновлениями. От этой угрозы внутри Jenkins защиты почти нет:
    плагин работает с теми же правами, что и сам Jenkins.

Ещё одно следствие, которое стоит запомнить: администратор Jenkins
не защищён RBAC-моделью от самого себя. Он всегда может выдать себе
права. RBAC защищает от случайности и от рядовых участников, а не
от того, кто управляет сервером.


=========================================================================
10. ЧЕК-ЛИСТ БЕЗОПАСНОСТИ, КОТОРЫЙ СТОИТ ПРОЙТИ СЕЙЧАС
=========================================================================

Пройдите по пунктам и убедитесь, что каждый выполнен. Это не теория:
каждый пункт — реальная дыра, которую находят при аудите.

  1. Анонимный доступ закрыт: Security Realm → Allow users to sign up
     снят, Authorization — матрица, а не «logged-in users can do anything».
  2. У каждого человека своя учётная запись, общих логинов нет.
  3. У администраторов не больше прав, чем нужно: в рабочей среде
     админов должно быть двое-трое, а не «вся команда».
  4. Автоматизация работает отдельным пользователем с API-токеном,
     а не паролем администратора.
  5. Ни один пароль не хранится в конфигурации задания открытым текстом:
     всё, что является секретом, лежит в credentials (практика 11).
  6. CSRF Protection включён.
  7. Порт входящих агентов закрыт, если входящие агенты не используются.
  8. Script Console доступна только администраторам; доступ в журнале
     виден (журнал загрузки скриптов пишется с уровнем WARNING).
  9. Резервная копия JENKINS_HOME делается регулярно и лежит
     не на той же машине (практика 14).
 10. Обновления Jenkins и плагинов планируются, а не выполняются
     «когда вспомним». Просроченный Jenkins — это известные уязвимости,
     которые уже есть в базах сканеров.

Проверить пункты 1–3 можно прямо в портале, но полезнее — командами,
чтобы получить воспроизводимый результат. Скрипт инвентаризации из
практики 9 печатает список пользователей с количеством токенов
и список заданий; его удобно запускать после каждого изменения
прав.


=========================================================================
11. РЕГУЛЯРНОЕ ОБСЛУЖИВАНИЕ: ЧТО ДЕЛАТЬ РАЗ В МЕСЯЦ
=========================================================================

Jenkins не требует ежедневного внимания, но несколько вещей, которые
не сделали вовремя, приводят к аварии. Минимальный месячный список:

  * обновить ядро Jenkins и, порциями, плагины — перед этим копия;
  * проверить свободное место: df -h и размер /var/lib/jenkins;
  * почистить историю заданий, у которых она растёт (Discard old builds,
    практика 3), и рабочие каталоги агентов;
  * проверить состояние агентов: все ли в сети, не растёт ли очередь;
  * просмотреть пользователей и их права: не появилось ли лишних,
    не остались ли права у уволившихся;
  * проверить срок жизни токенов: старые токены автоматизации
    лучше перевыпускать;
  * проверить, что резервная копия делается и открывается (не только
    «создаётся» — именно открывается; практика 14);
  * посмотреть журнал на предмет повторяющихся ошибок плагинов.

ПОЧЕМУ «ОТКРЫВАЕТСЯ», А НЕ «СОЗДАЁТСЯ»: копия, которую нельзя
распаковать, хуже отсутствия копии — она создаёт уверенность, что
защита есть.


=========================================================================
12. НАБЛЮДАЕМОСТЬ: ЧТО СМОТРЕТЬ, КОГДА ВСЁ РАБОТАЕТ
=========================================================================

Проблемы удобнее замечать до жалоб. Три встроенных источника, которые
всегда под рукой:

  * Manage Jenkins → System Information — память Java, потоки, время
    работы. Рост занятой памяти после каждой сборки и отсутствие
    возврата к прежнему уровню означает, что пора разбираться;
  * Build Executor Status и Build Queue на главной странице — сколько
    сборок идёт и сколько ждёт. Постоянная очередь при свободных
    агентах означает нехватку меток или исполнителей;
  * Load Statistics (Manage Jenkins → Load Statistics) — графики
    загрузки исполнителей и длины очереди. Полезно, когда обсуждают
    «нужен ли ещё один агент».

Для более серьёзного наблюдения ставят плагин metrics и снимают метрики
в Prometheus, а панели рисуют в Grafana. На стенде это избыточно,
но знать, что у Jenkins есть /metrics-подобный эндпоинт, полезно:
сам Jenkins — тоже система, за которой нужно следить.


=========================================================================
13. ПРОВЕРКА ПРАВ НА ПРАКТИКЕ
=========================================================================

Чтобы не гадать, «есть ли права», их проверяют. Простейший способ —
войти под проверяемым пользователем в другом окне браузера (в режиме
инкогнито) и попробовать сделать то, что он должен уметь, и то, чего
не должен.

Полезный приём: право можно проверить со стороны администратора. Откройте
Script Console (практика 9) и посмотрите разрешения пользователя —
в Jenkins это делается через API авторизации. Но гораздо важнее
практический навык: после каждого изменения матрицы прав пройдите
по списку «что должен уметь этот пользователь» и проверьте каждый пункт
руками. Одна минута проверки экономит вечер поиска причины «почему
у него не запускается».

Проверять стоит как минимум:

  * видит ли пользователь портал (Overall: Read);
  * видит ли задание и может ли его запустить (Job: Read, Job: Build);
  * может ли он открыть настройки задания (Job: Configure — не должен);
  * виден ли ему раздел Manage Jenkins (не должен, если он не админ);
  * может ли он зайти в Script Console (не должен ни при каких
    обстоятельствах, кроме администраторов).


=========================================================================
14. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: после изменения прав потерян доступ к управлению Jenkins

Ситуация неприятная, но известная: вы сняли себе Overall: Administer
и нажали Save. Если остался доступ хотя бы к Script Console — права
возвращаются через неё. Если нет — правят файл конфигурации
при остановленной службе:

sudo systemctl stop jenkins
sudo cp /var/lib/jenkins/config.xml /var/lib/jenkins/config.xml.bak
sudo vim /var/lib/jenkins/config.xml

Найдите блок authorizationStrategy и временно замените его так:

  <useSecurity>false</useSecurity>

Затем:

sudo systemctl start jenkins

Портал откроется без проверки прав. Верните себе права, а затем обязательно
верните настройку безопасности обратно: <useSecurity>true</useSecurity>
и перезапустите Jenkins. Оставлять <useSecurity>false</useSecurity> —
значит сделать Jenkins общедоступным для всей сети.

МОРАЛЬ: перед правкой матрицы прав всегда держите открытой вторую сессию
или будьте готовы к этой процедуре. Резервная копия на этот случай тоже
есть (практика 14).

ПРОБЛЕМА: пользователь не может войти

Разбирайте по шагам, не перескакивая:

  1. Вообще не принимает пароль — аутентификация. Проверьте в Users,
     что пользователь существует, что Security Realm — своя база
     (а не LDAP), и что пароль действительно тот;
  2. Принимает пароль, но сразу выкидывает — чаще всего у пользователя
     нет права Overall: Read. Выдайте и проверьте;
  3. Входит, но не видит ни одного задания — нет View: Read
     или не совпадает представление (View);
  4. Входит, видит задание, но не может запустить — нет Job: Build;
  5. Входит, запускает, но сборка падает с «missing permission
     to build on agent» — нет Agent: Build или у задания метка
     на другого агента.

Такой разбор по шагам полезен и как навык администрирования, и как
привычка: сначала понять, на каком именно уровне отказ, потом лечить.

ПРОБЛЕМА: раздел настроек исчез после установки плагина

Плагин не загрузился. Смотрите Manage Jenkins → System Log и ищите имя
плагина. Частые причины: плагин требует более новое ядро Jenkins, плагин
зависит от другого плагина, плагин устарел и несовместим с текущей
версией Java. Лечение: обновить ядро, доустановить зависимость или
отключить плагин.

ПРОБЛЕМА: портал стал заметно медленнее

По частоте причин:

  1. Кончилось место на диске. df -h;
  2. Мало памяти для Java: смотрите System Information, кучу;
  3. Слишком много плагинов и заданий на контроллере, который собирает
     сборки сам (в практике 4 мы это исправим);
  4. Тяжёлые операции в Script Console или на страницах списка заданий
     (например, открытая страница «все сборки» огромного задания).

ПРОБЛЕМА: настройка не применяется

Если вы обновили файл конфигурации на диске, а Jenkins его «не видит»,
выберите Manage Jenkins → Reload Configuration from Disk. Если настройку
перезаписывает что-то ещё (например, JCasC — практика 14), правка
в портале будет исчезать после перезапуска: это не поломка, а следствие
того, что конфигурация управляется кодом.
