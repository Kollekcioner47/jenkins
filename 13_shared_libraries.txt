Практика 13. Общие библиотеки: один раз написать, везде использовать.

До сих пор каждый конвейер курса жил сам по себе. В практике 11 выкат
сайта описан прямо в Jenkinsfile: рядом лежат функция выката на один
сервер и свой блок отката в post. Пока конвейер один, так и надо.

Проблема начинается, когда конвейеров становится много. Логика выката
размножается по файлам, версии расходятся, а привычная фраза «поправь
выкат» превращается в обход десятка репозиториев.

Здесь мы выносим общую логику в отдельный репозиторий — общую
библиотеку конвейеров (Shared Library). Её подключает любой конвейер
одной строкой, а правка выката делается в одном месте и сразу
действует для всех, кто эту версию библиотеки использует.

Готовые файлы к практике:

  files/shared-library/vars/sayHello.groovy         простейший шаг
  files/shared-library/vars/deployToNodes.groovy    выкат на серверы
  files/shared-library/vars/rollbackNodes.groovy    откат
  files/shared-library/src/ru/iklimarev/BuildInfo.groovy   класс
  files/pipelines/Jenkinsfile.library               конвейер с библиотекой
  files/pipelines/Jenkinsfile.build-test-deploy     он же без библиотеки

Последние два файла стоит открыть рядом: разница между ними и есть
тема этой практики.


=========================================================================
ЧТО МЫ СДЕЛАЕМ И ЗАЧЕМ
=========================================================================

Возьмём проблему на нашем же примере. В конвейере
files/pipelines/Jenkinsfile.build-test-deploy стадия выката выглядит так:

    stage('4. Выкатить сайт') {
        parallel {
            stage('node1 (10.0.2.13)') {
                steps { deployToHost('10.0.2.13') }
            }
            stage('node2 (10.0.2.14)') {
                steps { deployToHost('10.0.2.14') }
            }
        }
    }

Две стадии отличаются одной строкой — адресом сервера. При десяти
серверах это десять стадий, десять строк вызова и десять мест, где
нужно не забыть поправить имя или адрес.

Хуже другое. Вызов в стадии короткий только потому, что вся работа
спрятана в функцию deployToHost — она объявлена после блока pipeline.
В конвейерах, которые пишут без такой функции (а пишут так чаще
всего), внутри каждой стадии лежат свои rm, mkdir, rsync, ssh и своя
проверка. Тогда один и тот же выкат существует в файле в нескольких
почти одинаковых копиях.

И ещё одна копия той же логики — блок отката в post. Он делает почти
то же самое, но по-своему: свой цикл по серверам, свой ssh, свой
разбор кода возврата.

ПОЧЕМУ ЭТО ПЛОХО, А НЕ «ПРОСТО НЕКРАСИВО»

Пока копии совпадают, всё работает. Расхождение появляется при первой
же правке: добавили опцию rsync, поменяли каталог выката, увеличили
таймаут проверки — и правку внесли не во все места. Дальше два сервера
живут по разным правилам, а журнал сборки выглядит нормально: обе
стадии зелёные, обе что-то выкатили.

При двадцати серверах синхронная правка двадцати мест — это уже не
вопрос аккуратности, а вопрос времени. Рассинхронизация гарантирована.

ТРИ УРОВНЯ РЕШЕНИЯ, И ВСЕ ТРИ НУЖНЫ

  1. КОПИПАСТА В ОДНОМ ФАЙЛЕ. То, что мы видели в конвейере без
     функции. Работает для двух серверов, разваливается на третьем.

  2. ФУНКЦИЯ ВНУТРИ JENKINSFILE. Так сделано в нашем конвейере:
     deployToHost объявлена один раз, стадии только вызывают её.
     Это уже большой шаг вперёд: правка — в одном месте файла.
     Ограничение одно: функция живёт ровно в этом Jenkinsfile.
     Второй конвейер (например, выкат по расписанию или канареечный
     выкат) снова начнёт с копии этой функции.

  3. ОБЩАЯ БИБЛИОТЕКА. Логика выката лежит в отдельном репозитории
     и подключается к любому конвейеру. Правка по-прежнему одна,
     но действует на все конвейеры организации, а не на один файл.

Именно третий уровень и разбирается в этой практике. Заодно мы
получаем то, чего у функции внутри Jenkinsfile нет: версии, ревью
и возможность откатиться к прежней версии одним изменением строки.

ЧТО ПОЛУЧИТСЯ В КОНЦЕ. Конвейер SiteDeployLibrary, который делает то же,
что SiteDeploy из приложения к практике 11 (раздел Д), но весь выкат
и весь откат — это два вызова шагов библиотеки. Плюс сам репозиторий
библиотеки с версией, README и понятным порядком изменений.


=========================================================================
КАК УСТРОЕНА ОБЩАЯ БИБЛИОТЕКА
=========================================================================

Библиотека — это обычный Git-репозиторий с определённой структурой
каталогов. Jenkins читает её при запуске сборки и делает шаги
библиотеки доступными внутри конвейера.

  vars/       глобальные шаги. Каждый файл с расширением .groovy
              превращается в шаг с именем файла: файл vars/sayHello.groovy
              даёт шаг sayHello. Тело шага — метод call() в этом файле.
              Имя файла должно быть допустимым именем в Groovy: пробелы,
              дефисы и точки в нём невозможны.

  src/        обычные Groovy-классы, как в любом проекте на Groovy:
              с пакетами и каталогами под них. Их не вызывают как шаг,
              их создают через new: new ru.iklimarev.BuildInfo(...).
              Здесь живёт логика — вычисления, разбор данных, проверки.

  resources/  вспомогательные файлы, которые библиотека читает во время
              работы: шаблоны, списки серверов, файлы конфигурации.
              Читаются они не напрямую, а через шаг libraryResource.
              В нашей библиотеке этот каталог не нужен: всё, что мы
              читаем, приходит параметрами.

  tests/      необязательный каталог для тестов самой библиотеки.
              О тестах — в разделе 11.

ПОЧЕМУ ИМЕННО ТАК: разделение vars/ и src/ — не формальность, а ответ
на вопрос «шаг или код». Шаг — это то, что видно в Jenkinsfile как
команда: sayHello, deployToNodes. Класс — это то, что внутри этих
шагов считает и проверяет. Если всё свалить в vars/, каталог
превращается в свалку однотипных шагов с методом call().

ЯЗЫК БИБЛИОТЕКИ — GROOVY, как и сам Jenkinsfile. Внутри шага доступны
штатные шаги конвейера: sh, echo, error, unstable, sshagent, parallel,
script. Их не нужно объявлять или импортировать — шаг библиотеки
выполняется в том же контексте, что и код конвейера.

ОТКУДА JENKINS БЕРЁТ БИБЛИОТЕКУ. Из репозитория, который вы укажете
в настройках. При запуске сборки библиотека выкачивается заново
(с учётом кэша) и кладётся рядом с рабочим каталогом задания —
в каталог с суффиксом @libs. Туда мы посмотрим в разделе 8.

=========================================================================
1. СОЗДАЁМ РЕПОЗИТОРИЙ БИБЛИОТЕКИ В GITEA
=========================================================================

Библиотека — это репозиторий, поэтому начинаем с него.

1.1. Открываем Gitea:

    http://10.0.2.5:3000

Входим под учётной записью engineer (её мы завели в практике 6).
Справа сверху — «+» → New Repository. Заполняем:

  Owner:           engineer
  Repository name: jenkins-shared-library
  Visibility:      Private

Галочки «Initialize repository with README» и «Add .gitignore» снимаем:
первый коммит мы сделаем со своей машины, и пустой репозиторий избавит
нас от разбора конфликтов при первом push.

ЗАЧЕМ PRIVATE, А НЕ PUBLIC: в библиотеке лежит логика выката, адреса
серверов и имена учётных записей. Открытый репозиторий — это подсказка
для того, кто ищет, куда влезть. В рабочей среде библиотеку почти
всегда держат в закрытом репозитории.

1.2. На машине admin проверяем доступ к Gitea по SSH (ключ engineer мы
добавляли в практике 6 в его профиль):

    ssh -T -p 2222 git@10.0.2.5

Ожидаемый ответ — приветствие Gitea с именем пользователя. Если вместо
этого спрашивают пароль или отвечают «Permission denied», вернитесь
к практике 6: без ключа дальше ничего не получится.

ЗАЧЕМ ПРОВЕРЯТЬ ОТДЕЛЬНОЙ КОМАНДОЙ: этот же ключ потом понадобится
самому Jenkins — в виде credentials gitea-reader. Если репозиторий не
читается с машины, он не прочитается и из сборки, а ошибка в сборке
будет выглядеть как «библиотека не найдена».

1.3. Готовим локальный репозиторий:

    cd ~
    mkdir -p jenkins-shared-library
    cd jenkins-shared-library
    git init -b main

    git remote add origin \
        ssh://git@10.0.2.5:2222/engineer/jenkins-shared-library.git

ИСПРАВЛЕНО, И ЭТО ВАЖНАЯ ДЕТАЛЬ: адрес обязательно записывается
в виде ssh://git@10.0.2.5:2222/engineer/jenkins-shared-library.git.
Привычная короткая форма git@10.0.2.5:engineer/jenkins-shared-library.git
не позволит указать порт 2222 и уйдёт на 22-й порт, где Gitea не
слушает. Ровно этот случай разбирался в практике 6; здесь он
встречается второй раз, уже в настройках Jenkins.

1.4. Кладём в репозиторий каталоги и файлы библиотеки. Разложите файлы
из материалов курса (files/shared-library/) так:

    jenkins-shared-library/
    ├── README.md
    ├── vars/
    │   ├── sayHello.groovy
    │   ├── deployToNodes.groovy
    │   └── rollbackNodes.groovy
    └── src/
        └── ru/
            └── iklimarev/
                └── BuildInfo.groovy

    mkdir -p vars src/ru/iklimarev

Структура здесь не декоративна: каталог src обязан повторять пакет.
Класс объявлен как package ru.iklimarev, значит файл должен лежать
в src/ru/iklimarev/BuildInfo.groovy. Перепутаете каталог — класс
не найдётся, и сборка упадёт с ошибкой про отсутствующий класс.

1.5. Пишем README. Библиотека без документации превращается в чёрный
ящик: коллега видит в Jenkinsfile вызов deployToNodes и не понимает,
какие у него параметры и что он делает. В README на каждый шаг должно
быть три вещи: что делает, какие параметры, пример вызова.

Минимальный README для нашей библиотеки:

    jenkins-shared-library

    Общая библиотека конвейеров лаборатории.
    Подключение: @Library('lab-shared-library@main') _

    Шаги (каталог vars/)

      sayHello(name)          приветствие и сведения о сборке
      deployToNodes(config)   выкат каталога на несколько серверов
      rollbackNodes(config)   откат на предыдущий релиз

    sayHello — параметры

      name           имя, которое подставляется в приветствие;
                     по умолчанию 'DevOps'

    Пример вызова

      sayHello('SiteDeployLibrary')

    Других параметров у шага нет: кроме приветствия он печатает имя
    агента и номер сборки.

    deployToNodes — параметры

      hosts          список адресов; по умолчанию 10.0.2.13 и 10.0.2.14
      siteDir        каталог выката на агенте, по умолчанию build/deploy
      deployUser     пользователь на сервере, по умолчанию jenkins
      expectedText   текст, который должен вернуть сайт; по умолчанию
                     'Hello from DevOps Engineer'
      buildNumber    номер сборки, по умолчанию номер текущей
      credentialsId  идентификатор ключа, по умолчанию node-ssh

    Пример вызова

      deployToNodes(
          hosts: ['10.0.2.13', '10.0.2.14'],
          siteDir: 'build/deploy',
          buildNumber: env.BUILD_NUMBER
      )

    rollbackNodes — параметры

      hosts          список адресов; по умолчанию пустой список, и тогда
                     шаг просто сообщает, что откатывать нечего
      buildNumber    номер сборки, по умолчанию номер текущей
      deployUser     пользователь на сервере, по умолчанию jenkins
      credentialsId  идентификатор ключа, по умолчанию node-ssh
      ignoreErrors   при значении true (по умолчанию) неудачный откат
                     не прерывает сборку, а помечает её нестабильной

    Пример вызова

      rollbackNodes(hosts: ['10.0.2.13', '10.0.2.14'])

    Классы (каталог src/)

      ru.iklimarev.BuildInfo  сведения о сборке для журнала

В рабочем репозитории README.md оформляют разметкой Markdown — Gitea
его отобразит. Содержание от этого не меняется: что за шаг, какие
параметры, пример вызова.

1.6. Первый коммит и push:

    git add -A
    git commit -m "первая версия библиотеки: sayHello, deployToNodes, rollbackNodes"
    git push -u origin main

1.7. Ставим тег версии:

    git tag -a v1.0.0 -m "первая рабочая версия библиотеки"
    git push origin v1.0.0

УТОЧНЕНО: тег создаётся с ключом -a (annotated tag) — у такого тега есть
автор, дата и сообщение, и по нему позже можно понять, что в него вошло.
Отдельная команда push нужна потому, что git push по умолчанию теги
не отправляет: git push --tags отправит все, а git push origin v1.0.0 —
только этот.

ЗАЧЕМ ТЕГ УЖЕ СЕЙЧАС, если библиотекой никто, кроме нас, не пользуется:
привычка. Тег — это единственный способ сказать «вот это состояние
проверено и работает». Конвейеры, которым нужна стабильность, будут
ссылаться именно на тег, а не на ветку main. Подробно — раздел 9.


=========================================================================
2. ПОДКЛЮЧАЕМ БИБЛИОТЕКУ В JENKINS
=========================================================================

Открываем портал и идём по адресу настройки:

    Manage Jenkins → System → Global Pipeline Libraries

Здесь пока пусто. Нажимаем Add и заполняем поля.

  Name: lab-shared-library

  Это имя, под которым библиотеку будут знать конвейеры. Именно оно
  пишется в строке @Library('lab-shared-library@main'). Имя —
  произвольное, но менять его потом больно: придётся править все
  Jenkinsfile. Пишите так, как будете писать в конвейерах.

  Default version: main

  Ветка или тег, которые Jenkins берёт, когда конвейер не указал версию
  явно. У нас ветка называется main (не master, как в старых
  руководствах), поэтому здесь именно main.

  [x] Allow default version to be overridden

  Галочка разрешает конвейеру запросить другую версию:
  @Library('lab-shared-library@v1.0.0'). Без неё Jenkins молча
  проигнорирует указанную в конвейере версию и возьмёт default —
  то есть зафиксировать версию в Jenkinsfile будет невозможно.

  [ ] Load implicitly

  Включённая галочка означает, что библиотека подключается ко ВСЕМ
  конвейерам Jenkins автоматически, без строки @Library.

  ПОЧЕМУ МЫ ЭТО НЕ ВКЛЮЧАЕМ, хотя выглядит удобно:
    * библиотека начинает влиять на все конвейеры сразу, включая
      учебные задания и чужие эксперименты;
    * из Jenkinsfile исчезает главное — видно ли, откуда взялся шаг.
      Читающий файл не понимает, где объявлен deployToNodes;
    * конфликт имён: глобальный шаг из библиотеки может совпасть
      с шагом другого плагина или с методом самого конвейера;
    * ошибка в библиотеке ломает всё сразу, а не один конвейер.
  Включайте Load implicitly только осознанно и для библиотеки, которую
  действительно должны видеть все.

  Retrieval method: Modern SCM

  Способ хранения. Modern SCM означает, что библиотека лежит в обычном
  репозитории и её адрес описывается средствами Jenkins. Есть ещё
  Legacy SCM (исторический вариант) — нам он не нужен.

  Source Code Management: Git

  Project Repository: ssh://git@10.0.2.5:2222/engineer/jenkins-shared-library.git

  Credentials: gitea-reader

  SSH-ключ, которым Jenkins читает репозиторий. Это ключ, добавленный
  в Gitea для служебного пользователя git (практика 6) — тот же самый,
  что читает репозиторий сайта. Отдельный ключ для библиотеки не нужен.

  Library Path (optional): оставляем пустым

  Поле нужно, когда библиотека лежит в подкаталоге репозитория, а рядом
  с ней что-то ещё. У нас vars/ и src/ лежат прямо в корне репозитория.

  [x] Include @Library changes in job recent changes

  Изменения библиотеки будут показаны в списке изменений сборки. Это
  мелочь, которая экономит время при разборе: сразу видно, что между
  двумя сборками поменялась не только страница сайта, но и библиотека.

Нажимаем Save. Перезапускать Jenkins не нужно: настройка читается при
следующем запуске конвейера.

ПРАВИЛО, КОТОРОЕ СТОИТ ЗАПОМНИТЬ: библиотека подключается по имени,
а не по адресу. Jenkins ищет имя в этом списке, и если его там нет,
сборка падает с сообщением «Library lab-shared-library not found» —
даже когда репозиторий доступен и файлы на месте. Опечатка в поле Name
или в строке @Library даёт одну и ту же ошибку.


=========================================================================
3. ИСПОЛЬЗУЕМ БИБЛИОТЕКУ В КОНВЕЙЕРЕ
=========================================================================

Открываем файл files/pipelines/Jenkinsfile.library. Его первая значимая
строка:

    @Library('lab-shared-library@main') _

Это не комментарий и не команда Jenkins — это аннотация Groovy, которая
говорит Jenkins: перед запуском конвейера загрузи библиотеку с именем
lab-shared-library версии main.

ПОЧЕМУ В КОНЦЕ СТОИТ ПОДЧЁРКИВАНИЕ. Аннотация в Groovy должна быть
к чему-то привязана — к объявлению или к выражению. Одиночное
подчёркивание и есть такое пустое выражение-заглушка: аннотации есть
к чему относиться, а самому конвейеру ничего не мешает.

Если подчёркивание забыть, аннотация привяжется к следующей
конструкции (в нашем случае — к вызову pipeline), и вместо запуска
конвейера вы получите ошибку разбора скрипта. Сообщение об этом
неочевидное: unexpected token: @Library. Об этом же — в разделе 14.

ВАЖНО: аннотация должна стоять до первого оператора скрипта. Комментарии
перед ней допустимы — в нашем файле там блочный комментарий с описанием.
А вот если поставить @Library после pipeline {, ничего не выйдет: для
Groovy это уже не аннотация, а мусор в середине файла.

УТОЧНЕНО: есть второй способ — шаг library, который подключает
библиотеку во время выполнения: script { library 'lab-shared-library@main' }.
Он нужен там, где версия вычисляется на ходу (например, выбирается
параметром). У аннотации преимущество: версия видна в первой строке
файла, и её невозможно не заметить при чтении Jenkinsfile.

Разберём файл по стадиям. Отступы в примерах ниже местами уменьшены,
чтобы строки помещались в ширину страницы; в самих файлах отступы
стандартные.

    pipeline {
        agent { label 'web' }
        ...
        stages {
            stage('1. Забрать код') {
                steps {
                    deleteDir()
                    checkout scm
                }
            }

Дальше — стадия сборки каталога выката. В ней два шага: сначала шаг
из библиотеки, потом обычный shell:

            stage('2. Собрать каталог выката') {
                steps {
                    sayHello env.JOB_NAME
                    sh '''
                        set -eu
                        ...
                    '''
                }
            }

sayHello — шаг из библиотеки. Выглядит как штатный шаг Jenkins, и это
главное свойство библиотеки: снаружи не видно, откуда он взялся.
Аргументом передаётся имя задания: шаг напечатает приветствие, имя
агента и номер сборки. В блоке sh стоит обычный текст в одинарных
тройных кавычках — Groovy такие строки не подставляет, поэтому все
${SITE_DIR} и ${BUILD_NUMBER} разбирает shell.

Стадия выката — та самая, ради которой всё затевалось:

            stage('3. Выкатить на все серверы') {
                steps {
                    deployToNodes(
                        hosts: (env.WEB_NODES ?: params.WEB_NODES).split(' ') as List,
                        siteDir: env.SITE_DIR,
                        expectedText: env.EXPECTED_TEXT,
                        buildNumber: env.BUILD_NUMBER
                    )
                }
            }

Сравните с конвейером без библиотеки: там по стадии на каждый сервер,
здесь одна стадия и один вызов. Серверы передаются списком, полученным
из параметра WEB_NODES, — добавление третьего сервера означает правку
значения параметра по умолчанию, а не новую стадию.

Стадия 4 показывает класс из каталога src:

            stage('4. Показать итог') {
                steps {
                    script {
                        def info = new ru.iklimarev.BuildInfo(
                            job: env.JOB_NAME,
                            buildNumber: env.BUILD_NUMBER,
                            commit: sh(script: 'git rev-parse --short HEAD',
                                      returnStdout: true).trim(),
                            agent: env.NODE_NAME
                        )
                        echo info.summary()
                    }
                }
            }

Класс вызывается через new и полное имя с пакетом. В декларативном
конвейере произвольный Groovy-код живёт внутри блока script — это
относится и к созданию объекта, и к вызову его методов.

И последнее место, где работает библиотека, — блок post:

        post {
            failure {
                script {
                    rollbackNodes(
                        hosts: (params.WEB_NODES).split(' ') as List,
                        buildNumber: env.BUILD_NUMBER
                    )
                }
            }
        }

ОТДЕЛЬНО ОБРАТИТЕ ВНИМАНИЕ: выкат и откат — теперь не код конвейера,
а два вызова шагов библиотеки, и в этом смысл вынесения. При этом файл
не является копией конвейера из практики 11. В него не перенесены
предполётная проверка страницы (стадия «3. Проверить до выката») и
archiveArtifacts, а в стадии сборки не создаётся build-info.txt: эти
вещи разбирались отдельно в практике 10, а здесь важно сравнить именно
дублирование выката, поэтому в Jenkinsfile.library оставлен минимум.
Проверка снаружи тоже заменена: её делает шаг библиотеки, но локально
на каждом сервере — об этом в разделе 4.


=========================================================================
4. РАЗБИРАЕМ ШАГ DEPLOYTONODES ПОСТРОЧНО
=========================================================================

Открываем files/shared-library/vars/deployToNodes.groovy. Первая строка:

    def call(Map config = [:]) {

Шаг принимает один параметр — Map, то есть набор именованных значений.
Так делают почти все шаги библиотек, и вот почему: набор параметров
у разных конвейеров разный, а вызов с именами читается сам по себе:

    deployToNodes(hosts: [...], siteDir: 'build/deploy')

Значение по умолчанию [:] (пустая карта) означает, что шаг можно
вызвать вообще без аргументов.

Дальше идут значения по умолчанию:

    List hosts = (config.hosts ?: ['10.0.2.13', '10.0.2.14']) as List
    String siteDir = (config.siteDir ?: 'build/deploy') as String
    String deployUser = (config.deployUser ?: 'jenkins') as String
    String expectedText =
        (config.expectedText ?: 'Hello from DevOps Engineer') as String
    String buildNumber = (config.buildNumber ?: env.BUILD_NUMBER) as String
    String credentialsId = (config.credentialsId ?: 'node-ssh') as String

ПОЧЕМУ ЭТО НЕ ЛЕНЬ, А НЕОБХОДИМОСТЬ. Шаг из общей библиотеки вызывают
десятки конвейеров, часть из которых вы не видели. Если сделать
параметр обязательным, все они сломаются в один момент — причём не
у вас, а у коллег, и в самый неподходящий день. Поэтому новый параметр
добавляют со значением по умолчанию, а поведение по умолчанию
сохраняют прежним. Это правило обратной совместимости, и оно главное
в работе с библиотекой.

Оператор ?: (элвис) означает «взять левое, а если оно пустое — правое».
Пустым считается null, пустая строка, пустая коллекция и ноль.

Приведение типов (as List, as String) — защита от того, что придёт
из конвейера. Список серверов может прийти как List, как массив
String[] после split(), а номер сборки — как GString (строка
с подстановкой). Дальше по коду мы хотим работать с обычными типами,
поэтому приводим их сразу, на входе, а не в середине логики.

ОБРАТИТЕ ВНИМАНИЕ: строка и список — разные вещи. Строку
'10.0.2.13 10.0.2.14' шаг не разберёт на адреса. Её делят до вызова,
как в нашем Jenkinsfile: (params.WEB_NODES).split(' ') as List.

Следующий блок — проверка и первый вывод в журнал:

    if (hosts.isEmpty()) {
        error 'deployToNodes: не передан ни один сервер'
    }
    echo "Выкат сборки ${buildNumber} на серверы: ${hosts.join(', ')}"

error — штатный шаг Jenkins, который останавливает сборку с сообщением.
Лучше упасть сразу, чем пройти половину выката и выяснить, что список
серверов пуст. echo с hosts.join(', ') печатает адреса одной строкой:
в журнале сразу видно, куда идёт выкат и какой номер сборки.

Теперь самое интересное — сборка параллельных веток. Приводим этот код
целиком: карта веток, тело одной ветки и запуск веток на выполнение.
Проверку на сервере покажем дальше — она внутри того же блока sh.

    Map branches = [:]
    hosts.each { rawHost ->
        String host = rawHost as String
        branches["выкат на ${host}"] = {
            sshagent(credentials: [credentialsId]) {
                sh """
                set -eu
                target=/tmp/site-deploy-${buildNumber}

                ssh -o StrictHostKeyChecking=accept-new \\
                    ${deployUser}@${host} "rm -rf \${target} && mkdir -p \${target}"

                rsync -a --delete -e "ssh -o StrictHostKeyChecking=accept-new" \\
                    ${siteDir}/ ${deployUser}@${host}:\${target}/

                ssh -o StrictHostKeyChecking=accept-new ${deployUser}@${host} \\
                    "cd \${target} && bash deploy_site.sh deploy www"
                ...
                """
            }
        }
    }

    parallel branches

Разберём по частям.

  sshagent(credentials: [credentialsId]) — подключает приватный ключ
  node-ssh в ssh-agent на время работы блока. Текст ключа при этом
  не попадает ни в переменные окружения сборки, ни в журнал: конвейер
  вообще не знает его содержимого.

  ПОЧЕМУ SSHAGENT ВНУТРИ ВЕТКИ, А НЕ СНАРУЖИ: ветки идут параллельно,
  каждая выполняется в своём потоке и со своим окружением. Ключ,
  подключённый один раз снаружи, доступен не всем веткам одинаково
  надёжно, поэтому sshagent стоит в каждой ветке.

  sh """ ... """ — тройные двойные кавычки означают, что Groovy сам
  подставляет значения: ${buildNumber}, ${deployUser}, ${host},
  ${siteDir}. Это и есть механизм передачи параметров в команды.

  \\ (двойная обратная косая черта) в конце строки — перенос длинной
  команды shell. В файле Groovy она пишется двойной, потому что
  одинарная уже занята самим Groovy.

  \${target} — экранирование. Здесь нам нужна НЕ подстановка Groovy,
  а переменная shell, которая живёт на агенте. Если написать ${target}
  без косой черты, Groovy попытается найти переменную target в конвейере
  и упадёт с сообщением про отсутствующее свойство. Это одна из самых
  частых ошибок при написании шагов библиотеки.

  rm -rf && mkdir -p — каталог выката на сервере создаётся заново,
  чтобы не тащить в новую сборку мусор от прежних.

  rsync -a --delete — копирует каталог выката на сервер. Ключ --delete
  убирает на сервере то, чего больше нет в сборке. Косая черта в конце
  ${siteDir}/ означает «содержимое каталога», а не «каталог целиком».

  deploy_site.sh deploy www — тот самый скрипт из практики 11. Именно
  он переключает симлинк и делает выкат атомарным; копирование файлов
  само по себе сайт не обновляет.

Завершает ветку проверка на самом сервере — это продолжение того же
блока sh, который показан выше:

                ssh -o StrictHostKeyChecking=accept-new ${deployUser}@${host} \\
                    "bash \${target}/smoke_test.sh http://127.0.0.1/ \\
                     '${expectedText}' ${buildNumber}"

                echo "сервер ${host}: выкат и проверка пройдены"

Проверка идёт по адресу http://127.0.0.1/ — то есть на самой машине,
через её собственный nginx. Так проверяется ровно то, что нужно знать
после выката: отдаёт ли веб-сервер новую версию. Сетевые задержки,
прокси и прочие посредники в этой проверке не участвуют.

О ключе -o StrictHostKeyChecking=accept-new: он разрешает подключиться
к серверу, которого ещё нет в файле known_hosts, и запоминает его ключ.
Для лаборатории это удобно. В рабочей среде так делать не стоит:
правильнее один раз положить отпечатки серверов в known_hosts, иначе
подмена сервера не будет замечена.

ЗАЧЕМ parallel СТОИТ ОТДЕЛЬНОЙ СТРОКОЙ, А НЕ В КОНЦЕ ЦИКЛА: parallel —
шаг конвейера, и он выполняется после того, как карта веток собрана
целиком (та самая карта, которую мы разобрали в начале раздела). Одна
упавшая ветка останавливает шаг целиком, и это правильное поведение:
выкат на половину серверов хуже, чем неудачный выкат, потому что
серверы начинают отдавать разные версии сайта.


=========================================================================
5. ЛОВУШКА: ЗАХВАТ ПЕРЕМЕННОЙ ЦИКЛА В ЗАМЫКАНИИ
=========================================================================

Выше была строка, которую легко счесть украшением:

    String host = rawHost as String

На самом деле это защита от ошибки, которая в Groovy встречается
постоянно и стоит дорого. Смысл в одной фразе: замыкание запоминает
не значение переменной, а саму переменную. Когда ветки начнут
выполняться, они прочитают у этой переменной то, что в ней лежит
в момент выполнения, — то есть последнее значение.

Как выглядит ошибка (так писать нельзя):

    hosts.each { rawHost ->
        branches["выкат на ${rawHost}"] = {
            echo "выкат на ${rawHost}"
        }
    }

Как выглядит правильно:

    hosts.each { rawHost ->
        String host = rawHost as String
        branches["выкат на ${host}"] = {
            echo "выкат на ${host}"
        }
    }

Разница только в одной строке: в первом варианте все замыкания смотрят
на одну переменную цикла, во втором у каждой ветки своя переменная,
созданная внутри итерации.

ПОЧЕМУ ЭТУ ОШИБКУ ТАК ТРУДНО ЗАМЕТИТЬ. Имя ветки вычисляется сразу,
при наполнении карты, а команды внутри замыкания — потом. Поэтому
в интерфейсе и в журнале будут честно показаны обе ветки:
«выкат на 10.0.2.13» и «выкат на 10.0.2.14». А в самих ветках rsync
уйдёт на один и тот же адрес — на последний из списка.

Получается худший из возможных сценариев: сборка зелёная, обе ветки
успешны, проверка на сервере тоже успешна (она проверяет тот же
последний сервер), а первый сервер остался на прежней версии. Ошибка
обнаруживается через день, когда кто-то открывает сайт и видит старую
страницу.

КАК ЛОВИТЬ: после любого шага, который выкатывает на несколько
серверов, открывать ВСЕ страницы, а не одну. У нас это
http://10.0.2.13/ и http://10.0.2.14/ — на каждой должен быть номер
последней сборки.

ОБРАТИТЕ ВНИМАНИЕ: та же природа у похожих ошибок с циклом for и с
вычислением путей внутри замыканий. Правило простое: если замыкание
создаётся в цикле и использует переменную цикла (или любую другую
переменную, которая меняется), скопируйте значение в отдельную
локальную переменную внутри итерации.


=========================================================================
6. РАЗБИРАЕМ ШАГ ROLLBACKNODES
=========================================================================

Открываем files/shared-library/vars/rollbackNodes.groovy. Логика отката
в этом шаге отдельная, хотя могла бы быть частью выката.

ЗАЧЕМ ОТДЕЛЬНЫЙ ШАГ:
  * откат вызывается при провале конвейера — из блока post;
  * откат вызывают вручную: инженер видит проблему и запускает откат,
    не пересобирая проект;
  * откат вызывают из другого конвейера (например, из ночного
    дежурного задания, которое проверяет сайты и возвращает
    предыдущую версию, если проверка не прошла).
Три разных места — одна логика. Правка тоже одна.

Разберём код.

    def call(Map config = [:]) {
        List hosts = (config.hosts ?: []) as List
        String buildNumber = (config.buildNumber ?: env.BUILD_NUMBER) as String
        String deployUser = (config.deployUser ?: 'jenkins') as String
        String credentialsId = (config.credentialsId ?: 'node-ssh') as String
        boolean ignoreErrors =
            config.containsKey('ignoreErrors') ? (config.ignoreErrors as boolean) : true

Здесь два интересных места.

ПОЧЕМУ У HOSTS ПО УМОЛЧАНИЮ ПУСТОЙ СПИСОК. Шаг вызывают из блока post,
а блок post выполняется при любом исходе. Если серверы не переданы
(например, конвейер упал раньше, чем получил параметры), шаг не должен
падать сам — откатывать просто нечего:

    if (hosts.isEmpty()) {
        echo 'rollbackNodes: серверы не переданы, откатывать нечего'
        return
    }

return из метода call() завершает шаг без ошибки. Это важно: падение
отката в блоке post затрёт настоящую причину провала сборки.

ПОЧЕМУ ДЛЯ ignoreErrors НУЖЕН containsKey. Обычное решение
(config.ignoreErrors ?: true) здесь не работает: в Groovy значение
false считается «пустым», и явно переданный false превратился бы
в true. А нам нужно различать «параметр не передали» и «передали
false» — поэтому проверяется наличие ключа в карте.

Дальше — сбор неудач:

    echo "Откат на серверы: ${hosts.join(', ')}"
    List failed = []

    sshagent(credentials: [credentialsId]) {
        hosts.each { rawHost ->
            String host = rawHost as String
            def result = sh(
                script: """
                    set -u
                    target=/tmp/site-deploy-${buildNumber}
                    if [ ! -f "\${target}/deploy_site.sh" ]; then
                        echo "нет скрипта выката в \${target} — откат пропущен"
                        exit 0
                    fi
                    ssh -o StrictHostKeyChecking=accept-new ${deployUser}@${host} \\
                        "bash \${target}/deploy_site.sh rollback"
                """,
                returnStatus: true
            )
            if (result != 0) {
                failed << host
                echo "откат на ${host} не удался (код ${result})"
            } else {
                echo "откат на ${host} выполнен"
            }
        }
    }

Здесь стоит остановиться на трёх решениях.

ПЕРВОЕ: returnStatus: true. Обычный sh при ненулевом коде возврата
сразу прерывает сборку исключением. С returnStatus: true шаг возвращает
код как число, и мы можем продолжить работу — перейти к следующему
серверу. Именно это и нужно откату.

ПОЧЕМУ ОШИБКИ СОБИРАЮТСЯ В СПИСОК, А НЕ ПРЕРЫВАЮТ РАБОТУ СРАЗУ.
Откат — аварийная операция, и его задача — вернуть рабочую версию
везде, где это получится. Если прерваться на первом недоступном
сервере, остальные останутся на новой версии, то есть в самом плохом
состоянии: часть серверов отдаёт одну страницу, часть другую. Поэтому
попытки идут до конца, а неудачи собираются в список failed и о них
сообщается в конце.

ВТОРОЕ: sshagent здесь один на весь цикл, а не внутри каждой итерации,
как в deployToNodes. Причина в том, что этот цикл последовательный:
подключать ключ заново на каждой итерации незачем.

ТРЕТЬЕ: в шаге нет parallel. Откат выполняется по серверам по очереди.
Так сделано осознанно: откат — редкая и аварийная операция, скорость
здесь не важна, а последовательный журнал читается без путаницы.
Плюс parallel останавливает все ветки при первой неудаче, а нам нужно
ровно обратное — довести попытки до конца.

Итог шага:

    if (failed && !ignoreErrors) {
        error "откат не выполнен на серверах: ${failed.join(', ')}"
    }
    if (failed) {
        unstable("откат не выполнен на серверах: ${failed.join(', ')}")
    }

ПОЧЕМУ unstable, А НЕ failure. Сборка, из-за которой вызвали откат,
уже помечена как проваленная — её провалил шаг выката. Наша задача
не переписать диагноз, а добавить информацию: «кроме того, откат
не везде прошёл, этим нужно заняться руками». Статус UNSTABLE говорит
именно это: сборка завершилась, но с замечанием.

УТОЧНЕНО: если сборка уже провалена, unstable её статус не изменит —
провал остаётся провалом. А вот при ручном запуске отката, когда всё
остальное прошло хорошо, сборка получит именно жёлтый статус вместо
зелёного, и это правильно: работа выполнена не полностью.


=========================================================================
7. РАЗБИРАЕМ КЛАСС BUILDINFO (КАТАЛОГ SRC)
=========================================================================

Открываем files/shared-library/src/ru/iklimarev/BuildInfo.groovy.

ЧЕМ SRC ОТЛИЧАЕТСЯ ОТ VARS. Шаг из vars/ — это команда конвейера:
имя файла становится именем шага, метод call() становится его телом.
Класс из src/ — обычный Groovy-класс: его не вызывают как шаг, его
создают через new. Он не появляется в конвейере как отдельная команда
и не виден в списке шагов.

Держать логику в vars/ неудобно: шаг обязан быть одним методом call(),
и он быстро превращается в длинный метод, который заодно считает,
проверяет и форматирует. Класс для этого и нужен — у него есть поля,
конструкторы и столько методов, сколько нужно.

Класс начинается с объявления пакета:

    package ru.iklimarev

    class BuildInfo implements Serializable {
        private static final long serialVersionUID = 1L

        String job = 'unknown'
        String buildNumber = '0'
        String commit = 'unknown'
        String agent = 'unknown'

Пакет задаёт полное имя класса: ru.iklimarev.BuildInfo. Именно так
он и вызывается в конвейере:

    def info = new ru.iklimarev.BuildInfo(job: env.JOB_NAME, ...)

ПОЧЕМУ КОНСТРУКТОР ИЗ MAP. Второй конструктор класса принимает карту:

    BuildInfo(Map values) {
        if (values?.job)         { this.job = values.job as String }
        if (values?.buildNumber) { this.buildNumber = values.buildNumber as String }
        if (values?.commit)      { this.commit = values.commit as String }
        if (values?.agent)       { this.agent = values.agent as String }
    }

В Groovy запись new BuildInfo(job: 'x', agent: 'y') — это вызов
конструктора с картой именованных аргументов. Такой конструктор удобен
по той же причине, что и Map в шаге: параметры можно добавлять, не
меняя все вызовы. Знак ?. — безопасная навигация: если карта не
передана вовсе, обращения к её полям не будет.

ЗАЧЕМ ОБЯЗАТЕЛЬНО Serializable. Конвейер Jenkins может приостановить
выполнение и записать своё состояние на диск: на стадии с ручным
подтверждением, при перезапуске Jenkins в момент сборки, при
параллельных ветках. Всё, что лежит в переменных конвейера, должно
уметь превращаться в байты и обратно. Несериализуемый объект ломает
это, причём сообщение об ошибке выглядит загадочно:

    java.io.NotSerializableException: ru.iklimarev.BuildInfo

Поэтому implements Serializable — не формальность, а требование
платформы. Поле serialVersionUID задаёт версию формата: если класс
изменится, старая запись не будет прочитана неправильно.

Дальше два метода.

    String summary() {
        return """
    Сборка ${job} #${buildNumber}
      ревизия : ${commit}
      агент   : ${agent}
    """.trim()
    }

summary() собирает текст для журнала сборки: имя задания, номер, ревизия
и агент — то, что нужно человеку, который через месяц открывает журнал
и хочет понять, что именно выкатывали. Метод возвращает строку, а печатает
её уже конвейер через echo info.summary(). Такой подход удобнее, чем echo
внутри класса: то же описание можно положить в файл, отправить в артефакт
или добавить в уведомление.

    boolean isComplete() {
        return job != 'unknown' && commit != 'unknown' && buildNumber != '0'
    }

isComplete() проверяет, что данные собраны: имя задания известно,
ревизия определена (а не осталась значением по умолчанию 'unknown'),
номер сборки не нулевой.

ОБРАТИТЕ ВНИМАНИЕ: в Jenkinsfile.library мы вызываем только summary().
isComplete() в библиотеке есть для случая, когда конвейер хочет
проверить данные перед выкатом. Выглядит это так (фрагмент, добавлять
его в конвейер не обязательно):

    script {
        def info = new ru.iklimarev.BuildInfo(
            job: env.JOB_NAME,
            buildNumber: env.BUILD_NUMBER,
            commit: sh(script: 'git rev-parse --short HEAD',
                      returnStdout: true).trim(),
            agent: env.NODE_NAME
        )
        if (!info.isComplete()) {
            error 'не удалось определить ревизию сборки — выкат остановлен'
        }
        echo info.summary()
    }

Смысл проверки простой: если ревизию определить не удалось, значит,
что-то не так с рабочим каталогом, и выкатывать такое не стоит.
Дешевле остановиться, чем потом выяснять, какая версия уехала на сайт.

8. ПРОВЕРЯЕМ РЕЗУЛЬТАТ

8.1. Сначала положим Jenkinsfile в репозиторий сайта — как в практиках
10 и 11:

    cd ~/site
    cp <материалы курса>/files/pipelines/Jenkinsfile.library \

(Путь к материалам курса подставьте свой; каталог клона репозитория
сайта у вас тоже может называться иначе. Файл должен оказаться
в репозитории именно по пути files/pipelines/Jenkinsfile.library —
этот путь мы укажем в задании.)

8.2. Создаём задание: New Item → имя SiteDeployLibrary → Pipeline → OK.
В разделе Pipeline выбираем Pipeline script from SCM и заполняем:

    SCM:               Git
    Repository URL:    ssh://git@10.0.2.5:2222/engineer/site.git
    Credentials:       gitea-reader
    Branch Specifier:  */main
    Script Path:       files/pipelines/Jenkinsfile.library

Сохраняем и запускаем Build with Parameters, оставив SITE_VERSION=v1.

8.3. Что смотреть в журнале сборки.

Первое — приветствие из библиотеки:

    Привет, SiteDeployLibrary! Это шаг из общей библиотеки лаборатории.
    Выполняется на агенте: node1, сборка 3

Второе — начало выката и обе ветки:

    Выкат сборки 3 на серверы: 10.0.2.13, 10.0.2.14
    [Pipeline] parallel
    [выкат на 10.0.2.13] ...
    [выкат на 10.0.2.14] ...
    сервер 10.0.2.13: выкат и проверка пройдены
    сервер 10.0.2.14: выкат и проверка пройдены

Третье — итог от класса из src/:

    Сборка SiteDeployLibrary #3
      ревизия : a1b2c3d
      агент   : node1

8.4. Проверяем сайт на обоих серверах:

    curl -s http://10.0.2.13/ | grep -i 'сборка'
    curl -s http://10.0.2.14/ | grep -i 'сборка'

На обеих страницах должен быть номер только что выполненной сборки.
ОБЯЗАТЕЛЬНО на обеих: именно так обнаруживается ловушка из раздела 5.

8.5. Сравниваем с журналом версии без библиотеки. Откройте любую
сборку задания SiteDeploy (оно создаётся в приложении к практике 11,
раздел Д) и найдите список стадий:

    SiteDeploy:            4. Выкатить сайт → node1 (10.0.2.13)
                                            → node2 (10.0.2.14)
    SiteDeployLibrary:     3. Выкатить на все серверы → выкат на 10.0.2.13
                                                     → выкат на 10.0.2.14

В первом случае параллельные стадии описаны в самом конвейере: сколько
серверов, столько стадий. Во втором — одна стадия, внутри которой шаг
библиотеки сам построил ветки по переданному списку. Это и есть
выигрыш в поддержке.

ВАЖНО, И ЭТО ЧЕСТНОЕ ОТЛИЧИЕ: конвейеры не эквивалентны по набору
стадий. В Jenkinsfile.library нет предполётной проверки страницы и
archiveArtifacts, а build-info.txt не создаётся; проверка снаружи
заменена локальной проверкой внутри deployToNodes. Поэтому сравнивайте
не «какой конвейер лучше», а одно и то же действие — выкат: в первом
файле он размножен по стадиям, во втором это один вызов шага.

8.6. Смотрим, где Jenkins держит библиотеку. Рядом с рабочим каталогом
задания появляется каталог с суффиксом @libs:

  ssh node1 'ls -d /home/jenkins/agent/workspace/*@libs'
  ssh node1 'ls /home/jenkins/agent/workspace/SiteDeployLibrary@libs/*/'
  ssh node1 'ls /home/jenkins/agent/workspace/SiteDeployLibrary@libs/*/lab-shared-library/vars'

ОБРАТИТЕ ВНИМАНИЕ на устройство этого каталога: сам @libs — не копия
репозитория. Внутри него лежит подкаталог с хешем (Jenkins складывает
туда версии библиотеки и не смешивает их между собой), а уже в нём —
каталог с именем библиотеки, в нашем случае lab-shared-library. В нём
и находятся каталоги vars и src. Если искать vars сразу в @libs,
команда ответит «No such file or directory».

Здесь же становится понятна одна из причин, по которой правки
в библиотеке иногда «не применяются»: Jenkins держит рядом готовую
копию и обновляет её по своим правилам.

ЗАЧЕМ ЭТО ЗНАТЬ: рабочий каталог агента — единственное место, где
видно, какая версия библиотеки реально использовалась в конкретной
сборке. Когда сборки начнут вести себя по-разному без видимых причин,
сравнение файлов в @libs двух агентов даёт ответ быстрее, чем чтение
журналов.

Если сборка запускается на самом контроллере (например, в задании
с agent any и без меток), тот же каталог будет лежать в
/var/lib/jenkins/workspace/<имя задания>@libs. У нас конвейер идёт на
метку web, поэтому ищем на агентах — на node1 или node2, смотря где
выполнялась сборка.

=========================================================================
9. ВЕРСИОНИРОВАНИЕ БИБЛИОТЕКИ
=========================================================================

Это тема, которую игнорируют чаще всего, а она важнее кода. Библиотека
без версий — это общий изменяемый объект: сегодня поведение одно,
завтра другое, и никто не знает, что именно поменялось.

ТРИ СПОСОБА УКАЗАТЬ ВЕРСИЮ

  1. Версия по умолчанию из настроек Jenkins. Конвейер пишет
     @Library('lab-shared-library') _, и Jenkins берёт версию из поля
     Default version — у нас это ветка main.

  2. Явная версия в конвейере:

         @Library('lab-shared-library@v1.0.0') _

     Работает, потому что в настройках стоит галочка Allow default
     version to be overridden. В качестве версии годится тег, ветка или
     даже хеш коммита.

  3. Версия по умолчанию задаётся тегом вместо ветки: в поле Default
     version пишут v1.0.0. Тогда все конвейеры без явной версии
     получают зафиксированное состояние.

ПОЧЕМУ ССЫЛКА НА MAIN ОПАСНА. main — это движущаяся точка. Любой
коммит в библиотеку меняет поведение всех конвейеров, которые на неё
ссылаются, и происходит это без единой правки в их Jenkinsfile.
Сборка, которая вчера проходила, сегодня может упасть — причём
причина будет не в проекте и не в серверах, а в библиотеке, которую
кто-то поправил.

Формулировка, которую стоит помнить: @Library('...@main') означает
«в любой момент поведение может измениться само».

СТРАТЕГИЯ ИЗМЕНЕНИЙ, КОТОРАЯ РАБОТАЕТ

  * ПО УМОЛЧАНИЮ — ТОЛЬКО ОБРАТНАЯ СОВМЕСТИМОСТЬ. Новый параметр
    добавляется со значением по умолчанию, поведение старых вызовов
    не меняется. Тогда новая версия библиотеки безопасна для всех:
    конвейеры, которые ничего не знают о новом параметре, работают
    как раньше.

  * ЛОМАЮЩИЕ ИЗМЕНЕНИЯ — ТОЛЬКО В НОВОЙ МАЖОРНОЙ ВЕРСИИ. Если нужно
    поменять имя шага, смысл параметра или убрать шаг, это версия 2.0.0,
    и переход на неё делают осознанно, конвейер за конвейером.

  * ТЕГ НА КАЖДОЕ ЗАМЕТНОЕ ИЗМЕНЕНИЕ. Тег — это точка, к которой можно
    вернуться. Без тегов откат невозможен в принципе: непонятно, к чему
    откатываться.

КАК ОТКАТИТЬ БИБЛИОТЕКУ, ЕСЛИ ОНА СЛОМАЛА ВСЁ

Ситуация типовая: вышла новая версия, утром сорок конвейеров падают
на одном и том же месте. Действовать нужно быстро и в таком порядке:

  1. Вернуть прежнее поведение одним движением. Если конвейеры
     используют версию по умолчанию, поменяйте Default version
     на прежний тег: Manage Jenkins → System → Global Pipeline Libraries
     → Default version: v1.0.0 → Save. Новые сборки снова используют
     прежний код, перезапуск Jenkins не нужен.

  2. Если часть конвейеров ссылается на библиотеку явно
     (@Library('...@v2.0.0')), им Default version не поможет — версию
     правят в их Jenkinsfile. Это тот случай, когда явная версия
     спасает: остальные конвейеры продолжают работать на своей версии
     и вообще не замечают аварии.

  3. Разбираться в причине и, если правка была ошибочной, откатить
     коммит в репозитории библиотеки, выпустив новую версию. Правки
     истории (git reset с последующим push --force) в общем репозитории
     не применяют: чужие рабочие копии уже содержат старые коммиты,
     и получится путаница.

ОБРАТИТЕ ВНИМАНИЕ: пункт 1 не поможет, если в поле Default version
стоит ветка main и в неё уже влит плохой коммит. Именно поэтому
в рабочей среде версию по умолчанию почти всегда указывают тегом,
а ветку main используют только для разработки библиотеки.


=========================================================================
10. КАК МЕНЯТЬ БИБЛИОТЕКУ БЕЗОПАСНО
=========================================================================

Правка библиотеки влияет на все конвейеры организации. По последствиям
это изменение продукта, а не «быстрая правка одной строчки», хотя
строчка действительно одна.

ПОРЯДОК, КОТОРЫЙ СТОИТ СОБЛЮДАТЬ

  1. Изменение делается в отдельной ветке репозитория библиотеки,
     а не прямо в main: git switch -c feature/timeout-param.

  2. В описании изменений пишется, ЧТО и ЗАЧЕМ:
       * что поменялось (новый параметр, исправленная команда,
         изменённое поведение);
       * зачем (какую проблему решает);
       * что будет со старыми вызовами (работают как раньше или
         требуют правки).
     Описание «поправил библиотеку» бесполезно: через полгода по нему
     невозможно понять, была ли эта правка нужна.

  3. Ревью обязательно. Смотрит человек, который отвечает за выкат:
     библиотека — общий код, и ошибка в ней стоит дороже ошибки
     в одном конвейере.

  4. Сначала выпускается новая версия (тег), потом на неё переводят
     конвейеры. Не наоборот: если сначала поменять Default version,
     а потом разбираться, все конвейеры получат изменение одновременно.

  5. Первым на новую версию переводится тестовый (канареечный)
     конвейер — раздел 11. Только после его успеха версию по умолчанию
     переключают для остальных.

КАК ВЫГЛЯДИТ «МЫ ПОПРАВИЛИ БИБЛИОТЕКУ И СЛОМАЛИ СОРОК СБОРОК»

Утро начинается с того, что все задания падают, и падают одинаково:
в журнале одна и та же ошибка на одном и том же шаге. Проект ни при
чём, серверы ни при чём — общий у всех только один элемент, и это
библиотека.

Причины, по которым так происходит, всегда одни и те же:

  * правку внесли прямо в main, без ветки и без ревью — ошибку никто
    не увидел до боевого запуска;
  * нет версий и тегов, поэтому откатывать некуда;
  * нет тестового конвейера, который попробовал бы новую версию
    на одном задании;
  * библиотека не проверяется тестами (раздел 11), и очевидная
    опечатка в имени параметра дожила до боевой сборки.

ХОРОШАЯ НОВОСТЬ: после того как версии и ревью введены, та же авария
развивается иначе. Плохая версия ломает одно тестовое задание, а сорок
рабочих конвейеров продолжают работать на прежнем теге. Это и есть
разница между «мы сломали всё» и «мы поймали ошибку на канарейке».


=========================================================================
11. ТЕСТИРОВАНИЕ БИБЛИОТЕКИ
=========================================================================

ЗАЧЕМ ТЕСТИРОВАТЬ БИБЛИОТЕКУ. Сломать библиотеку дороже, чем сломать
конвейер: у конвейера одна область применения, у библиотеки — все.
Дешевле поймать ошибку до того, как новая версия попадёт в main.

ЧТО МОЖНО ПРОВЕРИТЬ АВТОМАТИЧЕСКИ. Для шагов библиотеки существует
инструмент JenkinsPipelineUnit — это библиотека для тестов на Groovy
(её подключают к проекту библиотеки и запускают обычным сборщиком,
например Gradle или Maven). Идея простая:

  * тест загружает файл шага так же, как это делает Jenkins,
    и получает объект шага;
  * заглушки вместо настоящих шагов конвейера перехватывают вызовы
    sh, echo, sshagent и записывают их в список;
  * тест проверяет, что вызвано: например, что при двух серверах
    построены ровно две ветки и что в команде rsync есть нужный
    каталог.

Проверяется при этом не «работает ли Linux», а логика самого шага:
собрана ли карта веток, подставлены ли параметры, вызван ли откат при
ошибке. Именно эти места ломаются при правках чаще всего.

В курсе мы тестов не пишем: для двух шагов это избыточно, а разбор
JenkinsPipelineUnit — отдельная тема. Но знать, что такой инструмент
существует и что он решает, стоит: в организации с десятками
конвейеров это единственный способ менять библиотеку без страха.

ЧТО ПРОВЕРЯЕТСЯ РУКАМИ, И ЭТО ОБЯЗАТЕЛЬНО

  * Прогон на тестовом задании с параметром-версией библиотеки.
    Заводим задание, в Jenkinsfile которого библиотека подключена
    по конкретному тегу (например, v1.1.0), и запускаем его. Выкат
    идёт на один сервер — node2, чтобы не трогать половину сайта.

  * Проверка обеих страниц после выката. Напоминание из раздела 5:
    одна страница не доказывает, что выкат прошёл везде.

  * Проверка отката: намеренно проваливаем проверку (например,
    передаём expectedText, которого на странице нет) и убеждаемся, что
    блок post вызвал rollbackNodes и сайт вернулся к предыдущей версии.

УТОЧНЕНО: версию библиотеки нельзя подставить в аннотацию @Library —
там допустимо только постоянное значение. Для выбора версии на ходу
есть шаг library (раздел 3), который вызывается внутри script.

ПРИЁМ «КАНАРЕЕЧНЫЙ КОНВЕЙЕР» — самое практичное из этого раздела.
Идея: один конвейер проверяет новую версию библиотеки до того, как на
неё перевели остальные.

  * заводим задание SiteDeployLibraryCanary, которое отличается от
    рабочего одной строкой — версией в аннотации;
  * выпускаем новую версию библиотеки тегом v1.1.0;
  * переводим на неё канареечное задание и прогоняем полный цикл:
    выкат на node2, проверка страницы, намеренный провал, откат;
  * только после этого меняем Default version на v1.1.0 — и все
    остальные конвейеры получают новую версию.

Если что-то не так, страдает одно тестовое задание. Это ровно тот же
приём, что и канареечный выкат в практике 11, только применяется он
не к сайту, а к самой библиотеке.

ОБРАТИТЕ ВНИМАНИЕ: канареечный конвейер бесполезен, если он проверяет
не то, что делают рабочие конвейеры. Он должен вызывать те же шаги
с теми же параметрами, иначе проверяется не библиотека, а тестовое
задание.


=========================================================================
12. БЕЗОПАСНОСТЬ: БИБЛИОТЕКА — ЭТО ДОВЕРЕННЫЙ КОД
=========================================================================

Это самый важный раздел практики, и он про то, чем мы платим за
удобство.

КАК ИСПОЛНЯЕТСЯ КОД БИБЛИОТЕКИ. Обычный код конвейера Jenkins
выполняется в песочнице Groovy: не каждый вызов разрешён, а часть
требует подтверждения администратора (Script Approval — практика 9).
Так сделано потому, что код приходит из репозитория, а репозиторий
могут править многие.

С глобальными библиотеками иначе. Библиотека настроена администратором
Jenkins, поэтому считается доверенной, и её код выполняется с полными
правами Jenkins — песочница для неё ослаблена. Из этого следует всё
остальное:

  * код библиотеки может читать любые credentials, доступные сборке;
  * он может выполнять любые команды на агентах и на контроллере;
  * он может обращаться к файловой системе Jenkins и к его API.

ПРАКТИЧЕСКИЙ ВЫВОД, КОТОРЫЙ НАДО ЗАПОМНИТЬ: доступ на запись
в репозиторий библиотеки равен доступу ко всем секретам всех
конвейеров. Человек, который может влить коммит в main библиотеки,
может получить ключ node-ssh, токен Gitea и всё остальное — просто
добавив в шаг библиотеки одну строку, печатающую секрет.

ЧТО ИЗ ЭТОГО СЛЕДУЕТ ДЕЛАТЬ

  * ЗАЩИЩЁННАЯ ВЕТКА MAIN. В Gitea (и в любом другом Git-сервере) для
    репозитория библиотеки включается защита ветки main: прямой push
    запрещён, изменения идут только через pull request. Настройка:
    страница репозитория → Settings → Branches → Add Rule для main.

  * ОБЯЗАТЕЛЬНОЕ РЕВЬЮ. Минимум один согласующий, и это человек,
    который отвечает за выкат. Ревью библиотеки — не формальность:
    именно здесь замечают и ошибку, и лишнюю строку с секретом.

  * ОТДЕЛЬНЫЙ СПИСОК ТЕХ, КТО ПУБЛИКУЕТ ВЕРСИИ. Право создавать теги
    в репозитории библиотеки стоит держать у одного-двух человек.
    Тег — это обещание «эта версия проверена», и выдавать его должны
    не все, кто может писать код.

  * НИКАКИХ СЕКРЕТОВ В КОДЕ БИБЛИОТЕКИ. Ключи, пароли и токены
    приходят параметрами или берутся из credentials по идентификатору.
    В самом репозитории секретов быть не должно: он читается всеми,
    кому нужен выкат.

  * ЖУРНАЛ ИЗМЕНЕНИЙ ЧИТАЮТ. Перед слиянием полезно посмотреть diff
    целиком, а не только описание. Лишний echo с переменной окружения
    в diff виден сразу, а в журнале сборки он уже напечатает секрет.

ОБРАТИТЕ ВНИМАНИЕ: библиотеки бывают доверенные и недоверенные.
Доверенная — поведение по умолчанию, и именно её мы используем
в курсе. Недоверенная библиотека требует отдельной явной настройки
и работает в песочнице: часть вызовов в ней придётся разрешать через
Script Approval, как обычному коду конвейера. В курсе мы берём
доверенную осознанно — потому что библиотеку пишем и ревьюим сами,
а вся её ценность именно в том, что она умеет работать с ключами
и серверами напрямую. Но платим мы за это тем, что доступ к её
репозиторию приравнивается к доступу к секретам.


=========================================================================
13. КОГДА БИБЛИОТЕКУ ПИСАТЬ НЕ НУЖНО
=========================================================================

Общую библиотеку легко начать писать там, где она не нужна, и получить
лишний репозиторий, лишние версии и лишний слой. Признаки, по которым
библиотека не нужна:

  * ЛОГИКА НУЖНА ОДНОМУ КОНВЕЙЕРУ. Пишите функцию внутри Jenkinsfile —
    именно так сделано с deployToHost в конвейере практики 11. Пока
    потребитель один, библиотека добавляет только накладные расходы:
    отдельный репозиторий, версии, ревью и ещё одну точку отказа.

  * ЛОГИКА — ЭТО ОДНА КОМАНДА. Тогда её место в скрипте рядом с кодом
    проекта, а не в шаге библиотеки. Ровно поэтому deploy_site.sh
    из практики 11 едет на сервер вместе с сайтом: версия скрипта так
    же важна, как версия страницы, и её видно в том же репозитории.
    Шаг библиотеки, который внутри делает одну команду, — лишний
    посредник.

  * НУЖЕН НОВЫЙ ТИП ШАГА ДЛЯ JENKINS ЦЕЛИКОМ — например, поддержка
    нового внешнего сервиса или новый тип отчёта. Это плагин, а не
    библиотека. Сравните трудоёмкость честно: плагин — это Java-код,
    сборка, публикация версии, совместимость с несколькими версиями
    ядра Jenkins, обновления при выходе новых LTS. Библиотека — это
    Groovy-файл в репозитории. Библиотеку пишут за час, плагин —
    за недели, и поддерживать его нужно годами.

КОГДА БИБЛИОТЕКА ОПРАВДАНА:

  * один и тот же порядок действий нужен трём и более конвейерам;
  * логика обязана совпадать буквально: стандарт выката, стандарт
    проверки, единые требования безопасности;
  * логику меняют регулярно, и правка в одном месте экономит время
    каждый раз;
  * нужен общий код, который неудобно держать в каждом Jenkinsfile:
    классы, разбор данных, формирование отчётов.

ПРОСТОЕ ПРАВИЛО: пока копий две, терпите копипасту. Когда появилась
третья — выносите в библиотеку.


=========================================================================
14. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: Library lab-shared-library not found

Сообщение означает, что Jenkins не смог получить библиотеку по имени
из строки @Library. Смотрим по порядку:

  1. Имя совпадает с полем Name в настройках? Manage Jenkins → System →
     Global Pipeline Libraries. Опечатка в одном символе даёт ровно это
     сообщение, причём репозиторий может быть полностью исправен;
  2. Библиотека вообще настроена? Пустой список в Global Pipeline
     Libraries даёт ту же ошибку;
  3. Версия существует? @Library('lab-shared-library@v1.0.0') при
     отсутствии тега v1.0.0 — та же ошибка. Проверьте в Gitea, что тег
     действительно отправлен: git push теги по умолчанию не отправляет
     (раздел 1);
  4. Репозиторий читается из Jenkins? Проверьте адрес и credentials
     gitea-reader. При проблеме с ключом сообщение будет другим (про
     аутентификацию), но начинать разбор всё равно полезно с этого;
  5. Снята ли галочка Allow default version to be overridden? Если она
     снята, а конвейер просит версию, Jenkins проигнорирует её и
     возьмёт значение по умолчанию — иногда это выглядит как «взялась
     не та версия».

ПРОБЛЕМА: No such DSL method 'deployToNodes' found

Jenkins не знает такого шага. Причины по частоте:

  1. Имя файла в vars/ не совпадает с вызовом. Файл deployToNodes.groovy
     даёт шаг deployToNodes — регистр букв важен;
  2. Библиотека не загрузилась: нет строки @Library (раздел 3) или она
     ниже первого оператора;
  3. Шаг вызван не из steps. В декларативном конвейере вызовы шагов
     живут в блоках steps или script; вызов в блоке options или
     environment — ошибка;
  4. Файл лежит не в vars/, а, например, в vars/steps/ или в src/.
     Jenkins читает только верхний уровень vars/.

ПРОБЛЕМА: ошибка компиляции Groovy в библиотеке

Симптом: сборка падает почти сразу, ещё до первой стадии, с сообщением
про синтаксис. Что делать:

  * открыть журнал сборки: Jenkins указывает файл и строку библиотеки —
    например deployToNodes.groovy:37. Это точное место, а не «где-то
    в библиотеке»;
  * проверить, что библиотека не взята из кэша в старой версии
    (см. следующую проблему);
  * помнить про экранирование: если Groovy ругается на неизвестное
    свойство, скорее всего, в sh """ ... """ написано ${target} вместо
    \${target}, и Groovy пытается подставить свою переменную.

ПРОБЛЕМА: unexpected token: @Library

Аннотация стоит не там, где нужно. Проверьте:

  * строка @Library находится до первого оператора файла. Комментарии
    перед ней допустимы, код — нет;
  * в конце строки стоит подчёркивание: @Library('lab-shared-library@main') _.
    Без него аннотация привязывается к следующей конструкции и файл
    не разбирается;
  * кавычки: в аннотации нужны одинарные или двойные кавычки, и внутри
    не должно быть подстановки переменных — только постоянное значение.

ПРОБЛЕМА: изменения в библиотеке не применяются

Классическая ситуация: вы поправили шаг, запушили, запустили сборку —
а поведение прежнее. Объяснение: Jenkins держит копию библиотеки
в рабочем каталоге (каталог @libs из раздела 8) и обновляет её не
всегда так, как вы ожидаете. Что помогает:

  1. Новый запуск сборки — в большинстве случаев достаточно его;
  2. Указать версию явно: @Library('lab-shared-library@main') _ вместо
     ссылки на версию по умолчанию;
  3. Указать конкретный коммит: @Library('lab-shared-library@a1b2c3d') _ —
     так проверяют правку до того, как создан тег;
  4. Если ничего не помогает, посмотреть, что реально скопировано.
     Путь тот же, что в разделе 8: внутри @libs лежит подкаталог
     с хешем, а в нём — каталог lab-shared-library:

     ssh node1 'ls -l ~/agent/workspace/*@libs/*/lab-shared-library/vars/deployToNodes.groovy'

     Здесь ~ — домашний каталог jenkins на агенте, то есть /home/jenkins.
     В выводе важна не столько длина файла, сколько дата изменения:
     по ней видно, обновилась ли копия библиотеки.
  5. Крайняя мера — перезапуск Jenkins (Safe Restart, практика 2).
     Помогает редко, но при странном поведении кэша бывает нужно.

ПРОБЛЕМА: RejectedAccessException внутри библиотеки

Сообщение вида «Scripts not permitted to use method ...» означает, что
вызов запрещён песочницей Groovy и ждёт подтверждения администратора.
Для доверенной библиотеки это нехарактерно, поэтому проверьте:

  * библиотека действительно доверенная, а не помечена как недоверенная
    при настройке;
  * вызов идёт из библиотеки, а не из Jenkinsfile: у кода конвейера
    песочница строже;
  * если подтверждение действительно нужно, оно выдаётся осознанно:
    Manage Jenkins → Security → Script Approval (практика 9). Выдавать
    разрешения «всем списком» нельзя — это отключает защиту целиком.

ПРОБЛЕМА: выкат ушёл только на один сервер

Признаки: сборка зелёная, обе ветки в журнале есть, обе отчитались
об успехе, но на одном из серверов старая версия. Почти всегда это
та самая ловушка захвата переменной цикла из раздела 5.

Что делать:

  1. открыть vars/deployToNodes.groovy и найти строку цикла;
  2. убедиться, что внутри итерации есть local-копия переменной:
     String host = rawHost as String, и что все подстановки в замыкании
     используют именно host;
  3. проверить, что ${host} не подставляется вместо ${rawHost} в самом
     замыкании;
  4. после правки прогнать выкат и открыть обе страницы:
     http://10.0.2.13/ и http://10.0.2.14/. Номер сборки должен
     совпадать на обеих.

Напоминание, почему ошибка коварна: имя ветки вычисляется сразу
и потому выглядит правильным, а команды внутри замыкания — потом,
и все они уходят на последний адрес из списка.


=========================================================================
УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

Задание SiteDeployLibrary и репозиторий библиотеки оставляем: разница
между конвейером с библиотекой и без неё полезна как наглядный пример,
а шаги библиотеки пригодятся любому следующему конвейеру. Задание
SiteDeploy из приложения к практике 11 тоже оставляем — именно на его
фоне видно, что дала библиотека.

УТОЧНЕНО: практика 14 про библиотеку не рассказывает — она про
конфигурацию как код, резервные копии и восстановление Jenkins. Удалять
эти задания перед ней не нужно, а специально готовить их к ней тоже не
надо: если вы снимете копию JENKINS_HOME, они просто попадут в копию.

Приводим настройки в порядок:

  1. Проверьте, что галочка Load implicitly снята:
     Manage Jenkins → System → Global Pipeline Libraries → lab-shared-library.
     Включённая галочка означает, что библиотека влияет на все конвейеры
     Jenkins, включая учебные.

  2. Приведите в порядок версию по умолчанию. Разумный вариант для
     стенда: Default version = v1.0.0 (проверенный тег), а галочка
     Allow default version to be overridden включена. Тогда конвейеры
     без явной версии получают стабильное состояние, а эксперименты
     можно вести через @Library('lab-shared-library@main').

     ВАЖНО, ЕСЛИ КОНФИГУРАЦИЯ УПРАВЛЯЕТСЯ КОДОМ: в файле
     files/jcasc/jenkins.yaml версия по умолчанию для нашей библиотеки
     указана как main. Если поменять её только в портале, следующее
     применение конфигурации (практика 14) вернёт main обратно —
     правку нужно внести и в файл, иначе настройка откатится сама.

  3. Удалите теги, которые заводили для проверки (например,
     v0.0.1-test, если вы его создавали):

     git tag -d v0.0.1-test
     git push origin --delete v0.0.1-test

  4. Проверьте, что остались только нужные теги:
     git tag -l
     В списке должен быть тот тег (или теги), которые вы считаете
     рабочими.

  5. Удалите временное канареечное задание, если заводили его для
     проверки: на странице задания → Delete Pipeline.

  6. Уберите временные каталоги на серверах и агентах:
     ssh node1 'rm -rf /tmp/site-deploy-*'
     ssh node2 'rm -rf /tmp/site-deploy-*'

  7. Финальная проверка — запустите SiteDeployLibrary и убедитесь, что
     выкат идёт на оба сервера:
     curl -s http://10.0.2.13/ | grep -i 'сборка'
     curl -s http://10.0.2.14/ | grep -i 'сборка'

ВАЖНО: если вы меняли версию по умолчанию на тег, проверьте, что
в библиотеке действительно есть этот тег. Отсутствующий тег в поле
Default version ломает все конвейеры без явной версии — с уже знакомым
сообщением «Library lab-shared-library not found».
