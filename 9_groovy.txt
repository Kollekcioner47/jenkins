Практика 9. Groovy и Script Console: сила и осторожность.
Script Console выполняет произвольный Groovy-код внутри работающего
Jenkins с правами администратора: ей доступны задания, агенты,
плагины, очередь сборок и настройки сервера. Это самый мощный
и самый опасный инструмент курса.
Готовые скрипты к практике лежат в files/groovy/:
inventory_report.groovy (инвентаризация), clean_old_builds.groovy
(очистка истории сборок), export_jobs.groovy (выгрузка описаний).
ИСПРАВЛЕНО: в прежней версии курса практика состояла из десяти строк
с примерами, и почти каждая не работала: опечатка в имени переменной
Jenkins, фигурные скобки вместо круглых, отсутствующий импорт Result
и задание с чужим именем.
=========================================================================
ЧТО МЫ СДЕЛАЕМ И ЗАЧЕМ ЭТО НУЖНО
=========================================================================
Портал показывает то, что предусмотрели авторы плагинов, а это далеко
не всё: через портал неудобно получить список всех заданий с числом
сборок, узнать, какие плагины ждут обновления, увидеть причины всей
очереди списком и выгрузить описания заданий. Всё это — операции над
внутренним API Jenkins, и Script Console даёт к нему прямой доступ:
код выполняется в том же процессе Java, что и сам Jenkins.
ЗАЧЕМ ЭТО НУЖНО: администратор постоянно отвечает на вопросы «что
у нас есть» и «что пора чистить». Скрипт превращает такой вопрос
в один запуск вместо получаса хождения по порталу.
ПОЧЕМУ ЭТО ОПАСНО: тот же доступ позволяет удалить все задания,
поменять настройки безопасности и прочитать ключи.

=========================================================================
1. SCRIPT CONSOLE: ГДЕ ОНА И ЧТО ДЕЛАЕТ
=========================================================================
  Manage Jenkins -> Script Console
  http://10.0.2.5:8080/script
На странице поле ввода, кнопка Run и два результата: всё, что скрипт
напечатал, и значение последнего выражения — оно показано в поле
Result. Если значение не нужно, заканчивайте скрипт строкой
return null.
ВАЖНО: Script Console выполняется БЕЗ ПЕСОЧНИЦЫ. Код не ограничен
списком разрешённых методов и работает с правами администратора
Jenkins. Единственная защита — права: консоль открывается только тем,
у кого есть разрешение Manage -> Scripts.
ПОЧЕМУ ЭТО ПРИНЦИПИАЛЬНО: у Groovy в конвейерах песочница есть
(раздел 9), и это два разных инструмента. Конвейерный Groovy
ограничен потому, что Jenkinsfile лежит в репозитории, доступном
многим; у Script Console ограничений нет — доступ к ней есть только
у администратора.
ПРАВИЛО, КОТОРОЕ НЕ ОБСУЖДАЕТСЯ: скрипт из интернета в Script
Console не вставляют ни при каких обстоятельствах. Скрипт, который
«просто почистит старые сборки», может содержать удаление всех
заданий или отправку credentials наружу, а проверить это глазами
невозможно. Нужен чужой скрипт — читайте построчно и переносите
в свой только понятную логику.

2. МИНИМУМ GROOVY, КОТОРЫЙ ПОНАДОБИТСЯ ДАЛЬШЕ
=========================================================================
2.1. def и типы: def name = 'FirstJob' — «тип не важен», String text —
тип указан явно. def не отменяет типы: класс у переменной есть, его
подставляет компилятор; List<Job> jobs = ... сразу скажет, что
в списке ожидаются задания.
2.2. Строки и интерполяция:
def number = 7
println "сборка ${number}"     // интерполяция
println 'сборка ${number}'     // а так — обычный текст
ОБРАТИТЕ ВНИМАНИЕ: интерполяция работает только в двойных кавычках.
2.3. Замыкания и it:
[1, 2, 3].each { println it }
Замыкание — блок кода, который передают другому коду. Слово it — имя
единственного параметра, его подставляет Groovy; если параметров
несколько, их называют явно: { computer -> println computer.name }.
2.4. Коллекции:
def jobs = jenkins.getAllItems(Job.class).toList()
jobs.each { println it.fullName }                  // перебрать
def empty = jobs.findAll { it.lastBuild == null }  // отобрать
def names = jobs.collect { it.fullName }           // преобразовать
def sorted = jobs.toList().sort { it.fullName }    // отсортировать
def rest = jobs.drop(3)                            // пропустить три
drop(n) отбрасывает первые n элементов; сборки идут от новых
к старым, поэтому drop(10) — «всё, кроме последних десяти сборок».
ПОЧЕМУ В КОДЕ ЧАСТО СТОИТ toList(): getAllItems и getBuilds
возвращают не список, а коллекцию, которая читает данные с диска
по мере обхода (раздел 7).
2.5. Null-безопасность:
def result = job.lastBuild?.result?.toString() ?: 'не запускалось'
?. — вызов только если объект слева не null. ?: — если слева null,
пустая строка или ноль, берётся значение справа.
2.6. Приведение типов словом as: Job job = item as Job, а также
String text = 42 as String. Если тип не тот, приведение закончится
ошибкой GroovyCastException.

3. ОБЪЕКТЫ JENKINS ИЗ GROOVY
=========================================================================
Точка входа — объект самого Jenkins, его возвращает статический
вызов Jenkins.get():
import jenkins.model.Jenkins
def jenkins = Jenkins.get()
Через него доступно остальное:
  jenkins.rootUrl        адрес портала, http://10.0.2.5:8080/
  jenkins.rootDir        каталог состояния /var/lib/jenkins
  jenkins.numExecutors   сколько сборок выполняет контроллер
  jenkins.computers      узлы: online, numExecutors, метки
  jenkins.pluginManager  плагины: plugins, getPluginsWithUpdateAvailable()
  jenkins.queue          очередь: items, у каждого task и why
  jenkins.securityRealm  пользователи: allUsers()
Задания ищутся так:
import hudson.model.Job
Job job = jenkins.getItemByFullName('FirstJob', Job.class)
def allJobs = jenkins.getAllItems(Job.class)   // все, включая папки
def topJobs = jenkins.getItems()               // только верхний уровень
getItemByFullName принимает полное имя ('сборки/FirstJob'), а второй
аргумент задаёт ожидаемый тип: если по имени лежит папка, вернётся
null, а не ошибка. От задания переходим к сборкам:
import hudson.model.Run
import hudson.model.Result
def builds = job.getBuilds()       // все сборки, новые первыми
def last = job.lastBuild           // последняя, может быть null
def ok = job.lastSuccessfulBuild   // последняя успешная
builds.each { Run b ->
    println "#${b.number} ${b.result} ${new Date(b.timeInMillis)}"
}
У сборки важны number, result (SUCCESS, FAILURE, UNSTABLE, ABORTED
либо null, если сборка ещё идёт) и timeInMillis — время начала
в миллисекундах, поэтому new Date(...).
Изменять состояние Jenkins из скрипта тоже можно:
job.delete()                  // удалить задание целиком
jenkins.setNumExecutors(2)    // изменить число исполнителей
jenkins.save()                // записать настройки на диск
ВАЖНО ПРО save(): без него изменение останется в памяти и исчезнет
после перезапуска службы.
ИСПРАВЛЕНО: ГЛАВНАЯ ОПЕЧАТКА ПРЕЖНЕГО КУРСА
Во всех примерах прежней версии стояло Jenkins.intance — пропущена
буква s. Скрипты не работали, а сообщение об ошибке выглядело так,
будто сломался сам Jenkins:
  No such property: intance for class: jenkins.model.Jenkins
  Possible solutions: instance
Правильно — Jenkins.get(); поле Jenkins.instance историческое
и оставлено для совместимости:
  было (не работало):   Jenkins.intance.getNumExecutors()
  стало (работает):     Jenkins.get().getNumExecutors()
ИСПРАВЛЕНО: ФИГУРНЫЕ СКОБКИ ВМЕСТО КРУГЛЫХ
Прежний пример приветствия:
  println {"Hello DevOps from Jenkins!"}
Скрипт выполнится без ошибки, но приветствия вы не увидите: фигурные
скобки в Groovy — это замыкание, блок кода, который создаётся, но сам
не выполняется. println получает объект-замыкание, а не строку,
и печатает в лучшем случае служебное имя вида
Script1$_run_closure1@5b9d3b0f. Правильно:
  println 'Hello DevOps from Jenkins!'
ИСПРАВЛЕНО: ФИГУРНЫЕ СКОБКИ В УСЛОВИИ
Прежний пример очистки истории:
  job = Jenkins.intance.getItemByFullName("gh_deploy")
  job.getBuilds().each {
      if{it.result == Result.SUCCESS} { it.delete() }
  }
Здесь if{...} — не условие, а замыкание, и строка вообще
не компилируется: скрипт падает с синтаксической ошибкой ещё до
первого println. Правильно:
  if (it.result == Result.SUCCESS) {
      it.delete()
  }
ИСПРАВЛЕНО: НЕ БЫЛО ИМПОРТА Result
Класс Result не был импортирован, а импортов в файле не было вообще;
сообщение в консоли — unable to resolve class Result. Правильно:
  import hudson.model.Result
УТОЧНЕНО: примеры прежнего курса были написаны для задания gh_deploy,
которого на нашем стенде нет. В курсе задания называются так:
FirstJob, build_with_params, periodic_report, gitea_build, site_pipeline,
site_docker, site_library.
В комментарии там же было написано FILURE вместо FAILURE, а удаление
сборок шло прямо внутри обхода job.getBuilds().each { } — об этом
в разделе 7.

4. ПЕРВЫЙ СКРИПТ: ВЕРСИЯ, ЗАДАНИЯ И ПОСЛЕДНИЕ СБОРКИ
=========================================================================
Соберём разобранное в один скрипт:
import jenkins.model.Jenkins
import hudson.model.Job
def jenkins = Jenkins.get()
println "версия Jenkins : ${Jenkins.getVersion()}"
println "URL портала    : ${jenkins.rootUrl}"
println "JENKINS_HOME   : ${jenkins.rootDir}"
println ''
println 'задания и последние сборки:'
def jobs = jenkins.getAllItems(Job.class).toList()
jobs.sort { it.fullName }        // стабильный порядок вывода
jobs.each { Job job ->
    def last = job.lastBuild
    def number = last ? "#${last.number}" : '-'
    def result = last?.result?.toString() ?: 'не запускалось'
    println String.format('  %-28s %-6s %s', job.fullName, number,
            result)
}
Результат на нашем стенде:
версия Jenkins : 2.528.1
URL портала    : http://10.0.2.5:8080/
  FirstJob                     #7     SUCCESS
  periodic_report              #12    FAILURE
  site_pipeline                #4     SUCCESS
Что здесь важно: Jenkins.getVersion() — статический вызов, версия
не зависит от полученного объекта Jenkins. rootUrl и rootDir — адрес
портала и каталог состояния; если rootUrl показывает localhost вместо
10.0.2.5, адрес задан неверно (Manage Jenkins -> System -> Jenkins
URL). Строка String.format задаёт ширину столбцов: %-28s — «строка
шириной 28, выровненная влево».

5. ИНВЕНТАРИЗАЦИЯ: files/groovy/inventory_report.groovy
=========================================================================
Откройте files/groovy/inventory_report.groovy, скопируйте целиком
в Script Console и запустите: скрипт отвечает на вопрос «что у нас
вообще есть» и печатает шесть блоков — контроллер (версия, адрес,
каталог состояния, исполнители, режим), агенты (имя, online/OFFLINE,
исполнители, метки), задания (имя, число сборок, результат
последней), плагины (сколько стоит, сколько ждёт обновления, какие
отключены), очередь сборок с причинами ожидания и пользователи
с числом токенов.
Знаки вопроса в блоке агентов не случайны: у контроллера как узла
может не быть объекта Node, и c.node?.labelString без ?. упал бы
с NullPointerException. Последняя строка скрипта возвращает короткую
сводку в поле Result — её удобно сравнивать между запусками.
ЧТО ИСКАТЬ В ВЫВОДЕ:
  * список плагинов с обновлениями — план обновления: сначала копия
    JENKINS_HOME, потом обновление порциями (практика 2);
  * задания со «сборок: 0» — их создали и забыли: либо они не нужны,
    либо не срабатывает триггер;
  * задания с «последняя: FAILURE» — красный список; на живом сервере
    в нём не должно быть ничего;
  * причина ожидания про свободный исполнитель означает нехватку
    исполнителей, причина с именем метки — что агент не в сети;
  * неожиданно много токенов у пользователя — повод разобраться.

6. КОМАНДЫ И ФАЙЛЫ ИЗ GROOVY
=========================================================================
println 'ls -la /var/lib/jenkins'.execute().text
println new File('/etc/passwd').text
Обе строки работают: первая печатает содержимое каталога состояния,
вторая — список пользователей системы.
ПОЧЕМУ ЭТО РАБОТАЕТ: скрипт выполняется внутри процесса Jenkins,
а процесс работает под пользователем jenkins и с его правами. Отсюда
и ограничение: /var/lib/jenkins читается свободно, а
secrets/initialAdminPassword — нет, файл доступен только владельцу.
ТРИ ВАЖНЫЕ ОГОВОРКИ
ПЕРВАЯ, И ГЛАВНАЯ: скрипт выполняется на КОНТРОЛЛЕРЕ, а не на
агентах: new File('/etc/nginx/nginx.conf').text читает файл машины
admin, а не node1. Классическая ошибка — «посмотреть конфиг nginx»
и удивиться, что файла нет: nginx стоит на node1 и node2, а скрипт
смотрит на admin. Файлы агентов из Script Console не видны, для этого
нужна сборка с привязкой к агенту или конвейер (практика 10).
ВТОРАЯ: у строки .execute() нет оболочки — команда разбивается
по пробелам и запускается напрямую, поэтому ни конвейеров (|),
ни перенаправлений (>) здесь нет:
'ls -la /var/lib/jenkins | head'.execute().text    // так НЕ сработает
Нужна оболочка — вызывайте её явно:
def p = ['bash', '-c', 'ls -la /var/lib/jenkins | head -5'].execute()
p.waitFor()
println p.text
ТРЕТЬЯ: .text — только стандартный вывод; ошибки уходят в отдельный
поток, и их читают через p.err.text после p.waitFor().

7. МАССОВЫЕ ОПЕРАЦИИ: files/groovy/clean_old_builds.groovy
=========================================================================
Уборка истории сборок — первая задача, для которой Script Console
действительно хороша: в портале сборки удаляют по одной крестиком,
а скрипт делает то же самое списком. Откройте
files/groovy/clean_old_builds.groovy; начинается он с настроек:
String jobName = 'FirstJob'    // '' — обработать все задания
int keepLast = 10              // сколько последних сборок оставить
boolean dryRun = true          // true — только показать
boolean onlyFailed = false     // true — чистить только неудачные
РЕЖИМ РЕПЕТИЦИИ (dryRun = true) ВКЛЮЧЁН ПО УМОЛЧАНИЮ: скрипт печатает
строки «[репетиция] удалил бы #12 (FAILURE, ...)» и ничего не удаляет.
Это не перестраховка: удаление истории НЕОБРАТИМО — вместе со сборкой
уходят журнал, артефакты и сведения о том, кто её запускал. В прежней
версии курса скрипт удалял сборки сразу и без проверок.
ОГРАНИЧЕНИЕ «ОСТАВИТЬ ПОСЛЕДНИЕ N» — ЭТО drop():
List<Run> builds = job.builds.toList()     // от новых к старым
List<Run> candidates = builds
        .drop(keepLast)                    // последние не трогаем
        .findAll { !onlyFailed || it.result == Result.FAILURE }
drop отбрасывает последние десять сборок — ровно то, что нужно
сохранить; остальное — кандидаты на удаление. Параметр onlyFailed
оставляет только неудачные сборки: успешные иногда нужны для истории
выкатов, а красные — почти никогда.
ВАЖНО ПРО ОБХОД СПИСКА. Обратите внимание на toList() в первой
строке: getBuilds() возвращает коллекцию, которая читает данные
по мере обхода, а мы во время обхода удаляем элементы — получилось бы
изменение коллекции прямо в цикле и ошибка
ConcurrentModificationException. Список, собранный заранее, от
удаления сборок не меняется: мы удаляем сборки, а не элементы списка.
Правило: список к удалению собираем ДО удаления (toList или collect).
Удаляет сборку один метод build.delete() — вместе с каталогом
и журналом на диске.
ПРЕДУПРЕЖДЕНИЕ ПРО updateNextBuildNumber(1)
В конце файла есть закомментированный блок про сброс нумерации:
job.updateNextBuildNumber(1). Метод работает, и в прежней версии курса
он предлагался как способ «обнулить счётчик» после удаления. Делать
этого не нужно: номер сборки попадает в имена артефактов
(site-${BUILD_NUMBER}.tar.gz), в теги образов в реестре (site:42)
и в записи о выкатах («на node1 выложена сборка 42»). Сбросив
нумерацию, вы получите две РАЗНЫЕ сборки с одним и тем же номером:
понять по номеру, какая из них лежит на сервере, станет невозможно,
а тег образа будет перезаписан — однажды это закончится выкатом
не того кода.
ЕСЛИ ЧИСТИТЬ НУЖНО ПОСТОЯННО: не сбрасывайте нумерацию, а задайте
политику хранения в самом задании: FirstJob -> Configure ->
Discard old builds (практика 3). Тогда старые сборки Jenkins удаляет
сам, и скрипт не нужен вовсе.
ПОРЯДОК РАБОТЫ: запускаем с dryRun = true и читаем вывод; проверяем
на одном задании (jobName = 'FirstJob'); меняем dryRun на false;
и только потом переходим к остальным заданиям.

8. ВЫГРУЗКА ОПИСАНИЙ ЗАДАНИЙ: files/groovy/export_jobs.groovy
=========================================================================
Третий скрипт выгружает описания всех заданий в файлы.
ЗАЧЕМ ЭТО НУЖНО: самая незаменимая часть Jenkins — не плагины
и не пользователи, их можно поставить и создать заново, а описания
заданий: расписания, параметры, шаги, привязки к агентам, настройки
триггеров. Задание, настроенное год назад и никем
не задокументированное, существует ровно в одном экземпляре —
в JENKINS_HOME на машине admin.
String backupRoot = '/var/lib/jenkins/backups'
String stamp = new Date().format('yyyyMMdd-HHmmss')
File targetDir = new File(backupRoot, "jobs-${stamp}")
String xml = job.getConfigFile().asString()
String fileName = job.fullName.replace('/', '__') + '.xml'
new File(targetDir, fileName).setText(xml, 'UTF-8')
Каждый запуск создаёт свой каталог с отметкой времени, например
/var/lib/jenkins/backups/jobs-20260514-101500/: выгрузки не
перезаписывают друг друга, и видно, какая из них свежее.
ПОЧЕМУ ДВОЙНОЕ ПОДЧЁРКИВАНИЕ: полное имя задания может содержать
папки ('сборки/web/site_pipeline'), а слэш в имени файла невозможен.
Он заменяется на '__', и получается файл
сборки__web__site_pipeline.xml. УТОЧНЕНО: в имени файла стоит полное
имя, а не короткое: FirstJob.xml не говорит, в какой папке задание
лежало.
ЧТО ЕСТЬ В ВЫГРУЗКЕ И ЧЕГО НЕТ: есть полное описание задания
(параметры, шаги, расписание, привязка к агенту, настройки хранения
истории); нет истории сборок, журналов и артефактов; нет значений
credentials — остаются только их идентификаторы (node-ssh,
gitea-reader, gitea-token, docker-registry), а сами секреты лежат
в credentials.xml и зашифрованы ключом из secrets/.
ВАЖНО ПОНИМАТЬ ПРАВИЛЬНО: выгрузка описаний — это не резервная
копия. Задание из неё восстановится, но ссылка на секрет
с идентификатором node-ssh заработает только там, где этот секрет
существует. Полная копия Jenkins — это весь JENKINS_HOME
(практика 14), а выгрузка — удобное дополнение: её можно положить
в git и посмотреть разницу между версиями.
Проверить результат: sudo ls -la /var/lib/jenkins/backups/jobs-*/

9. GROOVY В КОНВЕЙЕРАХ И ПЕСОЧНИЦА
=========================================================================
В конвейерах (практика 10) Groovy используется постоянно, но правила
там другие. Своя логика пишется внутри блока script { }:
pipeline {
    agent any
    stages {
        stage('Отчёт') {
            steps {
                script {
                    echo "сборка №${currentBuild.number}"
                    echo "результат: ${currentBuild.currentResult}"
                    echo "агент: ${env.NODE_NAME}"
                }
            }
        }
    }
}
Этот код выполняется в песочнице: Jenkins пропускает только те
вызовы, которые занесены в список разрешённых. Список ведут авторы
плагинов и администратор вручную:
  Manage Jenkins -> Security -> Script Approval
  http://10.0.2.5:8080/scriptApproval/
ПЕРВЫЙ запуск конвейера с незнакомым вызовом завершится ошибкой:
org.jenkinsci.plugins.scriptsecurity.sandbox.RejectedAccessException:
Scripts not permitted to use new java.io.File java.lang.String.
Administrators can decide whether to approve or reject this signature.
RejectedAccessException — это НЕ ошибка вашего кода: код написан
правильно, но делает то, что песочница запрещает. В списке ожидающих
одобрения появится подпись «new java.io.File java.lang.String»
и кнопки Approve и Deny.
ПОЧЕМУ УСТРОЕНО ИМЕННО ТАК: Jenkinsfile лежит в репозитории,
а в репозиторий пишут многие. Без песочницы любой, кто может
отправить изменение в ветку, получил бы право выполнить произвольный
код на контроллере: прочитать credentials, изменить задания,
выкатить что угодно.
РЕШЕНИЕ, КОТОРОЕ ПРИНИМАТЬ НЕЛЬЗЯ: «нажму Approve на всё, что
появится». Так песочница превращается в декорацию: вместо одной
разрешающей строчки администратор открывает все опасные операции
сразу, и следующий Jenkinsfile из чужой ветки выполнится без единого
вопроса. Правильный подход — посмотреть, ЧТО просят разрешить
(«new java.io.File» — доступ к файлам контроллера, «method
java.lang.String execute» — запуск команд), понять, зачем это
конвейеру, и выдавать разрешение точечно.

10. МАССОВЫЕ ОПЕРАЦИИ НА ЖИВОМ JENKINS: ПРАВИЛА БЕЗОПАСНОСТИ
=========================================================================
1. РАБОТАЙТЕ В ЧАСЫ НИЗКОЙ НАГРУЗКИ: обход истории сотни заданий
   читает диск и держит объекты в памяти, а днём конкурирует
   со сборками за те же ресурсы.
2. СНАЧАЛА ПЕЧАТЬ, ПОТОМ ДЕЛАНИЕ: сначала «показать, что будет
   сделано», и только потом «сделать» — для этого в
   clean_old_builds.groovy есть dryRun.
3. РАЗБИВАЙТЕ НА ПОРЦИИ: по одному-два задания за запуск — ошибка
   в фильтре будет стоить одной истории, а не всей.
4. ПРОВЕРЯЙТЕ НА ОДНОМ, ПОТОМ НА ВСЕХ.
5. НЕ ДЕЛАЙТЕ ТЯЖЁЛЫХ ОБХОДОВ БЕЗ НУЖДЫ: getBuilds() у задания
   с тысячей сборок читает метаданные каждой. Спросите себя, нужны
   ли все сборки: lastBuild читается мгновенно.
6. ПОМНИТЕ, ЧТО СКРИПТ ДЕРЖИТ КОНСОЛЬ И ПАМЯТЬ: скрипт, складывающий
   сборки всех заданий в один список, на большом Jenkins съест память
   контроллера (разбор — в разделе «Если что-то пошло не так»).
7. ГЛАВНОЕ ПРАВИЛО: ЛЮБАЯ МАССОВАЯ ОПЕРАЦИЯ — ТОЛЬКО ПОСЛЕ КОПИИ.
   Копия JENKINS_HOME (практика 14) превращает «я удалил не то»
   в неприятность на полчаса, а без копии это происшествие
   с разбором последствий.

11. АУДИТ И ИНВЕНТАРИЗАЦИЯ С ПОМОЩЬЮ GROOVY
=========================================================================
Ниже — вопросы, на которые Script Console отвечает за секунды.
В примерах предполагается, что import jenkins.model.Jenkins и
import hudson.model.Job уже сделаны.
11.1. Что менялось за последние N дней — полезно перед обновлением:
int days = 30
long edge = System.currentTimeMillis() - days * 86400000L
Jenkins.get().getAllItems(Job.class).each { Job job ->
    long changed = job.getConfigFile().getFile().lastModified()
    if (changed >= edge) {
        println "  ${job.fullName}: изменено ${new Date(changed)}"
    }
}
11.2. Задания без ограничения истории — у них каталог builds растёт,
пока не кончится место:
Jenkins.get().getAllItems(Job.class).each { Job job ->
    if (job.getBuildDiscarder() == null) {
        println "  ${job.fullName}: история не ограничена," +
                " сборок ${job.builds.size()}"
    }
}
Задание с политикой Discard old builds в список не попадёт.
11.3. Задания, которые держатся за устаревший плагин: описание
задания — это XML, и имя класса плагина видно в нём как есть.
String marker = 'publish_over'
Jenkins.get().getAllItems(Job.class).each { Job job ->
    if (job.getConfigFile().asString().contains(marker)) {
        println "  ${job.fullName}: описание использует ${marker}"
    }
}
Так находят задания, которые ещё используют плагин, снятый
с поддержки. Исторический пример курса — «Publish over SSH»: он
больше не поддерживается, и в практике 11 показано, чем его
заменили (ssh-agent и rsync).
11.4. Пользователи и их токены — токен это полноценный доступ
к Jenkins, поэтому у каждого должна быть понятная причина:
import hudson.security.ApiTokenProperty
Jenkins.get().securityRealm.allUsers().each { u ->
    def tokens = u.getProperty(ApiTokenProperty)?.tokenList?.size() ?: 0
    println "  ${u.id} (${u.fullName}): токенов ${tokens}"
}
У engineer токены появятся после практики 5 (Jenkins CLI),
у serviceuser — если автоматизация ходит в API. Десяток токенов
у одной записи — почти всегда забытые эксперименты.
11.5. Кто где собирается: метка из описания задания и узел последней
сборки в одном списке.
import hudson.model.Queue
Jenkins.get().getAllItems(Job.class).each { Job job ->
    def label = (job instanceof Queue.Task) ? job.assignedLabel : null
    def labelText = label ? label.displayName : 'метка не задана'
    def node = job.lastBuild?.builtOn
    def nodeText = node ? (node.nodeName ?: 'встроенный узел') : 'нет'
    println String.format('  %-24s %-16s %s', job.fullName,
            labelText, nodeText)
}
Строка «метка не задана» вместе с узлом «встроенный узел» означает,
что задание выполняется на контроллере: в рабочей среде это ошибка
конфигурации, а не норма (практика 4).

12. ИНИЦИАЛИЗАЦИОННЫЕ СКРИПТЫ: /var/lib/jenkins/init.groovy.d/
=========================================================================
Есть ещё одно место, где Jenkins выполняет Groovy сам: каталог
/var/lib/jenkins/init.groovy.d/. Jenkins обходит его при КАЖДОМ
запуске службы и выполняет найденные файлы .groovy по очереди,
в алфавитном порядке; по умолчанию каталога нет, его создают руками.
ЗАЧЕМ ЭТО НУЖНО: настроить что-то до того, как сервер начнёт
принимать работу, — создать служебного пользователя, выставить
системное сообщение.
// /var/lib/jenkins/init.groovy.d/01-system-message.groovy
import jenkins.model.Jenkins
Jenkins.get().setSystemMessage('Учебный стенд. Рабочих ключей нет.')
Jenkins.get().save()
Цифра в начале имени — не украшение: файлы выполняются в алфавитном
порядке, и нумерация задаёт последовательность, когда скриптов
несколько.
ПОЧЕМУ В КУРСЕ МЫ ПРЕДПОЧИТАЕМ JCASC (ПРАКТИКА 14)
ПЕРВОЕ: у них нет состояния — скрипт выполняется при каждом старте
и не помнит, что уже был запущен, поэтому повторный запуск не должен
ничего ломать.
ВТОРОЕ: их сложно откатывать — записи о том, какими настройки были
до запуска, не остаётся. С JCasC наоборот: правите YAML, применяете,
не понравилось — вернули прежнюю версию файла из репозитория.
ТРЕТЬЕ, САМОЕ НЕПРИЯТНОЕ: ошибка ломает запуск. Если скрипт падает,
дальнейшая инициализация может не выполниться, и Jenkins запустится
не полностью — например, без части настроек безопасности.
КОГДА init.groovy.d УМЕСТЕН: для разовой операции, которую нельзя
описать декларативно, например для миграции данных нестандартного
плагина. Скрипт запускают один раз, а файл после этого удаляют.
ВАЖНО: правила здесь те же, что и для Script Console. Код выполняется
при запуске сервера с правами Jenkins, а чужой скрипт, скачанный
из интернета и положенный в этот каталог, — способ отдать сервер
вместе со всеми ключами.

ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================
ПРОБЛЕМА: «No such property: intance for class: jenkins.model.Jenkins»
Это опечатка в имени свойства, а не поломка Jenkins: «No such
property» означает «у объекта нет такого поля». Правильно —
Jenkins.get() или историческое Jenkins.instance; Jenkins сам
подсказывает варианты строкой Possible solutions: instance.
ПРОБЛЕМА: «No signature of method ... is applicable for argument types»
Метод есть, но переданы не те аргументы. Самый частый случай — забыт
второй параметр у getItemByFullName:
No signature of method:
static jenkins.model.Jenkins.getItemByFullName() is applicable for
argument types: (java.lang.String) values: [FirstJob]
Правильно: jenkins.getItemByFullName('FirstJob', Job.class). Другой
случай — строка вместо объекта: метод ждёт Job, а ему передали имя
задания строкой.
ПРОБЛЕМА: NullPointerException, когда задания с таким именем нет
getItemByFullName вернёт null, и следующая строка вида
job.getBuilds() упадёт с NullPointerException, в котором не будет
сказано, что задания нет. Проверяйте на null ДО обращения к методам:
def job = Jenkins.get().getItemByFullName('FirstJob', Job.class)
if (job == null) {
    println 'задания FirstJob нет — проверьте имя'
    return
}
println job.getBuilds().size()
Слово return в Script Console завершает скрипт целиком, а внутри
замыкания each — только текущую итерацию.
ПРОБЛЕМА: «Scripts not permitted to use method ...» в конвейере
Это песочница, а не ошибка вашего кода. Полный текст начинается
с RejectedAccessException: Scripts not permitted to use, дальше идёт
подпись вызова. Разбор и что делать — в разделе 9.
ПРОБЛЕМА: удаление во время обхода списка
(ConcurrentModificationException)
Элементы коллекции удаляются прямо в цикле, который её перебирает,
и перебор падает с java.util.ConcurrentModificationException. Разбор
в разделе 7; правильный способ — собрать список заранее:
def job = Jenkins.get().getItemByFullName('FirstJob', Job.class)
def victims = job.builds.drop(10).toList()   // собрали ДО удаления
victims.each { it.delete() }
ПРОБЛЕМА: скрипт «съел» память контроллера и Jenkins не отвечает
Симптомы: портал отвечает медленно или не отвечает, страница Script
Console висит, в журнале — сообщения о сборке мусора. Причина:
скрипт собрал в память слишком много объектов, например историю
сборок всех заданий сразу. Что делать:
  1. НЕ паниковать и не перезапускать службу сразу: скрипт работает
     в том же процессе, и когда он завершится или упадёт по нехватке
     памяти, сборщик мусора освободит объекты, а Jenkins обычно
     возвращается к работе сам;
  2. дождаться — дайте две-пять минут;
  3. если Jenkins не отвечает, посмотреть память и журнал на admin:
     free -h и sudo tail -50 /var/log/jenkins/jenkins.log — в журнале
     будет видно java.lang.OutOfMemoryError;
  4. если портал мёртв — перезапустить службу
     (sudo systemctl restart jenkins). ВАЖНО: перезапуск прервёт
     выполняющиеся сборки; если идут выкаты, лучше дождаться
     их окончания (Safe Restart, практика 2);
  5. после запуска переписать скрипт порциями: по одному заданию
     за запуск вместо «все сборки всех заданий».
ПРОБЛЕМА: «я удалил не то, что хотел»
  1. остановить скрипт: закрыть страницу Script Console недостаточно,
     процесс на сервере продолжается, надёжный способ — перезапуск
     службы со всеми его следствиями;
  2. оценить ущерб: посмотреть, какие задания и сборки остались;
  3. восстановить из копии (практика 14); точечно задания
     восстанавливаются из выгрузки export_jobs.groovy (раздел 8)
     командой create-job (практика 5);
  4. если копии нет — создать удалённое заново по практикам,
     в которых эти задания появились.
Поэтому и существует режим репетиции: скрипт, который сначала
печатает, что собирается сделать, избавляет от пункта 3.
ПРОБЛЕМА: Script Console не открывается
Пункт Manage Jenkins -> Script Console не виден, либо адрес
http://10.0.2.5:8080/script отвечает отказом. Причина всегда одна:
у пользователя нет разрешения Manage -> Scripts, а это уровень
администратора Jenkins. Выдавать его «на минуточку» не следует:
разрешение на Script Console — это разрешение на всё. Выдаётся
в Manage Jenkins -> Security -> Authorization (матрица прав), столбец
Manage -> Scripts. Проверка, что дело именно в правах: зайдите
под учётной записью engineer.

УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

1. ВЫГРУЖЕННЫЕ ОПИСАНИЯ: если выгрузка не нужна, удалите конкретный
каталог.
sudo ls -la /var/lib/jenkins/backups/
sudo rm -rf /var/lib/jenkins/backups/jobs-20260514-101500
ОСТОРОЖНО С rm -rf: путь указывается до конкретного каталога, а не
до backups целиком — в практике 14 он станет частью резервного
копирования.
2. ЧИСЛО ИСПОЛНИТЕЛЕЙ КОНТРОЛЛЕРА: если меняли через
setNumExecutors, верните прежнее значение (в лаборатории 1) —
в портале Manage Jenkins -> System -> # of executors или скриптом:
Jenkins.get().setNumExecutors(1)
Jenkins.get().save()
3. СИСТЕМНОЕ СООБЩЕНИЕ: если пробовали пример из раздела 12,
уберите его тем же способом — setSystemMessage('') и save().
4. ЗАДАНИЯ: проверьте, что на месте весь список курса — FirstJob,
build_with_params, periodic_report, gitea_build, site_pipeline.
Удалённое создаётся заново по тем практикам, где оно появилось.
5. РАЗРЕШЕНИЯ В SCRIPT APPROVAL: Manage Jenkins -> Security ->
Script Approval; всё, что одобрено «на попробовать», верните
в состояние ожидания — пока подпись одобрена, любой Jenkinsfile
в вашем репозитории может использовать этот вызов.
6. ФАЙЛЫ init.groovy.d: если создавали файл из раздела 12 ради
эксперимента, удалите его, иначе он будет выполняться при каждом
запуске Jenkins.
sudo rm /var/lib/jenkins/init.groovy.d/01-system-message.groovy
Проверка, что всё чисто:
sudo ls -la /var/lib/jenkins/backups/
sudo ls -la /var/lib/jenkins/init.groovy.d/
systemctl is-active jenkins
