Практика 7. Триггеры: что запускает сборку.

До сих пор сборки запускались руками: кнопкой Build Now, из Jenkins CLI
(практика 5) и вручную в задании, которое забирает код из репозитория
(практика 6). Так проверяют настройку задания. Автоматизация начинается
там, где сборка запускается сама, по событию.

Триггер — правило, по которому Jenkins решает, что пора собирать.
Готовый файл к практике: files/jobs/periodic_report.xml — задание
с расписанием, которое мы разберём построчно.

=========================================================================
ОБЗОР: ЧЕМ МОЖНО ЗАПУСТИТЬ СБОРКУ
=========================================================================

  СПОСОБ                            КОГДА ПРИМЕНЯТЬ     ЧЕГО СТОИТ
  --------------------------------  ------------------  -------------------
  Вручную (Build Now)               отладка, проверка   время человека
  Внешний запрос по токену          вызов из скриптов   раскрытая дверь
  После другой сборки (каскад)      цепочка этапов      цепочка не видна
  По расписанию                     регламентные задачи собирает впустую
  Опрос репозитория (Poll SCM)      вебхук невозможен   задержка, нагрузка
  Вебхук из репозитория             наш основной путь   нужен доступ внутрь
  Из конвейера (build step)         шаг конвейера       см. практику 10
  Из CLI и API                      автоматизация       токен и права

ПО РАСПИСАНИЮ. Jenkins запускает сборку в заданные моменты. Незаменимо
для регламентных работ; обратная сторона — расписание не знает,
есть ли что собирать.

ПО ИЗМЕНЕНИЯМ В РЕПОЗИТОРИИ. Jenkins сам спрашивает Git-сервер,
не изменилось ли что (Poll SCM), или Git-сервер сам сообщает о push
(вебхук). Первый работает всегда, но с задержкой и нагрузкой.

#########################################################################
ЧАСТЬ 1. БАЗОВАЯ ПРАКТИКА
#########################################################################

=========================================================================
1. ТРИГГЕР ПО ВНЕШНЕМУ ЗАПРОСУ
=========================================================================

1.1. Создаём задание: New Item → имя Build_auto_trigger1 → тип
Freestyle project.

1.2. Добавляем шаг сборки: Build Steps → Execute shell.

sleep 5
echo "Hello, World!"
sleep 5
echo "Build id: $BUILD_ID"
echo "Запущено: $(date '+%Y-%m-%d %H:%M:%S')"

1.3. Включаем триггер: Build Triggers → Trigger builds remotely
(e.g., from scripts) → Authentication Token:

PrIvEt213123

Токен — произвольный набор букв и цифр, но не осмысленное слово.

1.4. Сохраняем. Адрес для запуска получается такой:

http://10.0.2.5:8080/job/Build_auto_trigger1/build?token=PrIvEt213123

1.5. Пробуем запустить без аутентификации:

curl -X POST \
  "http://10.0.2.5:8080/job/Build_auto_trigger1/build?token=PrIvEt213123"

ПОЧЕМУ ЗАПРОС ПОЛУЧИТ ОТКАЗ, И ЭТО ПРАВИЛЬНО. В практике 2 закрыт
анонимный доступ: запускать что-либо может только аутентифицированный
пользователь. Токен триггера этого правила не отменяет — он лишь
подтверждает, что запрос адресован нужному заданию.

1.6. Создаём API-токен: engineer → Configure → API Token →
Add new Token → имя trigger-lab → Generate → копируем значение.

1.7. Запускаем сборку с аутентификацией:

curl -u engineer:API_ТОКЕН -X POST \
  "http://10.0.2.5:8080/job/Build_auto_trigger1/build?token=PrIvEt213123"

ЗАЧЕМ ДВА РАЗНЫХ ТОКЕНА. Токен триггера — «ключ от звонка»: он
означает, что запрос адресован этому заданию. API-токен пользователя —
«кто звонит»: он определяет права. engineer — администратор, а
serviceuser умеет только запускать сборки. Пароль вместо токена
не годится: он виден в истории команд и в списке процессов.

ВАЖНО: токен триггера в чужих руках позволяет запускать сборку,
но не читать журналы и не менять задание. Поэтому для внешних вызовов
заводят пользователя с минимальными правами.

1.8. Проверяем код ответа, а не только текст:

curl -s -o /dev/null -w '%{http_code}\n' -u engineer:API_ТОКЕН \
  -X POST \
  "http://10.0.2.5:8080/job/Build_auto_trigger1/build?token=PrIvEt213123"

  201 Created — сборка поставлена в очередь (обычный ответ на /build);
  200 OK — запрос обработан; так отвечает проверка состояния;
  302 Found — Jenkins перенаправил запрос, сборка запущена;
  403 Forbidden — нет -u, неверный токен или защита от подделки (CSRF);
  404 Not Found — нет задания или не тот токен триггера.

ОБРАТИТЕ ВНИМАНИЕ: curl не идёт по перенаправлению, поэтому 302
без ключа -L — не ошибка.

1.9. Про защиту от подделки запросов (CSRF). Если в ответе видно
«No valid crumb was included in the request», одного API-токена
для POST мало: нужен ещё crumb, выдаваемый сессионно. Запрашиваем:

curl -s -u engineer:API_ТОКЕН http://10.0.2.5:8080/crumbIssuer/api/json

Полученное значение передают заголовком Jenkins-Crumb:

curl -u engineer:API_ТОКЕН -H "Jenkins-Crumb: ЗНАЧЕНИЕ" -X POST \
  "http://10.0.2.5:8080/job/Build_auto_trigger1/build?token=PrIvEt213123"

=========================================================================
2. ИСПРАВЛЕНО: АНОНИМНЫЙ ДОСТУП И ГДЕ ХРАНИТЬ ТОКЕН
=========================================================================

СОВЕТ ПЕРВЫЙ, КАК БЫЛО: «Если вы хотите обеспечить запуск по триггеру
без авторизации, то нужно включить Allow anonymous read access
в Manage Jenkins → Security → Authorization».

ПОЧЕМУ ЭТО ПЛОХО. Анонимный доступ — это доступ ко всему порталу:
список заданий, журналы сборок (а в них бывают токены и внутренние
адреса), история, иногда артефакты. Ради одного curl открывается весь
Jenkins любому, кто дотянулся до порта 8080.

КАК ПРАВИЛЬНО: анонимный доступ оставляем закрытым (практика 2),
а запросу передаём API-токен ключом -u, как в разделе 1.7.

СОВЕТ ВТОРОЙ, КАК БЫЛО: «Обязательно запишите этот токен в какой-то
текстовый файл».

ПОЧЕМУ ЭТО ПЛОХО. «Какой-то текстовый файл» оказывается файлом
с правами по умолчанию и попадает в резервные копии каталога,
в синхронизацию облачного диска и в историю правок.

КАК ПРАВИЛЬНО. Для опытов — файл, доступный только владельцу:

umask 077
printf '%s' 'PrIvEt213123' > ~/.jenkins-trigger-token
chmod 600 ~/.jenkins-trigger-token

TOKEN=$(cat ~/.jenkins-trigger-token)
curl -u engineer:API_ТОКЕН -X POST \
  "http://10.0.2.5:8080/job/Build_auto_trigger1/build?token=$TOKEN"

Для работы — хранить токен в credentials Jenkins (Secret text —
это подходит для токена триггера, который читает сам конвейер)
и подставлять его в конвейере через привязку секретов (практика 11).

УТОЧНЕНО: сам токен триггера всё равно уходит в URL, а URL попадает
в журналы доступа Jenkins и обратного прокси. Полностью спрятать его
нельзя — это особенность механизма. Поэтому в рабочей среде заводят
отдельный токен на каждое задание и меняют его при подозрении
на утечку.

=========================================================================
3. КАСКАД: BUILD AFTER OTHER PROJECTS ARE BUILT
=========================================================================

3.1. Создаём Build_auto_trigger2 копией первого: Build_auto_trigger1
→ New Item → имя Build_auto_trigger2 → внизу списка копирования
выбираем Build_auto_trigger1 → OK.

3.2. Снимаем Trigger builds remotely и отмечаем Build after other
projects are built. В поле Projects to watch пишем Build_auto_trigger1.

3.3. Разбираем остальные поля раздела:

  Trigger even if the build fails — запускать B, даже если A упало;
  Trigger even if it is unstable — запускать, даже если A завершилось
    «нестабильно» (есть неудачные тесты, но сборка дошла до конца);
  Если не отмечено ни то, ни другое — B запускается только после
    полностью успешной A. Это и есть пороговое поведение, которое
    в интерфейсе описывают словами «only if the build is stable».

ВАЖНО: по умолчанию оба флажка сняты, и это разумно. Включённый
«Trigger even if the build fails» превращает каскад в цепочку, которая
продолжает работать после поломки, — а это ровно то, чего не хочется
при выкате.

3.4. Проверяем: запускаем первое задание запросом из раздела 1.7
и открываем журнал второго.

  Started by upstream project "Build_auto_trigger1" build number 3

3.5. Смотрим связи в портале: Upstream Builds (кто запускает задание)
и Downstream Builds (кого запускает оно). Это единственное место,
где каскад виден целиком.

ПОЧЕМУ У КАСКАДОВ ЕСТЬ ЦЕНА:

  * ЦЕПОЧКА ПЛОХО ВИДНА: в упавшей сборке видно только «Started
    by upstream project», а что было до неё — в другом задании;
  * ОДИН УПАВШИЙ ШАГ ОСТАНАВЛИВАЕТ ВСЁ: если A упало, B не запустится,
    и по истории B этого не видно — там просто нет новой сборки;
  * «СБОРКА РАДИ СБОРКИ» СЪЕДАЕТ ИСПОЛНИТЕЛЕЙ: цепочка из пяти заданий
    занимает исполнителя пять раз, каждое со своим git clone.

КОГДА КАСКАД УМЕСТЕН: когда этапы разные по смыслу и по исполнителям —
сборка кода, тесты на отдельном агенте, выкат на стенд, проверка сайта.
КОГДА ЛУЧШЕ ОДИН КОНВЕЙЕР: когда речь о последовательности внутри
одной задачи. В конвейере это видно как стадии одной сборки; сделаем
это в практике 10, а в практике 11 доведём выкат до node1 и node2.

=========================================================================
4. BUILD PERIODICALLY: СБОРКА ПО РАСПИСАНИЮ
=========================================================================

4.1. Создаём Build_auto_trigger3 копией первого задания, снимаем
Trigger builds remotely и отмечаем Build periodically. В поле Schedule:

H/5 * * * *

4.2. Синтаксис расписания — пять полей через пробел:

  ПОЛЕ          ЧТО ЗАДАЁТ       ДИАПАЗОН
  ------------  ---------------  -------------------
  минута        минута часа      0-59
  час           час суток        0-23
  день месяца   число месяца     1-31
  месяц         номер месяца     1-12
  день недели   день недели      0-7 (0 и 7 — воскресенье)

Звёздочка означает «любое значение», слэш задаёт шаг (*/15 — «каждые
15 единиц»), дефис — диапазон (1-5), запятая перечисляет значения.

4.3. Примеры:

  РАСПИСАНИЕ        СМЫСЛ
  ----------------  ---------------------------------------------------
  H/15 * * * *      каждые 15 минут, смещение выбирает сам Jenkins
  */15 * * * *      каждые 15 минут по общим часам (см. ниже про H)
  H * * * *         раз в час, минуту выбирает Jenkins
  H H * * *         раз в сутки, время выбирает Jenkins
  0 3 * * *         каждый день ровно в 03:00
  H(0-7) * * * *    каждый час в течение первых восьми минут

4.4. Символ H и почему он лучше звёздочки. H — не опечатка и не
«hour». Это хеш: Jenkins вычисляет его из имени задания и получает
постоянное, но своё для каждого задания смещение внутри интервала.

ОБРАТИТЕ ВНИМАНИЕ, разница видна на числах. Двадцать заданий
с */15 стартуют одновременно — в 00:00, 00:15, 00:30: получается пик,
а между пиками контроллер и исполнители простаивают. Те же задания
с H/15 размазаны по интервалу: одно в 00:01, другое в 00:03, третье
в 00:07. Нагрузка ровная, число сборок то же.

4.5. Часовой пояс. Расписание считается в поясе операционной системы
контроллера: в облачных машинах это почти всегда UTC.

date
timedatectl

Если расписание должно считаться в другом поясе, пояс указывают прямо
в расписании первой строкой:

TZ=Europe/Moscow
H 3 * * *

Теперь «03:00» означает три часа ночи по Москве, а не по часам сервера.

ВАЖНО: часовой пояс — самая частая причина «расписание не работает».

4.6. Как проверить следующий запуск: в разделе Build Triggers Jenkins
показывает ближайшие моменты запуска по расписанию. Названия пунктов
могут немного отличаться в вашей версии Jenkins — ориентируйтесь
на смысл.

4.7. УТОЧНЕНО про точность. Расписание не гарантирует запуск ровно
в назначенную минуту: Jenkins проверяет его периодически и ставит
сборку в очередь, а дальше она ждёт свободного исполнителя.

ОТСЮДА ВЫВОД: не ставьте на расписание то, что должно выполняться
строго по времени, — такие задачи решают системным планировщиком,
а Jenkins дёргают внешним запросом из раздела 1.

4.8. Смотрим, как тот же триггер выглядит в XML. Открываем
files/jobs/periodic_report.xml — готовое задание с расписанием:

<triggers>
  <hudson.triggers.TimerTrigger>
    <spec>H/15 * * * *</spec>
  </hudson.triggers.TimerTrigger>
</triggers>

Раздел triggers содержит один триггер типа TimerTrigger, а внутри —
строка расписания, ровно та же, что вводится в портале.

ЗАЧЕМ ЭТО ЗНАТЬ: через XML задание переезжает на другой Jenkins
целиком, задание можно создавать из командной строки (практика 5)
и хранить его описание в репозитории, а при разборе поломки видно,
что реально сохранено.

=========================================================================
5. POLL SCM: JENKINS СПРАШИВАЕТ РЕПОЗИТОРИЙ
=========================================================================

Jenkins сам, по расписанию, обращается к репозиторию и проверяет,
не появились ли новые коммиты. Если появились — запускает сборку.

5.1. Открываем задание gitea_build из практики 6 (источник кода
ssh://git@10.0.2.5:2222/engineer/site.git, ветка main, credentials
gitea-reader), в разделе Build Triggers отмечаем Poll SCM и задаём
H/5 * * * *. Через несколько минут в истории появится запись:

  Started by an SCM change

5.2. Что Jenkins делает при опросе. Он обращается к Git-серверу
и спрашивает список ссылок (операция вида git ls-remote): какой коммит
сейчас в ветке main. Если хеш совпадает с запомненным от прошлой
сборки, новых коммитов нет.

ОБРАТИТЕ ВНИМАНИЕ: этим же механизмом пользуется и вебхук. Разница
только в том, кто просит проверить репозиторий: при опросе — таймер
Jenkins, при вебхуке — Git-сервер. Поэтому в разделе 6 нам понадобится
тот же триггер Poll SCM, но с ПУСТЫМ расписанием: таймер не нужен,
а способность «опросить по требованию» — нужна.

Увидеть это можно своими глазами: на странице задания есть ссылка
Polling Log. Если изменений не было, в журнале опроса будет:

  No changes

Именно эту строку ищут, когда кажется, что «опрос не работает»:
No changes при отсутствии Started by an SCM change означает, что опрос
работает, а изменений в отслеживаемой ветке нет.

5.3. Сравниваем с вебхуком.

  ЗАДЕРЖКА: при H/5 среднее ожидание — около двух с половиной минут,
  максимальное — пять. При вебхуке сборка стартует через секунды.

  НАГРУЗКА: двести заданий с опросом раз в минуту дают двести
  обращений к Git-серверу каждую минуту, днём и ночью. Двести
  вебхуков — двести запросов за день, по числу реальных push.


=========================================================================
6. ВЕБХУК ИЗ GITEA: ГЛАВНАЯ ТЕМА ПРАКТИКИ
=========================================================================

Это основной для нас способ: самый быстрый и самый дешёвый
по нагрузке. Именно поэтому в практике 6 мы поставили свой Git-сервер
Gitea — внешний сервис до нашего Jenkins не дотянется.

Как это работает. Разработчик делает push. Gitea сразу отправляет
HTTP-запрос на адрес Jenkins с описанием события: кто, в какой
репозиторий, в какую ветку, какой коммит. Jenkins принимает запрос
и запускает задания, связанные с этим репозиторием.

6.1. Проверяем плагин: Manage Jenkins → Plugins → Installed plugins
(или Available plugins) → в поиске gitea. Он есть в списке
files/jcasc/plugins.txt; если его нет — ставим со страницы
Available plugins и перезапускаем Jenkins.

6.2. Описываем сервер Gitea: Manage Jenkins → System → раздел
с настройками Gitea. Добавляем сервер:

  имя:    gitea-lab
  адрес:  http://10.0.2.5:3000
  токен:  credentials gitea-token (это credential вида Gitea Personal
          Access Token, созданный в практике 6; обычный Secret text
          в списке не появится)
  управление вебхуками: включить, если плагин это предлагает

ГДЕ ВЗЯТЬ ТОКЕН. Это токен API Gitea, и создаётся он в самой Gitea:
аватар → Settings → Applications → Manage Access Tokens → Generate New
Token. Области прав: доступ к репозиториям на чтение и запись (плагин
сам создаёт и обновляет вебхуки) и чтение профиля; права администратора
не нужны. Токен показывается ровно один раз, поэтому его сразу кладут
в Jenkins — в credential вида Gitea Personal Access Token (это вид,
который объявляет сам плагин) с идентификатором gitea-token. Обычный
Secret text в этом поле не появится: плагин предлагает только credential
своего вида, и это фильтр по типу, а не поломка. Весь порядок действий
вместе с проверкой разобран в практике 6, раздел 7, ШАГ 5 «Токен API:
вторая дверь в Gitea».

Проверить токен можно до настройки плагина, с машины admin:

  curl -s -H "Authorization: token ЗНАЧЕНИЕ_ТОКЕНА" \
    http://10.0.2.5:3000/api/v1/version

Ответ с версией в JSON означает, что токен рабочий. Код 401 или
{"message":"token is required"} — токен отозван, потерян или скопирован
не целиком: создайте новый и обновите значение в credentials.

ЕСЛИ ПОЛЕ ДЛЯ CREDENTIALS ПУСТОЕ. Плагин работает и без токена: тогда
вебхук создаётся руками по шагам ниже, а автоматическая регистрация
вебхуков и список репозиториев будут недоступны. Для одного задания
этого достаточно, но токен мы настраиваем: он же понадобится, когда
заданий и репозиториев станет больше.

ЧТО ДОЛЖНО БЫТЬ В ЗАДАНИИ, ИНАЧЕ ВЕБХУК НИЧЕГО НЕ ЗАПУСТИТ

Это вторая ловушка вебхуков, и она не в Gitea, а в Jenkins. Вебхук
не запускает сборку сам: он говорит Jenkins «в этом репозитории что-то
изменилось — проверь его сейчас». А проверку делает тот же механизм,
что и у опроса репозитория. Отсюда два условия, и нужны оба.

1. В ЗАДАНИИ НАСТРОЕН ИСТОЧНИК КОДА. Раздел «Source Code Management»
должен быть заполнен: Git, адрес нашего репозитория, credentials
gitea-reader (практика 6, раздел 7). Если источника нет, проверять
нечего: запрос Jenkins примет, а сравнивать присланную ревизию будет
не с чем.

2. ВКЛЮЧЁН ТРИГГЕР POLL SCM — С ПУСТЫМ РАСПИСАНИЕМ. Выглядит странно,
но так и задумано:

  Build Triggers → [x] Poll SCM
  Schedule: поле оставляем ПУСТЫМ

Пустое расписание означает «сам по себе не опрашивай, но если попросят —
опроси». Просит как раз вебхук. Если вписать сюда H/5 * * * *, задание
будет ходить в репозиторий каждые пять минут и без вебхука: получатся
сборки «на всякий случай» и, при неудачном совпадении, двойные запуски
(раздел 9).

ОТДЕЛЬНОГО ПУНКТА «ПРИНИМАТЬ ВЕБХУКИ» В ЗАДАНИИ НЕ ТРЕБУЕТСЯ. Здесь
есть отличие от плагина GitHub, где в разделе Build Triggers появляется
своя галочка: у плагина Gitea такого обязательного пункта нет. Принятый
вебхук приводит к опросу всех заданий, у которых включён опрос
репозитория и совпадает адрес. Проверено на стенде: с этими двумя
условиями сборка запускается, а стоит снять Poll SCM — и вебхук
перестаёт что-либо запускать, хотя Gitea продолжает получать ответ 200.

Если в вашей версии плагина в разделе Build Triggers всё же есть пункт
со словами Gitea и hook, включать его не обязательно: к описанному
механизму он ничего не добавляет.

ЖДАТЬ БЫСТРОГО РЕЗУЛЬТАТА НЕ СТОИТ: сборка запустится не мгновенно,
а после того как Jenkins опросит репозиторий и увидит новую ревизию.
Поэтому первая же сборка после push помечается в журнале как
«Started by an SCM change» — это нормальный признак, что всё сработало.

ТО ЖЕ САМОЕ ДЛЯ КОНВЕЙЕРА. Задание site_pipeline из практики 10 описано
в репозитории («Pipeline script from SCM») — правило то же: источник
кода заполнен и включён Poll SCM с пустым расписанием.

6.3. Добавляем вебхук в Gitea: открываем репозиторий

http://10.0.2.5:3000/engineer/site
Settings → Webhooks → Add Webhook

  тип:         Gitea (для старых версий плагина — Gogs)
  Target URL:  http://10.0.2.5:8080/gitea-webhook/post
  метод:       POST
  тип данных:  application/json
  события:     Push events
  фильтр:      ветка main
  Active:      включено

Точный путь вебхука зависит от версии плагина: в настройках сервера
Gitea в Jenkins рядом с адресом обычно показан готовый адрес вебхука.
Название пункта может немного отличаться в вашей версии плагина,
ориентируйтесь на смысл.

СНАЧАЛА ПРОВЕРЬТЕ ОДНО НАСТРОЕНИЕ GITEA, ИНАЧЕ ВЕБХУК НЕ СОЗДАСТСЯ.
В Gitea 1.16 и новее вебхуки по умолчанию разрешены только на внешние
адреса (значение external в параметре ALLOWED_HOST_LIST): так Git-сервер
защищают от SSRF — обращения к внутренним адресам по чужой указке.
Наш Jenkins находится на приватном адресе 10.0.2.5, поэтому такой вебхук
Gitea отвергнет: API ответит 403 с сообщением о недопустимом адресе,
и это сообщение легко принять за проблему токена.

Лечится это в файле /etc/gitea/app.ini (он разбирается в практике 6,
раздел 2):

  [webhook]
  ALLOWED_HOST_LIST = 10.0.2.5

После правки:

  sudo systemctl restart gitea

ВАЖНО ПРО САМ ПАРАМЕТР: ставить * (разрешить все адреса) не нужно.
Перечислите конкретные адреса — тогда защита остаётся, а наш Jenkins
в неё попадает. Проверка перед созданием вебхука:

  curl -s -o /dev/null -w '%{http_code}\n' http://10.0.2.5:8080/login

6.4. Проверяем доставку. В Gitea на странице вебхука есть Recent
Deliveries: видно запрос, ответ Jenkins и код ответа. Ответ 200
означает, что Jenkins запрос принял; рядом есть кнопка повторной
отправки (Redeliver).

ВАЖНО: успешная доставка (200) ещё не означает, что сборка запущена.
Jenkins может принять запрос и не найти подходящего задания — ответ
будет тем же, а сборки не будет. Разбираем в разделе 11.

6.5. Смотрим, что происходит в Jenkins: Manage Jenkins → System Log →
New Log Recorder, имя регистратора (например, gitea) и уровень FINE.
Имя регистратора зависит от версии плагина, поэтому ориентируйтесь
на смысл. После следующего push там будут строки о приёме вебхука.

6.6. Проверка по-настоящему. На машине admin, в рабочей копии
репозитория из практики 6:

cd ~/site
git pull
echo "Вебхук проверен $(date '+%Y-%m-%d %H:%M:%S')" >> index.html
git add index.html
git commit -m "Проверка вебхука из Gitea"
git push

6.7. Смотрим результат в Jenkins: открываем задание gitea_build
и его последнюю сборку. В журнале первой строкой будет примерно:

  Started by Gitea push by engineer

Дальше идут обычные шаги задания — в практике 6 это вывод каталога
и содержимого index.html.

6.8. ПОЧЕМУ ТО ЖЕ САМОЕ НЕВОЗМОЖНО ДЛЯ ОБЛАЧНОГО GITHUB.

У нашего стенда нет белого IP, и весь он живёт внутри подсети
10.0.2.0/24. Адрес http://10.0.2.5:8080 снаружи не существует:
он не маршрутизируется из интернета. Когда GitHub обрабатывает push,
он пытается отправить вебхук на указанный адрес — и не может.

Это не вопрос настройки, который решается галочкой. Чтобы вебхук
из интернета дошёл, нужен внешний адрес, обратный прокси или туннель
наружу, либо промежуточный сервис, принимающий вебхук из интернета
и переправляющий его внутрь. Все три варианта означают, что Jenkins
или его часть становится доступен снаружи.

Для учебного стенда это лишнее, поэтому в практике 6 мы поставили
Gitea на машине admin: вебхук от неё до Jenkins идёт внутри подсети,
за миллисекунды, и весь механизм разбирается по-настоящему.

=========================================================================
7. ТИШИНА ПЕРЕД ЗАПУСКОМ (QUIET PERIOD)
=========================================================================

Тишина (quiet period) — пауза между моментом, когда Jenkins решил,
что пора собирать, и моментом старта сборки. Значение по умолчанию —
5 секунд; настроить можно глобально: Manage Jenkins → Configure System
→ поле Quiet period (в секундах).

ЗАЧЕМ ЭТО НУЖНО. Разработчик заканчивает работу и делает пять
коммитов подряд. Без тишины каждый push порождает свою сборку: пять
сборок одного кода, четыре из которых собирают промежуточное
состояние. С тишиной Jenkins ждёт указанное время, и если за это время
приходит новое сообщение об изменении, оно относится к той же сборке,
которая уже стоит в очереди: второй записи не появляется, а собран
будет последний коммит.

Где переопределить для задания: в настройках задания, в разделе
Build Triggers, есть кнопка Advanced — там находится поле Quiet period
для этого задания. В некоторых версиях Jenkins то же поле находится
в разделе Advanced Project Options. Название может немного отличаться,
ориентируйтесь на смысл.

Для опроса репозитория есть отдельное значение — тишина опроса
(SCM polling quiet period): сколько ждать после того, как опрос
обнаружил изменения. По умолчанию ноль.

Чего тишина НЕ делает: не отменяет сборку, а откладывает её,
не склеивает сборки разных заданий и не спасает от двух сборок, если
включены два механизма запуска — вебхук и опрос запустят каждое своё
дело, а тишина лишь сдвинет старт.

8. СРАВНЕНИЕ СТРАТЕГИЙ
=========================================================================

Сведём способы запуска в таблицу, добавив то, чего не было в первой:
чем каждый способ ломается.

  СПОСОБ          ЗАДЕРЖКА  НАГРУЗКА     ДОСТУП   ЧТО ЛОМАЕТСЯ
  --------------  --------  -----------  -------  -------------------
  вебхук          секунды   низкая       да       плагин и путь к нему
  Poll SCM        до минут  растёт       нет      нагрузка на Git
  расписание      нет       постоянная   нет      сборки без изменений
  каскад          секунды   цепочка      нет      скрытая связь заданий
  внешний запрос  секунды   низкая       да       токен в чужом скрипте

ВЫВОД ДЛЯ НАШЕГО СТЕНДА:

  * вебхук из Gitea — основной способ для всего, что связано
    с репозиторием: сборка, тесты, выкат;
  * Poll SCM — запасной: он остаётся настроенным на случай,
    если вебхук не доставился;
  * расписание — только для регламентных задач, у которых нет
    источника изменений: отчёты о состоянии, чистки, проверки;
  * внешний запрос — для интеграций, где Jenkins дёргает внешняя
    система.

=========================================================================
9. ОПАСНЫЕ СОЧЕТАНИЯ
=========================================================================

Пять ситуаций, которые встречаются в работе постоянно.

ВЕБХУК И POLL SCM ОДНОВРЕМЕННО. Один коммит — две сборки: одну
запустил вебхук, другую нашёл опрос. Сборки разные, номера разные,
история путается; при выкате сайт выкатывается дважды.
ЛЕЧЕНИЕ: выбрать одно. У нас — вебхук.

КАСКАД И РАСПИСАНИЕ ВМЕСТЕ. Задание B запускается и после сборки A,
и по расписанию. Расписание тратит исполнителей на ненужные сборки,
а в журнале B чередуются «Started by upstream project» и «Started
by timer».
ЛЕЧЕНИЕ: у задания должна быть одна причина запуска.

ОДНОВРЕМЕННЫЕ СБОРКИ ОДНОГО ЗАДАНИЯ. Два push подряд, два вебхука,
две сборки идут параллельно и пишут в один рабочий каталог. Итог:
перепутанные файлы и выкат, собранный из двух разных коммитов.
ЛЕЧЕНИЕ: не отмечать в настройках задания Execute concurrent builds
if necessary.

СБОРКА ПО РАСПИСАНИЮ ПРИ ЕЖЕЧАСНЫХ ИЗМЕНЕНИЯХ. Задание собирается
каждую ночь, а код меняется каждый час. Днём разработчики смотрят
на результаты ночной сборки — то есть на код, которого уже нет.
ЛЕЧЕНИЕ: если у задачи есть источник изменений в репозитории,
расписание ей не нужно.

ЧАСТЫЕ ТРИГГЕРЫ БЕЗ ОГРАНИЧЕНИЯ ИСТОРИИ. Десять заданий с вебхуком
на активный репозиторий плюс задание с расписанием H/5 — это сотни
сборок в сутки. Без Discard old builds каталог JENKINS_HOME растёт,
и однажды кончается место. Место кончается молча: сборки идут,
но начинают падать с самыми разными ошибками.
ЛЕЧЕНИЕ: правило хранения сборок задавать вместе с триггером.

=========================================================================
10. ТРИГГЕР И ПАРАМЕТРЫ СБОРКИ
=========================================================================

У параметризованного задания триггер работает так же, но появляется
вопрос: откуда берутся значения параметров, если сборку запустил
не человек?

  * ПО РАСПИСАНИЮ И ПО КАСКАДУ — значения по умолчанию, объявленные
    в задании: формы ввода нет;
  * ПО ВНЕШНЕМУ ЗАПРОСУ — параметры в адресе. Сборка ставится
    не на /build, а на /buildWithParameters:

curl -u engineer:API_ТОКЕН -X POST \
  "http://10.0.2.5:8080/job/build_with_params/buildWithParameters" \
  -d "TARGET_PATH=/etc"

Если у задания включён триггер Trigger builds remotely, в запрос
добавляется и token триггера — но у build_with_params он не включён,
поэтому в примере его нет.

  * ПО ВЕБХУКУ — параметры из полезной нагрузки, которую прислал
    Git-сервер: ветка, имя коммита, автор. Чтобы использовать их
    в задании, нужен либо плагин, который их пробрасывает, либо
    плагин универсальных вебхуков: он разбирает JSON и делает
    из его полей параметры сборки.

ВАЖНО: параметры из вебхука — это пользовательский ввод, и доверять
ему нельзя. Проверка ввода — тема практики 8. Здесь ограничимся
подводкой: у параметризованного задания (build_with_params) триггер
и параметры связаны, и разбирать их вместе удобнее.

=========================================================================
11. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

Триггеры — самая «молчаливая» часть Jenkins: сломанный триггер
не показывает ошибку, просто ничего не происходит.

ПРОБЛЕМА: триггер по URL возвращает 403.

  * ЗАПРОС БЕЗ АУТЕНТИФИКАЦИИ: анонимный доступ закрыт (практика 2).
    Лечение: добавить ключ -u engineer:API_ТОКЕН.
  * НЕТ CRUMB: в ответе «No valid crumb was included in the request».
    Лечение: получить crumb (раздел 1.9) и передать заголовком.
  * НЕВЕРНЫЙ ИЛИ ОТОЗВАННЫЙ API-ТОКЕН. Проверить отдельно:

curl -s -o /dev/null -w '%{http_code}\n' -u engineer:API_ТОКЕН \
  http://10.0.2.5:8080/api/json

  Ответ 200 означает, что токен рабочий, и дело не в нём.
  * НЕТ ПРАВА ЗАПУСКАТЬ СБОРКИ: у serviceuser право есть, у читателя
    чужого задания — нет.

ПРОБЛЕМА: ответ 200, но сборка не запускается.

  * НЕ ТОТ ТОКЕН ТРИГГЕРА: сравнить с полем Authentication Token
    в задании — буква в букву, включая регистр.
  * ЗАДАНИЕ НА ПАУЗЕ: оно серое и подписано Disabled; триггеры
    у такого задания не работают вообще.
  * ЗАДАНИЕ ЖДЁТ ИСПОЛНИТЕЛЯ: нет свободных агентов или ни один агент
    не подходит по метке; видно в списке очереди слева в портале.
  * ЗАПРОС ПРИШЁЛ МЕТОДОМ GET: Jenkins отдаёт HTML-страницу задания,
    и код 200 означает совсем не то, что мы думали.

ПРОБЛЕМА: вебхук в Gitea показывает 200, но сборки нет.

  * ЗАДАНИЕ НЕ ОПРАШИВАЕТСЯ — и это самая частая причина. Вебхук
    не запускает сборку, а просит Jenkins проверить репозиторий,
    поэтому в задании должны быть заполненный Source Code Management
    (Git, адрес репозитория, credentials gitea-reader) и включённый
    Poll SCM с ПУСТЫМ расписанием. Отдельного пункта «принимать
    вебхуки» у плагина Gitea нет и не требуется. Нет любого
    из двух условий — запрос принимается, а сборки не будет. Смотреть
    Polling Log задания: после push там появляется опрос, вызванный
    вебхуком, а сборка помечается «Started by an SCM change».
  * ИМЯ ЗАДАНИЯ НЕ СОВПАДАЕТ С ОЖИДАЕМЫМ: проверить, что задание
    gitea_build связано с репозиторием engineer/site.
  * ПЛАГИН НЕ УСТАНОВЛЕН: запрос принимает сам Jenkins, а обрабатывать
    его некому.
  * ВЕТКА НЕ ТА ЖЕ: задание следит за main, а push сделан в другую
    ветку; сверить ветку в задании и фильтр ветки в вебхуке.
  * ЗАДАНИЕ НЕ СОБИРАЛОСЬ НИ РАЗУ: Jenkins сравнивает присланный
    коммит с тем, что помнит от прошлой сборки, а сравнивать не с чем.
  * ИЩЕМ НЕ ТАМ: сборка могла пойти в другое задание, которое тоже
    связано с этим репозиторием.

ПРОБЛЕМА: в настройках сервера Gitea нельзя выбрать Secret text.

  Это не поломка, а фильтр по типу: плагин принимает только credentials
  своего вида и остальные в списке не показывает. Создаём credential
  вида Gitea Personal Access Token (Manage Jenkins → Credentials →
  Add Credentials) с идентификатором gitea-token — после сохранения
  он появится в списке. Если вида от плагина нет вообще, проверьте,
  что плагин установлен, включён и Jenkins перезапускался: практика 6,
  раздел 7, ШАГ 5.

  Вид «Gitea Username with private key» из того же списка для этой задачи
  не подходит: он про вход по SSH-ключу, а не про токен API.

ПРОБЛЕМА: плагин отвечает 403 при работе с сервером Gitea.

  403 — «опознан, но не разрешено». Проверяйте по порядку:

  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "Authorization: token ЗНАЧЕНИЕ_ТОКЕНА" \
    http://10.0.2.5:3000/api/v1/version

  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "Authorization: token ЗНАЧЕНИЕ_ТОКЕНА" \
    http://10.0.2.5:3000/api/v1/repos/engineer/site/hooks

  * первая 401 — токен не принят: опечатка, отозван, потерян;
  * первая 200, вторая 403 — не хватает областей прав: для управления
    вебхуками нужен доступ к репозиториям на чтение и запись;
  * первая 200, вторая 404 — нет доступа к репозиторию (он приватный);
  * обе 200, а плагин всё равно ругается — проверьте адрес сервера:
    он должен быть http://10.0.2.5:3000, без /api/v1 в конце (путь
    к API плагин добавляет сам).

ОТДЕЛЬНО ВАЖНО: 403 БЫВАЕТ ДВУХ РАЗНЫХ ВИДОВ, и путать их нельзя.
Первая — отказ API по правам токена (то, что разобрано выше). Вторая —
отказ самого Git-сервера создавать вебхук на приватный адрес: в Gitea
1.16 и новее параметр ALLOWED_HOST_LIST по умолчанию равен external,
то есть вебхуки на внутренние адреса запрещены. Сообщение об этом
выглядит похоже, но токен здесь ни при чём: лечится не пересозданием
токена, а строкой в /etc/gitea/app.ini

  [webhook]
  ALLOWED_HOST_LIST = 10.0.2.5

и перезапуском службы (sudo systemctl restart gitea). Признак, по
которому эти случаи различаются: API отвечает на запросы нормально
(проверки из начала раздела проходят с кодом 200), а вебхук всё равно
не создаётся или не доставляется.

ПРОБЛЕМА: вебхук не доставляется вообще.

  * ЗАПРЕЩЁН ПРИВАТНЫЙ АДРЕС — и это самая частая причина на стенде.
    В Gitea 1.16 и новее ALLOWED_HOST_LIST по умолчанию равен external,
    поэтому вебхук на http://10.0.2.5:8080 не создаётся (403) или
    не доставляется. Добавьте адрес в /etc/gitea/app.ini:

  [webhook]
  ALLOWED_HOST_LIST = 10.0.2.5

    и перезапустите службу: sudo systemctl restart gitea. Проверить
    действующее значение: grep -A2 '\[webhook\]' /etc/gitea/app.ini
  * НЕВЕРНЫЙ АДРЕС ИЛИ ПОРТ: путь и порт 8080; частая ошибка —
    поставить 3000, порт самой Gitea.
  * JENKINS НЕ ЗАПУЩЕН. Проверяем:

systemctl status jenkins
curl -s -o /dev/null -w '%{http_code}\n' http://10.0.2.5:8080/login

  * СЕТЬ МЕЖДУ СЛУЖБАМИ: обратный прокси или фильтрация. На нашем
    стенде обе службы на машине admin, но в рабочей среде проверяют
    именно сеть между Git-сервером и Jenkins.

ПРОБЛЕМА: Poll SCM не видит изменения.

  * CREDENTIALS: ключ gitea-reader не подходит репозиторию; смотреть
    Polling Log, а не журнал сборки.
  * ВЕТКА: изменения в другой ветке — опрос сообщит No changes.
  * ИЗМЕНЕНИЯ ЕСТЬ, НО НЕ НА СЕРВЕРЕ: правка не отправлена (git commit
    без git push).
  * ТИШИНА НЕ ИСТЕКЛА: между обнаружением изменения и стартом сборки
    есть пауза (раздел 7).
  * РАСПИСАНИЕ ОПРОСА СЛИШКОМ РЕДКОЕ: при H H * * * опрос идёт
    раз в сутки.

ПРОБЛЕМА: расписание не срабатывает.

  * НЕВЕРНОЕ ИЛИ СЛИШКОМ РЕДКОЕ РАСПИСАНИЕ: пять полей, порядок
    которых легко перепутать, — минута идёт первой.
  * ЧАСОВОЙ ПОЯС: расписание считается в поясе сервера (в облаке
    обычно UTC); лечение — команда date и явный TZ (раздел 4.5).
  * JENKINS БЫЛ ВЫКЛЮЧЕН: пропущенные запуски не догоняются, и
    в истории такой пропуск не виден — просто нет сборки.
  * ЗАДАНИЕ ОТКЛЮЧЕНО ИЛИ ЖДЁТ ИСПОЛНИТЕЛЯ: причины те же, что выше.
  * ТРИГГЕР СНЯТ: копирование задания или ручная правка оставляют
    задание без галочки Build periodically.

ПРОБЛЕМА: сборка запускается дважды.

  * ВКЛЮЧЕНЫ И ОПРОС, И ВЕБХУК: оставить один механизм.
  * ДВА ВЕБХУКА НА ОДНО СОБЫТИЕ: Settings → Webhooks, удалить лишние.
  * ВЕБХУК И ВНЕШНИЙ ЗАПРОС: скрипт выката дёргает задание, а оно
    само реагирует на push; оставить что-то одно.
  * ДВА ЗАДАНИЯ НА ОДИН РЕПОЗИТОРИЙ: вебхук запускает оба.

ПРОБЛЕМА: сборка стоит в очереди после триггера.

Очередь — не ошибка: сборка ждёт исполнителя.

  * НЕТ СВОБОДНЫХ ИСПОЛНИТЕЛЕЙ: посмотреть Manage Jenkins → Nodes
    и понять, кто занят и чем.
  * МЕТКА НЕ СОВПАДАЕТ: у нас метки web node1 и web node2 docker;
    опечатка в настройке задания приводит к вечной очереди.
  * АГЕНТ В СОСТОЯНИИ OFFLINE: узел недоступен — например, на node1
    остановлена служба SSH.
  * ПРЕДЫДУЩАЯ СБОРКА ЕЩЁ ИДЁТ: при запрете одновременных сборок
    вторая ждёт освобождения первой — это правильное поведение,
    но выглядит оно как «сборка зависла».

Рядом с каждой записью в списке очереди Jenkins печатает причину
ожидания — это самое полезное место при разборе «почему ничего нет».

=========================================================================
УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

1. Удаляем задания-опыты Build_auto_trigger1, Build_auto_trigger2
и Build_auto_trigger3: в списке заданий у каждого — стрелка справа →
Delete Project → Yes.

2. В задании gitea_build снимаем галочку Poll SCM: оно остаётся
с вебхуком, и этого достаточно. Задание periodic_report оставляем
с расписанием H/15 * * * *, но помните: пока оно включено, оно
собирается каждые 15 минут и занимает исполнителя.

3. Вебхук в Gitea: http://10.0.2.5:3000/engineer/site → Settings →
Webhooks. Если вебхук был нужен только для опытов — удаляем его;
если он остаётся основным механизмом запуска, оставляем включённым
и удаляем только дубликаты и «пробные» записи.

4. Токен триггера: меняем значение Authentication Token в задании
или удаляем задание целиком. Если токен попал в чужой документ
или переписку, обнуляем его обязательно.

5. API-токен: созданный для опытов токен engineer отзываем —
engineer → Configure → API Token → Revoke рядом с ненужным токеном.
Лишние токены потом находятся в старых скриптах и чужих заметках.

Файл с токеном триггера, если вы его создавали, удаляем:

rm -f ~/.jenkins-trigger-token

Проверяем, что чисто:

curl -s -o /dev/null -w '%{http_code}\n' -u engineer:API_ТОКЕН \
  -X POST \
  "http://10.0.2.5:8080/job/Build_auto_trigger1/build?token=PrIvEt213123"

Ожидаемый ответ — 404: задания больше нет.

ЧТО ДАЛЬШЕ
=========================================================================

Мы научились запускать сборку без человека. В следующей практике
разберёмся, что делать, когда запускать её нужно по-разному: одному
нужен выкат на node1, другому — на node2, третьему — только проверка
без выката.

Практика 8 — параметризованные сборки: типы параметров, подстановка
их в команды, проверка пользовательского ввода и запуск параметров
из командной строки и API. Там же станет понятно, что происходит
с параметрами при запуске по триггеру: у расписания и каскада берутся
значения по умолчанию, у внешнего запроса параметры приходят
в адресе, а у вебхука — в его полезной нагрузке.
