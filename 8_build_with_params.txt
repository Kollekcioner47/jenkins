Практика 8. Параметризованные сборки: одно задание вместо десяти.

Готовые файлы: files/jobs/build_with_params.xml (задание с параметрами)
и files/pipelines/Jenkinsfile.build-test-deploy (конвейер, где параметры
используются при выкате сайта).

=========================================================================
ЗАЧЕМ НУЖНЫ ПАРАМЕТРЫ
=========================================================================

Раньше каждое задание делало одну неизменную работу: чтобы посмотреть
другой каталог, приходилось править конфигурацию. Десять похожих
каталогов — десять почти одинаковых заданий, которые потом расходятся.
Параметр — значение, которое приходит в сборку при запуске. Задание
остаётся одним, меняется только то, что ввели в форму:

  * одно задание вместо десяти: правка логики делается в одном месте;
  * значение выбирается при запуске, а не правкой конфигурации;
  * видно, кто и с какими значениями запускал: значения сохраняются
    вместе со сборкой;
  * задание вызывается повторно с разными значениями, не трогая своё
    описание, — это основа и для ручных операций, и для автоматики.
ОБРАТИТЕ ВНИМАНИЕ: параметр — не «настройка задания». Настройка
описывает, как задание работает всегда; параметр — что делать именно
этой сборке. Смешивать их — самая частая ошибка при проектировании.

=========================================================================
ПАРАМЕТР, ПЕРЕМЕННАЯ И НАСТРОЙКА
=========================================================================

  ПАРАМЕТР — вход сборки: его задаёт человек или автоматика при запуске.
  ПЕРЕМЕННАЯ ОКРУЖЕНИЯ — окружение процесса сборки; их ставит Jenkins
    (BUILD_NUMBER, JOB_NAME, WORKSPACE, NODE_NAME, NODE_LABELS). Они
    описывают сборку, но входными данными не являются.
  НАСТРОЙКА — то, что описывает сам Jenkins и не меняется от сборки
    к сборке: адреса агентов, идентификаторы credentials, плагины, права;
    в курсе настройки задаются файлами и JCasC (практика 14).
Значение параметра Jenkins экспортирует в переменные окружения шага
сборки, поэтому в шаге Execute shell параметр виден как переменная
оболочки — $TARGET_PATH. Отсюда и путаница в именах (раздел 4). Адрес
сервера выката и идентификатор credentials — настройка; что выкатывать
и в каком окружении — параметр; номер сборки и имя задания — переменная,
их задаёт Jenkins.

=========================================================================
КАК ВКЛЮЧАЮТСЯ ПАРАМЕТРЫ
=========================================================================

  Configure → General → This project is parameterized → Add Parameter
Каждый параметр — строка в списке: тип, имя (Name), значение по умолчанию
(Default Value) и описание (Description). Описание не украшение: оно
видно в форме запуска и отвечает на вопрос «что сюда писать».
ВАЖНО: пункт Build with Parameters появляется в меню задания только после
того, как задание СОХРАНЕНО с параметрами. До сохранения Jenkins о новом
входе не знает, и в меню будет обычная кнопка Build Now; самый первый
запуск (до добавления параметров) идёт без них. Если параметры есть,
Build Now тоже работает — она запускает сборку со значениями
по умолчанию, ничего не спрашивая.

ЧАСТЬ 1. БАЗОВАЯ ПРАКТИКА

=========================================================================
1. Создаём задание и включаем параметры
=========================================================================

Открываем портал http://10.0.2.5:8080 и входим учётной записью engineer:
анонимный доступ к Jenkins закрыт, поэтому портал, API и командная строка
работают только с логином. New Item → имя build_with_params → Freestyle
project → OK.

1.1. Первая сборка — БЕЗ параметров: Build → Add build step → Execute
shell, текст:
mkdir -p reports
ls -l /etc > reports/report.txt
cat reports/report.txt
Save → Build Now: в Console Output видно содержимое каталога /etc.
ЗАЧЕМ ЭТО ДО ПАРАМЕТРОВ: чтобы увидеть, что именно меняет галочка.
Задание без параметров — одна неизменная программа действий с жёстко
вписанными значениями.

1.2. Configure → General → This project is parameterized → Add Parameter.
Три параметра — такие же, как в файле files/jobs/build_with_params.xml:
  String Parameter:  Name TARGET_PATH, Default Value /etc
  Choice Parameter:  Name REPORT_FILE, Choices report.txt, listing.txt
  Boolean Parameter: Name VERBOSE, по умолчанию снят

1.3. В Build → Execute shell заменяем текст на скрипт из раздела 3.

1.4. Save. В левом меню появляется Build with Parameters: форма из трёх
полей со значениями по умолчанию. Нажимаем Build: в журнале видно строку
Building in workspace, значения параметров, содержимое отчёта и путь к нему.

1.5. Запускаем ещё раз с TARGET_PATH = /var/log, REPORT_FILE = listing.txt
и включённым VERBOSE: задание одно, результаты разные.
ОБРАТИТЕ ВНИМАНИЕ на строку Building in workspace: задание без метки может
выполниться и на контроллере, и на любом свободном агенте. Значит,
TARGET_PATH относится к той машине, где сборка реально пошла, а не к той,
где вы сидите в браузере. Поэтому имя машины печатается в отчёте.

=========================================================================
2. Типы параметров
=========================================================================

STRING PARAMETER — однострочное поле, в сборку приходит строка как есть.
Когда: значение неизвестно заранее и не сводится к списку — путь, имя
ветки, номер сборки для отката. Галочка Trim the string убирает пробелы
по краям: невидимый пробел превращает /var/log в «/var/log », а такого
пути нет.
TEXT PARAMETER — поле в несколько строк, в сборку приходит текст
с переводами строк. Когда: содержимое файла конфигурации, список адресов.
Такое значение сначала пишут в файл, а потом читают из файла.
BOOLEAN PARAMETER — галочка. В сборку приходит СТРОКА «true», если флажок
стоит, и «false», если снят: не 1 и не «да». Отсюда сравнение
[ "$VERBOSE" = "true" ]. Когда: включить или выключить что-то в сборке.

CHOICE PARAMETER — выпадающий список. Значение по умолчанию — ПЕРВЫЙ
вариант списка, а не отдельное поле: переставить варианты местами значит
поменять значение по умолчанию. Когда: набор значений конечен и известен
— версия страницы (v1, v2), окружение (dev, staging, prod). Здесь Choice
лучше String: список сам защищает от опечатки.
PASSWORD PARAMETER — поле с точками, значение маскируется в журнале.
Когда: почти никогда, потому что маскирование не защита (раздел 7).
FILE PARAMETER — выбор файла на вашем компьютере; Jenkins копирует файл
в рабочий каталог сборки и подставляет путь к нему в переменную
(раздел 8).

CREDENTIALS PARAMETER — выпадающий список уже существующих в Jenkins
credentials (node-ssh, gitea-reader, gitea-token, docker-registry);
в сборку приходит идентификатор записи, а не сам секрет. Это правильный
способ передать секрет параметром.
RUN PARAMETER — список сборок выбранного задания; в сборку приходит строка
вида имя_задания#42, рядом доступны номер и результат. Когда: одно задание
работает с результатом другого.
ПАРАМЕТРЫ ИЗ ПЛАГИНОВ: Extended Choice Parameter — расширенный список
(варианты из файла или вручную, множественный выбор), Active Choices —
список, который строит Groovy-скрипт (нужен плагин и согласование скрипта
в Script Approval, практика 9). УТОЧНЕНО: для простых случаев хватает
штатных типов.

=========================================================================
3. Разбираем задание build_with_params
=========================================================================
В файле files/jobs/build_with_params.xml лежит то же задание целиком: так
его переносят на другой стенд или создают командой (практика 5). Раздел
с параметрами описан тремя классами Jenkins: StringParameterDefinition
(TARGET_PATH, по умолчанию /etc), ChoiceParameterDefinition (REPORT_FILE,
report.txt или listing.txt) и BooleanParameterDefinition (VERBOSE, false).
Что важно понять: ParametersDefinitionProperty — свойство задания со
списком параметров (без него формы Build with Parameters нет); тип
параметра — это имя класса; варианты Choice хранятся объектом Java
(java.util.Arrays$ArrayList) — так их пишет XStream, поэтому править
список удобнее в портале, а XML использовать для переноса задания;
trim: false означает, что пробелы по краям значения сохраняются
намеренно. Есть в файле и служебное: LogRotator (хранить отчёты 14 дней,
не больше 20 сборок), запрет одновременных сборок и пустой список
триггеров — задание запускается только вручную.
Шаг сборки — то, что выполняется после того, как параметры пришли:

set -eu

echo "Параметры этой сборки:"
echo "  TARGET_PATH = $TARGET_PATH"
echo "  REPORT_FILE = $REPORT_FILE"
echo "  VERBOSE     = $VERBOSE"

# Проверяем входные данные, а не надеемся на них.
# Параметр — это пользовательский ввод, а он бывает любым.
if [ ! -e "$TARGET_PATH" ]; then
    echo "ОШИБКА: пути $TARGET_PATH не существует на $(hostname)"
    exit 1
fi

if [ "$VERBOSE" = "true" ]; then
    ls -la "$TARGET_PATH" > "$REPORT_FILE"
else
    ls -l "$TARGET_PATH" > "$REPORT_FILE"
fi

echo "--- начало $REPORT_FILE ---"
cat "$REPORT_FILE"
echo "--- конец $REPORT_FILE ---"
echo "Отчёт сохранён в $WORKSPACE/$REPORT_FILE на $(hostname)"

ПОЧЕМУ ПАРАМЕТР ОБЯЗАТЕЛЬНО ПРОВЕРЯТЬ: параметр — ввод от человека,
а Jenkins передаст в сборку что угодно: он не знает, что вы имели в виду.
Может прийти путь, которого не существует (невнятная ошибка из недр ls);
путь с пробелом — /var/log/nginx logs (оболочка разберёт его как два
аргумента); пустая строка (подстановка даёт «ls -l »); опасные символы —
; && $(...) — без кавычек они становятся отдельными командами оболочки,
и параметр превращается в способ выполнить произвольный код на агенте.
Правило: проверяйте существование пути, непустое значение и попадание
в список разрешённых — и печатайте параметры в журнал, чтобы при разборе
аварии было видно, с чем работала сборка.

=========================================================================
4. ИСПРАВЛЕНО: имя параметра и имя подстановки
=========================================================================

В прежней версии курса параметр назывался FOLDERNAME со значением
по умолчанию /home, а в шаге сборки стояла команда с другим именем:
ls -l $FILENAME > /home/engineer/jenkins/file1.txt
cat /home/engineer/jenkins/file1.txt
Задание запускалось, и ошибки не было ни одной. В файл уходила команда
вида «ls -l »: переменной FILENAME в сборке не существует, а Jenkins
подставляет то, что написали, — пустоту.
ПОЧЕМУ ЭТО НЕ ВЫЗВАЛО НИ ОДНОЙ ОШИБКИ: оболочка не считает «ls -l» без
аргумента ошибкой — это законная команда, она печатает содержимое
текущего каталога, то есть рабочего каталога сборки (отчёт получался
непустой и правдоподобный, просто не о том каталоге); а имя файла отчёта
было задано жёстко, поэтому файл каждый раз создавался, и по факту его
существования казалось, что всё сработало.
ЧТО ИЗ ЭТОГО СЛЕДУЕТ ЗАПОМНИТЬ:

  * имя параметра и имя подстановки должны совпадать БУКВА В БУКВУ.
    Jenkins не проверяет, существует ли такая переменная, — он подставляет
    значение. Опечатка не даёт ошибки, она даёт пустоту. Регистр тоже
    важен: target_path и TARGET_PATH — разные имена;
  * печатайте параметры в журнал перед использованием: три строки echo
    в начале шага — и поломка видна в первой же сборке;
  * проверяйте пустое значение явно: if [ -z "$TARGET_PATH" ]; then
    echo "ОШИБКА: параметр TARGET_PATH пуст"; exit 1; fi
  * ДОБАВЛЕНО: шаг начинается со set -eu. Режим -u (nounset) завершает
    скрипт при обращении к необъявленной переменной, и прежняя опечатка
    проявилась бы сразу, с сообщением parameter not set; режим -e
    останавливает шаг на первой ошибке.

=========================================================================
5. Подстановка значений
=========================================================================

Jenkins не ищет в тексте шага имена переменных: он экспортирует параметры
в окружение процесса, который запускает шаг, а подмену делает оболочка.

$ИМЯ И ${ИМЯ} — одно и то же, значение переменной. Фигурные скобки нужны
там, где имя сливается с соседними символами. Имя может состоять из букв,
цифр и подчёркивания, поэтому:

  $REPORT_FILE.bak      — точка имя заканчивает, сработает и так;
  $REPORT_FILE_old      — оболочка ищет переменную REPORT_FILE_old;
  ${REPORT_FILE}_old    — а так подставится значение и _old.

Правило: если сразу за именем идёт буква, цифра или подчёркивание,
ставьте фигурные скобки.
ОДИНАРНЫЕ И ДВОЙНЫЕ КАВЫЧКИ. Подстановку делает оболочка, а она различает
кавычки:
echo "$TARGET_PATH"     # печатает значение: /etc
echo '$TARGET_PATH'     # печатает текст: $TARGET_PATH
В одинарных кавычках подстановки не происходит вообще — это самая частая
причина вопроса «параметр не работает». Двойные кавычки нужны почти
всегда: они удерживают значение как ОДИН аргумент. Значение
"/var/log/nginx logs" без кавычек рвётся на части, и ls -l $TARGET_PATH
получает два пути вместо одного.
ВАЖНО ещё одно следствие кавычек: ls -l $TARGET_PATH при пустом значении
даёт «ls -l» и список каталога, а ls -l "$TARGET_PATH" — честную ошибку
cannot access ''. Кавычки превращают молчаливую пустоту в громкую ошибку.
Без кавычек оболочка разбирает значение ещё и как код: значение вида
/etc; rm -rf ... выполнится как две команды. Поэтому значение всегда
в двойных кавычках, а перед этим — проверка на пустоту и допустимость.
И ещё: не называйте параметр так же, как системную переменную Jenkins
(BUILD_NUMBER, WORKSPACE, JOB_NAME): иначе непонятно, что победит — то,
что передал человек, или то, что поставил Jenkins.

=========================================================================
6. Запуск с параметрами
=========================================================================
Все способы ведут в одну точку — в переменные окружения шага сборки.
6.1. ИЗ ПОРТАЛА. Открываем http://10.0.2.5:8080/job/build_with_params/
и нажимаем Build with Parameters: поля заполнены значениями по умолчанию,
их можно изменить. Кнопка Build ставит сборку в очередь, а значения,
с которыми она шла, видны на её странице.
6.2. ИЗ КОМАНДНОЙ СТРОКИ (клиент, токены и команды — практика 5):

java -jar jenkins-cli.jar -auth engineer:ТОКЕН \
  -s http://10.0.2.5:8080 \
  build build_with_params \
  -p TARGET_PATH=/var/log -p VERBOSE=true

  -s http://10.0.2.5:8080 — адрес портала (localhost не подойдёт: клиент
    запускается на вашей машине и будет указывать на неё);
  -auth engineer:ТОКЕН — логин и API-токен (Manage Jenkins → Users →
    engineer → Configure → API Token): его, в отличие от пароля, можно
    отозвать, не меняя пароль;
  -p ИМЯ=ЗНАЧЕНИЕ — значение параметра; неуказанные получат значения
    по умолчанию. Значение с пробелами берём в кавычки, чтобы их съел
    shell, а не CLI: -p 'TARGET_PATH=/var/log/nginx logs'.
6.3. ЧЕРЕЗ API. Запуск сборки с параметрами — обычный POST-запрос:

curl -X POST --user engineer:ТОКЕН \
  --data-urlencode "TARGET_PATH=/var/log" \
  --data-urlencode "VERBOSE=true" \
  http://10.0.2.5:8080/job/build_with_params/buildWithParameters

Адрес buildWithParameters принимает параметры; если записать их в /build,
часть значений потеряется. --data-urlencode кодирует пробелы, слэши
и амперсанды, а --user с логином и токеном обязателен: анонимный доступ
к Jenkins закрыт. Если защита от подделки запросов (CSRF) включена, POST
без crumb отвергается с кодом 403 (crumb — маркер, который Jenkins выдаёт
клиенту, чтобы запрос нельзя было подделать чужой страницей):

base=http://10.0.2.5:8080
crumb=$(curl -s --user engineer:ТОКЕН "$base/crumbIssuer/api/json" \
  | sed -n 's/.*"crumb":"\([^"]*\)".*/\1/p')
curl -X POST --user engineer:ТОКЕН -H "Jenkins-Crumb: $crumb" \
  "$base/job/build_with_params/buildWithParameters?TARGET_PATH=/var/log"

Кавычки вокруг адреса обязательны: знак & для оболочки служебный. Ответ
201 Created означает, что сборка принята и поставлена в очередь; 403 —
нет или просрочен crumb; 404 — не то имя задания; 400 — параметр
не передан или не подошёл по типу.

=========================================================================
7. Безопасность параметров
=========================================================================
7.1. PASSWORD-ПАРАМЕТР — ЭТО НЕ ЗАЩИТА СЕКРЕТА. В журнале значение
маскируется (печатается ****), но защитой это не является:

  * значение приходит в сборку открытым текстом как переменная окружения,
    и его видит любой процесс сборки;
  * оно легко оказывается в файле: сборке достаточно записать значение
    в файл для конфигурации приложения — и дальше файл содержит настоящий
    пароль. Маскирование работает только на печать в журнал;
  * из файла значение уходит в артефакты сборки, в резервную копию;
  * значение сохраняется в описании сборки на диске контроллера — в файле
    build.xml в каталоге сборки внутри /var/lib/jenkins, то есть в копии
    Jenkins лежит пароль;
  * оно попадает в журналы программ, печатающих полученные аргументы.

Вывод: маскирование защищает от случайного взгляда на журнал, а не
от того, кто получил доступ к машине, где шла сборка или лежит её файл.
7.2. ПРАВИЛЬНЫЙ СПОСОБ — CREDENTIALS. Секрет не передают значением: его
хранят в Jenkins как credentials, а в сборку передают идентификатор
записи, а не её содержимое. В конвейере секрет подставляется в среду
только на время блока withCredentials:

withCredentials([usernamePassword(credentialsId: 'docker-registry',
                 usernameVariable: 'REG_USER',
                 passwordVariable: 'REG_PASS')]) {
    sh 'echo "$REG_PASS" | docker login -u "$REG_USER" --password-stdin'
}

Так значение живёт ровно столько, сколько нужно, не печатается в журнале
и не сохраняется в описании сборки. Полный разбор — практика 11, там же
ssh-agent для ключа node-ssh. В курсе четыре идентификатора credentials:
node-ssh, gitea-reader, gitea-token, docker-registry.
7.3. ЗНАЧЕНИЯ ПАРАМЕТРОВ ВИДНЫ ВСЕМ, КТО ЧИТАЕТ ЗАДАНИЕ: параметры
хранятся в конфигурации задания, значения — в описаниях сборок. Любой,
у кого есть право читать задание, видит и параметры, и то, с какими
значениями шли сборки. Отсюда правило: «пароль для прода» параметром —
плохая идея, даже если тип Password.
7.4. ПАРАМЕТР С ПУТЁМ ПОЗВОЛЯЕТ ЧИТАТЬ ЧУЖИЕ ФАЙЛЫ: можно передать
TARGET_PATH=/etc/shadow, и сборка попробует прочитать файл паролей —
правами пользователя jenkins на той машине, где идёт сборка. В учебном
стенде это безобидно, в рабочей среде тот же шаг выполняется на сервере,
где рядом лежат ключи и конфигурация с паролями. Поэтому проверяют
не только существование пути, но и допустимость значения:

case "$TARGET_PATH" in
    /etc|/etc/*|/var/log|/var/log/*) ;;
    *) echo "ОШИБКА: путь $TARGET_PATH не разрешён"; exit 1 ;;
esac

Проверка «путь существует» без проверки «путь разрешён» отсекает
опечатки, но не намеренный выбор.
7.5. ОПЕЧАТКИ И ПОДМЕНА ЗНАЧЕНИЙ НА ВЫКАТЕ. Параметры, влияющие на выкат
(SITE_VERSION, окружение, список серверов), — отдельный риск: опечатка
или подмена означают, что на серверы уедет не то, что вы проверяли.
Что делать: ограниченный набор значений задавать типом Choice, а не
String; проверять значение по списку допустимых; помнить, что пробел
в конце значения — тоже подмена («v1 » и «v1» при сравнении разные);
для опасных действий нужны ещё права и подтверждение — стадия input
(практика 10), выкат и откат — практика 11.

=========================================================================
8. File-параметр
=========================================================================

File Parameter добавляют так же: Configure → General → This project
is parameterized → Add Parameter → File Parameter. У него два поля:
File location — имя, под которым загруженный файл окажется в рабочем
каталоге сборки (это не имя файла на вашем компьютере), и Files to upload
— какие типы файлов принимаются (пустое значение означает «любые»).

Что происходит при запуске: вы выбираете файл на своей машине; Jenkins
передаёт его на контроллер, а затем на машину, где пойдёт сборка; файл
оказывается в рабочем каталоге сборки под именем File location, а в
переменной с этим же именем сборка получает ПОЛНЫЙ путь к загруженному
файлу. При File location = UPLOADED_FILE в рабочем каталоге появляется
файл $WORKSPACE/UPLOADED_FILE.
ПОЧЕМУ ЭТО НЕ ГОДИТСЯ ДЛЯ СЕКРЕТОВ: загруженный файл просто остаётся
на диске — он лежит в рабочем каталоге сборки на агенте и остаётся там
после окончания сборки, успешной или упавшей. Его видят все, у кого есть
доступ к этой машине и каталогу: пользователь jenkins, администраторы
агента, любой, кто читает резервную копию. Секрет, один раз проехавший
через File-параметр, надо считать раскрытым.
ПОЧЕМУ ЭТО НЕУДОБНО В АВТОМАТИЗАЦИИ: остальные параметры — строки, и их
можно передать в CLI ключом -p или в API полем запроса. File-параметр так
не передать: это форма с загрузкой файла, для неё нужен отдельный запрос
с телом multipart/form-data. Если содержимое нужно сборке постоянно,
правильнее положить файл в репозиторий Gitea (практика 6) и забирать его
обычным checkout.
ИСПРАВЛЕНО: в прежней версии курса File-параметр был основным способом
передать содержимое в сборку, и в примере стояла строка cat UPLOADED_FILE
— без знака $, с пометкой «без $». Она работала случайно: Jenkins кладёт
загруженный файл в рабочий каталог сборки под именем File location, а шаг
сборки запускается в этом же каталоге, поэтому относительный путь
UPLOADED_FILE случайно указывал на нужный файл. Совпадение ломается
от любого изменения: достаточно в шаге перейти в другой каталог (cd) —
и путь перестанет находить файл; достаточно поменять File location —
и строка начнёт читать постороннее. Правильно — подставлять переменную:
её значение не зависит от текущего каталога:
cat "$UPLOADED_FILE"
ИСПРАВЛЕНО, коротко: cat UPLOADED_FILE заменено на cat "$UPLOADED_FILE".
Так значение берётся из переменной, а не из совпадения имени файла
с текущим каталогом, и работает при любом каталоге сборки.

=========================================================================
9. Параметры в декларативном конвейере
=========================================================================
В конвейере параметры описываются в самом Jenkinsfile, блоком parameters:

pipeline {
    agent { label 'web' }
    parameters {
        string(name: 'TARGET_PATH', defaultValue: '/var/log')
        choice(name: 'SITE_VERSION', choices: ['v1', 'v2'])
        booleanParam(name: 'VERBOSE', defaultValue: false)
        password(name: 'LEGACY_TOKEN', defaultValue: '')
        credentials(name: 'REGISTRY_CRED',
                    credentialType: 'Username with password')
    }
    stages {
        stage('Показать') { steps { sh 'ls -l "${TARGET_PATH}"' } }
    }
}

Типы в блоке parameters называются иначе, чем в интерфейсе: string, text,
booleanParam, choice, password, credentials. Типов File и Run здесь нет —
они относятся к заданиям, настраиваемым в портале. Точные имена аргументов
удобно проверять в самом Jenkins: Pipeline Syntax → Declarative Directive
Generator → parameters → credentials.
КАК ЧИТАТЬ ЗНАЧЕНИЯ: params.ИМЯ — объект параметров конвейера, основной
способ (params.TARGET_PATH, params.SITE_VERSION); значение доступно
в любом месте скрипта, в том числе в условиях. env.ИМЯ — переменные
окружения: параметры попадают и туда, поэтому в шаге sh их можно писать
как $TARGET_PATH или ${TARGET_PATH} — именно так сделано в файле
files/pipelines/Jenkinsfile.build-test-deploy, где в шагах используются
SITE_VERSION и WEB_NODES. Разница практическая: env — среда конкретного
шага, params — вход самой сборки. И не пишите $ИМЯ в двойных кавычках
в Groovy: подстановку делает Groovy, он будет искать свою переменную
и упадёт с ошибкой No such property.
ПОЧЕМУ ПАРАМЕТРЫ НЕ ПОДСТАВЛЯЮТСЯ В ENVIRONMENT НАПРЯМУЮ: блок
environment собирается один раз при подготовке конвейера, до стадий,
и служит для постоянных величин — пути выката, имени сайта, адреса
проверки. Параметр приходит в момент запуска, и превращать его в ещё одну
«постоянную» не стоит: переменная окажется зафиксированной не тогда,
когда вы думали. Что с этим делать: постоянные величины держите
в environment, а параметры читайте там, где они нужны, — params.ИМЯ
в Groovy и $ИМЯ (или ${ИМЯ}) в шагах sh. Значения по умолчанию нужны
и потому, что запуск бывает не ручным: по расписанию, по вебхуку из Gitea
или каскадом от другого задания параметры не спрашивают.
Не дублируя практику 10, скажем коротко: параметры — такая же часть
конвейера, как стадии, и описываются они в том же файле; параметры
из Jenkinsfile появляются у задания только после того, как Jenkins
прочитает файл, то есть после первой сборки.

=========================================================================
10. Как проектировать набор параметров
=========================================================================

Параметры — публичный интерфейс задания: чем их больше, тем больше
обещаний, которые надо поддерживать.

  * ЗНАЧЕНИЯ ПО УМОЛЧАНИЮ ДОЛЖНЫ БЫТЬ БЕЗОПАСНЫМИ И РАБОЧИМИ. Рабочими —
    чтобы запуск не падал на проверке входных данных; безопасными —
    чтобы этот же запуск ничего не сломал. Плохой пример: ENVIRONMENT
    со значением по умолчанию prod — задание рано или поздно запустят
    по расписанию или каскадом, и выкат уйдёт на рабочий контур;
  * ЛУЧШЕ ДЕСЯТЬ ОСМЫСЛЕННЫХ ПАРАМЕТРОВ, ЧЕМ ТРИДЦАТЬ. Каждый параметр
    надо описать, проверить и объяснить коллеге; тридцать параметров
    означают, что половину не понимают и оставляют по умолчанию;
  * ИМЯ ПАРАМЕТРА — ЗАГЛАВНЫМИ БУКВАМИ: так принято для входных данных,
    и так имена не путаются с переменными Groovy и системными
    переменными Jenkins;
  * ОПИСАНИЕ ОБЯЗАТЕЛЬНО: оно видно в форме запуска и отвечает на вопрос
    «что сюда писать»; формат значения — часть описания;
  * ПАРАМЕТР НЕ ЗАМЕНЯЕТ КОНФИГУРАЦИЮ. Адреса серверов, идентификаторы
    credentials, пути выката — это настройка, её место в файле,
    в Jenkinsfile или в JCasC (практика 14). Параметр, значение которого
    всегда одно и то же, — скрытая настройка, которую никто не найдёт;
  * ПРИ ИЗМЕНЕНИИ НАБОРА ПАРАМЕТРОВ СТАРЫЕ СБОРКИ НЕ ПЕРЕЗАПУСКАЮТСЯ
    С НОВЫМИ ЗНАЧЕНИЯМИ: значения хранятся вместе со сборкой, и повторный
    запуск идёт со СТАРЫМИ значениями той сборки, а не с текущими. Удобно,
    когда нужно повторить прежний эксперимент, и неприятно, когда вы
    поправили значение по умолчанию и ждёте нового поведения;
  * ПЕРЕИМЕНОВАНИЕ ПАРАМЕТРА — ОПАСНАЯ ОПЕРАЦИЯ: сборка хранит старое
    имя, шаг читает новое, переменная оказывается пустой — та же история,
    что в разделе 4.

=========================================================================
11. Параметризованный выкат
=========================================================================

Самый частый случай параметров в работе — выкат приложения. Выкатывать
будем сайт на nginx на node1 (10.0.2.13) и node2 (10.0.2.14). Три
типичных параметра.
ПАРАМЕТР ОКРУЖЕНИЯ: choice(name: 'ENVIRONMENT',
choices: ['dev', 'staging', 'prod']). Отвечает на вопрос «куда». Проблема
в том, что параметр — это выбор запускающего, а не решение системы: пока
prod стоит последним в списке, ошибка «выбрал не тот пункт» — вопрос
времени. Помогают здесь не параметры, а права (кто вообще может запускать
задание на рабочий контур), отдельное задание для прода и подтверждение
перед выкатом.
ПАРАМЕТР ВЕРСИИ ВЫКАТЫВАЕМОГО КОДА: choice(name: 'SITE_VERSION',
choices: ['v1', 'v2']). Отвечает на вопрос «что»: номер сборки, тег или
версия из набора. Именно этот параметр используют при откате. Опасность
не в самом параметре, а в выкате без проверки, поэтому после выката идёт
проверка снаружи: сборка запрашивает страницу по адресу и убеждается, что
на ней ожидаемый текст и номер сборки (практика 11).
ПАРАМЕТР «ВЫКАТЫВАТЬ ЛИ НА ВТОРОЙ СЕРВЕР»:
booleanParam(name: 'DEPLOY_NODE2', defaultValue: false). Значение
по умолчанию — false: безопасный вариант, при котором выкат идёт на одну
машину, а вторая подключается осознанно.
В файле files/pipelines/Jenkinsfile.build-test-deploy та же мысль выражена
иначе — список серверов задан строковым параметром WEB_NODES со значением
по умолчанию '10.0.2.13 10.0.2.14'. У такого параметра-списка две
ловушки. Первая: пустое значение — цикл по списку не выполнится ни разу,
ошибки не будет, и сборка останется зелёной, не выкатив ничего:
if [ -z "$WEB_NODES" ]; then
    echo "ОШИБКА: список серверов пуст"; exit 1
fi
Вторая: лишний адрес — список вводит человек, и там может оказаться чужая
машина. Лечится проверкой каждого адреса по списку допустимых.
ЧЕМ ЭТО ВСЁ ОПАСНО, ЕСЛИ НЕ ДУМАТЬ: параметры выката — ровно то место,
где человеческая ошибка превращается в происшествие: можно выбрать prod
по ошибке, перепутать версию, дописать лишний адрес и не заметить этого.
Параметр ничего из этого не запрещает — он лишь передаёт значение.
Поэтому на выкате к параметрам добавляют права (практика 2),
подтверждение (стадия input, практика 10), проверку входных данных
в скрипте и проверку результата после выката с откатом при провале
(практика 11). Итог: параметр не защита — он отвечает на вопрос «что
делать», а «можно ли это делать» решают права, подтверждение и проверки.

=========================================================================
ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================
ПРОБЛЕМА: нет кнопки Build with Parameters
  Проверяйте по порядку: заданы ли параметры вообще (Configure → General
  → This project is parameterized и непустой список под ней); сохранено ли
  задание — пока не нажато Save, Jenkins о параметрах не знает, и формы
  не будет (самая частая причина при первом включении); для конвейера —
  есть ли блок parameters в Jenkinsfile: если параметры добавлены только
  что, форма появится после первой сборки, в которой Jenkins прочитает
  файл.
ПРОБЛЕМА: параметр в сборке пустой
  Причины: опечатка в имени (параметр TARGET_PATH, а в шаге $TARGET_PAHT
  или $target_path — регистр имеет значение); значение не передали
  при запуске, и взялось пустое значение по умолчанию; подстановка стоит
  в одинарных кавычках (echo '$TARGET_PATH' печатает текст, а значение
  печатает echo "$TARGET_PATH"); параметр переименовали, а подстановки
  в шаге — нет. Печатайте параметры в журнал в начале шага и держите
  в шаге set -u — тогда пустая переменная видна сразу.
ПРОБЛЕМА: значение с пробелами рвёт команду
  Пример: TARGET_PATH = /var/log/nginx logs, команда ls -l $TARGET_PATH.
  Оболочка отдаёт ls два аргумента вместо одного. Что делать: брать
  подстановку в двойные кавычки — ls -l "$TARGET_PATH"; при запуске из CLI
  кавычки нужны и там, чтобы значение не разрезал shell, —
  -p 'TARGET_PATH=/var/log/nginx logs'; при запуске через API использовать
  --data-urlencode. Если параметр по смыслу список (WEB_NODES),
  не подставлять его в команду целиком, а разбирать циклом.
ПРОБЛЕМА: параметр не виден в конвейере
  Причины: забыли блок parameters в Jenkinsfile; параметр добавили после
  первого запуска — Jenkins узнаёт о параметрах, только прочитав файл;
  в коде на Groovy написали $ИМЯ в двойных кавычках — подстановку делает
  Groovy, он ищет свою переменную и падает с ошибкой No such property,
  поэтому в Groovy читайте params.ИМЯ; смотрите не туда — в шагах sh
  доступны $ИМЯ и ${ИМЯ}, а в условиях и в Groovy только params.ИМЯ.
ПРОБЛЕМА: повторный запуск сборки использует старые параметры
  Это не поломка, а устройство Jenkins: значения параметров хранятся
  вместе со сборкой, и повторный запуск идёт со значениями той сборки,
  которую повторяют, — даже если значения по умолчанию в конфигурации уже
  поправлены. Нужны новые значения — запускайте заново через
  Build with Parameters.
ПРОБЛЕМА: значение параметра видно в журнале открытым текстом
  Скорее всего, вместо Credentials использован Password-параметр, или
  сборка сама печатает значение. Что делать: хранить секрет как
  credentials и передавать его через withCredentials (практика 11); убрать
  из шага echo и cat, которые печатают значение; помнить, что маскирование
  в журнале не отменяет того, что значение уже побывало в переменных
  окружения, в файлах и в описании сборки на диске /var/lib/jenkins.
  ДОБАВЛЕНО: следите за режимом трассировки — строка set -x печатает
  каждую команду уже с подставленными значениями, включая секреты;
  отладку с set -x в заданиях с секретами не оставляют включённой.
ПРОБЛЕМА: java.io.IOException при использовании File-параметра
  Причины: файл слишком большой (у загрузки есть предел, и при превышении
  сборка падает с ошибкой ввода-вывода, не начиная работу); на машине,
  куда копируется файл, нет места — проверьте командой df -h; загрузка
  прервалась (браузер, сеть). Если файл нужен сборке постоянно,
  File-параметр — плохой инструмент: положите файл в репозиторий Gitea
  (практика 6) и забирайте сборкой.

=========================================================================
Уборка после практики
=========================================================================

13.1. Удаляем файлы отчётов: они лежат в рабочем каталоге задания, путь
виден в журнале в строке Building in workspace (на контроллере это
/var/lib/jenkins/workspace/build_with_params). Проще всего из портала:
страница задания → Workspace → Wipe Out Current Workspace.

13.2. Возвращаем значения по умолчанию: Configure → TARGET_PATH → /etc,
REPORT_FILE → report.txt, VERBOSE → снят → Save. Так задание останется
рабочим примером для следующих практик.

13.3. Если задание больше не нужно — удаляем: страница задания →
Delete Job → подтверждение. Проверяем, что осталось на стенде командой
ls /var/lib/jenkins/jobs.
УТОЧНЕНО: удаление задания удаляет его рабочий каталог на контроллере,
но не на агенте: рабочие каталоги агентов живут своей жизнью. Если сборки
шли на node1 или node2, проверьте их каталоги — там оседают и отчёты,
и загруженные файлы, и выкаченные из репозитория копии.

    стадия input для подтверждения перед выкатом; файл
    files/pipelines/Jenkinsfile.build-test-deploy — тот самый конвейер,
    параметры которого мы разбирали в разделе 11;
  * практика 11 — секреты и выкат приложения: credentials вместо
    Password-параметра, ssh-agent для доступа на node1 и node2, выкат
    на nginx, проверка снаружи и откат;
  * практика 5 — Jenkins CLI и API: запуск заданий с параметрами
    из командной строки, токены, создание заданий; практика 14 —
    конфигурация как код: описания заданий и их параметры задаются
    файлами, а не руками в портале. Наше задание
    files/jobs/build_with_params.xml — ровно такой файл, только
    применённый вручную.
Самое полезное, что стоит унести из этой практики: параметр — это
пользовательский ввод. Его печатают в журнал, проверяют перед
использованием и берут в кавычки. Всё остальное в этой теме — удобство,
а это — надёжность.
