Практика 5. Jenkins CLI: управление порталом из командной строки.

Готовые файлы к этой практике лежат в files/jobs/: FirstJob.xml и
build_with_params.xml — их мы загрузим в Jenkins командами CLI.

=========================================================================
ЗАЧЕМ НУЖЕН CLI, ЕСЛИ ЕСТЬ ПОРТАЛ
=========================================================================

Портал — основной интерфейс курса, и почти всё в нём делается мышью.
Но у мыши есть три свойства, из-за которых в работе появляется CLI:
  * ОДНО НАЖАТИЕ — ОДНО ДЕЙСТВИЕ. Выгрузить одно задание можно
    за полминуты; сорок заданий — это сорок раз по полминуты, и на
    двадцатом обязательно перепутается имя файла;
  * ДЕЙСТВИЕ НЕ ОСТАЁТСЯ ТЕКСТОМ: нажатия не превращаются ни в скрипт,
    ни в документацию, ни в инструкцию по восстановлению после аварии;
  * ДЕЙСТВИЕ НЕЛЬЗЯ ЗАПУСТИТЬ С ДРУГОЙ МАШИНЫ и нельзя вставить
    в середину сценария: «после установки создай задание».

CLI закрывает все три пункта: команда помещается в текстовый файл,
а выполнить её можно с любой машины, которая видит Jenkins.

ПОЧЕМУ ЭТО НАЗЫВАЮТ ВОСПРОИЗВОДИМОСТЬЮ: скрипт с командами можно
запустить дважды — сегодня на своём стенде, завтра на новом. Порталом
так не поделишься: можно показать только «нажми вот сюда».

КОГДА CLI НЕ НУЖЕН: разовая правка одного задания; раздел портала,
до которого CLI не дотягивается; чтение журнала сборки глазами.

ОБРАТИТЕ ВНИМАНИЕ: CLI не заменяет портал, а входит в ту же систему
с другой стороны; это один Jenkins, а не два.

=========================================================================
ЧТО ПОНАДОБИТСЯ
=========================================================================

  admin 10.0.2.5   контроллер Jenkins, портал http://10.0.2.5:8080
  engineer         администратор Jenkins, пароль Console47
  serviceuser      служебный пользователь, создаём его здесь
  Java 21          установлена в практике 1
  файлы курса      files/jobs/FirstJob.xml, files/jobs/build_with_params.xml

Команды выполняются на машине admin; с node1 и node2 они тоже
сработают, потому что адрес 10.0.2.5 оттуда доступен.

#########################################################################
ЧАСТЬ 1. БАЗОВАЯ ПРАКТИКА
#########################################################################

=========================================================================
1. ЧТО ТАКОЕ JENKINS CLI
=========================================================================

Клиент Jenkins CLI — это один файл jenkins-cli.jar. Внутри нет ни копии
Jenkins, ни базы заданий. Это клиент remoting: команда уходит
на сервер по выбранному транспорту (HTTP, WebSocket или SSH),
выполняется там, а клиент получает готовый ответ и печатает его.
Команда

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 list-jobs

выполняется на стороне Jenkins, а не превращается в один HTTP-запрос
к API. Именно поэтому версия клиента должна соответствовать версии
сервера (раздел 9). При этом почти всё, что делается с заданиями
через CLI, доступно и через API (раздел 5).

1.1. Скачиваем клиент на машину admin:

cd ~
wget http://10.0.2.5:8080/jnlpJars/jenkins-cli.jar

ИСПРАВЛЕНО: в прежней версии курса везде использовался адрес
http://localhost:8080. Это работало только на самой машине admin: с node1
и node2 никакого Jenkins на localhost нет, там свой localhost. В курсе
везде адрес http://10.0.2.5:8080, чтобы команда работала с любой машины.

1.2. Первая команда — справка:

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 help

1.3. Параметры запуска. Почти всегда нужны первые два:

  -s АДРЕС              адрес сервера Jenkins
  -auth ЛОГИН:СЕКРЕТ    логин и пароль либо логин и API-токен
  -webSocket            работать через WebSocket
  -http                 работать через обычный HTTP (старый транспорт)

Без -s клиент идёт на http://localhost:8080, то есть на localhost той
машины, где вы сидите. Без -auth он остаётся гостем, а анонимный доступ
в текущих версиях Jenkins закрыт, поэтому команда возвращает ошибку
про права. -webSocket и -http выбирают транспорт: HTTP считается
устаревшим, WebSocket предпочтителен за обратным прокси.

=========================================================================
2. АУТЕНТИФИКАЦИЯ: ТРИ СПОСОБА И ОДИН ДОПОЛНИТЕЛЬНЫЙ
=========================================================================

Способ 1. Логин и пароль:

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 \
     -auth engineer:Console47 who-am-i

ПОЧЕМУ ПАРОЛЬ В КОМАНДНОЙ СТРОКЕ — ПЛОХО: аргументы процесса видны
в списке процессов всем пользователям машины.

ps -eo user,args | grep jenkins-cli

На учебном стенде это не страшно, пароль и так напечатан в курсе.
В рабочей среде пароль из командной строки попадает ещё в историю
оболочки и в журналы аудита, поэтому там используют токены.

Способ 2. API-токен — основной способ для скриптов. Токен создаёт сам
пользователь для себя: значок пользователя в правом верхнем углу ->
Configure -> раздел API Token -> Add new Token -> имя (например,
cli-admin) -> Generate. Значение копируем сразу.

ПОЧЕМУ КОПИРОВАТЬ НАДО СРАЗУ: Jenkins хранит не токен, а его хеш
и показать значение второй раз не может.

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 \
     -auth engineer:11a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6de who-am-i

УТОЧНЕНО: вместо настоящего токена здесь стоит похожая на токен строка.
В прежней версии курса заполнители писались как %token% и %buildname%,
и их регулярно забывали заменять — команда уходила на сервер с буквальным
текстом «%token%» и завершалась ошибкой аутентификации.

printf '%s' 'ВАШ_ТОКЕН' > ~/.jenkins-token
chmod 600 ~/.jenkins-token

ИСПРАВЛЕНО: в прежней версии курса токен сохранялся командой
echo -n %token% > servicetoken — без ограничения прав. Файл с токеном,
доступный на чтение всем, — это отданный пароль: любой пользователь
машины сможет действовать от вашего имени, причём токен, в отличие
от пароля, сам не меняется. Нужны chmod 600 и отдельный каталог; если файл
лежит в каталоге проекта, добавьте его в .gitignore.

Способ 3. Переменные окружения. Тогда -auth в команде не нужен:

export JENKINS_USER_ID=engineer
export JENKINS_API_TOKEN=ВАШ_ТОКЕН
java -jar jenkins-cli.jar -s http://10.0.2.5:8080 who-am-i

ЗАЧЕМ ЭТОТ СПОСОБ: он удобнее для скриптов — токен не попадает
ни в командную строку, ни в историю оболочки.

Дополнительный способ. Аутентификация по SSH-ключу:

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 -i ~/.ssh/id_ed25519 \
     -user engineer who-am-i

Плюс: пароль и токен не нужны. Минус: на стенде SSH-эндпоинт не включён,
ключ нужно предварительно загрузить в профиль, а набор команд и права
те же самые — преимуществ этот способ не даёт.

2.1. Служебный пользователь serviceuser

Manage Jenkins -> Users -> Create User

  username: serviceuser
  password: Console47
  confirm password: Console47
  full name: my service user
  e-mail: test@test.test

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 \
     -auth serviceuser:Console47 who-am-i

Токен создаём, войдя в портал ИМЕННО под serviceuser: токен создаёт
пользователь для себя, а не администратор для пользователя.

ОБРАТИТЕ ВНИМАНИЕ, ЭТО ВАЖНО: пока в Jenkins не включена матричная
авторизация, действует стратегия по умолчанию — «вошедший может всё».
serviceuser сейчас фактически администратор, и ограничить его права
можно только явно (практика 2). Для сборок достаточно прав Overall/Read,
Job/Read, Job/Build и Job/Cancel.

=========================================================================
3. ОСНОВНЫЕ КОМАНДЫ
=========================================================================

Ниже рабочий минимум; полный список — на странице Manage Jenkins ->
Jenkins CLI, он зависит от версии Jenkins и плагинов. Проверить
отдельную команду можно так:

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 help build

Чтобы не повторять длинный префикс, дальше он записан как CLI:

CLI="java -jar $HOME/jenkins-cli.jar -s http://10.0.2.5:8080"
export JENKINS_USER_ID=engineer
export JENKINS_API_TOKEN=ВАШ_ТОКЕН

3.1. Кто мы, версия сервера, список заданий:

$CLI who-am-i
$CLI version
$CLI list-jobs

3.2. Запуск сборки:

$CLI build FirstJob
$CLI build -s -v FirstJob
$CLI build -s -v -p TARGET_PATH=/etc build_with_params

Первая команда ставит сборку в очередь и сразу возвращает управление,
вторая ждёт окончания (-s) и печатает журнал (-v), третья передаёт
параметр ключом -p. Без -s скрипт побежит дальше и проверит результат
раньше, чем сборка закончится; с флагом -s код возврата команды
показывает, удалась сборка или нет.

3.3. Журнал сборки и описания заданий:

$CLI console FirstJob
$CLI console FirstJob 12
$CLI get-job FirstJob > myjob.xml
$CLI create-job FirstJob < files/jobs/FirstJob.xml
$CLI update-job FirstJob < myjob.xml
$CLI copy-job FirstJob FirstJob-backup
$CLI delete-job FirstJob-backup

console печатает журнал последней сборки или сборки с указанным
номером. get-job выгружает описание задания в виде XML — из него
Jenkins «рисует» форму. create-job создаёт задание из файла, update-job
заменяет описание существующего: create-job отказывается работать,
если задание с таким именем уже есть.

ВАЖНО: удаление необратимо, вместе с заданием исчезнут история сборок,
артефакты и рабочий каталог. Перед удалением ценного задания выгрузите
его описание в файл — так в практике 14 мы будем собирать резервную
копию Jenkins.

3.4. Конфигурация и служба:

$CLI reload-configuration
$CLI safe-restart
$CLI restart
$CLI shutdown

reload-configuration заставляет Jenkins перечитать файлы с диска; нужно
после правки файлов напрямую или загрузки конфигурации как код.
safe-restart ждёт окончания идущих сборок и только потом перезапускает
Jenkins — в работе это правильный вариант. restart перезапускает сразу
и может оборвать сборки, shutdown останавливает Jenkins; запустить его
обратно командой CLI не выйдет:

sudo systemctl start jenkins

3.5. Плагины:

$CLI list-plugins
$CLI install-plugin git

list-plugins печатает установленные плагины с версиями. УТОЧНЕНО:
в новых версиях команда install-plugin помечена устаревшей, а кое-где
отключена: ставить плагины надёжнее через Manage Jenkins -> Plugins
или описанием в конфигурации как код (практика 14).

3.6. Выполнение Groovy-скрипта:

$CLI groovy script.groovy

ВНИМАНИЕ. Это самая опасная команда CLI: она выполняет произвольный код
на сервере от имени того пользователя, чьи данные предъявлены. Скрипт
может прочитать любой файл, удалить все задания и изменить настройки
безопасности, поэтому пользуйтесь ей только осознанно. Подробный разбор,
включая Script Approval, — в практике 9.

=========================================================================
4. ЗАДАНИЯ КАК ФАЙЛЫ: ПЕРЕНОС, ШАБЛОНЫ, РЕЗЕРВНАЯ КОПИЯ
=========================================================================

Jenkins хранит каждое задание как XML-файл. Значит, задание — это текст,
а текст можно копировать, править и хранить в репозитории.

4.1. Выгружаем описание и смотрим структуру:

$CLI get-job FirstJob > myjob.xml
cat myjob.xml

Внутри описание (description), свойства (properties) и шаги сборки
(builders) — то же, что показано в форме задания в портале.

4.2. Правим файл и создаём из него новое задание:

vim myjob.xml
$CLI create-job FirstJob-copy < myjob.xml
$CLI list-jobs

ЗАЧЕМ: так делают шаблоны — один раз настроили задание, выгрузили
его, и дальше однотипные задания создаются заменой имени и параметров.

4.3. Загружаем задания курса из files/jobs/:

$CLI create-job build_with_params < files/jobs/build_with_params.xml
$CLI create-job FirstJob < files/jobs/FirstJob.xml
$CLI build -s -v -p TARGET_PATH=/etc build_with_params

ЗАЧЕМ: стенд можно собрать заново из текстовых файлов, не настраивая
всё мышью; кроме того, build_with_params понадобится в практике 8.
Тот же приём можно применить ко всем заданиям сразу — цикл по списку
из list-jobs мы напишем целиком в разделе 6.

=========================================================================
5. API БЕЗ CLI: ТО ЖЕ САМОЕ ЧЕРЕЗ CURL
=========================================================================

Почти всё, что делается с заданиями через CLI, доступно и через API.
Ниже — те же результаты запросами к API напрямую: этот способ нужен,
когда jenkins-cli.jar недоступен или на машине нет Java.

curl -s --user engineer:ВАШ_ТОКЕН http://10.0.2.5:8080/api/json

Ответ — список заданий в формате JSON. История сборок задания:
параметр tree указывает, какие поля вернуть.

curl -s --user engineer:ВАШ_ТОКЕН \
    "http://10.0.2.5:8080/job/FirstJob/api/json?tree=builds[number,result]"

ОБРАТИТЕ ВНИМАНИЕ: адрес взят в кавычки не случайно — внутри есть
знак вопроса и квадратные скобки, а в более сложных запросах
встретится амперсанд, который оболочка поймёт как «запустить
в фоне». Описание задания отдаёт тот же адрес, что и get-job:

curl -s --user engineer:ВАШ_ТОКЕН \
    http://10.0.2.5:8080/job/FirstJob/config.xml

Запуск сборки — это уже POST, а не GET:

curl -s -X POST --user engineer:ВАШ_ТОКЕН \
    http://10.0.2.5:8080/job/FirstJob/build

Параметризованная сборка:

curl -s -X POST --user engineer:ВАШ_ТОКЕН \
    "http://10.0.2.5:8080/job/build_with_params/buildWithParameters?\
TARGET_PATH=/etc"

ЗАЧЕМ ЗАГОЛОВОК CRUMB. Сервер может потребовать заголовок crumb, который
защищает от подделки запросов: браузер жертвы отправил бы запрос с чужого
сайта, а у чужого сайта crumb нет. Получают его так:

CRUMB=$(curl -s --user engineer:ВАШ_ТОКЕН \
    http://10.0.2.5:8080/crumbIssuer/api/json \
    | sed -n 's/.*"crumb":"\([^"]*\)".*/\1/p')

curl -s -X POST --user engineer:ВАШ_ТОКЕН \
    -H "Jenkins-Crumb: $CRUMB" \
    http://10.0.2.5:8080/job/FirstJob/build

ДОБАВЛЕНО: crumb нужен не всегда — он защищает аутентификацию
по cookie, то есть браузерную сессию. Если crumb устарел (Jenkins
перезапустился), ответ будет «Found invalid crumb».

=========================================================================
6. АВТОМАТИЗАЦИЯ РУТИНЫ: СКРИПТ ВЫГРУЗКИ И СВОДКИ
=========================================================================

Самая частая задача, ради которой берут CLI, — регулярная выгрузка
описаний заданий и быстрый взгляд на состояние стенда. Ниже скрипт
целиком: он выгружает описания всех заданий в каталог с датой и печатает
сводку «задание — последняя сборка — результат».

#!/bin/bash
# export_jobs.sh — выгружает описания всех заданий Jenkins
# и печатает сводку: имя задания, номер последней сборки, результат.
set -euo pipefail

JENKINS_URL="http://10.0.2.5:8080"
TOKEN_FILE="$HOME/.jenkins-token"
BACKUP_DIR="$HOME/jenkins-jobs-$(date +%Y-%m-%d)"
CLI_JAR="$HOME/jenkins-cli.jar"

# Есть ли чем аутентифицироваться и закрыт ли файл.
if [ ! -r "$TOKEN_FILE" ]; then
    echo "Нет файла с токеном: $TOKEN_FILE" >&2
    echo "нужен printf '%s' 'ВАШ_ТОКЕН' > $TOKEN_FILE и chmod 600" >&2
    exit 1
fi

# Учётные данные — через окружение: в командной строке их не видно.
export JENKINS_USER_ID="engineer"
export JENKINS_API_TOKEN="$(cat "$TOKEN_FILE")"

# Клиент скачиваем один раз, обязательно с самого сервера.
if [ ! -r "$CLI_JAR" ]; then
    wget -q -O "$CLI_JAR" "$JENKINS_URL/jnlpJars/jenkins-cli.jar"
fi

cli() {
    java -jar "$CLI_JAR" -s "$JENKINS_URL" "$@"
}

mkdir -p "$BACKUP_DIR"

if ! cli list-jobs > "$BACKUP_DIR/jobs.list"; then
    echo "Не удалось получить список заданий. Jenkins доступен?" >&2
    exit 1
fi

echo "Выгружаю описания заданий в $BACKUP_DIR"
while IFS= read -r job; do
    job="$(printf '%s' "$job" | sed 's/^[[:space:]]*//; s/[[:space:]]*$//')"
    if [ -z "$job" ]; then
        continue
    fi
    cli get-job "$job" > "$BACKUP_DIR/$job.xml"
done < "$BACKUP_DIR/jobs.list"

echo
echo "Сводка по заданиям:"
printf '%-24s %-8s %s\n' "JOB" "BUILD" "RESULT"

curl -s --user "$JENKINS_USER_ID:$JENKINS_API_TOKEN" \
    "$JENKINS_URL/api/json?tree=jobs[name,lastBuild[number,result]]" \
    | python3 -c '
import json, sys

data = json.load(sys.stdin)
for job in sorted(data.get("jobs", []), key=lambda j: j["name"]):
    build = job.get("lastBuild")
    if build:
        number, result = build.get("number", "-"), \
            build.get("result") or "выполняется"
    else:
        number, result = "-", "сборок не было"
    print("%-24s %-8s %s" % (job["name"], number, result))
'

echo
echo "Готово. Файлов выгружено: $(ls -1 "$BACKUP_DIR"/*.xml | wc -l)"

Разберём его по частям.
  * set -euo pipefail останавливает скрипт на первой ошибке: без этого
    цикл с опечаткой в адресе отработал бы «успешно», создав пустые файлы;
  * export JENKINS_USER_ID и JENKINS_API_TOKEN: учётные данные уходят
    в клиент через окружение, а не через -auth, поэтому в списке
    процессов их не видно — значит, в функции cli нет -auth;
  * скачивание клиента с самого сервера: версия клиента всегда совпадает
    с версией сервера, и класс поломок из раздела 9 снимается;
  * проверка if ! cli list-jobs и цикл while IFS= read -r job: если
    Jenkins недоступен, выгрузка прекращается сразу, а имена заданий
    читаются из файла целиком, вместе с пробелами. Следующая строка
    с sed срезает отступы, которые часть версий CLI добавляет к именам;
  * cli get-job "$job" > "$BACKUP_DIR/$job.xml": выгрузка описаний
    и есть резервная копия конфигурации заданий;
  * сводка одним запросом curl с параметром tree — здесь пригодился
    API из раздела 5: через CLI результат сборок одним вызовом не
    получить. У работающей сборки поле result пустое (null), поэтому
    python3 подставляет слово «выполняется».

ЗАЧЕМ ВСЁ ЭТО, ЕСЛИ ЕСТЬ ПОРТАЛ: скрипт можно поставить в расписание
и получить ежедневную копию описаний заданий. Это дёшево и очень
успокаивает, когда задание удалили «случайно».

=========================================================================
7. CLI ИЗ КОНВЕЙЕРА: ПОЧЕМУ ЭТО ОБЫЧНО ПЛОХАЯ ИДЕЯ
=========================================================================

Мысль «раз CLI умеет создавать задания, пусть конвейер создаёт их сам»
возникает часто. Технически это возможно, но по умолчанию так делать
не стоит:
  * ТОКЕН АДМИНИСТРАТОРА В СБОРКЕ. Чтобы CLI создавал задания или
    перезапускал Jenkins, ему нужны административные права. Такой
    токен придётся положить в credentials и выдать сборке — и полный
    доступ к Jenkins получит всякий, кто может запустить конвейер;
  * ВЕРСИЯ КЛИЕНТА. Клиенту нужна подходящая версия сервера (раздел 9);
    конвейер, работающий сегодня, после обновления Jenkins может упасть;
  * ШТАТНЫЕ СРЕДСТВА ЛУЧШЕ. Всё, что нужно конвейеру, Jenkins умеет
    сам: описание задания — это Jenkinsfile в репозитории, параметры —
    блок parameters, запуск другого задания — шаг build, секреты —
    withCredentials (практики 8-11). Плюс конвейер не зависит от сети,
    версии Java и наличия файла на агенте.

КОГДА CLI ИЗ КОНВЕЙЕРА ВСЁ ЖЕ ОПРАВДАН: когда нужно то, чего штатные
шаги не умеют (перезапуск Jenkins, перечитывание конфигурации), и когда
конвейер обслуживает сам Jenkins. Токен при этом дают служебному
пользователю с минимальными правами, а не администратору.

=========================================================================
8. CLI ПО SSH: КОРОТКО И ЧЕСТНО
=========================================================================

Кроме HTTP у клиента есть ещё один транспорт — SSH:

java -jar jenkins-cli.jar -s http://10.0.2.5:8080 -i ~/.ssh/id_ed25519 \
     -user engineer who-am-i

ЧЕСТНО О ГРАНИЦАХ ЭТОГО РАЗДЕЛА: на стенде курса SSH-эндпоинт CLI
не включался, поэтому рабочего примера с конкретным портом здесь нет
и выдумывать его мы не будем. Включается он так: Manage Jenkins ->
Security -> раздел SSH Server, там же задаётся порт (по умолчанию
служба слушает 50022), после чего открытый ключ пользователя
загружается в его профиль: Configure -> SSH Public Keys.

ОБРАТИТЕ ВНИМАНИЕ, ЧТО ПРОВЕРИТЬ ПОСЛЕ ВКЛЮЧЕНИЯ: SSH-эндпоинт — это
ещё одна дверь в Jenkins, и права в ней определяются правами
пользователя, чей ключ предъявлен. Проверьте, что порт не выставлен
наружу без необходимости, ключи выданы конкретным людям и служебным
записям, а ненужный ключ удалён из профиля.

=========================================================================
9. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: «ERROR: You must authenticate to access this Jenkins» или
«anonymous is missing the Overall/Read permission».
ПРИЧИНА: не указаны учётные данные или забыт export переменных.
ЧТО ДЕЛАТЬ: добавьте -auth ЛОГИН:ТОКЕН либо задайте JENKINS_USER_ID
и JENKINS_API_TOKEN; проверьте себя командой who-am-i.

ПРОБЛЕМА: «No such job 'FirstJob'».
ПРИЧИНА: такого имени на сервере нет: опечатка, задание не создано
или вы смотрите не туда. Отдельная ловушка — похожие буквы: латинская
буква, подменённая кириллической, не видна ни в редакторе, ни в diff.
ЧТО ДЕЛАТЬ: $CLI list-jobs и сверить имя посимвольно.

ПРОБЛЕМА: команда завершается успешно, но выводит пустоту.
ПРИЧИНА: чаще всего это перенаправление вывода — get-job > файл
печатает не на экран, а в файл; реже — команда вернула пустой список.
ЧТО ДЕЛАТЬ: проверьте ls -l файла, код возврата echo $? и 2>&1.

ПРОБЛЕМА: POST-запрос через curl возвращает 403.
ПРИЧИНА: либо сервер требует crumb, либо не хватает прав.
ЧТО ДЕЛАТЬ: получите crumb и передайте его в заголовке Jenkins-Crumb
(раздел 5); если не помогло — проверьте право Job/Build и ключ --user.

ПРОБЛЕМА: «Found invalid crumb».
ПРИЧИНА: crumb устарел: Jenkins перезапускался или crumb получен
в другой сессии.
ЧТО ДЕЛАТЬ: получите crumb заново непосредственно перед POST.

ПРОБЛЕМА: «Connection refused».
ПРИЧИНА: на этом адресе и порту никто не слушает: Jenkins не запущен,
либо адрес или порт указаны неверно.
ЧТО ДЕЛАТЬ: на контроллере проверьте службу (systemctl status jenkins)
и порт (ss -lntp), а в команде — что стоит именно 10.0.2.5, если
команда идёт не с admin.

ПРОБЛЕМА: «Connection timed out».
ПРИЧИНА: адрес верный, но пакеты не доходят: другая подсеть,
выключенная машина, правило файрвола.
ЧТО ДЕЛАТЬ: проверьте машину (ping 10.0.2.5) и портал:
curl -s -o /dev/null -w '%{http_code}\n' http://10.0.2.5:8080/login
Ответ 200 означает, что портал отвечает, и дело не в сети.

ПРОБЛЕМА: токен отозвали или в -auth неверное имя пользователя.
ПРИЧИНА: сервер отвечает 401 или «invalid password/token»: токен мог
быть отозван, пользователя могли переименовать, а в команде осталась
старая копия из истории оболочки.
ЧТО ДЕЛАТЬ: создайте новый токен в профиле и обновите файл с токеном.

ПРОБЛЕМА: версия клиента не совпадает с версией сервера.
ПРИЧИНА: jenkins-cli.jar скачан давно, а сервер обновился;
проявляется по-разному: неизвестная команда, странный ответ, обрыв.
ЧТО ДЕЛАТЬ: скачайте клиент заново с самого сервера:
wget -O ~/jenkins-cli.jar http://10.0.2.5:8080/jnlpJars/jenkins-cli.jar

ПРОБЛЕМА: команда есть в курсе, но клиент её не знает.
ПРИЧИНА: набор команд зависит от версии Jenkins и плагинов, а часть
команд со временем помечается устаревшими и удаляется.
ЧТО ДЕЛАТЬ: сверьтесь со списком на странице Manage Jenkins ->
Jenkins CLI и с выводом help; если команды нет — сделайте то же
самое в портале или через API.

ПРАВИЛО: сначала читайте текст ошибки — в нём прямо сказано, чего
не хватает: учётных данных, прав, crumb или доступного сервера.

=========================================================================
10. УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

10.1. Удаляем задания, созданные через CLI:

$CLI list-jobs
$CLI delete-job FirstJob-copy

В списке должны остаться только нужные задания курса: FirstJob,
build_with_params и periodic_report (третье появится в практике 7).
Задание NodeCheck из практики 4 тоже может остаться: его удаление —
по желанию (см. практику 4).

10.2. Удаляем файлы с секретами и служебные файлы:

rm -f ~/.jenkins-token ~/myjob.xml
rm -rf ~/jobs-backup ~/jenkins-jobs-*

ЗАЧЕМ: файл с токеном — это ключ от Jenkins. Привычка проверять такие
файлы после работы остаётся с вами и на рабочем стенде.

10.3. Отзываем токен, если он попал в чужие руки: значок пользователя
-> Configure -> API Token -> Revoke. Отзыв мгновенный и пароль не
затрагивает, а скрипты со старым токеном перестают работать. Если файл
попал в git-репозиторий, одного отзыва мало — значение осталось
в истории коммитов: удалите файл и добавьте его в .gitignore.
