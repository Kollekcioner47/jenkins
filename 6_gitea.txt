Практика 6. Свой Git-сервер: Gitea и сборка из репозитория.

Готовые файлы: files/gitea/app.ini, files/gitea/gitea.service,
страница сайта files/www/index.html.

=========================================================================
ЗАЧЕМ СВОЙ GIT-СЕРВЕР
=========================================================================

Раньше задания работали с файлами, которые создавали сами. Настоящая
сборка начинается там, где есть репозиторий: из него Jenkins берёт код,
и из него же в практике 11 будет выкатываться страница сайта на node1
и node2 через nginx.

Зачем свой Git-сервер, если есть GitHub?

  * У СТЕНДА НЕТ БЕЛОГО IP. Чтобы GitHub известил Jenkins о новом
    коммите, он должен сам обратиться к нему из интернета, а у стенда
    адрес частный — 10.0.2.5. Вебхук не дойдёт;
  * НЕТ HTTPS И ЛИШНИХ УЧЁТНЫХ ЗАПИСЕЙ: соединение открытое, внешние
    сервисы требуют регистрации и токенов;
  * ИНТЕРНЕТ ТОЛЬКО НА ИСХОДЯЩИЕ: входящие соединения извне невозможны.

Решение: Git-сервер на той же машине, что и Jenkins, в той же подсети.
Jenkins — http://10.0.2.5:8080, Gitea — http://10.0.2.5:3000, git по ssh
— 10.0.2.5, порт 2222.

Облачный GitHub привычен и даёт готовые интеграции, но вебхук в наш
Jenkins недоступен, нужен интернет и учётная запись, а код уходит наружу.
Gitea даёт полный контроль над сервером и данными, вебхуки работают без
интернета; но обслуживать сервер нужно самим: обновления, место
на диске, резервные копии (практика 14).

ИСПРАВЛЕНО: прежде практика называлась «развёртывание из GitHub», и в ней
же стояла пометка «нужен белый IP». Без белого IP вебхук из GitHub не
придёт никогда, поэтому раздел про триггер по вебхуку был нерабочим.
Практика переписана на свой Git-сервер: Gitea стоит в одной подсети
с Jenkins и выбран за простоту — один бинарный файл, служба systemd
из десятка строк, конфигурация, которую можно прочитать целиком.

ЧТО ПОНАДОБИТСЯ
=========================================================================

Машины те же, что и в предыдущих практиках: admin 10.0.2.5 (контроллер
Jenkins и он же Git-сервер Gitea), node1 10.0.2.13 и node2 10.0.2.14
(агенты Jenkins и веб-серверы nginx). Нужны Jenkins LTS 2.528.1

Дальше все команды выполняются на admin, если не сказано иное.

=========================================================================
1. Установка Gitea на admin
=========================================================================

Gitea ставится одним бинарным файлом: ни пакетного менеджера, ни
отдельной базы данных. Страница загрузок: https://dl.gitea.com/gitea/

ВАЖНО: берите стабильный релиз, а не первый попавшийся файл: рядом со
стабильными версиями лежат выпуски-кандидаты (release candidate), они
помечены отдельно. Текущая стабильная ветка — 1.24.x; точный номер
смотрим на странице и подставляем в переменную. В тексте номер не указан
намеренно: он меняется, а команда проверки версии остаётся.

GITEA_VER=НОМЕР_СТАБИЛЬНОГО_РЕЛИЗА
curl -fsSL -o /tmp/gitea \
  https://dl.gitea.com/gitea/${GITEA_VER}/gitea-${GITEA_VER}-linux-amd64
sudo install -m 755 /tmp/gitea /usr/local/bin/gitea
rm -f /tmp/gitea
gitea --version

install кладёт файл на место и выставляет права 755; сверьте выведенный
номер версии со скачанным.

Службе нужен свой пользователь:

sudo adduser --system --shell /bin/bash --gecos 'Git Version Control' \
  --group --disabled-password --home /home/git git

ЗАЧЕМ ОТДЕЛЬНЫЙ ПОЛЬЗОВАТЕЛЬ, А НЕ ROOT: Gitea принимает данные от кого
угодно, и, работая от root, любая её ошибка означает полный доступ
к машине, на которой стоит и Jenkins. Флаги: --system — служебная запись
без срока пароля, --disabled-password — войти по паролю нельзя, --group —
группа git для файлов git:git, --home /home/git — там Gitea держит
служебные файлы.

sudo mkdir -p /var/lib/gitea/custom /var/lib/gitea/data \
  /var/lib/gitea/log /var/lib/gitea/repositories
sudo chown -R git:git /var/lib/gitea
sudo chmod -R 750 /var/lib/gitea

sudo mkdir -p /etc/gitea
sudo chown root:git /etc/gitea
sudo chmod 770 /etc/gitea

ЗАЧЕМ РАЗДЕЛЯТЬ ДАННЫЕ И КОНФИГУРАЦИЮ: данные в /var/lib/gitea растут
и должны быть доступны службе на запись; конфигурация меняется редко
и читается при старте. Копия делается по частям (практика 14), службе
можно дать права на данные, не открывая доступ к её настройкам.
Программа лежит в /usr/local/bin/gitea, конфигурация — в /etc/gitea,
база и репозитории — в /var/lib/gitea.


=========================================================================
2. Конфигурация: /etc/gitea/app.ini
=========================================================================

sudo cp files/gitea/app.ini /etc/gitea/app.ini
sudo chown git:git /etc/gitea/app.ini
sudo chmod 640 /etc/gitea/app.ini

Права 640: владелец читает и пишет, группа читает, остальные не видят
файла, а в конфигурации лежат секреты. Ниже — ключевые параметры
(sudo nano /etc/gitea/app.ini).

Раздел [server]:

  PROTOCOL  = http
  DOMAIN    = 10.0.2.5
  HTTP_ADDR = 0.0.0.0
  HTTP_PORT = 3000
  ROOT_URL  = http://10.0.2.5:3000/

ЗАЧЕМ ТРИ АДРЕСА, А НЕ ОДИН. HTTP_ADDR — на каком интерфейсе слушать
(0.0.0.0 означает «на всех», иначе портал был бы доступен только с самой
машины). ROOT_URL — какой адрес Gitea подставляет в ссылки, которые
отдаёт наружу: с localhost портал у вас откроется, а ссылки
на репозитории будут вести на localhost с node1 и node2.

  SSH_DOMAIN       = 10.0.2.5
  START_SSH_SERVER = true
  SSH_PORT         = 2222
  SSH_LISTEN_PORT  = 2222

ПОЧЕМУ 2222, А НЕ 22. На порту 22 на машине admin уже слушает sshd
операционной системы: им пользуемся мы и агенты Jenkins (практика 4).
Занять этот порт Gitea не может, поэтому в адресах репозиториев порт
указывается явно:

  ssh://git@10.0.2.5:2222/engineer/site.git

START_SSH_SERVER = true означает, что Gitea поднимает собственный
SSH-сервер и не требует настройки sshd и authorized_keys в системе.

Разделы [database] и [repository]:

  DB_TYPE        = sqlite3
  PATH           = /var/lib/gitea/data/gitea.db
  ROOT           = /var/lib/gitea/repositories
  DEFAULT_BRANCH = main

ВАЖНО ПРО DEFAULT_BRANCH = main: это ветка, которую Gitea создаёт в новом
репозитории. В прежней версии курса репозиторий жил в main, а задание
Jenkins искало master и падало с сообщением, что не нашло ревизию.

Раздел [security] — самое важное место в файле:

  INSTALL_LOCK   = true
  SECRET_KEY     = заполните_своим_значением
  INTERNAL_TOKEN = заполните_своим_значением

ВАЖНО, ЭТО СТОИТ ПРОЧИТАТЬ ДВАЖДЫ. INSTALL_LOCK = true означает
«первичная настройка пройдена». Если он выключен или отсутствует, Gitea
при первом открытии портала показывает мастер установки, и тот, кто
пройдёт его первым, станет администратором сервера: в лаборатории это
сосед по сети, в интернете такие порталы находят сканеры. У нас мастер
не появится — администратора создаём командой в разделе 4.

SECRET_KEY — подпись сессий и cookie: при утечке сессии можно подделать,
при смене все пользователи разлогинятся. INTERNAL_TOKEN — внутренний
токен Gitea. Оба значения уникальны для каждой установки:

SECRET_KEY="$(openssl rand -hex 32)"
INTERNAL_TOKEN="$(openssl rand -hex 32)"
LFS_JWT_SECRET="$(openssl rand -hex 32)"

sudo sed -i "s|^SECRET_KEY.*|SECRET_KEY = ${SECRET_KEY}|" \
  /etc/gitea/app.ini
sudo sed -i "s|^INTERNAL_TOKEN.*|INTERNAL_TOKEN = ${INTERNAL_TOKEN}|" \
  /etc/gitea/app.ini
sudo sed -i "s|^LFS_JWT_SECRET.*|LFS_JWT_SECRET = ${LFS_JWT_SECRET}|" \
  /etc/gitea/app.ini

grep -c 'заполните_своим_значением' /etc/gitea/app.ini

Команда должна вывести 0. ОБРАТИТЕ ВНИМАНИЕ: эти значения понадобятся
при переезде на другую машину и при восстановлении из копии (практика
14), поэтому храните файл вместе с резервной копией.

Раздел [service]: DISABLE_REGISTRATION = true закрывает самостоятельную
регистрацию (учётные записи заводит администратор), REQUIRE_SIGNIN_VIEW
= true не показывает содержимое репозиториев анонимным посетителям. На
стенде без HTTPS это принципиально: портал доступен любому в подсети.
УТОЧНЕНО: в рабочей среде app.ini делают владельцем root с группой git
и правами 0640 — тогда служба читает конфигурацию, но не может её
переписать. В лаборатории владелец — git, чтобы вам было удобнее
править. Почта не настроена: в разделе [mailer] стоит ENABLED = false.

РАЗДЕЛ [webhook] — ПРО НЕГО ПРИДЁТСЯ ВСПОМНИТЬ В ПРАКТИКЕ 7. Там мы
заставим Gitea уведомлять Jenkins о каждом push, и вот здесь на пути
стоит защита самого Git-сервера:

  [webhook]
  ALLOWED_HOST_LIST = 10.0.2.5

В Gitea 1.16 и новее значение по умолчанию — external, то есть вебхуки
разрешены только на внешние адреса. Причина — защита от SSRF: иначе
любой пользователь Git-сервера через вебхук заставил бы сервер
обращаться к внутренним адресам и по коду ответа «прощупывать» сеть.

Наш Jenkins стоит на приватном адресе 10.0.2.5, поэтому при значении
external Gitea откажется создавать такой вебхук: API вернёт 403,
и это будет выглядеть как проблема токена, хотя дело не в нём.
Отсюда правило: адрес Jenkins вписывается в ALLOWED_HOST_LIST явно.
Ставить * (все адреса) не надо — это отменяет защиту; перечислите
конкретные адреса через запятую.

После правки app.ini службу перезапускаем:

  sudo systemctl restart gitea
  systemctl status gitea --no-pager

Проверить действующее значение можно так:

  grep -A2 '\[webhook\]' /etc/gitea/app.ini


=========================================================================
3. Служба systemd: gitea
=========================================================================

sudo cp files/gitea/gitea.service /etc/systemd/system/gitea.service
sudo systemctl daemon-reload
sudo systemctl enable --now gitea
systemctl status gitea
sudo journalctl -u gitea -n 50 --no-pager

daemon-reload заставляет systemd перечитать описания служб: без него
новый файл не будет замечен. enable --now включает автозапуск при
загрузке и запускает службу сейчас. В статусе мы хотим увидеть active
(running) и строку запуска:

  /usr/local/bin/gitea web --config /etc/gitea/app.ini

Запускать сервер вручную нельзя: процесс умрёт при первом закрытии
терминала или при перезагрузке, а причину «Jenkins не видит репозиторий»
будут искать в Jenkins. Разберём файл службы построчно:

  User=git
  Group=git
  ConditionFileNotEmpty=/etc/gitea/app.ini
  Environment=GITEA_WORK_DIR=/var/lib/gitea
  Environment=HOME=/home/git
  ExecStart=/usr/local/bin/gitea web --config /etc/gitea/app.ini
  Restart=always

Условие ConditionFileNotEmpty: если конфигурации нет, служба не стартует
и пишет condition failed — это понятнее, чем сервер с неизвестными
настройками. Restart=always поднимает службу заново после сбоя. Ограничения
прав — то, ради чего этот файл стоит разбирать:

  NoNewPrivileges=true
  PrivateTmp=true
  ProtectSystem=strict
  ProtectHome=read-only
  ReadWritePaths=/var/lib/gitea /home/git /etc/gitea
  RestrictSUIDSGID=true

ProtectSystem=strict делает файловую систему доступной только для чтения:
запись возможна лишь в ReadWritePaths. ProtectHome=read-only закрывает
домашние каталоги, а /home/git разрешён явно — он нужен Gitea.



Проверим портал: http://10.0.2.5:3000 — должна открыться страница входа
Gitea, а не мастер установки.

curl -s -o /dev/null -w '%{http_code}\n' http://10.0.2.5:3000/
# 200


=========================================================================
4. Первый администратор и создание репозитория
=========================================================================

Мастера установки мы не проходили: INSTALL_LOCK = true отключил его.
Заведём администратора командой:

sudo -u git gitea admin user create --config /etc/gitea/app.ini \
  --username engineer --admin --password Console47 \
  --email engineer@lab.local --must-change-password=false

Здесь --username engineer — владелец репозитория и администратор Gitea,
--admin даёт права администратора сервера, а --must-change-password=false
означает «не требовать смены пароля при первом входе» (в рабочей среде
этот флаг не выключают, а пароль не пишут в командной строке: он
остаётся в истории оболочки).

sudo -u git gitea admin user list --config /etc/gitea/app.ini

Заходим в портал http://10.0.2.5:3000 под engineer с паролем Console47
и создаём репозиторий: «+» в правом верхнем углу → New Repository.

  Owner                 engineer
  Repository Name       site
  Visibility            Private (галочка)
  Initialize Repository НЕ ставить ни README, ни .gitignore, ни лицензию
  → Create Repository

ПОЧЕМУ ПРИВАТНЫЙ. Публичный репозиторий виден и клонируется кем угодно
без входа; приватный доступен владельцу и тем, кому он выдал доступ.
На стенде нет HTTPS, и всё передаваемое, включая учётные данные, идёт
по сети открытым текстом, а в репозитории со временем появятся имена
серверов и адреса.

ПОЧЕМУ БЕЗ README. Иначе Gitea сама создаст первый коммит, и наш push
столкнётся с несвязанными историями: сервер ответит «rejected — fetch
first» и предложит сделать git pull. Нам нужен пустой репозиторий:
первую ветку создаст наш собственный push. Адрес репозитория (он же
понадобится Jenkins):

  ssh://git@10.0.2.5:2222/engineer/site.git


=========================================================================
5. SSH-ключ для работы с репозиторием
=========================================================================

Работать с git по http неудобно: пароль пришлось бы вводить на каждый
push. Генерируем ключ на рабочей машине от имени engineer:

ssh-keygen -t ed25519 -C "engineer@admin"

cat ~/.ssh/id_ed25519.pub

Публичная часть — одна строка, начинающаяся словами ssh-ed25519; копируем
её целиком, приватную часть не показываем никому. Добавляем публичную
в Gitea: справа вверху → Settings (Настройки) → вкладка SSH / GPG Keys
→ Add Key.

ЗАЧЕМ КАЖДОМУ СВОЙ КЛЮЧ. Ключ — это имя: по нему Gitea понимает, кто
именно подключается. С общим ключом невозможно понять, кто сделал push,
и нельзя отозвать доступ одному человеку, не сломав работу остальным.
Поэтому у каждого человека свой ключ, а у Jenkins — отдельный (раздел 7).

chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
ssh -T -p 2222 git@10.0.2.5

Ожидаемый ответ (текст зависит от версии Gitea, смысл один):

  Hi there, engineer! You've successfully authenticated with the key
  named engineer@admin, but Gitea does not provide shell access.

ВАЖНО: «does not provide shell access» — не ошибка. Git по ssh не даёт
интерактивной оболочки, он умеет только обслуживать репозитории. Иначе
ответ был бы Permission denied (publickey); разбор — в разделе 12.


=========================================================================
6. Настройка git и первый push
=========================================================================

git config --global user.name "Engineer"
git config --global user.email "engineer@lab.local"
git config --global init.defaultBranch main

cd ~
git clone ssh://git@10.0.2.5:2222/engineer/site.git
cd ~/site
mkdir -p www
cp ~/jenkins-course/files/www/index.html www/index.html
git add www/index.html
git commit -m "Первая версия страницы сайта"
git push -u origin main

ОБРАТИТЕ ВНИМАНИЕ на путь к странице: подставьте свой каталог
с материалами курса — в примере это ~/jenkins-course, полный путь
получается ~/jenkins-course/files/www/index.html. Относительный путь
files/www/index.html здесь не сработает: мы уже перешли в ~/site, и git
искал бы файлы курса внутри репозитория.

ЗАЧЕМ init.defaultBranch main: чтобы локальные репозитории создавались
сразу в ветке main — это страховка от путаницы master/main. Репозиторий
пуст, поэтому git предупредит «warning: You appear to have cloned an
empty repository»: это ожидаемо. Теперь три вещи, которые стоит понять.

1) ПОРТ 2222 В АДРЕСЕ ОБЯЗАТЕЛЕН. Сокращённая запись вида
git@10.0.2.5:engineer/site.git порт указать не позволяет вообще: такой
формат всегда идёт на порт 22, где отвечает sshd самой операционной
системы — пользователя git он не знает и ответит Permission denied
(publickey), хотя ключ добавлен. Поэтому адрес Gitea всегда пишется
в форме ssh:// с портом 2222, и ту же строку вы вставите в задание.

2) ВЕТКА main, А НЕ master. Раньше ветка по умолчанию в git называлась
master, сегодня — main, и в конфигурации Gitea у нас DEFAULT_BRANCH =
main. Путаница даёт поломку, которую трудно понять: push проходит, файлы
в репозитории видны, а задание Jenkins падает с сообщением, что не нашло
ни одной ревизии, — потому что ищет ветку master, которой нет.

git branch --show-current
# main

3) ЧТО ЗНАЧИТ «ОТСЛЕЖИВАНИЕ ВЕТКИ». Ключ -u (--set-upstream) связывает
локальную ветку main с удалённой origin/main: после этого достаточно
писать просто git push и git pull, а git status покажет, на сколько
коммитов вы опережаете или отстаёте.

В браузере http://10.0.2.5:3000/engineer/site должны появиться файл
www/index.html, ветка main и один коммит. В странице остались маркеры
__BUILD_NUMBER__ и __GIT_COMMIT__: сейчас это просто текст, заменять их
будет конвейер выката в практике 11.


=========================================================================
7. Подключение Jenkins к репозиторию
=========================================================================

Чтобы Jenkins мог читать репозиторий, нужно четыре вещи: ключ, который
Gitea примет; запись о ключе хоста сервера; credentials в Jenkins, где
ключ хранится; и права ровно на чтение — писать сборке незачем.

ШАГ 1. ОТДЕЛЬНЫЙ КЛЮЧ ДЛЯ JENKINS. В практике 4 у пользователя jenkins
появился ключ для агентов; для репозитория заведём второй: один ключ —
одно назначение.

sudo mkdir -p /var/lib/jenkins/.ssh
sudo chown jenkins:jenkins /var/lib/jenkins/.ssh
sudo chmod 700 /var/lib/jenkins/.ssh

sudo -u jenkins ssh-keygen -t ed25519 -N "" \
  -f /var/lib/jenkins/.ssh/id_ed25519_gitea -C "jenkins@gitea-reader"

sudo cat /var/lib/jenkins/.ssh/id_ed25519_gitea.pub

Флаг -N "" задаёт пустую парольную фразу: служба не может вводить пароль.

ШАГ 2. ПУБЛИЧНЫЙ КЛЮЧ В GITEA. Правильный вариант — DEPLOY KEY
репозитория (Settings → Deploy Keys → Add Deploy Key), галочку Write
access НЕ ставить: доступ только к этому репозиторию и только на чтение.
Ключ в учётной записи (Settings → SSH / GPG Keys) проще, но тогда Jenkins
действует от имени engineer и видит все его репозитории; мы пользуемся
первым вариантом.

ШАГ 3. CREDENTIALS В JENKINS. Manage Jenkins → Credentials → System →
Global credentials (unrestricted) → Add Credentials:

  Kind          SSH Username with private key
  ID            gitea-reader
  Description   SSH-ключ для репозиториев Gitea
  Username      git
  Private Key   Enter directly → Add → содержимое приватного ключа
                (весь файл целиком, включая строки BEGIN и END)

ОБРАТИТЕ ВНИМАНИЕ ДВАЖДЫ. Username здесь git, а не engineer: по SSH
к Gitea все подключаются под служебным пользователем git, а учётную
запись сервер определяет по предъявленному ключу, а не по имени
в адресе. И второе: приватный ключ, скопированный в буфер обмена или
в заметки, нужно оттуда убрать — его место в поле credentials.


ШАГ 4. КЛЮЧ ХОСТА В known_hosts. SSH-клиент сверяет ключ сервера
с записанным у него в known_hosts. У Jenkins свой домашний каталог,
значит, и свой файл: /var/lib/jenkins/.ssh/known_hosts.

ssh-keyscan -p 2222 10.0.2.5 \
  | sudo tee -a /var/lib/jenkins/.ssh/known_hosts > /dev/null

sudo chown -R jenkins:jenkins /var/lib/jenkins/.ssh
sudo chmod 700 /var/lib/jenkins/.ssh
sudo chmod 600 /var/lib/jenkins/.ssh/known_hosts
sudo grep -c '\[10.0.2.5\]:2222' /var/lib/jenkins/.ssh/known_hosts

Последняя команда должна показать хотя бы одну запись. Форма записи
[10.0.2.5]:2222 — именно так в known_hosts выглядит хост с нестандартным
портом; без -p 2222 в файл попадёт ключ sshd самой машины.

Настроим проверку ключей серверов: Manage Jenkins → Security → Git Host
Key Verification Configuration. Нужен вариант Known hosts file — сверка
с /var/lib/jenkins/.ssh/known_hosts. Manually provided keys перечисляет
ключи в настройке, No verification не проверяет ничего, так делать
не нужно. ДОБАВЛЕНО: промежуточный вариант Accept first connection
принимает ключ при первом подключении и запоминает его — для лаборатории
допустимо, в рабочей среде «первое соединение» может оказаться чужим.

Проверим всё вместе, от имени пользователя jenkins:

sudo -u jenkins ssh -p 2222 -o BatchMode=yes git@10.0.2.5

Ожидаем то же приветствие от Gitea (с deploy key имени пользователя в нём
может не быть). ЗАЧЕМ ЭТА ПРОВЕРКА ДО ЗАДАНИЯ: она отделяет проблемы SSH
от проблем Jenkins.


ШАГ 5. ТОКЕН API: ВТОРАЯ ДВЕРЬ В GITEA. До сих пор мы подключались
к Gitea по SSH — это дверь для git: клонирование, push, pull. Но у Gitea
есть ещё и API: HTTP-интерфейс, через который программы управляют
сервером — читают список репозиториев, создают вебхуки, узнают сведения
о коммитах. Ключ SSH здесь не поможет: другой протокол, другие права.

ЗАЧЕМ ОН НАМ. В практике 7 мы настроим вебхук: Gitea будет сообщать
Jenkins о каждом push. Плагин gitea в Jenkins умеет делать это сам, но
для этого ему нужен доступ к API Gitea, то есть токен. Без токена вебхук
придётся создавать руками, а часть возможностей плагина не заработает
(список репозиториев, автоматическая регистрация вебхуков).

Создаём токен в Gitea:

  аватар (правый верхний угол) → Settings → Applications →
  Manage Access Tokens → Generate New Token

  Token Name   jenkins-lab
  Scopes       доступ к репозиториям — чтение и запись,
               чтение профиля пользователя
  → Generate Token

ПРО ОБЛАСТИ ПРАВ (SCOPES). Права администратора не нужны. В новых
версиях Gitea области выбираются по отдельности (например,
read:repository и write:repository), в прежних — крупными наборами
(repository, user). Запись в репозиторий нужна не для коммитов, а
потому что плагин сам создаёт и обновляет вебхуки в его настройках.

ВАЖНО: ТОКЕН ПОКАЗЫВАЮТ ОДИН РАЗ. Скопируйте его сразу — второй раз
Gitea значение не покажет, у себя он хранит только хеш. Потеряли —
удалите старый токен на той же странице и создайте новый. Ушли из
команды или токен засветился — отзовите там же: токен действует, пока
его не удалили.

Кладём токен в Jenkins. Здесь есть тонкость, на которой спотыкаются
почти все: обычный Secret text в настройках сервера Gitea выбрать
НЕЛЬЗЯ — его там просто не будет в списке.

ПОЧЕМУ ТАК. Плагин объявляет собственный вид credentials и в своих
полях предлагает только его: он не умеет читать произвольные секреты,
ему нужен секрет своего типа, из которого он знает, как достать токен.
Поэтому список видов в поле «Credentials» короче, чем в разделе
Credentials, — это фильтр по типу, а не поломка.

Создаём credential нужного типа:

  Manage Jenkins → Credentials → System → Global credentials
  → Add Credentials

  Kind          Gitea Personal Access Token
                (вид от самого плагина: в списке он назван по имени
                плагина и словом Token; в старых версиях может
                называться просто Gitea API Token)
  ID            gitea-token
  Token         значение токена
  Description   Токен API Gitea для плагина Gitea

ЕСЛИ ВИДА ОТ ПЛАГИНА В СПИСКЕ НЕТ, проверяем по порядку:

  1. плагин установлен и включён: Manage Jenkins → Plugins → Installed,
     в поиске gitea; рядом не должно быть пометки о том, что плагин
     отключён или не загрузился;
  2. Jenkins перезапускали после установки: кнопка Install without
     restart оставляет часть возможностей плагина недоступной до
     перезапуска службы;
  3. в журнале нет ошибок загрузки: Manage Jenkins → System Log.

Идентификатор gitea-token — то самое имя, которое встретится в
настройках плагина Gitea в практике 7. Имя выбрано осмысленным: задания
и настройки ссылаются на ID, а не на описание.

ВАЖНО ПРО ВИД «GITEA USERNAME WITH PRIVATE KEY». Он тоже принадлежит
плагину и потому виден в том же списке, но предназначен для входа
по SSH-ключу — имени пользователя и приватного ключа. Токен в него
подставлять нельзя: ключ и токен — разные способы аутентификации.
Если использовать этот вид для обращений к API, Gitea ответит отказом
(обычно 403), потому что приватным ключом API не аутентифицируется:
заголовок Authorization: token ... принимает только токен.

Проверяем, что токен рабочий, с машины admin:

  curl -s -H "Authorization: token ЗНАЧЕНИЕ_ТОКЕНА" \
    http://10.0.2.5:3000/api/v1/version

Ожидаемый ответ — JSON с версией, например {"version":"1.24.0"}.
Ответ вида {"message":"token is required"} или код 401 означает, что
токен скопирован не целиком, уже отозван или в заголовке опечатка.

ЕСЛИ ПРИШЁЛ ОТКАЗ 403, проверяем не токен, а права. Разница между
кодами здесь принципиальная:

  401 — токен не принят вовсе: опечатка, отозван, потерян;
  403 — токен принят и Gitea поняла, кто вы, но действие не разрешено.

ОТДЕЛЬНО: 403, КОТОРЫЙ К ТОКЕНУ ОТНОШЕНИЯ НЕ ИМЕЕТ. Если отказ
приходит не на запросы ниже, а при попытке создать вебхук на адрес
Jenkins, дело в защите Git-сервера от SSRF: в Gitea 1.16 и новее
параметр ALLOWED_HOST_LIST по умолчанию равен external, и вебхуки на
приватные адреса запрещены. Лечится строкой в /etc/gitea/app.ini
(раздел [webhook], см. выше) и перезапуском службы — разбор в практике 7.

Три причины 403 по токену и как их различить. Выполняем по очереди
с машины admin (в каждой команде подставьте значение токена):

  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "Authorization: token ЗНАЧЕНИЕ_ТОКЕНА" \
    http://10.0.2.5:3000/api/v1/version

  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "Authorization: token ЗНАЧЕНИЕ_ТОКЕНА" \
    http://10.0.2.5:3000/api/v1/repos/engineer/site

  curl -s -o /dev/null -w '%{http_code}\n' \
    -H "Authorization: token ЗНАЧЕНИЕ_ТОКЕНА" \
    http://10.0.2.5:3000/api/v1/repos/engineer/site/hooks

Как читать результат:

  * первая команда 401 или 403 — дело в самом токене;
  * первая 200, вторая 403 или 404 — у пользователя нет доступа
    к репозиторию engineer/site (он приватный, владелец — engineer);
  * первая и вторая 200, третья 403 — у токена не хватает областей
    прав: чтобы плагин создавал и обновлял вебхуки, нужен доступ
    к репозиториям на чтение И запись (write:repository или набор
    repository в старых версиях). Такой токен пересоздают.

Подставлять вместо токена приватный SSH-ключ бессмысленно: API
аутентифицируется только токеном, ключ для этого не годится — Gitea
ответит тем же 403.

ОТДЕЛЬНО ПРО БЕЗОПАСНОСТЬ. Токен — это пароль, только длиннее: он даёт
всё, что разрешено его областями прав, не привязан к сеансу и работает
с любой машины, пока его не отозвали. Поэтому токен не коммитят в
репозиторий (для этого и есть credentials), не пересылают в чатах и
отзывают при смене ответственного. Подробнее про секреты — практика 11.

ЧТО ДЕЛАТЬ, ЕСЛИ ТОКЕН НЕ НАСТРАИВАЕТСЯ ВООБЩЕ. Токен нужен плагину,
а не вебхуку: вебхук в Gitea создаётся руками (практика 7, пункт 6.3)
и работает без токена. Без токена будут недоступны автоматическая
регистрация вебхуков, список репозиториев и сведения о ветках — для
обучения это не мешает пройти практику до конца.


=========================================================================
8. Сборка из репозитория: задание gitea_build
=========================================================================

Убедимся, что плагин Git установлен: Manage Jenkins → Plugins → Installed
plugins → ищем Git (он есть в списке плагинов курса,
files/jcasc/plugins.txt). Если его нет: Available plugins → Git → Install.

Создаём задание: New Item → имя gitea_build → Freestyle project → OK.
В разделе Source Code Management → Git:

  Repository URL     ssh://git@10.0.2.5:2222/engineer/site.git
  Credentials        gitea-reader
  Branches to build  Branch Specifier: */main

Поле Repository URL проверяется сразу после ввода: Jenkins пытается
подключиться и показывает либо ошибку, либо успех. Затем Build Steps →
Add build step → Execute shell:

  echo "------> Сборка началась"
  pwd
  ls -la
  cat www/index.html
  git log -1 --oneline
  echo "------> Сборка закончилась"

Сохраняем и запускаем: Build Now, затем Console Output. Плагин Git
печатает, что забирает изменения (Fetching upstream changes), и ревизию,
которую выписал (Checking out Revision <хеш>); после этого идёт наш вывод.
Хеш в журнале и хеш последнего коммита в репозитории должны совпадать —
это первое, что проверяют, если «собралось не то».

ГДЕ ИМЕННО JENKINS КЛОНИРУЕТ РЕПОЗИТОРИЙ: в рабочий каталог задания
на том узле, где выполняется сборка (строка pwd в журнале): на
контроллере это /var/lib/jenkins/workspace/gitea_build, на агентах —
/home/jenkins/agent/workspace/gitea_build.

ПОЧЕМУ РАБОЧИЙ КАТАЛОГ — НЕ МЕСТО ДЛЯ ПРАВОК. Каталог принадлежит
Jenkins, и перед каждой сборкой плагин приводит его в соответствие
с репозиторием: правки будут перезаписаны или помешают обновлению.
Каталог может исчезнуть (кнопка Wipe Out Workspace), а при смене узла
сборка получит новый каталог на другой машине. Если изменение нужно
постоянно, его место — в репозитории: тогда оно видно всем,
версионируется и попадает в сборку законным путём.

=========================================================================
9. Jenkinsfile в репозитории
=========================================================================

Описание сборки лежало в настройках задания на контроллере Jenkins. Это
неудобно: оно не версионируется (непонятно, кто и когда поменял шаг
сборки), его не видно при просмотре репозитория, правка не проходит
ревью, а при переезде Jenkins (практика 14) настройки заданий
приходится восстанавливать отдельно от кода. Другой подход — держать
описание конвейера рядом с кодом, в файле Jenkinsfile в корне
репозитория: история сборки лежит в git рядом с историей кода, правка
проходит такое же ревью, а репозиторий становится самодостаточным.

  pipeline {
      agent any

      stages {
          stage('Проверка репозитория') {
              steps {
                  sh 'pwd; ls -la'
                  sh 'cat www/index.html'
                  sh 'git log -1 --oneline'
              }
          }
      }
  }

Создайте файл Jenkinsfile в каталоге сайта и вставьте в него листинг,
приведённый выше:

cd ~/site
vim Jenkinsfile

Отправляем в репозиторий:

cd ~/site
git add Jenkinsfile
git commit -m "Добавлен Jenkinsfile"
git push

Обратите внимание: pipeline { } и stages { } — обязательные блоки
декларативного конвейера, команды лежат внутри steps { }, а не рядом
со stage, а sh '...' выполняет команду оболочки на агенте, в рабочем
каталоге сборки, — то же самое, что делал шаг Execute shell. Чтобы
задание собиралось по файлу, меняем тип описания: в задании gitea_build
→ Pipeline → Definition: Pipeline script from SCM → SCM: Git, тот же
адрес и те же credentials gitea-reader → Script Path: Jenkinsfile.

ЗАЧЕМ МЫ РАЗБИРАЕМ ЭТО ЗДЕСЬ ТОЛЬКО КОНЧИКОМ. Подробно про конвейеры —
практика 10: стадии, блок post, параллельность, работа с секретами,
ограничения. Здесь важно понять мысль: описание сборки переезжает
из настроек Jenkins в репозиторий, а задание становится ссылкой
на файл. Готовый пример минимального конвейера — в материалах курса:
files/pipelines/Jenkinsfile.simple.


=========================================================================
10. Ветки и теги: что именно собирает Jenkins
=========================================================================

За выбор того, что собирать, отвечает поле Branch Specifier, которое
умеет шаблоны: */main — ветка main, */release/* — все ветки вида
release/1.0, refs/tags/v* — все теги, начинающиеся с v.

ВАЖНО: шаблон сверяется с полным именем ссылки, поэтому для тегов он
пишется целиком, вместе с refs/tags/. И чтобы теги вообще оказались
в клонированной копии, в разделе Source Code Management у Git нужно
раскрыть Advanced и включить Fetch tags; без этого задание не найдёт тег
и упадёт с сообщением про отсутствующую ревизию.

Тег — метка на конкретном коммите: v1.0 всегда указывает на один и тот
же код, что бы потом ни происходило в ветке, поэтому релизы собирают
по тегам: сборка воспроизводима.

git tag -a v1.0 -m "Первая версия сайта"
git push origin v1.0

МНОГОВАРИАНТНЫЙ КОНВЕЙЕР (MULTIBRANCH PIPELINE) решает обратную
задачу: он сам читает список веток в репозитории и создаёт по заданию
на каждую найденную. New Item → Multibranch Pipeline → Branch Sources →
Add source → Git → тот же адрес и credentials gitea-reader → Behaviours
→ Discover branches → Save. Новая ветка — новое задание, без ручной
настройки; ветка удалена — задание помечается удалённым.

СБОРКИ ЗАПРОСОВ НА СЛИЯНИЕ. Multibranch умеет собирать и pull request:
проверяется именно то, что предлагают влить в main, до того как это туда
попало. Для Gitea это делается через плагин Gitea: репозиторий
отправляет в Jenkins событие, Jenkins по нему запускает проверку
предложенной ветки. Механизм опирается на то, что Gitea и Jenkins стоят
рядом, в одной подсети, и событие доходит за миллисекунды, — чего нельзя
сделать с облачным GitHub на нашем стенде. Подробно про события
и вебхуки — в практике 7: там мы свяжем репозиторий с заданием
gitea_build так, что сборка будет запускаться сама при каждом push.


=========================================================================
11. Гигиена репозитория
=========================================================================

ЧТО НЕЛЬЗЯ КЛАСТЬ В GIT:

  * пароли, токены, приватные ключи. Любой секрет, попавший
    в репозиторий, надо считать известным всем, у кого есть доступ, —
    и это не только коллеги, но и все резервные копии и все клоны;
  * файлы окружения вроде .env с настоящими значениями: рядом держат
    .env.example без значений, он показывает, какие переменные нужны;
  * собранные артефакты: они воспроизводятся сборкой за секунды,
    а в истории репозитория занимают место навсегда;
  * большие файлы и образы: история git не уменьшается при удалении
    файла новым коммитом, она только растёт;
  * данные конкретного стенда — адреса, пути, пароли.

Файл .gitignore в корне репозитория перечисляет, что git не должен
отслеживать:

  build/
  *.log
  *.tmp
  .env
  *.key
  *.pem
  id_ed25519*
  id_rsa*
  .idea/
  .vscode/
  *.swp

Читается это как набор шаблонов: build/ — каталог целиком, *.log — все
файлы журналов, id_ed25519* — ключ и его публичная часть. Проверить,
что git ничего лишнего не видит: git status --ignored.

ЕСЛИ СЕКРЕТ УЖЕ ПОПАЛ В ИСТОРИЮ. Удалить файл новым коммитом
недостаточно: git хранит все объекты, включая содержимое удалённых
файлов, и команда git log -p покажет пароль любому, кто клонирует
репозиторий. Порядок действий: сначала считаем секрет скомпрометированным
и меняем его (новый пароль, перевыпущенный токен, отозванный ключ) —
переписывание истории не отменяет того, что секрет уже могли прочитать;
затем чистим историю (git filter-repo или BFG), обновляем ветку
принудительно и просим всех переклонировать репозиторий; и напоследок
разбираемся, почему секрет оказался в коде. Место секретов — в Jenkins
(практики 8 и 11), а не в файлах репозитория.

ЗАЩИТА ВЕТКИ. Репозиторий → Settings → Branches → Add Branch Protection
Rule, шаблон имени main: запрет прямого push (только через pull request),
запрет force push и, при необходимости, обязательное одобрение
изменений. После этого main перестаёт быть веткой, куда пишет кто угодно.

ОТВЕТСТВЕННОСТЬ ЗА КОД. Push в main означает «это можно собирать
и выкатывать», и отвечает за это тот, кто пушит. Эксперименты делайте
в отдельной ветке, а в main вливайте их, когда сборка проходит: в рабочем
проекте main — это то, что уезжает на серверы.


=========================================================================
12. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: Permission denied (publickey) при git clone или ssh -T

Симптом: «git@10.0.2.5: Permission denied (publickey)». SSH-соединение
состоялось, но ни один из предложенных ключей сервер не принял. Причины:
ключ не добавлен в Gitea или добавлен в другой учётной записи; предложен
не тот ключ, потому что у вас их несколько и клиент берёт первый
подходящий; команда выполняется не от того пользователя — например,
вы работаете от root, а ключ лежит в /home/engineer/.ssh.

ssh -v -p 2222 git@10.0.2.5

В выводе будут строки вида «Offering public key: ...». Сравните отпечаток
с тем, что видит Gitea (Settings → SSH / GPG Keys), и проверьте права:

ssh-keygen -lf ~/.ssh/id_ed25519.pub
chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519

Отдельно про Jenkins: у него свои ключи и свой пользователь, и ключ,
добавленный от имени engineer, в credentials Jenkins не поможет.

ПРОБЛЕМА: Host key verification failed

Симптом первый: «Host key verification failed» — записи о сервере нет
в known_hosts, и клиент не может убедиться, что говорит с нужным
сервером:

ssh-keyscan -p 2222 10.0.2.5 >> ~/.ssh/known_hosts

Симптом второй: «REMOTE HOST IDENTIFICATION HAS CHANGED» — ключ сервера
изменился. Относиться к этому надо внимательно: причины бывают
безобидные (Gitea переустановили, ключ хоста создан заново) и не очень
(по этому адресу отвечает не наш сервер). Посмотреть и удалить запись:

ssh-keygen -F '[10.0.2.5]:2222' -f ~/.ssh/known_hosts
ssh-keygen -R '[10.0.2.5]:2222'

Помните: у Jenkins свой файл /var/lib/jenkins/.ssh/known_hosts, и правки
в домашнем каталоге engineer на него не влияют.

ПРОБЛЕМА: адрес без порта 2222

Симптом: адрес вроде бы верный, но в ответ «repository not found» или
«Permission denied (publickey)», а в выводе ssh -v видно, что соединение
идёт на порт 22. Проверьте адрес:

  верно:        ssh://git@10.0.2.5:2222/engineer/site.git
  не сработает: git@10.0.2.5:engineer/site.git

Второй вариант — не опечатка, а другой формат записи: он не умеет
указывать порт и всегда использует 22. А на 22 отвечает sshd самой
машины admin: пользователя git он не знает и отвечает отказом.

ПРОБЛЕМА: Jenkins не может склонировать репозиторий

Симптом: в журнале сборки «Failed to connect to repository»,
«Authentication failed» или «Permission denied (publickey)». Проверяем
по порядку: выбраны ли credentials (Source Code Management → Git →
Credentials — пустое поле самая частая причина: Jenkins попробует
подключиться анонимно, а репозиторий приватный); тот ли ключ (значение
credentials скрыто, поэтому проще создать их заново из файла ключа);
тот ли пользователь (в credentials должно быть git); есть ли у ключа
доступ именно к этому репозиторию (deploy key привязан к одному);
известен ли Jenkins ключ хоста (раздел 7); работает ли сама Gitea:

  systemctl status gitea
  curl -s http://10.0.2.5:3000/api/v1/version

ПРОБЛЕМА: Couldn't find any revision to build

Симптом: подключение прошло, репозиторий склонирован, а сборка падает
с сообщением «ERROR: Couldn't find any revision to build». Почти всегда
это несовпадение имени ветки: в задании указано */master, а репозиторий
живёт в main. Ошибка выглядит как проблема доступа, хотя на самом деле
это опечатка в имени ветки, — на этом в прежней версии курса терялось
время. Посмотрите ветки в репозитории (git branch -r покажет origin/main)
и поставьте в задании Branch Specifier */main; для сборки по тегу
не забудьте про Fetch tags (раздел 10).

ПРОБЛЕМА: рабочий каталог пуст

Симптом: сборка завершилась успешно, а ls -la показывает только «.»
и «..». Причины:

  * сборка идёт на агенте, у которого нет доступа к Gitea. Клонирование
    выполняет тот узел, где идёт сборка: если задание ограничено меткой
    node1, то и ключ, и запись о ключе хоста нужны на node1, а не только
    на контроллере. На контроллере всё настроено и работает, на агенте
    нет — и в журнале это видно строками ошибки клонирования;
  * не та ветка: репозиторий склонирован, но в этой ветке нужных файлов
    нет — например, ветка создана пустой;
  * шаг сборки выполняется не там, где вы думаете: если в нём есть cd
    в другой каталог, остальные команды уходят туда. Первой строкой шага
    печатайте pwd — это стоит секунды, а вопросов снимает много.

ПРОБЛЕМА: Permission denied в рабочем каталоге агента

Симптом: шаг сборки не может создать файл или каталог, в журнале
«Permission denied» с путём вида
/home/jenkins/agent/workspace/gitea_build/... Причины:

  * каталог принадлежит другому пользователю — обычно потому, что его
    создали вручную под root. Владельцем должен быть пользователь
    jenkins: sudo chown -R jenkins:jenkins /home/jenkins/agent, а на
    контроллере /var/lib/jenkins/workspace;
  * вы пытаетесь писать в системный каталог, например /var/www/html.
    Прав у jenkins там нет, и это сделано намеренно: выкат на веб-серверы
    делается ограниченным набором команд (практика 11);
  * место на диске кончилось: df -h. Переполненный раздел даёт самые
    разные сообщения, включая похожие на отказ в правах, — проверяйте
    это до того, как искать «правильного владельца».


=========================================================================
УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

Задание gitea_build мы НЕ удаляем и не переименовываем: в практике 7
мы поставим ему триггер, и оно должно уже работать. Уборка минимальная:
локальную копию репозитория на рабочей машине можно удалить, если она
больше не нужна.

rm -rf ~/site

Как отозвать SSH-ключ: Gitea → Settings → SSH / GPG Keys → удалить ключ;
для служебного ключа сборки — репозиторий → Settings → Deploy Keys →
удалить. Отзыв действует немедленно: следующее подключение этим ключом
будет отвергнуто. Если отозванный ключ лежит в credentials Jenkins,
замените его там же: Manage Jenkins → Credentials → gitea-reader →
Update.

Как посмотреть журнал службы Gitea:

sudo journalctl -u gitea -n 100 --no-pager
sudo journalctl -u gitea -f

Резервные копии: в Gitea нужно копировать каталог /var/lib/gitea (база,
репозитории, LFS) и файл /etc/gitea/app.ini, причём согласованно: если
база от одного дня, а репозитории от другого, восстановление даст
сервер, который не понимает сам себя. Порядок копирования и проверка
восстановления разбираются в практике 14; здесь достаточно запомнить,
что данные Git-сервера — часть стенда, за которую вы теперь отвечаете.

Практика 7 — про триггеры: как заставить сборку запускаться самой. Наш
репозиторий и задание gitea_build уже готовы: Remote trigger запускает
сборку по http-запросу с токеном, каскад — после сборки другого задания,
расписание — по времени, Poll SCM заставляет Jenkins раз в несколько
минут проверять, не появилось ли новых коммитов. И главное для нас —
вебхук: Gitea отправляет событие в Jenkins сразу после push, и сборка
начинается без задержки. Это то, чего не мог дать облачный GitHub
на стенде без белого IP, и ради чего мы поднимали свой Git-сервер.
