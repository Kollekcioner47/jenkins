Практика 3. Задания: первая сборка и что из неё видно.

Практика про самое простое в Jenkins: задание, сборка и журнал. Мы создадим
задание, разберём переменные окружения сборки, найдём файлы задания на диске и
поймём, откуда берутся код возврата 127 и «сборка зелёная, а результата нет».

Имена заданий в курсе: FirstJob, build_with_params, periodic_report,
gitea_build (сборка из репозитория Gitea, практика 6), site_pipeline,
site_docker, site_library. Сейчас мы делаем первое из них.

ЧТО МЫ СДЕЛАЕМ И ЗАЧЕМ
=========================================================================

Мы создадим задание в портале, запустим его, прочитаем журнал, настроим
ограничение истории и архивирование артефактов, посмотрим, где Jenkins хранит
задание и его историю.

ЗАЧЕМ НАЧИНАТЬ С ЭТОГО. Задание — единица работы в Jenkins, а агенты,
триггеры, параметры, конвейеры и выкат это надстройки над ним. Пока не ясно,
что такое рабочий каталог, чем артефакт отличается от файла в нём и что
означает код возврата шага, всё остальное превращается в заучивание галочек.

ЧЕГО ЗДЕСЬ НЕ БУДЕТ. Мы не копируем файлы на другие машины: выкат на node1 и
node2 разбирается в практике 11, там же объясняется, почему старый способ
копирования по SSH устарел.

=========================================================================
1. ЧТО ТАКОЕ ЗАДАНИЕ И КАКИЕ ТИПЫ БЫВАЮТ
=========================================================================

Задание (job) — единица работы в Jenkins: у него есть имя, настройки, история
сборок и рабочий каталог. Сборка (build) — один запуск задания. Тип задания
выбирается при создании и потом не меняется: ошиблись — создавайте заново.

  Freestyle project — «свободный проект»: настройка полями и галочками.
    Уместен для простых и служебных задач: проверка, резервная копия, запуск
    скрипта. Этот тип мы сейчас и создадим.

  Pipeline — «конвейер»: сборка описывается кодом (Jenkinsfile) в репозитории.
    Уместен там, где сборка должна версионироваться и проходить ревью; разбор
    — в практике 10.

  Folder — «папка»: контейнер для заданий, чтобы разложить их по проектам; у
    папки свои права и свои credentials.

  Multibranch Pipeline — конвейер, который сам создаёт задание на каждую ветку
    репозитория (практика 6).

Внешнее задание (External Job) — задание-наблюдатель: само ничего не
запускает, а показывает результат внешнего процесса (например, ночного скрипта
на другой машине).

ПРЕДУПРЕЖДЕНИЕ: не начинайте знакомство с Jenkins с конвейера. Конвейер это
код, и ошибка в коде выглядит как упавшая сборка без объяснений. Понятия, на
которых он стоит, — журнал, рабочий каталог, код возврата, артефакты —
разбираются на Freestyle.


=========================================================================
2. СОЗДАЁМ FIRSTJOB В ПОРТАЛЕ
=========================================================================

Открываем http://10.0.2.5:8080 и входим под своей учётной записью.

1. В левом меню выбираем New Item («новый элемент»). 2. Вводим имя FirstJob:
оно станет именем каталога и частью адреса, поэтому без пробелов, кириллицы и
слэшей. 3. Выбираем Freestyle project и нажимаем OK. 4. В разделе Build Steps
(«шаги сборки») нажимаем Add build step и выбираем Execute shell. 5. В поле
Command вводим команду из листинга ниже. 6. Нажимаем Save, затем Build Now
(«собрать сейчас»). 7. В разделе Build History появится сборка #1: щёлкаем по
номеру и выбираем Console Output («вывод консоли»).

echo "------------- Build started -------------"
echo "Hello, World!"
echo "------------- Build finished -------------"


ЧТО ВИДНО В ЖУРНАЛЕ. Журнал — основной инструмент работы с Jenkins:

  * строку запуска «Started by user engineer» — кто запустил сборку;
  * машину и каталог: «Building in workspace ...»;
  * сами команды: Jenkins запускает shell с ключами -xe, поэтому команда
    печатается перед выполнением (в журнале она начинается с плюса), а сборка
    останавливается на первой команде, вернувшей не ноль;
  * вывод команд и итоговую строку «Finished: SUCCESS».

ПРО КОД ВОЗВРАТА: цифрой он в журнале не печатается — Jenkins превращает его в
результат сборки (ноль это SUCCESS, не ноль это FAILURE). Если код нужен
глазами, печатайте его сами, помня про ключ -e.

set +e
ls /etc/nginx/nginx.conf
echo "код возврата предыдущей команды: $?"
set -e


=========================================================================
3. РАЗБИРАЕМ ПРИМЕР ИЗ files/jobs/FirstJob.xml
=========================================================================

Полный текст задания есть в материалах курса: files/jobs/FirstJob.xml. Это то
же задание, но описанное файлом, без портала; понадобится в практике 5.

  <description>            описание задания: видно в портале;
  <scm class="hudson.scm.NullSCM"/>   источник кода не подключён;
  <concurrentBuild>false   не разрешать две сборки одновременно;
  <builders>               раздел Build Steps с пунктом Execute shell.

echo "------------- Build started -------------"
echo "Hello, World!"
echo "Номер этой сборки: $BUILD_NUMBER"
echo "Отображаемое имя:  $BUILD_DISPLAY_NAME"
echo "Имя задания:       $JOB_NAME"
echo "Рабочий каталог:   $WORKSPACE"
whoami
pwd
hostname
echo "------------- Build finished -------------"

BUILD_NUMBER — номер этой сборки (первая сборка нового задания это 1); номера
не переиспользуются, поэтому после удаления истории первый номер снова не
появится.

BUILD_DISPLAY_NAME — как сборка называется в интерфейсе, по умолчанию «#1».

JOB_NAME — имя задания, а для задания в папке — вместе с именем папки
(web/FirstJob): пути из JOB_NAME собирать не стоит.

WORKSPACE — абсолютный путь рабочего каталога на машине, где сборка
выполняется.

whoami — от чьего имени идёт сборка; на стенде это jenkins.

pwd — текущий каталог процесса; он равен WORKSPACE: Jenkins перед запуском
шага переходит в рабочий каталог задания.

hostname — имя машины, на которой сборка выполнилась.

ПОЧЕМУ pwd РАЗНЫЙ НА КОНТРОЛЛЕРЕ И НА АГЕНТЕ. Пока агентов нет, сборка идёт на
машине admin:

/var/lib/jenkins/workspace/FirstJob

В практике 4 появятся агенты node1 и node2, и то же задание на агенте даст
другой путь:

/home/jenkins/agent/workspace/FirstJob

потому что рабочий каталог агента строится от его корневого каталога (Remote
root directory), а у нас это /home/jenkins/agent.

ВАЖНО: путь к рабочему каталогу нельзя записывать жёстко — скрипт с cd
/var/lib/jenkins/workspace/FirstJob работает только на контроллере. Внутри
задания всегда используется $WORKSPACE.


=========================================================================
4. ПЕРЕМЕННЫЕ ОКРУЖЕНИЯ, КОТОРЫЕ ПОДСТАВЛЯЕТ JENKINS
=========================================================================

Перед сборкой Jenkins добавляет в её окружение переменные со сведениями о
самой сборке:

  ПЕРЕМЕННАЯ           ЧТО СОДЕРЖИТ
  BUILD_NUMBER         номер сборки: 1, 2, 3 и далее
  BUILD_ID             уникальный идентификатор сборки; у обычного
                       задания совпадает с номером, у конвейера
                       может от него отличаться
  BUILD_DISPLAY_NAME   отображаемое имя: по умолчанию #<номер>
  BUILD_URL            адрес страницы сборки, например
                       http://10.0.2.5:8080/job/FirstJob/1/
  JOB_NAME             имя задания; для задания в папке — вместе
                       с именем папки
  JOB_BASE_NAME        последняя часть имени, без папки: FirstJob
  WORKSPACE            абсолютный путь рабочего каталога сборки
  NODE_NAME            имя узла, на котором идёт сборка; на
                       контроллере — built-in
  EXECUTOR_NUMBER      номер исполнителя на этом узле: 0, 1, 2 ...
  BUILD_CAUSE          причина запуска: MANUALTRIGGER (человек),
                       TIMERTRIGGER (расписание), SCMTRIGGER
                       (изменение в репозитории)

ЗАЧЕМ ИХ ПЕЧАТАТЬ: NODE_NAME и hostname отвечают, где выполнилась сборка;
WORKSPACE показывает, откуда сборка брала файлы; BUILD_NUMBER и BUILD_URL дают
ссылку на конкретный запуск; BUILD_CAUSE объясняет, почему сборка запустилась;
EXECUTOR_NUMBER нужен, когда на узле несколько исполнителей.

ИХ ПОДСТАВЛЯЕТ НЕ JENKINS, А SHELL: текст команды Jenkins записывает в скрипт
как есть, а значения передаёт через окружение процесса. Поэтому echo "сборка
$BUILD_NUMBER" напечатает номер, а echo 'сборка $BUILD_NUMBER' — сам текст.
Переменная, заданная в одном шаге, в следующем не видна: каждый шаг это
отдельный процесс shell.


=========================================================================
5. ГДЕ JENKINS ХРАНИТ ЗАДАНИЯ
=========================================================================

Задания лежат в JENKINS_HOME: у нас это /var/lib/jenkins/jobs. Заглянем туда
по SSH на машине admin:

sudo ls -la /var/lib/jenkins/jobs
sudo ls -la /var/lib/jenkins/jobs/FirstJob

Внутри каталога задания:

  config.xml        все настройки: ровно то, что видно в Configure;
  builds/           история, подкаталог на каждую сборку: 1, 2, 3 ...;
  nextBuildNumber   номер, с которого начнётся следующая сборка;
  workspace/        рабочий каталог, если сборка идёт на контроллере.

Внутри каталога сборки (builds/1): build.xml (результат, время, длительность,
причина запуска), log (тот самый журнал), changelog.xml (изменения из
репозитория, практика 6) и archive/ (артефакты, если включено архивирование).

sudo cat /var/lib/jenkins/jobs/FirstJob/nextBuildNumber
sudo tail -n 20 /var/lib/jenkins/jobs/FirstJob/builds/1/log

ЧТО МОЖНО ПОНЯТЬ, ПОСМОТРЕВ ТУДА РУКАМИ: сколько места занимают история и
рабочие каталоги (du -sh по каталогу jobs — способ найти виновника
заполненного диска); что имя задания это имя каталога и часть адреса; и что
задание внутри папки лежит по пути с двумя jobs: jobs/<папка>/jobs/<имя>.

ПОЧЕМУ НЕЛЬЗЯ ПРАВИТЬ ЭТИ ФАЙЛЫ ПРИ РАБОТАЮЩЕМ JENKINS. Jenkins держит
настройки задания в памяти: правка config.xml не попадёт в загруженное
задание, а при следующем сохранении из портала файл перезапишется — и правка
исчезнет молча. Кроме того, испорченный XML ломает загрузку: задание не
появится в списке, а причина будет видна только в
/var/log/jenkins/jenkins.log.

=========================================================================
6. РАБОЧИЙ КАТАЛОГ СБОРКИ (WORKSPACE)
=========================================================================

Рабочий каталог (workspace) — каталог, в котором сборка выполняется: туда
Jenkins переходит перед запуском шага, там сборка создаёт файлы и оттуда
забирает артефакты.

  на контроллере   /var/lib/jenkins/workspace/<имя задания>
  на агенте        /home/jenkins/agent/workspace/<имя задания>

ПОЧЕМУ СОДЕРЖИМОЕ СОХРАНЯЕТСЯ МЕЖДУ СБОРКАМИ: Jenkins не удаляет рабочий
каталог сам — ни перед сборкой, ни после. Так сделано сознательно: сборке не
нужно каждый раз заново скачивать зависимости. Плата за это — неприятности:

  * МУСОР И МЕСТО НА ДИСКЕ: сборка оставляет архивы, распакованные каталоги,
    отчёты, и со временем они занимают больше, чем история сборок;
  * СТАРЫЕ ФАЙЛЫ, КОТОРЫЕ «СЛУЧАЙНО ПОДХОДЯТ»: скрипт проверяет наличие файла
    и находит его от прошлой сборки — это и есть «работает только со второго
    раза»;
  * СБОРКА, ПРОХОДЯЩАЯ У ВАС, МОЖЕТ НЕ ПРОЙТИ НА ЧИСТОМ СТЕНДЕ: у вас файл
    остался с прошлого раза, а на новом агенте его нет;
  * ДВЕ СБОРКИ С РАЗНЫМИ ПАРАМЕТРАМИ пишут в одни имена файлов и затирают
    результаты друг друга.

ЧТО ДЕЛАТЬ: не считать рабочий каталог местом хранения (он временный),
результат складывать в артефакты (раздел 9), а для проверки «с нуля» включать
обёртку Delete workspace before build starts.


=========================================================================
7. ОГРАНИЧЕНИЕ ИСТОРИИ: DISCARD OLD BUILDS
=========================================================================


Порядок настройки: Configure → General → галочка Discard old builds. После
включения появляется Strategy: Log Rotation («ротация журналов») и два поля:
Days to keep builds (сколько дней хранить сборки) и Max # of builds to keep
(сколько последних сборок хранить); пустое поле или 0 означает, что по этому
условию ограничения нет.

ПОЧЕМУ ЭТО ПЕРВОЕ, ЧТО СТОИТ НАСТРОИТЬ: по умолчанию ограничений нет, а каждая
сборка это журнал, метаданные и, если включено архивирование, копия
артефактов. Задание, собирающееся каждые пять минут, за месяц накопит десятки
тысяч сборок, и диск кончится — а при заполненном диске Jenkins перестаёт
запускать сборки.

ВАЖНО: когда заданы оба поля, сборка удаляется при нарушении любого из условий
(30 дней и 20 сборок значат: не старше 30 дней и не больше 20 штук). Вместе со
сборкой удаляются журнал, метаданные и артефакты, поэтому ссылка на артефакт
однажды перестанет работать. Для стенда разумно 20 сборок и 30 дней.


=========================================================================
8. КОДЫ ВОЗВРАТА И СОСТОЯНИЯ СБОРКИ
=========================================================================

Каждый шаг сборки это процесс. Завершаясь, он возвращает код: 0 означает «всё
хорошо», любое другое число — «что-то не так».

  0     успех: шаг выполнен;
  1     общая ошибка: сломался скрипт, не прошла проверка, упал тест;
  126   команда есть, но нет права на запуск (файл без +x);
  127   команда не найдена: опечатка, не установлен пакет, чужой PATH;
  137   процесс убит сигналом KILL: чаще всего кончилась память;
  143   процесс получил SIGTERM: сборку остановили снаружи.

ПОЧЕМУ 137 И 143 СТОИТ РАЗЛИЧАТЬ: 137 это 128+9, то есть KILL — почти всегда
нехватка памяти; 143 это 128+15, SIGTERM: так заканчивают сборки, которые
остановили кнопкой, сняли таймаутом или потеряли вместе с агентом.

Свой код скрипт задаёт командой exit, и для Jenkins всё, что не ноль,
одинаково: сборка станет неудачной. Состояния сборки:

  * SUCCESS (синий) — все шаги вернули 0;
  * FAILURE (красный) — хотя бы один шаг вернул не ноль;
  * UNSTABLE (жёлтый) — сборка дошла до конца, но результат требует внимания:
    так помечают, например, упавшие тесты;
  * ABORTED (серый) — сборку отменили: кнопка остановки, таймаут или
    выключенный во время сборки агент.

КАК ПОЛУЧИТЬ UNSTABLE ОСОЗНАННО: в Freestyle кнопки «сделать нестабильной»
нет, состоянием управляют публикация результатов или сам шаг. Публикация
отчёта о тестах (JUnit) даёт UNSTABLE при упавших тестах, а в конвейере для
этого есть функция unstable() (практика 10). Пометить сборку нестабильной по
тексту в журнале позволяет плагин Text Finder, но в списке плагинов курса его
нет намеренно: состояние сборки задают своим кодом — выход с ненулевым кодом
(это FAILURE) или шаг unstable в конвейере. Смысл UNSTABLE в том, чтобы не
смешивать «сломалось» и «работает, но посмотри».


=========================================================================
9. АРТЕФАКТЫ СБОРКИ
=========================================================================

Артефакт — файл, который сборка оставляет как результат и который Jenkins
сохраняет вместе с историей сборки. Настройка: Configure → Post-build Actions
→ Add post-build action → Archive the artifacts («архивировать артефакты»). В
поле Files to archive перечисляются шаблоны:

index.html
build/*.tar.gz
reports/**/*.xml

Одна звёздочка заменяет часть имени в пределах каталога, две — любое число
каталогов. В архив попадают только файлы, подходящие под шаблон, и только из
рабочего каталога: ничего не архивируется автоматически, и об отсутствии
артефактов Jenkins не сообщает.

ЧЕМ АРТЕФАКТ ОТЛИЧАЕТСЯ ОТ ФАЙЛА В РАБОЧЕМ КАТАЛОГЕ: файл перезапишет
следующая сборка, и он исчезнет вместе с рабочим каталогом, а артефакт
копируется в builds/<номер>/archive/ и живёт столько же, сколько сборка: на
него можно дать ссылку и скачать его через месяц. Он попадает в резервную
копию JENKINS_HOME (практика 14), но исчезает вместе со сборкой, когда
срабатывает Discard old builds.

ЗАЧЕМ НУЖЕН ОТПЕЧАТОК (FINGERPRINT): это запись о том, какая сборка создала
файл с таким содержимым и какие сборки его использовали; считается он по
содержимому, поэтому переименование файла ничего не меняет. Включается
галочкой Record fingerprints of files to track usage в настройке Archive the
artifacts. Отпечаток позволяет узнать, из какой сборки пришёл файл, лежащий
сейчас на сервере, и не собирать одинаковый файл заново; записи хранятся в
JENKINS_HOME/fingerprints.

=========================================================================
10. ОБЁРТКИ СБОРКИ (BUILD WRAPPERS)
=========================================================================

Обёртка (build wrapper) меняет условия выполнения всей сборки, а не отдельного
шага; находятся они в разделе Build Environment формы Configure.

Add timestamps to the Console Output — каждая строка журнала получает отметку
времени. ЗАЧЕМ: без отметок не видно, где сборка провела время; в старых
сборках отметки не появятся задним числом.

Abort the build if it's stuck — таймаут: прерывает сборку, если она идёт
слишком долго или слишком долго молчит. Результат — ABORTED. ЗАЧЕМ: зависшая
сборка занимает исполнителя и вместе с настройкой Do not allow concurrent
builds блокирует следующие запуски.

Delete workspace before build starts — удаляет рабочий каталог перед сборкой.
ЗАЧЕМ: гарантия, что сборка не пользуется остатками прошлой. ПОЧЕМУ ОСТОРОЖНО:
всё содержимое исчезнет, а сборка станет дольше.


=========================================================================
11. ГИГИЕНА ЗАДАНИЯ
=========================================================================

ЕДИНЫЕ ИМЕНА. В курсе имена такие: FirstJob — первое задание;
build_with_params — параметризованная сборка (практика 8); periodic_report —
сборка по расписанию (практика 7); gitea_build — сборка из репозитория Gitea
(практика 6); site_pipeline и site_docker — конвейеры выката (практики 10 и
12); site_library — конвейер с общей библиотекой (практика 13). Имя должно
отвечать на вопрос «что делает» и обходиться без пробелов, кириллицы и слэшей,
а переименование меняет адрес задания и ломает ссылки.

ОПИСАНИЕ ЗАДАНИЯ. Поле Description в верхней части формы Configure: укажите,
что собирается, куда выкладывается, кто владелец и где лежит код — через месяц
без описания никто не вспомнит, зачем задание есть.

СБОРОК НА КОНТРОЛЛЕРЕ БЫТЬ НЕ ДОЛЖНО. Пока агентов нет, Jenkins собирает на
самом себе. В рабочей среде так нельзя: сборка запускает чужой код на машине,
где лежит весь JENKINS_HOME с настройками и секретами. Число исполнителей
контроллера задаётся в Manage Jenkins → Nodes → Built-In Node → Configure,
поле # of executors (практика 4).

DO NOT ALLOW CONCURRENT BUILDS. Галочка в разделе General; в XML это
<concurrentBuild>false</concurrentBuild>, как в разобранном файле. Вторая
сборка того же задания не стартует, а встанет в очередь.

ПОЧЕМУ ЭТО ВАЖНЕЕ, ЧЕМ КАЖЕТСЯ: у задания есть общий ресурс — его рабочий
каталог. Две одновременные сборки пишут в одни файлы: одна удаляет рабочий
каталог (обёртка из раздела 10), другая в нём работает. Ошибка выглядит
случайной и не воспроизводится.


=========================================================================
12. ЕСЛИ ЧТО-ТО ПОШЛО НЕ ТАК
=========================================================================

ПРОБЛЕМА: сборка падает сразу после старта, в журнале «...: not found»

Это код возврата 127: команда не найдена. Причины по частоте: опечатка в
имени; команда не установлена на этой машине; команда лежит в /usr/sbin или
/sbin, а в PATH процесса её нет (у службы jenkins путь короче); команда есть,
но не в той оболочке — в Execute shell работает sh; в команду попал невидимый
символ из документа («умные» кавычки, неразрывный пробел). Что смотреть:

echo "PATH=$PATH"
command -v ИМЯ_КОМАНДЫ

ПРОБЛЕМА: задание «выполнилось успешно», но нужного файла нет

Шаг вернул 0, Jenkins нарисовал зелёную галочку, а результата нет. Это
неверное ожидание: Jenkins считает успехом КОД ВОЗВРАТА ШАГА, а не достижение
цели — скрипт, который ничего не сделал, но завершился с нулём, для Jenkins
успешен. Поэтому сборку заканчивают проверкой результата и печатают в журнал
подтверждение (ls -l файла, его размер, контрольную сумму).

test -f build/site.tar.gz || { echo "артефакт не создан"; exit 1; }

ПРОБЛЕМА: сборка висит часами

Признак: сборка в состоянии «в процессе», журнал не обновляется, исполнитель
занят. Причины: команда ждёт ввода (ssh или пакетный менеджер спрашивают
подтверждение); команда ждёт недоступную сеть, и соединение висит до таймаута
операционной системы; шаг запустил службу, которая не завершается. Что делать:
поставить таймаут (раздел 10), включить отметки времени и посмотреть, на каком
шаге сборка встала, затем остановить её и прочитать журнал до последней
строки.

ПРОБЛЕМА: кнопки Build Now нет или сборка стоит в очереди

Build Now не показывается, когда у вас нет прав на запуск задания. Если же
сборка запущена, но остаётся в очереди, значит её некому выполнять. Смотреть
по порядку: панель Build Executor Status (есть ли свободный исполнитель);
Manage Jenkins → Nodes (узел offline сборку не получит); галочка Restrict
where this project can be run (метка, которой нет ни у одного узла, заставит
сборку ждать бесконечно); свободное место на диске.

ПРОБЛЕМА: в журнале пусто

Значит, до shell дело не дошло. Проверяйте: шаг добавлен в правильный раздел
(команды выполняются из Build Steps, а не из описания, Build Triggers или
Post-build Actions); поле Command действительно заполнено; открыт журнал ТОЙ
сборки, а не старой из истории.

ПРОБЛЕМА: диск кончился из-за истории и рабочих каталогов

Сначала смотрим, кто занял место:

df -h
sudo du -sh /var/lib/jenkins/jobs/*
sudo du -sh /var/lib/jenkins/workspace/*

Меры в порядке полезности: включить Discard old builds там, где его нет
(раздел 7); удалить старые сборки вручную или скриптом
files/groovy/clean_old_builds.groovy; удалить ненужные рабочие каталоги
(раздел 13). ВАЖНО: при нехватке места сборки не запускаются, а конфигурация
может оказаться обрезанной.


=========================================================================
13. УБОРКА ПОСЛЕ ПРАКТИКИ
=========================================================================

Удаляем учебное задание: открываем FirstJob, в левом меню выбираем пункт
Delete Project («удалить задание») и подтверждаем; в некоторых версиях он
подписан иначе (например, Delete Job) — смысл один. Jenkins удаляет каталог
задания целиком — с настройками, историей и артефактами; рабочий каталог
удаляется не всегда, поэтому проверяем и убираем руками:

sudo ls -la /var/lib/jenkins/workspace/
sudo rm -rf /var/lib/jenkins/workspace/FirstJob

ОСТОРОЖНО С rm -rf: путь должен быть точным, до конкретного рабочего каталога;
каталог workspace целиком удалять не нужно.

Старые сборки, не удаляя само задание, убирают тремя способами: по одной
крестиком в списке Build History; массово скриптом из практики 9
(files/groovy/clean_old_builds.groovy); автоматически настройкой Discard old
builds (раздел 7).

Проверяем, что чисто:

df -h /var/lib/jenkins
